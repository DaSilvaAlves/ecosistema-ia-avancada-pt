**[AUTO-DECISION A1]** Tarefas sem `dueDate` **não aparecem no calendário**. Não há onde colocá-las (calendário é grid de dias). Alternativa "secção 'Sem data' abaixo do grid" descartada — scope creep, não está no wireframe spec §3.2 linha 459. Tarefas sem `dueDate` continuam acessíveis nas vistas Lista e Kanban.

**[AUTO-DECISION A2]** Reordenação intra-dia (ordem dos chips dentro do mesmo dia) **fora-de-scope**. FR12 especifica "entre dias", não intra-dia. Schema `Task` não tem campo `order` / `position`. Mesmo precedente da Story 2.4 [AUTO-DECISION A1].

**[AUTO-DECISION A3]** Filtro Status em modo Calendário **filtra os chips visíveis** (não oculta dias). Razão: ocultar dias da semana quebra o conceito de calendário semanal (semana tem sempre 7 dias). Em vez disso, chips com status fora do filtro desaparecem mas o dia mantém-se visível. Coerente com filtros Projecto/Tag/Prioridade. Alternativa "ocultar dias com 0 chips" descartada — calendário perderia ancoragem temporal.

**[AUTO-DECISION A4]** Botão `+ Nova Tarefa` no header **mantém-se `disabled`** nesta story. Razão: criação UI (Flow 1.3 do spec §1.3) é funcionalidade separada — não está nos FRs alvo desta story (FR11, FR12). Consistente com Stories 2.3 e 2.4 (D4-2.3, A4-2.4).

**[AUTO-DECISION A5]** Keyboard navigation para drag usa **`@dnd-kit` built-in `KeyboardSensor`** + `sortableKeyboardCoordinates` — exactamente como 2.4 A5. Space/Enter para pegar, Arrow Keys para mover, Enter/Space para largar, Escape para cancelar. ARIA `announcements` PT-PT: "A mover [título] de [dia origem] para [dia destino]", "Tarefa [título] movida para [dia destino]".

**[AUTO-DECISION A6]** Drag entre semanas (arrastar chip para fora do grid actual) **fora-de-scope**. Razão: requer interacção complexa (auto-scroll? portal? cross-week drop targets?) que duplica scope. Para mover uma tarefa para uma data fora da semana visível, o utilizador navega primeiro com `← →` e depois faz drag — pattern conhecido. Alternativa "implementar week-jump on drag near edges" descartada.

**[AUTO-DECISION A7]** Write API: usar **`updateTask(id, { dueDate, lastWorkedAt })`** do repo (já existe em `lib/db/repos/tasks.ts:71`) em vez de criar `setTaskDueDate`. Razão: `setTaskStatus` existe como wrapper exclusivo porque status muda lifecycle/ordering; `dueDate` é apenas mais um campo — `updateTask` é a API genérica adequada. Alternativa "criar `setTaskDueDate` para simetria com `setTaskStatus`" descartada — adiciona API sem benefício claro, viola YAGNI. Importante: actualizar `lastWorkedAt: new Date().toISOString()` no mesmo `updateTask` para reflectir actividade recente (paridade comportamental com `setTaskStatus`).

**[AUTO-DECISION A8]** Semana inicia à **segunda-feira** (`weekStartsOn: 1` no `date-fns`). Razão: convenção europeia/PT-PT. O wireframe spec §3.2 linha 459 diz "seg-dom". Alternativa "weekStartsOn: 0 (Domingo)" (convenção US) descartada — não é a convenção PT-PT.

**[AUTO-DECISION A9]** Formato de `dueDate` ao persistir: manter o **mesmo padrão usado em toda a base** — string ISO 8601 date (`YYYY-MM-DD`, sem time) como confirmado no shape Task (`types/db.ts` documentado na Story 2.4 linhas 89-100). Conversão `Date → ISO date string` via `format(date, 'yyyy-MM-dd')` do `date-fns`. **NUNCA** persistir com componente de hora (evita bugs de timezone que a Story 2.3 Iter 2 já enfrentou com `formatDueDate`).

## User Story

**As a** Eurico,
**I want** uma vista calendário semanal na página `/tarefas` que mostre as minhas tarefas distribuídas pelos 7 dias da semana (segunda a domingo) com possibilidade de arrastar chips entre dias para mudar a data,
**so that** possa replanear visualmente a minha semana sem abrir cada tarefa — uma interacção directa de calendarização, cumprindo FR11 (terceira vista) e FR12 (drag entre dias persiste `dueDate`), fechando o trio Lista/Kanban/Calendário do Epic 2.

Ao clicar no tab Calendário, a vista muda para o layout calendário semanal; ao clicar em "Lista" ou "Kanban", regressa às respectivas vistas. O estado activo do tab persiste via `useState` na page (não em URL params nesta story — paridade com 2.4). Tooltip "Em construção · Story 2.5" removido.

- **AC2:** A vista Calendário apresenta exactamente **7 colunas** representando os dias de **segunda a domingo** da semana navegada. Cada coluna (`CalendarDay`) tem:
  - Header com **label PT-PT abreviado** em JetBrains Mono 0.65rem weight 700 (ex: "Seg", "Ter", "Qua", "Qui", "Sex", "Sáb", "Dom") + **número do dia** em JetBrains Mono 1.4rem weight 800 (ex: "12", "13", ..., "18").

  - Min-height `120px` (R2); expande verticalmente quando há chips suficientes.
  - Drop zone visualmente distinta quando chip está a ser arrastado sobre ela (border subtle glow cyan `rgba(0,245,255,0.3)` quando `isOver === true`).

- **AC3:** Header do **CalendarBoard** apresenta controlos de navegação semanal:
  - Botão `←` "Semana anterior" (label PT-PT, ícone seta esquerda + texto).
  - Label central `weekLabel` (formato PT-PT, ex: "Semana de 12 Mai 2026").
  - Botão `→` "Semana seguinte" (idem).
  - Botão "Hoje" — reset para semana actual (cyan accent quando já está na semana corrente fica desabilitado ou com `aria-pressed="true"`).
  - Todos os botões com `aria-label` PT-PT (R5).

- **AC4:** Cada **CalendarCard** (chip) apresenta:
  - Título da tarefa truncado a ~25 caracteres com `text-overflow: ellipsis` (Inter 0.8rem weight 600).
  - Cor de fundo determinada pelo estado: **Lime** `rgba(57,255,20,0.12)` + border `rgba(57,255,20,0.3)` se `status==='done'`; **Magenta** `rgba(255,0,110,0.12)` + border `rgba(255,0,110,0.3)` se `isOverdue(task)`; **Cyan** `rgba(0,245,255,0.08)` + border `rgba(0,245,255,0.2)` caso contrário. Precedência done → overdue → futuro (§Contexto).
  - Border-radius 6px, padding 0.4rem 0.6rem.
  - Indicador de prioridade: dot 6px à esquerda — magenta (high), cyan (medium), grey (low).
  - Ícone projecto (📁) prefixed ao título se `projectId !== null` (lookup opcional via `useProjects`).
  - Drag handle via `useSortable({ id: task.id })`.

- **AC5:** **Drag-and-drop entre dias** com `@dnd-kit/core` + `@dnd-kit/sortable`:
  - Arrastar um chip de qualquer dia para outro dia chama `updateTask(taskId, { dueDate: novoIso, lastWorkedAt: new Date().toISOString() })` (A7).
  - **Optimistic UI**: o chip move-se visualmente para o novo dia imediatamente (antes de confirmar Dexie). Padrão `useRef<Record<string, string>>` para `overrides` (mesmo pattern Story 2.4 Iter 1 / Completion Note #3).
  - **Rollback em erro**: se `updateTask` rejeitar, o chip regressa ao dia original com toast PT-PT primitivo ("Erro ao mover tarefa — tenta novamente"). Padrão `setTimeout` 4s (mesmo da 2.4 Completion Note #5).
  - A operação chama **apenas `updateTask`** do repo `@/lib/db/repos/tasks` — **NUNCA** `db.tasks.update` directamente no componente.
  - Após `updateTask` com sucesso, `useLiveQuery` re-renderiza automaticamente (Dexie reactivo) — não setState manual.
  - Handler exportado como **factory pura `createCalendarDragEndHandler`** (mesmo padrão Story 2.4 Iter 1 — testabilidade sem pointer events).

- **AC5b:** **Drag rápido sequencial não corrompe estado — mutation token por task-id** (precedente 2.4 Iter 2 fix race condition):
  - `inFlightByTaskRef: useRef<Record<string, number>>({})` declarado no `CalendarBoard`.
  - Cada drag-end **incrementa** `inFlightByTaskRef.current[taskId]` e **captura local** do valor incrementado **antes** de iniciar o `updateTask`.
  - Após o `await updateTask`, o handler **compara** o token capturado com `inFlightByTaskRef.current[taskId]` actual; se divergem, a completion (sucesso ou rejeição) é **stale** e o handler **não executa rollback nem cleanup** — uma mutação mais recente já está em curso ou completa.
  - Comportamento observável: mover task A do dia D1 para D2 e, antes do `await updateTask` da 1ª mutação resolver, mover novamente para D3. Apenas a 2ª mutação prevalece — `dueDate` final no Dexie = D3, override visual = D3, sem flicker visual para D1 (rollback da 1ª stale ignorado).

```typescript
// CalendarBoard.tsx — estrutura mínima (reaproveita padrão Story 2.4)

import { updateTask } from '@/lib/db/repos/tasks';
import { format } from 'date-fns';

const sensors = useSensors(
  useSensor(PointerSensor),
  useSensor(KeyboardSensor, { coordinateGetter: sortableKeyboardCoordinates })
);

// Factory pura — testável sem pointer events (padrão Story 2.4 Iter 1 + Iter 2 fix race condition)
export function createCalendarDragEndHandler(deps: {
  tasks: Task[] | undefined;
  overridesRef: React.MutableRefObject<Record<string, string>>;
  /**
   * Mutation token por task-id — incrementa antes de cada `updateTask` e captura local; após
   * `await`, se o valor actual em `inFlightByTaskRef.current[taskId]` divergir do capturado, esta
   * é uma stale completion/failure (chegou tarde após uma mutação mais recente) e deve ser ignorada.
   *
   * Padrão Story 2.4 Iter 2 fix — trace `components/tarefas/KanbanBoard.tsx:85-91, :132-138, :286-289`.
   */
  inFlightByTaskRef: React.MutableRefObject<Record<string, number>>;
  rerender: () => void;
  setError: (msg: string | null) => void;
}) {
  return (event: DragEndEvent) => {
    const { active, over } = event;
    if (!over) return;
    const taskId = active.id as string;
    const novoIso = over.id as string;  // 'YYYY-MM-DD'
    const task = deps.tasks?.find(t => t.id === taskId);
    if (!task) return;
    const dueAtual = deps.overridesRef.current[taskId] ?? task.dueDate;
    if (dueAtual === novoIso) return;  // mesmo dia → ignorar

    // Mutation token: incrementar + capturar antes de iniciar a write (AC5b)
    const mutationId = (deps.inFlightByTaskRef.current[taskId] ?? 0) + 1;
    deps.inFlightByTaskRef.current[taskId] = mutationId;

    // Optimistic UI
    deps.overridesRef.current[taskId] = novoIso;
    deps.rerender();

    const nowIso = new Date().toISOString();
    updateTask(taskId, { dueDate: novoIso, lastWorkedAt: nowIso })
      .then(() => {
        // Stale completion → uma mutação mais recente está em curso; não fazer cleanup
        if (deps.inFlightByTaskRef.current[taskId] !== mutationId) return;
        // (cleanup do override é feito pelo useEffect sobre `tasks` — padrão 2.4 Completion Note #4)
      })
      .catch(() => {
        // Stale failure → ignorar rollback; a mutação mais recente vai resolver-se sozinha
        if (deps.inFlightByTaskRef.current[taskId] !== mutationId) return;
        delete deps.overridesRef.current[taskId];
        deps.rerender();
        deps.setError('Erro ao mover tarefa — tenta novamente');
        setTimeout(() => deps.setError(null), 4000);
      });
  };
}

// CalendarDay.tsx — useDroppable com id = ISO date string
```

### Helper `weekRange.ts` (esqueleto)

```typescript
// lib/tarefas/weekRange.ts
import { startOfWeek, addDays, format, isSameDay } from 'date-fns';
import { pt } from 'date-fns/locale';

export interface CalendarDay {
  date: Date;
  iso: string;        // 'YYYY-MM-DD' — usado como id do useDroppable
  label: string;      // 'Seg' | 'Ter' | ... | 'Dom'
  longLabel: string;  // 'Segunda-feira' | 'Terça-feira' | ...
  dayNumber: number;  // 1-31
  monthLabel: string; // 'Mai' (abreviado, PT-PT)
  isToday: boolean;
}

export interface WeekRange {
  start: Date;
  end: Date;
  days: CalendarDay[];  // length === 7
  weekLabel: string;    // 'Semana de 12 de Maio de 2026'
}

export function getWeekRange(anchor: Date = new Date()): WeekRange {
  const start = startOfWeek(anchor, { weekStartsOn: 1 });
  const today = new Date();
  const days: CalendarDay[] = Array.from({ length: 7 }, (_, i) => {
    const date = addDays(start, i);
    return {
      date,
      iso: format(date, 'yyyy-MM-dd'),
      label: format(date, 'EEE', { locale: pt }),       // 'Seg', 'Ter', ...
      longLabel: format(date, 'EEEE', { locale: pt }),  // 'Segunda-feira', ...
      dayNumber: date.getDate(),
      monthLabel: format(date, 'MMM', { locale: pt }),
      isToday: isSameDay(date, today),
    };
  });
  return {
    start,
    end: addDays(start, 7),
    days,
    weekLabel: format(start, "'Semana de' d 'de' MMMM 'de' yyyy", { locale: pt }),
  };
}

export function getPreviousWeek(current: WeekRange): WeekRange {
  return getWeekRange(addDays(current.start, -7));
}

export function getNextWeek(current: WeekRange): WeekRange {
  return getWeekRange(addDays(current.start, 7));
}
```

### Anti-padrões a evitar

| Anti-padrão | Correcto |
|-------------|----------|
| `db.tasks.update(id, { dueDate: ... })` no componente | `await updateTask(id, { dueDate, lastWorkedAt })` do repo |
| Persistir `dueDate` com componente de hora (`new Date().toISOString()`) | `format(date, 'yyyy-MM-dd')` — date string puro (A9) |
| `startOfWeek(date)` sem `{ weekStartsOn: 1 }` | Sempre `{ weekStartsOn: 1 }` — A8 |
| Comparar datas com `dateA === dateB` ou `dateA > dateB` directamente | Usar `format(a, 'yyyy-MM-dd') === format(b, 'yyyy-MM-dd')` ou `isSameDay` do `date-fns` (evita timezone bugs) |
| Recriar `WeekRange` em cada render | `useState` para `currentWeek`; navegação altera via `setCurrentWeek(getPreviousWeek(currentWeek))` |
| `useTasks({ dueDateRange: ... })` para filtrar por semana | Não — `useTasks()` sem filtro de data + agrupar client-side por `iso`. Razão: simplicidade + reactividade total a writes. (Pode optimizar em futura story se volume justificar.) |
| Tarefa sem `dueDate` aparecer no calendário | Filtrar `tasks.filter(t => t.dueDate !== null)` antes de agrupar (A1) |
| Ocultar dias com 0 chips após filtro | Não — manter os 7 dias visíveis sempre (A3) |
| Sem rollback quando `updateTask` falha | Sempre: try/catch + restaurar `overrides` + toast PT-PT |
| Recriar handler `onDragEnd` a cada render | `useMemo` ou `useCallback` com deps mínimas (tasks ref, overrides ref) |
| Drag handler **sem mutation token** (race condition em drag rápido — bug original da 2.4 Iter 1) | Sempre: `inFlightByTaskRef: useRef<Record<string, number>>({})` + incrementar+capturar antes do `updateTask` + ignorar completion/failure se token actual divergir do capturado (AC5b, precedente 2.4 Iter 2 fix) |
| Rollback executado em **stale failure** (a 2ª mutação está em curso mas a 1ª `.catch` ainda dispara setError) | Comparar `inFlightByTaskRef.current[taskId] === mutationId` no `.catch`; se divergir, return cedo — a mutação mais recente vai resolver-se sozinha (AC5b) |

```typescript
    handler({ active: { id: 'task-1' }, over: null } as DragEndEvent);
    expect(spy).not.toHaveBeenCalled();
  });

    // Cenário: mover task-1 de D1=2026-05-12 para D2=2026-05-15; ANTES do await resolver,
    // mover novamente para D3=2026-05-16. A 1ª completion (D2) chega tarde — é stale,
    // não pode disparar rollback nem cleanup. Apenas a 2ª mutação (D3) prevalece.
    let resolve1: () => void = () => {};
    let resolve2: () => void = () => {};
    const spy = vi.spyOn(tasksRepo, 'updateTask')
      .mockImplementationOnce(() => new Promise<void>(r => { resolve1 = r; }))
      .mockImplementationOnce(() => new Promise<void>(r => { resolve2 = r; }));

    const tasks = [{ id: 'task-1', dueDate: '2026-05-12' } as Task];
    const overridesRef = { current: {} as Record<string, string> };
    const inFlightByTaskRef = { current: {} as Record<string, number> };
    const rerender = vi.fn();
    const setError = vi.fn();
    const handler = createCalendarDragEndHandler({
      tasks, overridesRef, inFlightByTaskRef, rerender, setError,
    });

    // 1ª mutação D1→D2
    handler({ active: { id: 'task-1' }, over: { id: '2026-05-15' } } as DragEndEvent);
    expect(inFlightByTaskRef.current['task-1']).toBe(1);
    expect(overridesRef.current['task-1']).toBe('2026-05-15');

    // 2ª mutação D2→D3 (override aponta agora a D3, token incrementa para 2)
    handler({ active: { id: 'task-1' }, over: { id: '2026-05-16' } } as DragEndEvent);
    expect(inFlightByTaskRef.current['task-1']).toBe(2);
    expect(overridesRef.current['task-1']).toBe('2026-05-16');

    // A 1ª completion chega — token capturado foi 1, actual é 2 → STALE → ignorada
    resolve1();
    await Promise.resolve(); await Promise.resolve();  // flush microtasks
    expect(overridesRef.current['task-1']).toBe('2026-05-16');  // override D3 mantido
    expect(setError).not.toHaveBeenCalled();

    // A 2ª completion chega — token capturado = actual = 2 → válida (cleanup natural via useEffect)
    resolve2();
    await Promise.resolve(); await Promise.resolve();
    expect(setError).not.toHaveBeenCalled();
    expect(spy).toHaveBeenCalledTimes(2);
    expect(spy).toHaveBeenNthCalledWith(1, 'task-1', expect.objectContaining({ dueDate: '2026-05-15' }));
    expect(spy).toHaveBeenNthCalledWith(2, 'task-1', expect.objectContaining({ dueDate: '2026-05-16' }));
  });
});
```
