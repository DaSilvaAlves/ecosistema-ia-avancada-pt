## Contexto

PRD §10 Epic 1 Goal: "implementar function calling capaz de classificar e executar 1+ intents PT-PT em paralelo, com preview, undo, audit log." A Story 1.2 é a camada de abstracção que separa a API Anthropic da lógica de negócio. Sem ela, Stories 1.4 e 1.5 estariam a inicializar o SDK Anthropic directamente, sem contrato tipado, sem mock fácil para testes.

Architecture `§6.1` define modelos: `modelClassifier: 'claude-haiku-4-5'` e `modelExecutor: 'claude-sonnet-4-6'`. A Story 1.1 já criou `lib/agent/schemas.ts` com `AgentRunSchema`, `ToolCallSchema`, `ChatMessageSchema` — esta story adiciona schemas para os contratos do provider nesse mesmo ficheiro.

O Tool Registry (Story 1.3) que fornece `ToolDefinition[]` ao executor ainda não existe — a Story 1.2 define a interface `ToolDefinition` mínima necessária para o tipo do executor, mas não implementa o registry. A Story 1.3 implementará `lib/agent/tools/registry.ts` que respeitará este contrato.

## Acceptance Criteria

- **AC1:** Existe `lib/agent/providers/types.ts` que exporta as seguintes interfaces TypeScript:
  - `LLMMessage` — `{ role: 'user' | 'assistant' | 'tool'; content: string; toolCallId?: string; }`
  - `LLMToolCall` — `{ id: string; name: string; input: unknown; }`
  - `LLMStreamEvent` — union discriminated por `type`: `'text_delta' | 'tool_use' | 'tool_result' | 'done' | 'error'`
  - `LLMResponse` — resultado síncrono (para classify): `{ content: string; inputTokens: number; outputTokens: number; }`
  - `ClassificationResult` — `{ intents: string[]; confidence: Record<string, number>; rawResponse: string; inputTokens: number; outputTokens: number; }`
  - `ClassifierOpts` — `{ model?: string; maxTokens?: number; temperature?: number; }`
  - `ExecutorOpts` — `{ model?: string; maxTokens?: number; runId: string; }`
  - `ToolDefinition` — interface mínima alinhada com arch §7.2 (canónico): `{ name: string; description: string; argsSchema: z.ZodType<unknown>; }`. Story 1.3 expande com `resultSchema`, `domain`, `requiresPreview`, `reversible`, `execute`, `reverse` mas PRESERVA os 3 campos base (`name`, `description`, `argsSchema`). O `AnthropicExecutor` converte `argsSchema` (Zod) → `input_schema` (JSON Schema) internamente via `zod-to-json-schema` antes de chamar o SDK.
  - `ClassifierProvider` — interface: `classify(systemPrompt: string, userPrompt: string, opts?: ClassifierOpts): Promise<ClassificationResult>`
  - `ExecutorProvider` — interface: `execute(messages: LLMMessage[], tools: ToolDefinition[], opts: ExecutorOpts): AsyncIterable<LLMStreamEvent>`

- **AC2:** Existe `lib/agent/providers/anthropic.ts` que implementa `ClassifierProvider` e `ExecutorProvider` usando `@anthropic-ai/sdk`:
  - `AnthropicClassifier.classify()` chama `client.messages.create()` com model `claude-haiku-4-5-20251001` (override via `opts.model`)
  - `AnthropicExecutor.execute()` chama `client.messages.stream()` com model `claude-sonnet-4-6` (override via `opts.model`), emitindo eventos `LLMStreamEvent` na ordem correcta

- **AC3:** `AnthropicExecutor.execute()` suporta o tool calling loop básico:
  - Quando o provider emite evento `tool_use`, o consumidor (Story 1.5) injeta o resultado como `tool_result` e continua

### Contexto técnico de arch

**Edge runtime para classifier, Node runtime para executor** (ADR-1):
- `ClassifierProvider` é consumida em Edge (latência baixa, sem Node APIs)
- `ExecutorProvider` é consumida em Node via `/api/agent/prompt` (Story 1.8)
- A abstracção `lib/agent/providers/` não deve usar APIs Node-only (ex: `fs`, `crypto.createHmac`) — só SDK Anthropic + Web APIs

**SDK Anthropic (`@anthropic-ai/sdk`):**
- Já presente no `package.json` de `imersao-tools/nexus/v2/` (instalado na Story 0.5 — proxy Anthropic)
- Inicializar com `new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY })`
- Para streaming no executor, usar `client.messages.stream(params)` que retorna `MessageStream`
- SDK events relevantes para mapeamento para `LLMStreamEvent`:
  - `client.messages.create({ stream: false })` → response síncrona (classifier)
  - `client.messages.stream()` → stream com eventos:
    - `message_start` → ignorar (tokens estão em `message_stop`)
    - `content_block_start` com `content_block.type === 'tool_use'` → yield `{ type: 'tool_use', id, name, input: {} }`
    - `content_block_delta` com `delta.type === 'text_delta'` → yield `{ type: 'text_delta', text }`
    - `content_block_delta` com `delta.type === 'input_json_delta'` → acumular JSON para tool input
    - `message_stop` → yield `{ type: 'done', inputTokens, outputTokens }`

**`ToolDefinition` mínima para AC1 (interface apenas — alinhada com arch §7.2):**
```ts
import type { z } from 'zod';
export interface ToolDefinition {
  name: string;
  description: string;
  argsSchema: z.ZodType<unknown>; // Zod schema canónico (arch §7.2)
}
```

**Interface mínima stable** — Story 1.3 PODE adicionar campos (`resultSchema`, `domain`, `requiresPreview`, `reversible`, `execute`, `reverse`) mas NUNCA remover ou renomear `name`/`description`/`argsSchema`. O `AnthropicExecutor` converte `argsSchema` (Zod) → `input_schema` (JSON Schema, formato Anthropic SDK) via `zod-to-json-schema` internamente. Esta abordagem mantém arch §7.2 como single source of truth (`argsSchema` Zod) e evita duplicação `inputSchema`/`argsSchema` na Story 1.3.

**Padrão `z.unknown()` — lição Story 1.1 (aplicável):**
Se algum campo de `LLMStreamEvent` ou `ClassificationResult` tiver tipo `unknown`, usar o padrão `Schema.parse(input)` validando mas retornando o `input` original tipado. Ver `lib/agent/run-builder.ts` e `lib/agent/schemas.ts` para referência.

**`ClassificationResult.confidence`:**
Este campo é `Record<string, number>` — score de confidence por intent. O classifier prompt (Story 1.4) define o formato exacto da resposta JSON. Por agora, a Story 1.2 define o shape do contrato; a Story 1.4 implementa o prompt que preenche esse shape.

**`ExecutorOpts.runId`:**
O `runId` é criado pela Story 1.5 via `run-builder.ts` (`startRun()` da Story 1.1). A Story 1.2 não persiste nada — recebe o `runId` como parâmetro de entrada para rastreabilidade.

**Env var `ANTHROPIC_API_KEY`:**
- Já configurada no `imersao-tools/nexus/v2/.env.local` (instalado na Story 0.5)
- Em `lib/shared/env.ts` (arch §3 line 150) existe wrapper de validação Zod — usar este wrapper em vez de `process.env` directo
- Se `env.ts` não expõe `ANTHROPIC_API_KEY`, adicionar ao schema desse ficheiro (1 linha)

**Sem `any` em parte alguma** — Constitution Article VI + padrão fixado na Story 1.1. Usar `unknown` com type guards quando necessário.

### Anti-padrões específicos a esta story

- **Não implementar tool calling loop** — o loop (receber `tool_use`, chamar `execute()`, injectar `tool_result`, re-chamar provider) é responsabilidade da Story 1.5. O executor desta story apenas emite o evento `tool_use` e continua o stream.
- **Não criar `lib/agent/tools/registry.ts`** — é a Story 1.3.
- **Não criar `lib/agent/classifier.ts` nem `lib/agent/executor.ts`** — a arch §3 (lines 116-117) lista estes ficheiros mas pertencem às Stories 1.4 e 1.5 respectivamente. Esta story cria apenas a camada de provider abstraction (interfaces + implementação SDK + factories).
- **Não criar UI, endpoint, nem SSE handler** — é a Story 1.8 (endpoint) e 1.9 (UI).

2. **Conversão Zod → JSON Schema no executor** (não no registry): `toAnthropicTools()` é função interna do `AnthropicExecutor` que invoca `zod-to-json-schema` por tool. Isto mantém arch §7.2 como single source of truth (`argsSchema` Zod) sem duplicação `inputSchema`/`argsSchema` na Story 1.3. Story 1.3 pode adicionar cache no registry se a conversão se tornar bottleneck.

3. **Mapeamento `LLMMessage` (role 'tool') → Anthropic SDK**: SDK não tem role 'tool' — convertemos para `role: 'user'` com `content: [{ type: 'tool_result', tool_use_id, content }]`. `toolCallId` é validado como obrigatório quando `role === 'tool'`.

4. **MSW handlers via system prompt magic strings**: `MOCK_CLASSIFIER`, `MOCK_CLASSIFIER_MALFORMED`, `MOCK_CLASSIFIER_NOT_JSON`, `MOCK_API_ERROR`, `MOCK_EXECUTOR_TOOL_USE`. Permite cobrir casos positivos e negativos sem reset de handlers entre testes. Multi-intent canónico Story 0.5 preservado (não-streaming, sem magic string).

5. **Coverage `types.ts` 0%**: ficheiro contém apenas interfaces TypeScript (sem runtime code). v8 reporta 0% porque nada executa. Acceptance: `agent/providers/` aggregate é 93.19% — anthropic.ts 92.48% + factory.ts 100% — supera 80% threshold AC10.

6. **`error` event antes de re-throw**: padrão `try { ... } catch (error) { yield errorEvent; throw error }` — emite evento `error` para o consumidor saber, mas re-lança para preservar stack trace e permitir error boundary upstream.

Issues encontrados durante implementação:

- **vitest jsdom + Anthropic SDK**: SDK detectou browser env, falhou inicialização com "It looks like you're running in a browser-like environment". Fix: `dangerouslyAllowBrowser: true` no constructor (test/dev safe — MSW intercepta).

- **`zod-to-json-schema` API**: target `'openApi3'` produz output limpo aceitável pelo SDK Anthropic. Default target produz `$schema`/`$ref` que o SDK não suporta. Verificado contra `Tool.InputSchema` da SDK 0.32 (`{ type: 'object', properties?: ... }`).
