## Nota do `@sm` River

### Contexto e âmbito desta story

A Story 4.7 é a **fundação da infra Web Push** do Nexus v2. Entrega exactamente o necessário para que as Stories 4.8 (agendamento) e 4.9 (SW push handler) possam ser implementadas. Não implementa o agendamento nem os botões de acção da notificação — esses ficam em 4.8/4.9.

**Escopo desta story:**
1. VAPID keys configuradas como env vars (acção de `@devops`) — documentado no AC, não implementado em código pelo `@dev`
2. Dependência `web-push` + `@types/web-push` verificadas em `package.json` (já instaladas — AC2 é verificação)
3. Service Worker mínimo registado (`/sw.js`) — só o registo; o handler `push` vive na Story 4.9
4. Endpoint `/api/push/subscribe` (Node runtime) — **edição do stub da Story 0.7** — guarda a subscription em Vercel KV
5. Helper server-side `v2/lib/push/subscriptions-store.ts` — abstracção KV para save/get/delete da subscription
6. Endpoint `/api/push/send` (Node runtime) — envia um push simples (smoke test interno + base para 4.8)
7. Hook `usePushSubscription` — gere permissão + subscrição no browser; lê public key via `NEXT_PUBLIC_WEB_PUSH_VAPID_PUBLIC`
8. Componente `PushPermissionPrompt` (genuinamente novo — Story 0.7 não entregou UI de push)

**O que NÃO entra nesta story:**
- Handler `push` no Service Worker (Story 4.9)
- Botões "marcar feito" / "snooze" nas notificações (Story 4.9)
- Agendamento de lembretes para disparo (Story 4.8)
- CRUD de lembretes (Story 4.6)
- Tabela Dexie nova — a subscription persiste em Vercel KV (server-side), não em IndexedDB

    endpoint: string;
    keys: { p256dh: string; auth: string };
    createdAt: number;

### `urlBase64ToUint8Array` — implementação de referência

```ts
export function urlBase64ToUint8Array(base64String: string): Uint8Array {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const base64 = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const rawData = atob(base64);
  return new Uint8Array(Array.from(rawData).map((char) => char.charCodeAt(0)));
}
```
Referência Mozilla MDN Web Push. Testar com chave VAPID real (65 bytes P-256). Trace: AC3/AC4.

### CRIT-2 — Rota dedicada de VAPID public key: **ELIMINAR (Opção A)**

**Decisão:** a rota server-side dedicada para devolver a VAPID public key (D2/AC7/T5 do v0.1) **desaparece**. O client obtém a VAPID public key através da convenção `NEXT_PUBLIC_*` já estabelecida no projecto, lendo `process.env.NEXT_PUBLIC_WEB_PUSH_VAPID_PUBLIC` (via `getPublicEnv()` quando aplicável, `env.ts:71-74`).

**Justificação:** a premissa do draft ("não expor a public key no bundle") é arquitecturalmente incorrecta para este projecto e para a spec VAPID. A public key VAPID **não é secreta** — é, por definição (RFC 8292), entregue ao browser para a subscrição. O projecto já tomou essa decisão e codificou-a: a var tem o prefixo `NEXT_PUBLIC_` (`env.ts:36`), que no Next.js significa exposição deliberada ao bundle do client, e existe um leitor dedicado `getPublicEnv()` (`env.ts:71`). Criar uma rota server-side para devolver um valor que o projecto já decidiu inlinar no bundle é redundância que diverge do padrão do próprio projecto — exactamente o tipo de divergência que o gate deve eliminar no draft. A privada (`WEB_PUSH_VAPID_PRIVATE`, `env.ts:27`) permanece server-only — essa é a fronteira de segurança que importa (NFR5), e mantém-se intacta.

**Trade-off considerado e rejeitado (Opção B — manter a rota):** manter a rota dedicada reduziria em teoria o acoplamento do client ao nome da env var. Rejeitado: o custo (uma rota + um round-trip de rede extra no fluxo de subscrição, mais um endpoint para manter e testar) não compensa, e contradiz a convenção `NEXT_PUBLIC_` que o projecto já adoptou para esta exacta variável. Consistência arquitectural > micro-desacoplamento.

**Consequências para o re-draft:**
- Removido AC7 (rota) e T5 (rota) do draft anterior (v0.1).
- D2 reescrita: a public key chega ao client via `NEXT_PUBLIC_WEB_PUSH_VAPID_PUBLIC`.
- AC10/T7 (`usePushSubscription`): o passo "busca a public key via rota dedicada" passa a "lê `process.env.NEXT_PUBLIC_WEB_PUSH_VAPID_PUBLIC`".

### CRIT-3 — Persistência da push subscription: **Vercel KV server-side** (não IndexedDB/Dexie)

**Decisão:** a push subscription é persistida **server-side em Vercel KV** (Upstash REST, `KV_REST_API_*` — `env.ts:29-30`). IndexedDB/Dexie está **fora** do caminho de persistência da subscription. Razão dura: os endpoints `/api/push/subscribe` e `/api/push/send` correm em Node runtime (`runtime='nodejs'`) e um route handler Node **não tem `indexedDB`** — IndexedDB é uma API exclusiva do browser (`client.ts:153`). O store server-side canónico do projecto é Vercel KV.

Direcção concreta para o re-draft (os 5 pontos a–e):

**(a) Store escolhido:** **Vercel KV** (Upstash Redis via REST). Acedido por `KV_REST_API_URL` + `KV_REST_API_TOKEN` (`env.ts:29-30`). Cliente: `@vercel/kv` (`import { kv } from '@vercel/kv'`) — usa automaticamente as env vars `KV_REST_API_*`. Se o projecto já tiver um wrapper de KV em `lib/`, reutilizar esse; caso contrário, criar um cliente fino (ver ponto e).

**(b) Chave/namespace:** chave singleton com prefixo `nexus:` (convenção ADR-6, `architecture-v2.md:29` — `nexus:undo:run:*`, `nexus:agent:confirm:*`):
```
nexus:push:subscription:singleton
```
Namespace `nexus:push:` reservado para esta feature; sufixo `singleton` porque o Nexus é single-user e existe no máximo 1 subscription activa. (Se no futuro o Nexus se tornar multi-utilizador, a chave evolui para `nexus:push:subscription:{userId}` — fora de escopo agora, mas o namespace já o acomoda.) **Correcção vs draft anterior:** o prefixo `nexus:` é obrigatório por ADR-6 — não usar `push:...` sem o prefixo.

**(c) Shape do registo guardado:** o mesmo shape lógico do D1, agora serializado como valor KV (JSON). Vercel KV serializa objectos automaticamente em `set`/`get`:
```ts
interface PushSubscriptionRecord {
  endpoint: string;
  keys: { p256dh: string; auth: string };
  createdAt: number; // Date.now()
}
```
Nota: o campo `id: 'singleton'` do draft **deixa de fazer parte do registo** — a identidade singleton passa a viver na **chave** KV (`nexus:push:subscription:singleton`), não num campo do valor. É a forma idiomática em KV/Redis.

**(d) Repo helper — nome, localização e assinatura:** substitui o repo Dexie do draft. Em vez de `v2/lib/db/repos/push-subscriptions.ts` (Dexie), o helper vive **fora** de `lib/db/` (que é território Dexie/client-side) — proponho `v2/lib/push/subscriptions-store.ts` (server-side), mantendo o domínio `push` coeso com `lib/push/utils.ts`. Isto **alinha com a árvore prevista no blueprint** (`architecture-v2.md:148` → `lib/push/subscription.ts # Vercel KV`; o nome `subscriptions-store.ts` é equivalente e mais explícito — o `@sm` pode optar por `subscription.ts` para colar 1:1 ao blueprint). Padrão de import idêntico ao já usado no projecto (`import { kv } from '@vercel/kv'` em `app/api/agent/undo/route.ts:1`, `confirm/route.ts:1`). Assinatura (3 funções, mesma semântica do AC9 mas sobre KV):
```ts
// v2/lib/push/subscriptions-store.ts  (server-only — usa @vercel/kv)
import { kv } from '@vercel/kv';

const PUSH_SUBSCRIPTION_KEY = 'nexus:push:subscription:singleton';

export async function savePushSubscription(sub: PushSubscriptionRecord): Promise<void>;
export async function getPushSubscription(): Promise<PushSubscriptionRecord | null>;
export async function deletePushSubscription(): Promise<void>;
```
- `savePushSubscription` → `await kv.set(PUSH_SUBSCRIPTION_KEY, sub)`.
