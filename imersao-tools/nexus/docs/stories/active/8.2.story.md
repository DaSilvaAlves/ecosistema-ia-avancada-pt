### DESIGN-DECISION D-8.2-REAGG — Reagregação de `tool_calls` fragmentados por `index` (buffer `Map<index,…>`)

**Pergunta:** A OpenAI Chat Completions, com `stream:true`, parte os `function.arguments` de cada tool call em múltiplos `delta`. Como reagregar correctamente sem parsear cedo (a mesma classe de bug que partiu a Story 1.2 no caminho Anthropic)?

**Decisão:** O `OpenAIExecutor` mantém um `Map<number, { id: string; name: string; argsAccumulator: string }>` **indexado por `tool_calls[].index`** (não por `id`). O **primeiro** chunk de cada `index` traz `index` + `id` + `function.name` + `function.arguments` (geralmente `""`); os chunks **seguintes** desse `index` trazem só fragmentos de `function.arguments` (sem `id`/`name`) que são **concatenados** ao `argsAccumulator`. O `JSON.parse(argsAccumulator)` corre **só** quando o tool call está completo — sinalizado por `finish_reason === 'tool_calls'` (ou fim do stream / `data: [DONE]`). Aí emite-se um `tool_use` `{ id, name, input }` canónico por cada entrada do `Map`. `argsAccumulator` vazio (`""`) é interpretado como `{}` (tool sem args) — paridade com o caminho Anthropic.

**Justificação com trace:**
1. ADR-10 §4.1 (citação acima) prescreve exactamente este padrão e diz textualmente "O `OpenAIExecutor` reusa o padrão `Map<index, {id, name, argsAccumulator}>` do `AnthropicExecutor`".
2. Código real do espelho: `anthropic.ts:272-275` (`toolUseBuffers = new Map<number, { id; name; jsonAccumulator }>`), `:309-317` (concatenação de `partial_json`), `:320-351` (parse só em `content_block_stop`). O `OpenAIExecutor` é o **mesmo padrão** com o gatilho de fim mudado de `content_block_stop` (por bloco) para `finish_reason:'tool_calls'`/fim de stream (por resposta).
3. ADR-10 §7 R1 marca a reagregação errada como risco **Alta** e trata-a como `internal-state-contract-gate.md` (mesma classe da 1.2). O parse cedo (a cada delta) é o anti-padrão proibido.
4. Indexar por `index` (não por `id`) é obrigatório: os chunks de continuação **não trazem `id`** — só `index`. Indexar por `id` perderia os fragmentos seguintes.

**Alternativa rejeitada:** acumular num único buffer string global e parsear no fim assumindo um só tool call. Razão: parte o cenário multi-tool (≥2 `index` no mesmo run, ADR-10 §6.3) — os fragmentos de `index` distintos intercalam-se no stream e seriam misturados. O `Map<index,…>` é a única forma correcta.

### DESIGN-DECISION D-8.2-MESSAGES — `toOpenAIMessages()` e o round-trip `id`↔`tool_call_id`

**Pergunta:** O `LLMMessage` canónico interno tem blocos **Anthropic-shaped** (`{type:'tool_use', id, name, input}` no assistant; `role:'tool'` + `toolCallId` no resultado) e o system prompt é passado à parte. Como mapear para o array de mensagens OpenAI sem partir o round-trip de `id`?

**Decisão:** Novo helper `toOpenAIMessages(messages: LLMMessage[])` no ficheiro `openai.ts` (irmão do `toAnthropicMessages` em `anthropic.ts:174-203`), que aplica as 4 regras do ADR-10 §4.3 (citação acima): (1) **prepend** `{ role:'system', content: EXECUTOR_SYSTEM_PROMPT }`; (2) `role:'tool'` → `{ role:'tool', tool_call_id: toolCallId, content }` (fail-loud PT-PT se `toolCallId` ausente, espelhando `anthropic.ts:179-183`); (3) bloco `tool_use` no `content: ContentBlock[]` do assistant → `{ role:'assistant', content: null, tool_calls:[{ id, type:'function', function:{ name, arguments: JSON.stringify(input) } }] }`; (4) texto simples (`content: string`) passa directo. O **`id`** emitido pelo `tool_use` (vindo do stream, D-8.2-REAGG) **tem de** reaparecer intacto como `tool_call_id` na ronda seguinte — senão a OpenAI rejeita a mensagem `role:'tool'` órfã.

**Justificação com trace:**
1. ADR-10 §4.3 (4 regras) + ADR-10 §7 R2 (round-trip parte → severidade **Alta**; "parity multi-tool obrigatório").
2. `schemas.ts:92-108` (`ContentBlockSchema`: `text` | `tool_use{id,name,input}` | `tool_result{tool_use_id,content}`) e `schemas.ts:128-142` (`LLMMessageSchema`: `content: string | ContentBlock[]`, `toolCallId` obrigatório quando `role==='tool'` via `superRefine`). O `toOpenAIMessages` lê exactamente este shape.
3. `EXECUTOR_SYSTEM_PROMPT` já é importado e usado pelo caminho Anthropic (`anthropic.ts:7,251`) — o `OpenAIExecutor` usa o **mesmo** prompt, agora como mensagem `system` em vez de param top-level. Mesmo cérebro, mesma instrução PT-PT.
4. `internal-state-contract-gate.md`: o estado de tool-calling atravessa **stream → loop → message → request**. O cenário multi-tool é o que prova que o round-trip não parte na fronteira do provider (ver AC9 + Testing C8).

**Alternativa rejeitada:** gerar `tool_call_id` novo no `toOpenAIMessages` em vez de preservar o `id` do stream. Razão: a OpenAI **exige** que o `tool_call_id` da mensagem `role:'tool'` corresponda a um `tool_calls[].id` da `assistant` anterior; gerar um novo id parte o vínculo e a API rejeita (ADR-10 §4.3/§7 R2).

### DESIGN-DECISION D-8.2-USAGE — `stream_options:{include_usage:true}` e mapeamento de tokens

**Pergunta:** Em streaming, onde vem o usage e como o mapear para o `done` event canónico?

**Decisão:** O request usa `stream: true` **e** `stream_options: { include_usage: true }`. Com isso, a OpenAI emite um chunk final com `choices: []` e `usage: { prompt_tokens, completion_tokens }` **antes** do `data: [DONE]`. O executor mapeia `prompt_tokens → inputTokens` e `completion_tokens → outputTokens` e emite-os no `done` event (`{ type:'done', inputTokens, outputTokens }`, validado por `LLMStreamEventSchema`). O chunk de usage tem `choices: []` — **não** deve ser tratado como um delta de conteúdo (guard explícito; ver D-8.2-LIFECYCLE / AC12).

**Justificação com trace:**
1. ADR-10 §4.1 (citação acima): "`usage` em streaming exige `stream_options: { include_usage: true }`; sem ele, o `done.{inputTokens,outputTokens}` ficaria a zero. Mapear `prompt_tokens → inputTokens`, `completion_tokens → outputTokens`."
2. Espelho Anthropic: `anthropic.ts:256-258` (`inputTokens`/`outputTokens` acumulados de `message_start`/`message_delta`) → `:365-371` (`done` event). O OpenAI lê o chunk de usage em vez de `message_start`/`message_delta`, mas emite o **mesmo** `done` canónico.

**Alternativa rejeitada:** omitir `stream_options` e estimar tokens. Razão: contraria o ADR e produz `done` com tokens a zero — o audit log (`AgentRun.inputTokens/outputTokens`, `schemas.ts:33-34`) ficaria enganador.

### DESIGN-DECISION D-8.2-FILE-SHARED — A 8.2 estabelece `openai.ts` + helpers de cliente partilhados (coordenação com a 8.3)

**Pergunta:** A 8.2 (`OpenAIExecutor`) e a 8.3 (`OpenAIClassifier`) tocam o **mesmo** ficheiro `lib/agent/providers/openai.ts`. Quem cria o quê para não haver colisão nem duplicação?

**Decisão:** A **8.2 cria o ficheiro** `lib/agent/providers/openai.ts` e estabelece os **helpers de cliente partilhados** que a 8.3 reutiliza sem os recriar:
- `isOpenAITestEnv()` — espelho de `isTestEnv()` (`anthropic.ts:72-74`);
- `buildOpenAIClientOptions(apiKey)` — espelho de `buildClientOptions` (`anthropic.ts:80-85`), gateando `dangerouslyAllowBrowser` só em ambiente de teste (o SDK `openai` tem a mesma opção);
- a construção do cliente `new OpenAI(buildOpenAIClientOptions(apiKey))` e o re-export de `DEFAULT_OPENAI_EXECUTOR_MODEL`/`DEFAULT_OPENAI_CLASSIFIER_MODEL`.

O `toOpenAIMessages()` é **específico do executor** (o classifier não envia mensagens de tool) — fica na 8.2 mas no mesmo ficheiro. A 8.3 **adiciona** `OpenAIClassifier` ao ficheiro, reutilizando `isOpenAITestEnv`/`buildOpenAIClientOptions`. Recomendação de sequência: **8.2 primeiro** (estabelece o ficheiro + helpers), **8.3 a seguir** (adiciona o classifier) — evita um merge-race no mesmo ficheiro. Se correrem em paralelo, a 8.3 faz rebase sobre a 8.2 antes do PR.

**Justificação com trace:**
1. ADR-10 §3.1: ambos (`OpenAIClassifier` + `OpenAIExecutor`) vivem em `lib/agent/providers/openai.ts`.
2. Precedente real: `anthropic.ts` aloja `AnthropicClassifier` (`:98-159`) **e** `AnthropicExecutor` (`:226-390`) no mesmo ficheiro, partilhando `isTestEnv`/`buildClientOptions` (`:72-85`). O caminho OpenAI espelha esta organização.
3. Hard-stop §8 (≤2 iterações CR por story) e `merge-authority.md` favorecem PRs pequenos e sequenciais; a sequência 8.2→8.3 minimiza conflito no ficheiro partilhado.

**Alternativa rejeitada:** dois ficheiros separados (`openai-executor.ts` + `openai-classifier.ts`). Razão: contraria o ADR-10 §3.1 (um só `openai.ts`) e o precedente `anthropic.ts`; duplicaria `isTestEnv`/`buildClientOptions`. Mantém-se um ficheiro, com a 8.2 a estabelecê-lo.

### DESIGN-DECISION D-8.2-LIFECYCLE — Ciclo de vida do buffer (internal-state-contract-gate)

**Pergunta:** O buffer `Map<index,…>` é estado mutável que atravessa o stream. Que caminhos de borda têm de ser cobertos para o contrato não partir?

**Decisão:** O `OpenAIExecutor` trata explicitamente:
- **Chunk de continuação sem `id`/`name`** (só fragmento de `arguments`): se já existe entrada no `Map` para o `index`, concatena; se **não** existe (delta fora de ordem / defensivo), ignora silenciosamente — paridade com `anthropic.ts:310-316`.
- **`finish_reason:'tool_calls'`** (ou fim de stream sem mais chunks): gatilho de `JSON.parse` + emissão dos `tool_use`. Um `finish_reason:'stop'` fecha sem tool calls pendentes (text-only).
- **`argsAccumulator` parcial/inválido no fim** (`JSON.parse` lança): emite `error` event canónico (`{type:'error', message}`) identificando a tool culpada (`name`/`id`), e re-throw via sentinela `StreamErrorAlreadyEmitted` para o outer catch não duplicar — espelho **exacto** de `anthropic.ts:53-60,331-341,372-388`.
- **Chunk de usage** (`choices: []`): tratado como fonte de tokens, **nunca** como delta de conteúdo (guard `choices.length === 0` antes de aceder a `choices[0]`).
- **Ordem de emissão:** `text_delta` à medida que `delta.content` chega; `tool_use` no boundary de `finish_reason:'tool_calls'`/fim; `done` no fim com usage. Valida cada evento com `LLMStreamEventSchema.parse(event)` antes do `yield` (padrão `anthropic.ts:305,348,370,385`).

**Justificação com trace:**
1. ADR-10 §7 R1 + `internal-state-contract-gate.md`: o estado de tool-calling atravessa stream→loop→message→request; os caminhos de borda (fora de ordem, finish_reason, args parcial inválido) são exactamente o que o gate exige cobrir.
2. Espelho `anthropic.ts` (referências de linha acima) — o `OpenAIExecutor` reproduz cada caminho com a sintaxe do wire OpenAI.

## Acceptance Criteria

> Traçados directamente ao **ADR-10 §8 row S2** (âmbito + AC) + §2 (contrato canónico) + §4.1 (streaming + reagregação + usage) + §4.3 (`toOpenAIMessages` + round-trip) + §4.5 (modelo) + §6.2/§6.3 (mock + cenários) + §7 R1/R2/R3. Wording preservado do ADR; nenhum AC inventado.

**AC1 (`OpenAIExecutor implements ExecutorProvider`, streaming via SDK `openai`)** — Em `lib/agent/providers/openai.ts` (NOVO), `OpenAIExecutor` implementa a interface `ExecutorProvider` (`execute(messages, tools, opts): AsyncIterable<LLMStreamEvent>`). Usa o SDK `openai` com `chat.completions.create({ model, stream: true, stream_options: { include_usage: true }, messages: toOpenAIMessages(messages), tools: toolsToOpenAIShape(tools) (quando há tools) })`. O modelo default é `DEFAULT_OPENAI_EXECUTOR_MODEL` (`opts.model ?? DEFAULT_OPENAI_EXECUTOR_MODEL`). Valida `messages` não-vazio e `opts.runId` obrigatório (paridade `anthropic.ts:238-243`).

Trace: ADR-10 §3.1 + §8 row S2 + §4.5 + `types.ts:110-116` + `models.ts:35` + `anthropic.ts:226-254`.

**AC2 (Stream text-only → `text_delta` + `done`)** — Para uma resposta sem tool calls, cada `choices[0].delta.content` (string incremental) é emitido como `{ type:'text_delta', text }`; no fim, um único `{ type:'done', inputTokens, outputTokens }` com a usage mapeada. Nenhum `tool_use` é emitido.

Trace: ADR-10 §4.1 (tabela: `delta.content` → `text_delta`) + §8 row S2 ("text-only → `text_delta`+`done`") + `anthropic.ts:300-307,365-371`.

**AC3 (Reagregação de `tool_calls` fragmentados por `index` — 1 tool)** — Para 1 tool call cujos `function.arguments` chegam fragmentados em ≥2 deltas, o executor acumula por `tool_calls[].index` num `Map<index,{id,name,argsAccumulator}>`; o `id` e o `function.name` são lidos do **primeiro** chunk do `index`; os fragmentos seguintes são concatenados; o `JSON.parse(argsAccumulator)` corre **só** em `finish_reason==='tool_calls'` (ou fim de stream). Emite `{ type:'tool_use', id, name, input }` com o `input` **completo**. Parsear cedo (a cada delta) é proibido (mesma classe de bug da Story 1.2).

Trace: ADR-10 §4.1 (regra de parsing) + §7 R1 + §8 row S2 ("1 tool → `tool_use` com input completo") + D-8.2-REAGG + `anthropic.ts:272-351`.

**AC4 (Multi-tool — `index` distintos → `id` distintos)** — Para ≥2 tool calls no mesmo run (índices `0` e `1`, fragmentos possivelmente intercalados), o executor emite ≥2 `tool_use` events com `id` **distintos** e `input` correcto por cada um. O `Map<index,…>` garante que fragmentos de índices diferentes não se misturam.

Trace: ADR-10 §6.3 (cenário "Multi tool call ≥2") + §8 row S2 ("multi-tool → ids distintos") + §7 R1 + D-8.2-REAGG.

**AC5 (Args malformados → `error` event)** — Se o `argsAccumulator` de um tool call não for JSON válido no boundary de fim (`JSON.parse` lança), o executor emite `{ type:'error', message }` identificando a tool culpada (`name`/`id`) e re-throw via sentinela `StreamErrorAlreadyEmitted` (sem duplicar o evento no outer catch). Paridade exacta com `anthropic.ts:331-341,372-388`.

Trace: ADR-10 §8 row S2 ("args malformados → `error`") + §6.3 (cenário "Args malformados") + §7 R3 + D-8.2-LIFECYCLE + `anthropic.ts:53-60,331-341`.

**AC6 (Tool sem args → `input: {}`)** — Um tool call cujo `function.arguments` acumulado é `""` (vazio) é interpretado como `input: {}` (objecto vazio), não como erro. Paridade `anthropic.ts:327-330`.

Trace: ADR-10 §6.3 (cenário "Tool sem args: `arguments: ""` → `{}`") + `anthropic.ts:327-330`.

**AC7 (Usage mapeada via `include_usage`)** — Com `stream_options:{include_usage:true}`, o chunk final (`choices:[]`, `usage:{prompt_tokens,completion_tokens}`) é lido e mapeado: `prompt_tokens → inputTokens`, `completion_tokens → outputTokens`, emitidos no `done` event. O chunk de usage (`choices.length === 0`) **nunca** é tratado como delta de conteúdo.

Trace: ADR-10 §4.1 (usage em streaming) + §8 row S2 ("usage mapeada") + D-8.2-USAGE + D-8.2-LIFECYCLE.

**AC8 (`toOpenAIMessages` — system/tool/assistant-tool_call)** — `toOpenAIMessages(messages)` aplica as 4 regras do ADR-10 §4.3: (1) prepend `{ role:'system', content: EXECUTOR_SYSTEM_PROMPT }`; (2) `role:'tool'` → `{ role:'tool', tool_call_id: toolCallId, content }` (fail-loud PT-PT se `toolCallId` ausente); (3) bloco `tool_use` no `content: ContentBlock[]` do assistant → `{ role:'assistant', content: null, tool_calls:[{ id, type:'function', function:{ name, arguments: JSON.stringify(input) } }] }`; (4) texto simples (`content: string`) passa directo.

Trace: ADR-10 §4.3 (4 regras) + D-8.2-MESSAGES + `schemas.ts:92-142` + `anthropic.ts:174-203`.

**AC9 (Round-trip `id`↔`tool_call_id` fecha — falsificável)** — O `id` emitido num `tool_use` (do stream) reaparece **intacto** como `tool_call_id` na mensagem `role:'tool'` da ronda seguinte e como `tool_calls[].id` da mensagem `assistant` que o `toOpenAIMessages` produz. Um teste do cenário **multi-tool** afirma esta correspondência — falharia se o `id` se perdesse ou fosse regenerado (a OpenAI rejeitaria a mensagem `role:'tool'` órfã).

Trace: ADR-10 §4.3 (round-trip) + §7 R2 + §6.3 (multi-tool obrigatório) + `internal-state-contract-gate.md` + D-8.2-MESSAGES.

**AC10 (Factory: branch executor `openai` → `OpenAIExecutor`)** — `getExecutor()` em `factory.ts`, quando `resolveActiveProvider() === 'openai'`, valida a key (`readApiKey('openai')`) e devolve `new OpenAIExecutor(readApiKey('openai'))` — **deixa de** chamar `throwOpenAINotImplemented('executor')`. O `getClassifier()` `openai` **continua** a fail-loud "não implementado" até a 8.3. O branch `anthropic` fica byte-a-byte o de hoje.

Trace: ADR-10 §3.2 + §8 row S2 + `factory.ts:80-89,105-112` (estado da 8.1) + NOTA DE COORDENAÇÃO 8.2↔8.3.

**AC11 (Eventos canónicos validados; pipeline a jusante intocado)** — Todos os eventos emitidos são validados com `LLMStreamEventSchema.parse(event)` antes do `yield` (padrão `anthropic.ts`). O `OpenAIExecutor` emite **exactamente** o mesmo conjunto discriminado (`text_delta`/`tool_use`/`error`/`done`) que o `AnthropicExecutor` — o `toolCallingLoop` (`executor.ts`), o gate de preview, o undo e a UI não são tocados.

Trace: ADR-10 §2 (contrato canónico agnóstico) + §11 (tudo a jusante intocado) + `schemas.ts:162-187` + `anthropic.ts:305,348,370,385`.

**AC12 (Ciclo de vida do buffer — caminhos de borda; `internal-state-contract-gate.md`)** — O executor cobre: (a) chunk de continuação sem `id`/`name` para um `index` **sem** entrada no `Map` → ignora defensivamente; (b) `finish_reason:'stop'` → fecha text-only sem tool calls; `finish_reason:'tool_calls'` → gatilho de parse/emissão; (c) `argsAccumulator` parcial inválido no fim → `error` (AC5); (d) chunk de usage (`choices:[]`) → tokens, nunca delta. Cada caminho tem teste dedicado.

Trace: ADR-10 §7 R1 + `internal-state-contract-gate.md` (eixo: estado mutável atravessa stream→loop→message→request) + D-8.2-LIFECYCLE.

**AC13 (MSW OpenAI streaming fiel + testes da 8.2)** — Existem fixtures MSW para `https://api.openai.com/v1/chat/completions` (SSE estilo `choices[].delta`) que **reflectem o wire real**: `tool_calls.function.arguments` **fragmentados em ≥2 deltas** (`mock-protocol-fidelity.md`), chunk final de `usage` (só com `include_usage`), terminador `data: [DONE]`, e `finish_reason:'tool_calls'` vs `'stop'`. Existe ≥1 teste **falsificável** que falharia se o mock entregasse os args completos num só delta (prova que o acumulador é exercido). Testes unit (Vitest) cobrem: text-only (AC2), 1 tool fragmentado (AC3), multi-tool ids distintos (AC4), args malformados→error (AC5), tool sem args→`{}` (AC6), usage mapeada (AC7), `toOpenAIMessages` 4 regras + fail-loud `toolCallId` (AC8), round-trip multi-tool (AC9), factory branch executor openai (AC10), buffer lifecycle (AC12).

Trace: ADR-10 §6.2 (mock fidelity) + §6.3 (cenários) + §7 R3 + `mock-protocol-fidelity.md`.

**AC14 (Não-regressão — caminho Anthropic intocado, suite verde por construção)** — Com `LLM_PROVIDER` ausente ou `anthropic`, o comportamento é byte-a-byte o de hoje. `lib/agent/providers/anthropic.ts`, `lib/agent/executor.ts`, `lib/agent/schemas.ts`, `app/api/anthropic/proxy/route.ts`, `lib/agent/inference-transport.ts` e `lib/agent/client-executor.ts` ficam **intocados**. A suite completa (`npm run test:unit`, baseline ~2453 PASS pós-8.1) continua verde. Qualquer falha num teste Anthropic durante a 8.2 é sinal de que se tocou onde não se devia → STOP (ADR-10 §6.1).

Trace: ADR-10 §6.1 + §5 (linhas "INTOCADO") + §11.

### Ponto de atenção — espelhar `anthropic.ts`, não reinventar

O `AnthropicExecutor` (`anthropic.ts:226-390`) é o **espelho exacto** a replicar. Mapa de equivalência do wire:

| Anthropic (`anthropic.ts`) | OpenAI (`openai.ts`, esta story) |
|----------------------------|----------------------------------|
| `message_start` → `usage.input_tokens` | chunk de `usage` (`include_usage`) → `prompt_tokens` |
| `content_block_delta`/`text_delta` (`:300-307`) | `choices[0].delta.content` |
| `content_block_start` tool_use → buffer (`:285-296`) | 1.º `delta.tool_calls[]` com `index`/`id`/`function.name` |
| `input_json_delta`/`partial_json` (`:309-317`) | `delta.tool_calls[].function.arguments` (fragmentos) |
| `content_block_stop` → `JSON.parse` (`:320-351`) | `finish_reason:'tool_calls'`/fim → `JSON.parse` |
| `message_stop` | `data: [DONE]` |

A diferença estrutural: no Anthropic o boundary de parse é **por bloco** (`content_block_stop` por `index`); no OpenAI é **por resposta** (`finish_reason:'tool_calls'` fecha **todos** os tool calls pendentes de uma vez). Logo, no OpenAI itera-se sobre **todas** as entradas do `Map` no boundary, não uma só.

### Ponto de atenção — `max_tokens` vs `max_completion_tokens`

O `AnthropicExecutor` usa `max_tokens` (`anthropic.ts:250`, default 4096). A OpenAI Chat Completions aceita `max_tokens` (depreciado em alguns modelos a favor de `max_completion_tokens`). O ADR-10 §4.5 default é `gpt-4.1`, que aceita `max_tokens`. **[AUTO-DECISION]** Usar `max_tokens` (paridade comportamental + `gpt-4.1` suporta-o); se o `@architect` no gate de entrada preferir `max_completion_tokens` por robustez face a modelos futuros (`gpt-5.x`), trocar — não é invenção, é escolha de param documentada. Confirmar a forma exacta na doc OpenAII via context7 no momento da implementação (sem assumir).

### Ponto de atenção — SDK `openai` streaming: iterar o `Stream`

O SDK `openai` devolve um `Stream<ChatCompletionChunk>` async-iterable de `chat.completions.create({stream:true})`. Cada chunk tem `chunk.choices[0]?.delta` (`content?`, `tool_calls?[]`) e `chunk.choices[0]?.finish_reason`. O chunk final de usage tem `chunk.choices === []` e `chunk.usage`. **Guard obrigatório:** verificar `chunk.choices.length > 0` antes de aceder a `choices[0]` (senão o chunk de usage rebenta). Confirmar a tipagem exacta do SDK `openai@^6.45.0` via context7 / tipos do package no momento da implementação.

### Ponto de atenção — `dangerouslyAllowBrowser` em ambiente de teste

O Vitest corre em jsdom (`window` presente). O SDK `openai`, tal como o `@anthropic-ai/sdk`, bloqueia construção em contexto browser sem `dangerouslyAllowBrowser:true`. Espelhar `buildClientOptions` (`anthropic.ts:80-85`): gatear a flag **só** quando `isOpenAITestEnv()` (NODE_ENV==='test' || VITEST==='true'); em produção fica `false`. MSW intercepta as chamadas → a key nunca sai do processo de teste.

### [AUTO-DECISION] Reuso do `StreamErrorAlreadyEmitted`

O sentinela `StreamErrorAlreadyEmitted` (`anthropic.ts:53-60`) é privado de `anthropic.ts`. **Opções:** (a) duplicar a classe em `openai.ts` (zero acoplamento entre providers, paridade com o isolamento actual); (b) extrair para um módulo partilhado (`providers/stream-errors.ts`). **Decisão preliminar:** (a) duplicar — mantém o caminho Anthropic com diff **vazio** (AC14) e os providers desacoplados; a extracção DRY é dívida de baixo valor (uma classe de 8 linhas). O `@architect` confirma no gate de entrada.
