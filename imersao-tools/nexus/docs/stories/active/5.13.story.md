- Opção C: 3 ficheiros — `journal.ts` (diário), `brain-dump.ts` (brain_dump), `knowledge.ts` (conhecimento) — separação máxima, 3 domains possíveis.

`@architect` DEVE verificar em `lib/agent/classifier.ts` e `lib/agent/prompts/classifier-system.ts` como os intents de diário/brain-dump/conhecimento são agrupados antes de decidir. NÃO assumir que o agrupamento é óbvio.

> **RATIFICADO [Opção A] (Architect Gate de Entrada, Aria, 15/06/2026):** 2 ficheiros — `lib/agent/tools/journal.ts` (`domain:'journal'`, 4 tools: `criar_entrada_diario`, `consultar_diario`, `pesquisar_diario`, `brain_dump`) e `lib/agent/tools/knowledge.ts` (`domain:'knowledge'`, 5 tools: `criar_area`, `criar_caderno`, `criar_nota`, `pesquisar_conhecimento`, `pesquisar_web_e_criar_nota`).

> **Justificação ancorada em código:** O classifier agrupa **brain dump dentro de `journal`**, não num domain separado — `classifier-system.ts:31` (`DOMAIN_DESCRIPTIONS.journal = 'diário pessoal, brain dumps, reflexões'`). `knowledge` é o seu próprio domain (`classifier-system.ts:32`). A lógica de orquestração `proposeWebSearchCreate`/`persistProposal` de `lib/conhecimento/web-search-create.ts` é **client-side puro** (importa `db` singleton + repos Dexie). Uma tool Edge não pode importar este módulo.

A proposta/preview é encapsulada no resultado da tool com `requiresPreview: true` — o mecanismo do executor emite `preview_request` e aguarda confirmação. Assim a tool é genuinamente Edge-safe e o executor faz o preview.
- Opção W2: A tool `pesquisar_web_e_criar_nota` devolve apenas os resultados de pesquisa (via fetch para `/api/conhecimento/web-search`) como `resultSchema`, sem persistir. A persistência fica delegada à UI `/knowledge` (a tool actua como "pesquisar" e a criação é manual pelo utilizador). Âmbito muito reduzido — perde o FR57 "pesquisar web e criar nota automaticamente".
- Opção W3: Criar um endpoint server-side novo (`/api/conhecimento/web-search-create`) que orquestra pesquisa + persistência em cascata (replicando a lógica da 5.12 no server). A tool faz fetch para este endpoint. O endpoint tem `runtime = 'nodejs'` (como o 5.11). O estado é gerido pelo endpoint, não pela tool.

`@architect` ratifica: qual a opção? A decisão afecta AC1 (da tool `pesquisar_web_e_criar_nota`), o mecanismo de preview/confirmação, e a necessidade de criar novo endpoint.

**PONTO DE RISCO CRÍTICO:** a Edge-safety (`internal-state-contract-gate.md`) de `pesquisar_web_e_criar_nota` — qualquer caminho escolhido distribui estado por ≥2 camadas (executor Edge + endpoint Node/client). A análise dos 3 eixos já foi feita na 5.12 ([D-5.12-FAILURE]) — o `@architect` deve reutilizá-la e adaptá-la ao mecanismo escolhido.

> **RATIFICADO [Opção W1] (Architect Gate de Entrada, Aria, 15/06/2026):** A tool `pesquisar_web_e_criar_nota` faz `ctx.fetch('/api/conhecimento/web-search', ...)` (endpoint 5.11, reutilizado) para obter `{ results, source }`, e persiste a cascata área→caderno→nota **inline numa única transacção `ctx.db.transaction('rw', [knowledge_areas, knowledge_notebooks, knowledge_notes], ...)`** replicando a lógica de `persistProposal`. **`requiresPreview: true`** + `reversible: false`. **W3 (endpoint novo) REJEITADA** — desnecessário e contraproducente (ver justificação). **W2 REJEITADA** — perde o FR57/FR56 ("e cria nota").
>
> **Correcção de premissa arquitectural (crítica):** A story assume "executor Edge". É **FALSO** desde a Story 1.11 (ADR-9). O `runAgent` e TODAS as tools correm **no browser** (`client-executor.ts:1` `'use client'`; `:7` injecta o singleton Dexie real `db`; `:19-27` "conduz o `runAgent` no **browser**… `ctx.db` = singleton Dexie real"). O único ponto Edge restante é `/api/anthropic/proxy` (`client-executor.ts:35`). Consequências que simplificam W1:
> 1. **`ctx.db` é o Dexie real** — a tool pode fazer `ctx.db.transaction('rw', […])` exactamente como `persistProposal` faz (`web-search-create.ts:258-301`). Não há "command pattern" nem distribuição de persistência por camadas: a persistência acontece toda no browser, numa transacção atómica local. Precedente directo: todas as tools 2.10/3.11/4.10 escrevem via `ctx.db.*` (`habits.ts:186`).
> 2. **`ctx.fetch` é um `fetch` de browser same-origin** (`executor.ts:558` `fetch: globalThis.fetch`). Um POST a `/api/conhecimento/web-search` **transporta o cookie de sessão automaticamente** (same-origin credentials) — o `getSession(req)` do endpoint (`web-search/route.ts:210`) vê-o. **Não há SSRF nem propagação manual de cookie do lado da tool**: o vector SSRF (REC-SSRF-2) é interno ao endpoint 5.11 (fetch Node→Edge ao proxy Anthropic, `web-search/route.ts:87-104`), JÁ mitigado por allowlist de origin completa, e W1 **não lhe toca** (não o pioro).
> 3. **"Edge-safe" para esta story** significa: o ficheiro `knowledge.ts` NÃO faz `import { db }` de `@/lib/db/client` nem importa repos (`AC8`) — não por o runtime ser Edge, mas pela invariante contratual (db injectável, testabilidade com fake-indexeddb, paridade com habits.ts). A tool importa apenas `ctx` e tipos. NÃO importa `web-search-create.ts` (que importa `db` estaticamente).
>
> **Porque W3 é rejeitada:** criar `/api/conhecimento/web-search-create` (Node) deslocaria a persistência para o servidor — mas o Dexie é client-side (IndexedDB do browser); um endpoint Node **não tem acesso ao IndexedDB do utilizador**. W3 seria impossível de implementar sem reescrever a camada de persistência. W1 é a única opção coerente com ADR-9.
>
> **Análise `internal-state-contract-gate.md` — 3 eixos (adaptada de [D-5.12-FAILURE]):** O estado distribui-se por 2 camadas — (i) endpoint 5.11 Node (pesquisa) e (ii) transacção Dexie no browser (persistência). A coerência entre elas:
> - **(a) Classes de estado:** As classes são `{pesquisa-pendente, pesquisa-ok-com-resultados, pesquisa-falhou, persistência-confirmada, persistência-cancelada-via-preview}`. Cada camada: o endpoint 5.11 só conhece pesquisa (devolve `results` não-vazio OU `{error}`); a transacção Dexie só persiste após preview confirmado. A área/caderno seguem get-or-create idempotente (classe "nova" vs "existente") — replicar `nameMatches` localeCompare PT-PT de `web-search-create.ts:122-128` para AMBOS área E caderno (bug-de-classe A2: não só um). A nota é sempre nova.
> - **(b) Transição-já-ocorrida:** Os IDs de área/caderno **resolvem-se DENTRO da transacção** (`ctx.db.transaction`), nunca antes — lição M3 da 4.9 e `[D-5.12-FAILURE]` eixo b: a proposta carrega NOMES, não IDs, evitando referência stale a uma área eliminada entre a leitura e o write. Se a área já existir no momento da transacção, reutiliza-se; se não, cria-se — get-or-create idempotente dentro do mesmo `'rw'` scope (`web-search-create.ts:262-285`).
> - **(c) Caminhos de falha:** A falha do fetch é detectada **inspeccionando o CORPO** (`!resp.ok` OU `results` ausente/não-array OU `results` vazio OU campo `error`), NUNCA só `resp.ok` — lição M4 4.9/5.11 (`web-search-create.ts:186-196`): o endpoint pode devolver erro com HTTP 200 herdado da web search Anthropic. Falha de pesquisa → a tool lança `Error` PT-PT, **zero writes** (nenhuma transacção é aberta). Falha de persistência (Dexie indisponível, validação) → a transacção Dexie faz **rollback automático total** — zero entidades, nunca estado parcial (`[D-5.12-FAILURE]` eixo c). A tool propaga o erro ao executor, que emite `tool_error` (o utilizador NÃO recebe falsa confirmação).
>
> **Mecanismo de preview:** `requiresPreview: true` → o executor emite `preview_request` ANTES de `tool.execute()` (`executor.ts:1304-1326`); com `ClientConfirmationProvider` (in-process, `client-executor.ts:21`) a UI confirma; cancel → `tool_error` "Cancelado pelo utilizador" + zero writes (`executor.ts:1378-1409`). A persistência (transacção Dexie) corre DENTRO de `execute()`, ou seja **só após confirmação** — alinhado com `[D-5.12-PREVIEW]` P3 consolidado (1 confirmação para as N entidades). Nota: a pesquisa web (fetch ao 5.11) corre dentro de `execute()` DEPOIS da confirmação, logo o preview confirma a intenção "pesquisar X e criar em área/caderno Y/Z" sem mostrar resultados ainda — trade-off aceitável (a UI consolidada de proposta da 5.12 vive em `/knowledge`, fora do executor; no cérebro o preview é o gate genérico de confirmação de tool). Se a pesquisa falhar pós-confirmação, `tool_error` informa.

**[D-5.13-CHAT-RETRO]** — Entrega de `[D-5.8-CHAT-RETRO]`: mecanismo de mensagem retroactiva do agente após Brain Dump:

A Story 5.8 diferiu para a 5.13 a mensagem "Brain dump processado: N itens guardados" no chat principal (FE spec §1.4 [8]). Contexto da ratificação 5.8: a escrita directa de `ChatMessage` com `role: 'assistant'` fora do loop do executor é uma "mensagem fantasma" sem `agentRunId`. A 5.13 tem a tool `brain_dump` a correr no loop do executor.

- Opção R1: A tool `brain_dump` inclui no seu `resultSchema` o campo `mensagem` PT-PT com o sumário (ex: `"Brain dump processado: 7 itens guardados."`). O executor usa este campo para construir a resposta de agente no seu loop normal de resultado — sem escrita directa em `chat_messages` pela tool. O chat mostra a resposta do executor naturalmente. É a opção mais limpa e alinhada com a arquitectura do executor.
- Opção R2: O `execute()` da tool `brain_dump` chama `ctx.db.chat_messages.add({ id: crypto.randomUUID(), conversationId: 'main', role: 'assistant', content: mensagem, timestamp: Date.now() })` directamente. Cria a mensagem com `agentRunId: undefined` (campo opcional em `ChatMessage`). O chat aparece reactivamente via `useLiveQuery`. É tecnicamente viável mas é o "anti-padrão" que a 5.8 quis evitar.

`@architect` ratifica: qual a opção? Se Opção R1, os AC de `brain_dump` devem especificar o campo `mensagem` no `resultSchema` com o formato PT-PT. Se Opção R2, o `@architect` deve confirmar que `agentRunId: undefined` é aceitável e que a escrita directa em `chat_messages` pelo `execute()` não quebra invariantes do chat.

> **RATIFICADO [Opção R1] (Architect Gate de Entrada, Aria, 15/06/2026):** A tool `brain_dump` devolve no seu `resultSchema` o campo `mensagem: z.string()` PT-PT (ex: `"Brain dump registado: «N» itens detectados. Vai a Brain Dump para aprovar."`). O executor injecta o resultado da tool como `tool_result` no loop (`executor.ts:1462-1466` via `stringifyToolResult`), e o Sonnet **gera a resposta de chat naturalmente** no seu próprio turno. **R2 (escrita directa em `ctx.db.chat_messages.add`) REJEITADA.**
>
> **Justificação ancorada em código:** O executor é **stateless quanto a persistência de chat** — NÃO escreve em `chat_messages` nem em `agent_runs`. `executor.ts:75-83`: "o executor NÃO escreve em IndexedDB. Persistência Dexie é responsabilidade do client consumer da SSE". A persistência de chat-log mantém-se no hook `useAgentStream` (`client-executor.ts:31` "A persistência de chat-log (agent_runs/chat_messages) mantém-se no hook"). Uma escrita directa em `ctx.db.chat_messages.add({ ... role:'assistant', agentRunId: undefined })` dentro de `execute()` criaria uma `ChatMessage` **fora do `runId` corrente** (a tool não tem o `conversationId` da UI nem o vínculo ao `AgentRun` que o hook está a construir) — é precisamente a "mensagem fantasma" que a ratificação 5.8 (variante B) quis evitar, e viola a fronteira de responsabilidade do executor. R1 entrega a mesma UX (a confirmação aparece no chat) pelo caminho arquitectural correcto: a tool informa via `mensagem`, o Sonnet responde, o hook persiste a resposta do agente com o `agentRunId` certo. **Consequência para AC2/T11:** o `resultSchema` de `brain_dump` DEVE incluir `mensagem: z.string()`; T11 (mock-fidelidade) assere que o resultado da tool flui para `tool_result` (não que a tool escreve em `chat_messages`).

**[D-5.13-BRAIN-DUMP-SCOPE]** — Âmbito da tool `brain_dump`: activação ou processo completo?

A Story 5.7 (parser AI) + 5.8 (approval flow) implementaram o Brain Dump como fluxo client-side: o utilizador abre o `BrainDumpLauncher`, o AI estrutura, e o utilizador aprova item-a-item. A tool `brain_dump` (FR50) activa este fluxo via cérebro multi-intent.

- Opção B1: A tool `brain_dump` **regista o texto do utilizador** num `BrainDump` com `status: 'pending'` (ou dispara o parser AI inline via `ctx.fetch`) e devolve um resultado que o executor usa para navegar o utilizador à página de Brain Dump para aprovação. A persistência final de tarefas/projectos/notas fica no approval flow da UI (5.8) — a tool não persiste entidades finais.
- Opção B2: A tool `brain_dump` faz **o processo completo** inline (chama o parser AI, devolve os 4 buckets propostos, usa `requiresPreview: true` para o utilizador aprovar via mecanismo do executor, e persiste as entidades aprovadas via `ctx.db`). Réplica completa do fluxo 5.7+5.8 dentro do executor.

`@architect` ratifica: qual o âmbito da tool? A Opção B1 é mais conservadora e reutiliza o fluxo existente. A Opção B2 é mais ambiciosa e duplica lógica. A decisão afecta AC3 (tool `brain_dump`) e o `resultSchema`.

> **RATIFICADO [Opção B1] (Architect Gate de Entrada, Aria, 15/06/2026):** A tool `brain_dump` **regista o texto** num `BrainDump` via `ctx.db.brain_dumps.add({ id: crypto.randomUUID(), createdAt: Date.now(), bodyMarkdown: args.texto, status: 'pending' })` e devolve `{ brainDumpId, mensagem }` para o utilizador ir aprovar à UI Brain Dump (5.8). **A tool NÃO processa o parser AI inline nem persiste tarefas/projectos/notas finais.** `requiresPreview: false`, `reversible: false`. **B2 (processo completo inline) REJEITADA.**
>
> **Transição de estado FIXADA — `status: 'pending'` (canónico):** O enum `BrainDump.status` é `'pending' | 'parsed' | 'partially_approved' | 'fully_approved'` (`types/db.ts:266`). O comentário canónico (`types/db.ts:256-257`) define-o como uma **máquina de estados que atravessa sessões: parse → aprovação item-a-item**. A tool `brain_dump` só faz o **registo inicial** (FR47 input original), logo o estado correcto é `'pending'` — o brain dump foi capturado mas ainda não passou pelo parser AI (5.7) nem pela aprovação (5.8). O estado `'parsed'` só seria correcto SE a tool corresse o parser inline (B2). Como B1 não corre o parser, `'pending'` é o valor canónico e não há ambiguidade (a preocupação do PO fica resolvida: B1 → `'pending'`; se fosse B2 → `'parsed'` após o parser, nunca `'pending'`). O `parsedOutput` fica `undefined` (a story 5.7 preenche-o quando o utilizador abrir o Launcher).
>
> **Justificação ancorada em código (porque B2 é rejeitada):** B2 duplicaria todo o fluxo 5.7 (parser AI) + 5.8 (approval) dentro de `execute()`, replicando `lib/brain-dump/*` que importa Dexie e repos client-side — risco de divergência de lógica (dois caminhos de parsing/persistência a manter sincronizados) e violação de DRY. O fluxo de aprovação item-a-item da 5.8 é uma UI dedicada com decisões INBOX/TAG por item (memória [[project_nexus_v2_story_5_8_gate_entrada]]: 7 stores numa transacção única, IDs UUID determinísticos) — não é replicável de forma fiel num `requiresPreview` genérico do executor sem reescrever a UI de aprovação. B1 reutiliza o fluxo existente intacto: a tool é apenas o ponto de entrada via cérebro multi-intent (FR50), e o approval da 5.8 mantém-se a fonte única de verdade da persistência final. **Consequência para AC2/T9:** `resultSchema` de `brain_dump` = `z.object({ brainDumpId: z.string(), mensagem: z.string() })`; T9 assere `BrainDump` criado com `status: 'pending'`, `bodyMarkdown` correcto, `parsedOutput` ausente.
