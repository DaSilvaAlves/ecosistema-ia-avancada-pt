[ARCHITECT-DECISION] D-ACTION-AUTH-COOKIE (Aria, v0.4/F3-b; implementada por Dex v0.5) → O `/api/push/action` usa **cookie de sessão same-origin** via `getSession` (mesmo padrão do `/api/push/schedule`), não `CRON_SECRET` Bearer. [AUTO-DECISION] D-SCHEDULE-GET-EXTEND → O `GET /api/push/schedule` é estendido (não um novo endpoint) para expor entradas `pending` com `fireAt`. Razão: o endpoint já faz `listSchedules()` que devolve todas as entradas (sent + pending); filtrar `pending` e incluir `fireAt` é uma adição de campo ao JSON existente sem quebrar o contrato (o cliente existente `fetchSentReminderIds` lê apenas `json.sent` e ignora campos desconhecidos — sem breaking change). Um novo endpoint separado criaria mais superfície auth sem necessidade.

## Story

**As a** utilizador do Nexus v2,
**I want** que as notificações Web Push mostrem o texto do lembrete com botões "marcar feito" e "snooze 10min" accionáveis directamente na notificação,
**so that** posso responder a um lembrete sem abrir a app (Epic 4 AC3 — FR36).

## Acceptance Criteria

> Trace directo: `PRD-NEXUS-V2.md` §6.6 FR36 + `EPIC-4.md` §6 AC3 + §4 (FR36) + §9 (gate manual Chrome+Edge).

**AC1 — Handler `push` real no SW**
Quando o servidor envia um push via `sendPushNotification` com payload `{ title, body, data: { reminderId } }`, o Service Worker exibe a notificação com `self.registration.showNotification(title, { body, data, actions })`. O `event.waitUntil` garante que o SW não termina antes de `showNotification` completar.

**AC2 — Botão "marcar feito" presente na notificação**
A notificação exibe a acção `{ action: 'marcar-feito', title: 'Marcar feito' }`. O label "Marcar feito" é visível na notificação (Chrome + Edge suportam `actions` com vibrate omitido — validação manual).

**AC3 — Botão "snooze 10min" presente na notificação**
A notificação exibe a acção `{ action: 'snooze', title: 'Snooze 10min' }`.

**AC4 — "marcar feito" fecha lembrete sem abrir a app (Epic 4 AC3)**
Quando o utilizador clica "Marcar feito" na notificação: (a) a notificação fecha (`event.notification.close()`); (b) o SW chama `/api/push/action` com `{ reminderId, action: 'marcar-feito' }` via `fetch` same-origin com `credentials: 'same-origin'` — o cookie de sessão é enviado automaticamente (auth por sessão, **não** Bearer; D-ACTION-AUTH-COOKIE); (c) a app **não abre** (`clients.openWindow` não é invocado); (d) na próxima abertura da app, o lembrete aparece com `status: 'sent'` (coberto pela reconciliação `reconcileSentReminders` já wired em `useDailyGenerationEngine` — sem alteração necessária para este caso).

**AC5 — "snooze 10min" adia sem abrir a app**
Quando o utilizador clica "Snooze 10min" na notificação: (a) a notificação fecha; (b) o SW chama `/api/push/action` com `{ reminderId, action: 'snooze', snoozeMinutes: 10 }` via `fetch` same-origin (cookie de sessão; D-ACTION-AUTH-COOKIE); (c) a app não abre; (d) na próxima abertura, o lembrete aparece com `status: 'snoozed'` e `fireAt` actualizado para `now + 10min` (via reconciliação on-mount — AC8).

**AC6 — Click na notificação sem acção específica abre a app**
Quando o utilizador clica no corpo da notificação (sem clicar num botão de acção), a app abre (ou foca a janela existente via `clients.matchAll` + `window.focus()`). Trace: comportamento padrão esperado pelo utilizador em notificações sem acção seleccionada.

**AC7 — Endpoint `/api/push/action` aplica a acção em KV**
O endpoint `/api/push/action` (Node runtime, **cookie-auth** via `getSession` → 401 se sessão inválida; D-ACTION-AUTH-COOKIE): recebe `{ reminderId, action: 'marcar-feito' | 'snooze', snoozeMinutes?: number }`; para `marcar-feito`: chama `markScheduleSent` no mirror KV (marca `status: 'sent'`); para `snooze`: chama `putSchedule` com `fireAt = now + snoozeMinutes * 60_000` mantendo `status: 'pending'` (a entrada KV não é removida — aguarda o próximo disparo do scheduler conforme D-RECON-SNOOZE-KEEP); devolve `{ ok: true }` em caso de sucesso. O `/api/push/dispatch` (cron, server-to-server) mantém `CRON_SECRET` Bearer — auth separada do `/api/push/action`.

**AC8 — Contrato `GET /api/push/schedule` estendido para expor entradas `pending` com `fireAt`**
O `GET /api/push/schedule` passa a devolver `{ sent: string[], pending: Array<{ id: string; fireAt: number }> }`. As entradas `pending` são filtradas de `listSchedules()` (já disponível em `schedule-store.ts`). O campo `sent` mantém-se inalterado — sem breaking change para `fetchSentReminderIds()` (que lê apenas `json.sent`).

**AC9 — Helper client `fetchPendingSchedules()` em `lib/push/schedule-client.ts`**
Novo helper `fetchPendingSchedules(): Promise<Array<{ id: string; fireAt: number }>>` em `schedule-client.ts`. Lê `GET /api/push/schedule` e extrai `json.pending`. Retorna `[]` em qualquer falha (best-effort — padrão `fetchSentReminderIds`). Usa a mesma auth de sessão (cookie) que o `fetchSentReminderIds`.

**AC10 — `lib/push/reconcile-snooze.ts` — reconciliação on-mount para `snoozed`**
Função `reconcileSnoozedReminders()`: (1) chama `fetchPendingSchedules()` para obter `{ id, fireAt }` das entradas pendentes no mirror; (2) para cada entrada, actualiza em Dexie via `updateReminder(id, { status: 'snoozed', fireAt })` — feedback visual imediato; (3) **não remove** a entrada do mirror (fica como `pending` para o próximo disparo pelo scheduler — D-RECON-SNOOZE-KEEP). Idempotente e best-effort (padrão `reconcileSentReminders`).

> **Nota de semântica:** `fetchPendingSchedules()` devolve todas as entradas `pending` do mirror — incluindo lembretes que ainda não foram accionados (agendados normalmente) e lembretes cujo `fireAt` foi actualizado por snooze. A distinção client-side não é necessária: `updateReminder(id, { status: 'snoozed', fireAt })` é idempotente e actualiza correctamente em ambos os casos. O `status: 'snoozed'` no Dexie é apenas feedback visual; o scheduler dispara quando `fireAt` chegar, independentemente do status Dexie.

**AC11 — Wiring de `reconcileSnoozedReminders()` em `useDailyGenerationEngine.ts`**
Em `hooks/useDailyGenerationEngine.ts`, `reconcileSnoozedReminders()` é adicionada no mesmo `useEffect` on-mount onde já existe `void reconcileSentReminders()` (linha 53 do ficheiro actual). Após a adição:

```typescript
// Story 4.8 (AC6, D-RECON-MOUNT) — reconciliação de lembretes disparados
void reconcileSentReminders();
// Story 4.9 (AC11) — reconciliação de lembretes com snooze actualizado
void reconcileSnoozedReminders();
```

Corre em cada mount, fora do gate diário (idêntico à lógica do `reconcileSentReminders` — barata, idempotente, precisa de ser imediata). Trace: `useDailyGenerationEngine.ts` L46-L53 (verificado no código real).

**AC12 — Testes de protocolo reais (mock-protocol-fidelity.md)**
Existem testes unitários que cobrem:
- C1: handler `push` — `showNotification` chamado com `actions` correcto quando `event.data.json()` devolve payload válido.
- C2: handler `push` — `event.waitUntil` é chamado (o SW não termina a tempo).
- C3: handler `notificationclick` — `action: 'marcar-feito'`: notificação fecha + fetch para `/api/push/action` + `openWindow` NÃO chamado.
- C4: handler `notificationclick` — `action: 'snooze'`: notificação fecha + fetch para `/api/push/action` com `snoozeMinutes: 10` + `openWindow` NÃO chamado.
- C5: handler `notificationclick` — sem acção (dismiss): `openWindow` chamado + notificação fecha.
- C6: fidelidade ao protocolo — ≥1 teste que falharia se `event.data.json()` devolvesse um shape diferente do esperado (ex: campo `reminderId` ausente → `showNotification` ainda corre mas `data` é `undefined` → AC4 falha).
- C7: `/api/push/action` — `marcar-feito`: mirror KV actualizado para `sent`; 401 sem `CRON_SECRET` correcto.
- C8: `/api/push/action` — `snooze`: `fireAt` actualizado no mirror KV; `status` mantém `pending`.
- C9: `GET /api/push/schedule` — resposta inclui campo `pending` com `{ id, fireAt }` das entradas `pending`; campo `sent` mantém comportamento anterior.
- C10: `fetchPendingSchedules()` — lê `json.pending`, retorna `[]` em falha.
- C11: `reconcileSnoozedReminders()` — chama `fetchPendingSchedules()` + `updateReminder` para cada entrada; não chama `removeReminderSchedule`.

**AC13 — Teste manual real em Chrome + Edge (gate obrigatório do epic)**
Verificação manual conforme `EPIC-4.md` §9: criar lembrete, aguardar disparo pelo scheduler (ou disparar manualmente via `POST /api/push/send`), confirmar que a notificação mostra os botões "Marcar feito" e "Snooze 10min" e que clicar em "Marcar feito" fecha o lembrete sem abrir a app. Resultado documentado no gate do `@architect`.

Os unit tests passam porque mockam `fetch`, mas não exercitam o contrato real. A mitigação documentada ("placeholder injectável") não existe como código nem como story.

2. **Mesmo que injectado, embeber `CRON_SECRET` num ficheiro estático é uma escalada de privilégio inaceitável.**
   `/sw.js` é servido a qualquer cliente (autenticado ou não). O `CRON_SECRET` protege também o `/api/push/dispatch` (4.8) — o trigger do envio de TODOS os pushes. Expor esse secret no bundle do SW permitiria a qualquer pessoa disparar o dispatch. O CRON_SECRET é um secret de servidor-para-servidor; nunca pode viver no cliente.

**A alternativa correcta (e mais simples) é cookie same-origin:**
O `notificationclick` corre no contexto same-origin do browser do utilizador autenticado. Um `fetch('/api/push/action', { method:'POST' })` a partir do SW é same-origin e envia o cookie de sessão automaticamente (default `same-origin` credentials; `SameSite=Lax` permite-o num POST same-origin top-level-navigation-independent — ver nota abaixo). É exactamente o modelo que `/api/push/schedule` já usa (`getSession(req)`, L116-120). O `/api/push/action` passa a usar `getSession` em vez de `secretsMatch`/`extractBearer`, eliminando o secret do SW por completo. O `/api/push/dispatch` (cron real, server-to-server) mantém o Bearer — os dois caminhos separam-se, como o spec previa na opção (b).

> Nota sobre `SameSite`: o cookie de sessão Nexus deve ser `SameSite=Lax` (ou `Strict`). Um `fetch` same-origin do SW (origin == origin do endpoint) envia o cookie em ambos os casos — não é uma requisição cross-site. ### Análise de ciclo de vida (porque M1+M2+M3 são bugs reais, não teóricos)

Ciclo de vida de uma entrada no mirror KV (`schedule-store.ts`, `dispatch/route.ts`, `reconcile-reminders.ts`):

1. Lembrete criado → `putReminderSchedule` → entrada `pending` (`fireAt` original).
2. Scheduler chama `/api/push/dispatch` quando `fireAt <= now` → `markScheduleSent(entry)` → entrada transita a **`sent`** (`dispatch/route.ts` L60).
3. **É neste momento (entrada já `sent`) que o push chega ao browser e o utilizador clica "Snooze".**
4. App abre → `reconcileSentReminders` lê `sent`, marca Dexie `sent`, e faz `removeReminderSchedule(id)` (DELETE) → **entrada desaparece do mirror**.

Consequências confirmadas no código:

- **M1:** quando o utilizador clica "Snooze" no passo 3/4, a entrada está `sent` (ou já removida). O `action/route.ts` faz `listSchedules().find(...)`. Se removida → `!entry` → `{ok:true, applied:false}` → **snooze silenciosamente perdido**. Se ainda `sent` → o `putSchedule({...entry, status:'pending'})` **re-escreve uma entrada `sent` para `pending`**, o que funciona por acaso mas é frágil e não testado.
- **M2+M3:** o `ScheduleEntrySchema` (`schedule-store.ts` L32-37) só tem `status: enum(['pending','sent'])` — **não existe estado `snoozed` no mirror**. Logo o GET `filter(status==='pending')` devolve **lembretes normais ainda-não-disparados** (a esmagadora maioria das entradas `pending`). O `reconcileSnoozedReminders` marca TODOS esses lembretes normais como `snoozed` em Dexie no próximo mount → **o utilizador vê lembretes futuros normais rotulados como "adiados"**. Corrupção de estado visível na UI.

### Contrato de snooze ratificado — D-SNOOZE-CONTRACT (Aria, Iter 3)

[ARCHITECT-DECISION] **D-SNOOZE-CONTRACT** (revoga D-RECON-SNOOZE-KEEP e a "Nota de semântica" da AC10) →

**Princípio:** uma entrada adiada por snooze tem de ser **inequivocamente distinguível** de uma `pending` normal, no servidor, com um marcador dedicado e persistente. A reconciliação on-mount actua **só** sobre entradas marcadas como snooze — nunca sobre o conjunto `pending` inteiro. O snooze não pode depender de a entrada ainda existir/estar `pending` no momento do clique.

**Mecanismo (marcador dedicado, não reutilizar `status`):**

1. **Estender `ScheduleEntrySchema`** (`schedule-store.ts`) com um campo opcional dedicado `snoozedAt?: number` (epoch ms do momento do snooze). Campo **opcional** → entradas existentes (sem o campo) continuam válidas (`listSchedules` defensivo não as descarta). É o marcador inequívoco: `snoozedAt` presente ⇔ entrada adiada por snooze. Não se sobrecarrega `status` (que continua `'pending'|'sent'`) — `status` exprime "a aguardar disparo / disparado"; `snoozedAt` exprime "foi adiado pelo utilizador". São eixos ortogonais.
   - *Alternativa avaliada e rejeitada:* adicionar `'snoozed'` ao enum `status`. Rejeitada porque o dispatch (`dispatch/route.ts` L42) dispara por `status==='pending' && fireAt<=now`; um status `'snoozed'` exigiria alterar o filtro do dispatch (contrato da 4.8) e perder-se-ia a re-disparabilidade. `snoozedAt` mantém `status='pending'` → o dispatch re-dispara naturalmente quando o novo `fireAt` chegar. Menor blast-radius sobre a 4.8.

2. **`action/route.ts` (snooze)** — ao adiar, escrever `putSchedule({ ...entry, fireAt: now+min*60_000, status: 'pending', snoozedAt: Date.now() })`. **Resolver M1:** se a entrada estiver ausente (`!entry`), o `snooze` **NÃO** pode devolver `{ok:true}` — tem de recriar a agenda a partir dos dados que tem, OU devolver não-sucesso. Como o SW só envia `reminderId` (não `text`/`fireAt` original), o endpoint não consegue recriar a entrada sozinho. **Decisão:** para `snooze` com entrada ausente, devolver `409 { ok:false, error:'schedule-gone' }` (não-sucesso) — o SW (M4) trata-o como falha e a app reconcilia o estado real no próximo mount. `marcar-feito` com entrada ausente mantém-se idempotente (`{ok:true, applied:false}`) — perder um "marcar feito" de uma entrada já removida é inofensivo (já foi reconciliada como `sent`). A assimetria é deliberada e documentada.

3. **`schedule/route.ts` (GET)** — o campo `pending` da resposta passa a conter **só entradas com `snoozedAt` definido**: `schedules.filter(s => s.status === 'pending' && typeof s.snoozedAt === 'number').map(s => ({ id, fireAt }))`. O campo `sent` mantém-se inalterado. **Resolve M2:** lembretes normais (sem `snoozedAt`) deixam de aparecer no `pending`.
   - *Nota de naming:* o campo da resposta chama-se `pending` por compatibilidade com o helper `fetchPendingSchedules` e os testes existentes; a sua **semântica** passa a ser "entradas adiadas por snooze a aguardar re-disparo". Documentar isso no JSDoc do GET (o nome do campo na resposta é contrato interno, não externo — `external-contract-identifiers.md` não se aplica a este rename semântico). Aceitável manter o nome; se o `@dev` preferir clareza, pode renomear para `snoozed` na resposta **desde que** actualize `fetchPendingSchedules` e os testes C9/C10 no mesmo commit. **Decisão Aria: manter `pending` no JSON** (menor blast-radius; a semântica fica no JSDoc).

4. **`reconcile-snooze.ts`** — sem alteração à lógica do loop (continua `updateReminder(id, {status:'snoozed', fireAt})` por entrada), porque a **fonte** já vem filtrada pelo GET (passo 3). **Resolve M3:** só entradas verdadeiramente adiadas chegam ao loop. Actualizar o JSDoc/"Nota de semântica" para reflectir que `fetchPendingSchedules()` passa a devolver **apenas** snoozes (não todas as `pending`).

5. **`sw.js` (`postAction`) — M4** — `postAction` passa a `await` a resposta e verificar `response.ok`. Em não-`ok` (401/4xx/5xx), **não** engolir: registar o status e re-mostrar a notificação para o utilizador saber que a acção não resultou (recovery path mínimo). Para `snooze` que recebe `409 schedule-gone`, o comportamento é o mesmo (notificação re-mostrada). Manter o `.catch` de erro de rede (best-effort para falhas transitórias), mas **falha HTTP ≠ sucesso**.
