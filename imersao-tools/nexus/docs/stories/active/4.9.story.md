## Story

**As a** utilizador do Nexus v2,
**I want** que as notificações Web Push mostrem o texto do lembrete com botões "marcar feito" e "snooze 10min" accionáveis directamente na notificação,
**so that** posso responder a um lembrete sem abrir a app (Epic 4 AC3 — FR36).

## Acceptance Criteria

> Trace directo: `PRD-NEXUS-V2.md` §6.6 FR36 + `EPIC-4.md` §6 AC3 + §4 (FR36) + §9 (gate manual Chrome+Edge).

**AC1 — Handler `push` real no SW**
Quando o servidor envia um push via `sendPushNotification` com payload `{ title, body, data: { reminderId } }`, o Service Worker exibe a notificação com `self.registration.showNotification(title, { body, data, actions })`. O `event.waitUntil` garante que o SW não termina antes de `showNotification` completar.

**AC2 — Botão "marcar feito" presente na notificação**
A notificação exibe a acção `{ action: 'marcar-feito', title: 'Marcar feito' }`. O label "Marcar feito" é visível na notificação (Chrome + Edge suportam `actions` com vibrate omitido — validação manual).

**AC3 — Botão "snooze 10min" presente na notificação**
A notificação exibe a acção `{ action: 'snooze', title: 'Snooze 10min' }`.

**AC4 — "marcar feito" fecha lembrete sem abrir a app (Epic 4 AC3)**
Quando o utilizador clica "Marcar feito" na notificação: (a) a notificação fecha (`event.notification.close()`); (b) o SW chama `/api/push/action` com `{ reminderId, action: 'marcar-feito' }` e `Authorization: Bearer CRON_SECRET`; (c) a app **não abre** (`clients.openWindow` não é invocado); (d) na próxima abertura da app, o lembrete aparece com `status: 'sent'` (coberto pela reconciliação `reconcileSentReminders` já wired em `useDailyGenerationEngine` — sem alteração necessária para este caso).

**AC5 — "snooze 10min" adia sem abrir a app**
Quando o utilizador clica "Snooze 10min" na notificação: (a) a notificação fecha; (b) o SW chama `/api/push/action` com `{ reminderId, action: 'snooze', snoozeMinutes: 10 }`; (c) a app não abre; (d) na próxima abertura, o lembrete aparece com `status: 'snoozed'` e `fireAt` actualizado para `now + 10min` (via reconciliação on-mount — AC8).

**AC6 — Click na notificação sem acção específica abre a app**
Quando o utilizador clica no corpo da notificação (sem clicar num botão de acção), a app abre (ou foca a janela existente via `clients.matchAll` + `window.focus()`). Trace: comportamento padrão esperado pelo utilizador em notificações sem acção seleccionada.

**AC7 — Endpoint `/api/push/action` aplica a acção em KV**
O endpoint `/api/push/action` (Node runtime, `CRON_SECRET` Bearer, sem cookie): recebe `{ reminderId, action: 'marcar-feito' | 'snooze', snoozeMinutes?: number }`; para `marcar-feito`: chama `markScheduleSent` no mirror KV (marca `status: 'sent'`); para `snooze`: chama `putSchedule` com `fireAt = now + snoozeMinutes * 60_000` mantendo `status: 'pending'` (a entrada KV não é removida — aguarda o próximo disparo do scheduler conforme D-RECON-SNOOZE-KEEP); devolve `{ ok: true }` em caso de sucesso.

**AC8 — Contrato `GET /api/push/schedule` estendido para expor entradas `pending` com `fireAt`**
O `GET /api/push/schedule` passa a devolver `{ sent: string[], pending: Array<{ id: string; fireAt: number }> }`. As entradas `pending` são filtradas de `listSchedules()` (já disponível em `schedule-store.ts`). O campo `sent` mantém-se inalterado — sem breaking change para `fetchSentReminderIds()` (que lê apenas `json.sent`).

**AC9 — Helper client `fetchPendingSchedules()` em `lib/push/schedule-client.ts`**
Novo helper `fetchPendingSchedules(): Promise<Array<{ id: string; fireAt: number }>>` em `schedule-client.ts`. Lê `GET /api/push/schedule` e extrai `json.pending`. Retorna `[]` em qualquer falha (best-effort — padrão `fetchSentReminderIds`). Usa a mesma auth de sessão (cookie) que o `fetchSentReminderIds`.

**AC10 — `lib/push/reconcile-snooze.ts` — reconciliação on-mount para `snoozed`**
Função `reconcileSnoozedReminders()`: (1) chama `fetchPendingSchedules()` para obter `{ id, fireAt }` das entradas pendentes no mirror; (2) para cada entrada, actualiza em Dexie via `updateReminder(id, { status: 'snoozed', fireAt })` — feedback visual imediato; (3) **não remove** a entrada do mirror (fica como `pending` para o próximo disparo pelo scheduler — D-RECON-SNOOZE-KEEP). Idempotente e best-effort (padrão `reconcileSentReminders`).

> **Nota de semântica:** `fetchPendingSchedules()` devolve todas as entradas `pending` do mirror — incluindo lembretes que ainda não foram accionados (agendados normalmente) e lembretes cujo `fireAt` foi actualizado por snooze. A distinção client-side não é necessária: `updateReminder(id, { status: 'snoozed', fireAt })` é idempotente e actualiza correctamente em ambos os casos. O `status: 'snoozed'` no Dexie é apenas feedback visual; o scheduler dispara quando `fireAt` chegar, independentemente do status Dexie.

**AC11 — Wiring de `reconcileSnoozedReminders()` em `useDailyGenerationEngine.ts`**
Em `hooks/useDailyGenerationEngine.ts`, `reconcileSnoozedReminders()` é adicionada no mesmo `useEffect` on-mount onde já existe `void reconcileSentReminders()` (linha 53 do ficheiro actual). Após a adição:

```typescript
// Story 4.8 (AC6, D-RECON-MOUNT) — reconciliação de lembretes disparados
void reconcileSentReminders();
// Story 4.9 (AC11) — reconciliação de lembretes com snooze actualizado
void reconcileSnoozedReminders();
```

Corre em cada mount, fora do gate diário (idêntico à lógica do `reconcileSentReminders` — barata, idempotente, precisa de ser imediata). Trace: `useDailyGenerationEngine.ts` L46-L53 (verificado no código real).

**AC12 — Testes de protocolo reais (mock-protocol-fidelity.md)**
Existem testes unitários que cobrem:
- C1: handler `push` — `showNotification` chamado com `actions` correcto quando `event.data.json()` devolve payload válido.
- C2: handler `push` — `event.waitUntil` é chamado (o SW não termina a tempo).
- C3: handler `notificationclick` — `action: 'marcar-feito'`: notificação fecha + fetch para `/api/push/action` + `openWindow` NÃO chamado.
- C4: handler `notificationclick` — `action: 'snooze'`: notificação fecha + fetch para `/api/push/action` com `snoozeMinutes: 10` + `openWindow` NÃO chamado.
- C5: handler `notificationclick` — sem acção (dismiss): `openWindow` chamado + notificação fecha.
- C6: fidelidade ao protocolo — ≥1 teste que falharia se `event.data.json()` devolvesse um shape diferente do esperado (ex: campo `reminderId` ausente → `showNotification` ainda corre mas `data` é `undefined` → AC4 falha).
- C7: `/api/push/action` — `marcar-feito`: mirror KV actualizado para `sent`; 401 sem `CRON_SECRET` correcto.
- C8: `/api/push/action` — `snooze`: `fireAt` actualizado no mirror KV; `status` mantém `pending`.
- C9: `GET /api/push/schedule` — resposta inclui campo `pending` com `{ id, fireAt }` das entradas `pending`; campo `sent` mantém comportamento anterior.
- C10: `fetchPendingSchedules()` — lê `json.pending`, retorna `[]` em falha.
- C11: `reconcileSnoozedReminders()` — chama `fetchPendingSchedules()` + `updateReminder` para cada entrada; não chama `removeReminderSchedule`.

**AC13 — Teste manual real em Chrome + Edge (gate obrigatório do epic)**
Verificação manual conforme `EPIC-4.md` §9: criar lembrete, aguardar disparo pelo scheduler (ou disparar manualmente via `POST /api/push/send`), confirmar que a notificação mostra os botões "Marcar feito" e "Snooze 10min" e que clicar em "Marcar feito" fecha o lembrete sem abrir a app. Resultado documentado no gate do `@architect`.
