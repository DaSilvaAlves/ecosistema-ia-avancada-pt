## User Story

**As a** `@dev` (Dex) a implementar o cérebro multi-intent do Nexus,
**I want** uma camada `lib/agent/executor.ts` que recebe um prompt PT-PT do utilizador, invoca `classifyPrompt()` (Story 1.4) para obter `domains`, filtra tools via `toolRegistry.byDomain(domain)` (Story 1.3), invoca `AnthropicExecutor.execute()` (Story 1.2) em loop de tool calling até o modelo parar de pedir tools ou se atingir o limite defensivo de iterações, e persiste o `AgentRun` completo via `run-builder.ts` (Story 1.1),
**so that** o Story 1.8 (`/api/agent/prompt`) possa chamar este executor e fazer stream SSE dos eventos para a UI (Story 1.9), o audit log registe cada execução completa, e o Story 1.6/1.7 consigam consumir `confidence` (preview) e `toolCalls` (undo) do `AgentRun`.

## Contexto

PRD §10 line 416 (Epic 1 Story 1.5): "Executor: executa tools em sequência ou paralelo". Architecture §8 (linhas 677-704) é o blueprint canónico do fluxo:

```text
User digita → POST /api/agent/prompt (Edge, SSE response)
                │
                ├─ classifier (Haiku) ──▶ { domains: ['tasks','finance'], confidence: 0.92 }
                │
                ├─ executor (Sonnet, stream=true)
                │     ├─ tool_use: criar_tarefa(...) ───▶ executa via registry ───▶ event
                │     ├─ tool_use: criar_finança_variavel(...) ───▶ executa ───▶ event
                │     └─ text resumo final ─▶ event
                │
                └─ persist ChatMessage + AgentRun → IndexedDB (no client após receber stream)
```

Eventos SSE canónicos (arch §8 linhas 692-698):
- `meta` — `{ runId, classifierResult }`
- `tool_start` — `{ toolName, args }`
- `tool_complete` — `{ toolName, result }`
- `tool_error` — `{ toolName, error }`
- `text_delta` — `{ delta }`
- `done` — `{ totals: { intents, toolCalls, durationMs } }`

**Token economy (arch §7.4):** Story 1.4 devolve `domains: ToolDomain[]`. Story 1.5 faz `toolRegistry.byDomain(d)` para cada domínio + `byDomain('meta')` — o executor recebe ~10 tools em vez de todas as 39 registadas. Enquanto o registry estiver vazio (Stories 2-7 ainda não executadas), o executor corre com tools `[]` — o Sonnet responde apenas com texto.

**Tool calling loop:** O `AnthropicExecutor.execute()` (Story 1.2) é **stateless** — emite eventos incluindo `tool_use` mas não executa a tool nem reinvoca o SDK. A Story 1.5 é responsável pelo loop:
1. `execute()` itera → emite `tool_use { id, name, input }`
2. Story 1.5 valida args via `tool.argsSchema.parse(input)`, invoca `tool.execute(validatedArgs, ctx)`
3. Injeta `tool_result` como nova mensagem `{ role: 'tool', content: JSON.stringify(result), toolCallId: id }`
4. Re-invoca `executor.execute(updatedMessages, tools, opts)` para o Sonnet continuar
5. Loop para quando o modelo emite `done` sem `tool_use` pendentes, ou se atingir `MAX_TOOL_ITERATIONS`

**`ExecutionContext`** (arch §7.2 lines 578-585): `{ userId: 'eurico', db, kv, fetch, logger, runId }`. Em Story 1.5, ambos `db` e `kv` são `null` (RESOLVED-2 e RESOLVED-3): executor é Edge-safe e stateless server-side; persistência Dexie acontece **no client** após receber stream SSE (arch §8 line 689). Story 1.7 introduz `kv` real (Vercel KV) para undo. Stories 2-7 que precisem de Dexie devem fazê-lo via "command pattern" no `result` da tool — o client interpreta o command e executa a operação Dexie localmente.

**Persistência `AgentRun` (RESOLVED-2):** `run-builder.startRun()` + `finishRun()` + `appendToolCall()` (Story 1.1) são as APIs canónicas mas são **invocadas pelo client consumer da SSE** (Story 1.9), não pelo executor. O executor:
1. Gera `runId = crypto.randomUUID()` (Edge-safe)
2. Emite `meta { phase: 'start', runId, prompt, modelClassifier, modelExecutor, startedAt }` — client invoca `startRun({ prompt, modelClassifier, modelExecutor })` retroactivamente passando este `runId`
3. Para cada tool resolvida: emite `tool_complete { runId, toolName, args, result, durationMs }` — client invoca `appendToolCall(runId, toolCall)`
4. No fim: emite `done { runId, status, intents, inputTokens, outputTokens, durationMs }` — client invoca `finishRun(runId, {...})`

Esta separação cumpre ADR-1 (Edge runtime no executor, sem IndexedDB no server) + ADR-2 (Dexie é client-only por design, conforme `lib/db/client.ts:64-69` JSDoc canónico).

**Anti-padrões críticos:**
- NÃO criar `/api/agent/prompt` — é Story 1.8 (com auth + rate limit)
- NÃO criar UI — é Story 1.9
- NÃO implementar preview-then-confirm — é Story 1.6 (consome `confidence` desta story)
- NÃO implementar undo — é Story 1.7 (consome `toolCalls` desta story)
- NÃO chamar API Anthropic real em testes — MSW obrigatório

## Acceptance Criteria

- **AC1:** Existe `lib/agent/executor.ts` que exporta:
  - `runAgent(userPrompt: string, opts?: RunAgentOpts): AsyncGenerator<ExecutorSSEEvent>` — função principal
  - `interface RunAgentOpts` — `{ model?: string; maxTokens?: number; maxToolIterations?: number; classifyOpts?: ClassifyOpts; }`. Defaults: `maxToolIterations = MAX_TOOL_ITERATIONS` (constante interna). `model`/`maxTokens` são pass-through para `AnthropicExecutor`. `classifyOpts` forwarded para `classifyPrompt`.
  - `type ExecutorSSEEvent` — union discriminada por `type` que cobre os 6 eventos SSE canónicos da arch §8: `meta`, `tool_start`, `tool_complete`, `tool_error`, `text_delta`, `done`. Definição em `lib/agent/executor.ts` (não em `schemas.ts` — são eventos de negócio, não contratos do provider).

- **AC2:** `runAgent(userPrompt, opts?)` implementa o pipeline completo (revisto pós-RESOLVED-2 — executor é Edge-safe e NÃO escreve em Dexie; persistência é responsabilidade do client consumer da SSE):
  1. Trim + valida `userPrompt` não vazio (lança `Error('Executor: userPrompt obrigatório')` se vazio/whitespace)
  2. Gera `runId = crypto.randomUUID()` (Web Crypto API — Edge-safe; idêntico ao `run-builder.startRun` mas sem write Dexie)
  3. Marca `startedAt = Date.now()`
  4. Emite evento `meta` (start) — `{ runId, prompt: trimmed, modelClassifier, modelExecutor, startedAt, classifierResult: null }`
  5. `classifyPrompt(trimmed, opts?.classifyOpts)` → `ClassificationResult` com `intents: ToolDomain[]`
  6. Emite evento `meta` (classified) — `{ runId, classifierResult }` (delta — apenas o resultado do classifier; client merge no estado local)
  7. Filtra tools: `const tools = getToolsForDomains(classificationResult.intents)`
  8. Executa `toolCallingLoop(messages = [{ role: 'user', content: trimmed }], tools, runId, opts)` — ver AC3
  9. Calcula `durationMs = Date.now() - startedAt`
  10. Emite evento `done` — `{ runId, status, intents, inputTokens, outputTokens, durationMs, errorMessage?, totals: { intents: intents.length, toolCalls: toolCallCount } }` — payload completo para o client invocar `startRun` retroactivamente + `finishRun` numa única operação ou via helper `persistAgentRunFromStream(events)` (Story 1.9 design)

- **AC3:** `toolCallingLoop` (função interna, não exportada):
  - Itera `AnthropicExecutor.execute(messages, tools, { model, maxTokens, runId })` via `getExecutor()` factory (Story 1.2)
  - Para cada `LLMStreamEvent` recebido:
    - `text_delta` → emite evento SSE `text_delta { delta: event.text }`
    - `tool_use` → ver AC4
    - `done` → acumula `inputTokens`/`outputTokens`; se sem `tool_use` pendentes nesta iteração, o loop para
    - `error` → emite evento SSE `tool_error { toolName: 'executor', error: event.message }` + registar no `AgentRun.errorMessage`
  - Se `iterationCount >= MAX_TOOL_ITERATIONS` antes de o modelo parar voluntariamente:
    - Para o loop
    - Emite `tool_error { toolName: 'loop_guard', error: 'Executor: limite de iterações atingido (MAX_TOOL_ITERATIONS)' }`
    - Status do run: `'partial'`

- **AC4:** Quando o executor emite `tool_use { id, name, input }` (revisto pós-RESOLVED-1 — execução sequencial, payload completo no SSE para client persistir via `appendToolCall` Story 1.1):
  1. `toolRegistry.get(name)` — se tool não encontrada, emite `tool_error { toolName: name, error: 'Tool "${name}" não registada' }` e continua (não aborta o loop)
  2. Valida args via `tool.argsSchema.parse(input)` — se falhar, emite `tool_error { toolName: name, error: ZodError PT-PT }` e continua
  3. Emite evento SSE `tool_start { runId, toolName: name, args: input }`
  4. Marca `toolStartedAt = Date.now()`
  5. Invoca `await tool.execute(validatedArgs, ctx)` SEQUENCIALMENTE com `ExecutionContext` adequado (ver AC5). Próximo `tool_use` na mesma iteração só processa após este resolver. NUNCA usar `Promise.all` em múltiplos tool_use.
  6. Calcula `toolCallDurationMs = Date.now() - toolStartedAt`
  7. Constrói `ToolCall = { toolName: name, args: input, result, durationMs: toolCallDurationMs, reverted: false }`
  8. Emite evento SSE `tool_complete { runId, toolName: name, args: input, result, durationMs: toolCallDurationMs }` — payload COMPLETO permite client invocar `appendToolCall(runId, toolCall)` directamente sem reconstruir
  9. Injecta mensagem `{ role: 'tool', content: JSON.stringify(result), toolCallId: id }` no array `messages` para próxima iteração do Sonnet
  10. Incrementa `toolCallCount` (contador interno do generator — usado no payload do `done`)

- **AC5:** `ExecutionContext` construído em `runAgent` (revisto pós-RESOLVED-2 e RESOLVED-3 — executor é Edge-safe, **zero acesso a Dexie/KV no server**):
  - `userId: 'eurico'` (constante — single user)
  - `db` — `null as unknown as NexusDB` com JSDoc: `/** @todo Stories 2-7 — tools que precisem de Dexie devem devolver "commands" no result (ver RESOLVED-2 desta story); persistência Dexie é client-only conforme arch §8 line 689 + ADR-2 */`. NÃO importar `@/lib/db/client` em `lib/agent/executor.ts` (verificável em build — Edge não tem IndexedDB).
  - `kv` — `null as unknown as VercelKV` com JSDoc: `/** @todo Story 1.7 — substituir por cliente Vercel KV real (@vercel/kv); tipagem segue pattern Zod canonical (ADR-5) tal como Tool Registry da Story 1.3 */`. `VercelKV` importado via `import type` (zero runtime cost; `@vercel/kv` NÃO é adicionado ao `package.json` nesta story).
  - `fetch` — `globalThis.fetch` (Edge + Node safe)
  - `logger` — objecto `{ info, error }` com `console.info`/`console.error` simples (Story 1.8 pode substituir por logger estruturado). **IMPORTANTE:** logger NÃO deve logar `userPrompt` nem `rawResponse` do classifier em claro — NFR11 (arch §10 NFR table): "Logs Vercel NÃO contêm conteúdo de prompts em claro". Logar apenas `runId`, `toolName`, `durationMs`.
  - `runId` — gerado in-process via `crypto.randomUUID()` (Web Crypto API — Edge-safe). Mesma forma UUID v4 que `run-builder.startRun()` (Story 1.1) usa, mas sem write Dexie (RESOLVED-2).

- **AC6:** `getToolsForDomains(domains: ToolDomain[]): ToolDefinition[]` (função interna, não exportada):
  - Para cada `domain` em `domains`: `toolRegistry.byDomain(domain)` → colecta tools
  - Sempre inclui `toolRegistry.byDomain('meta')` independentemente dos domains classificados (cross-domain queries)
  - Remove duplicados se 'meta' estiver em `domains` (Set por nome)
  - Retorna `ToolDefinition[]` — pode ser vazio se registry vazio (Stories 2-7 não executadas)
  - **NUNCA** chama `toolRegistry.all()` ou `toolRegistry.toAnthropicTools()` com todos os 39 — token economy obrigatória (arch §7.4)

- **AC7:** Constante `MAX_TOOL_ITERATIONS = 5` definida e exportada de `lib/agent/executor.ts` (permite override em testes + documentada como knob de tuning). Justificação: 5 iterações cobrem multi-intent realista (2-4 tools por domínio) com margem de segurança. Revisível em Story 1.10 com dados reais.

- **AC8:** Stream SSE carrega payloads completos para o **client** persistir o `AgentRun` (revisto pós-RESOLVED-2 — executor é stateless no server):
  - Cada evento `tool_complete` carrega `{ runId, toolName, args, result, durationMs }` — suficiente para o client invocar `appendToolCall(runId, toolCall)` (Story 1.1 API canónica)
  - Evento `done` final carrega `{ runId, status, intents, inputTokens, outputTokens, durationMs, errorMessage? }` — suficiente para o client invocar `startRun(...)` retroactivamente (com o `runId` recebido em `meta`) e `finishRun(...)`
  - O client (Story 1.9) tipicamente faz: ao receber `meta` (start) → `startRun({ prompt, modelClassifier, modelExecutor })`; ao receber cada `tool_complete` → `appendToolCall(runId, toolCall)`; ao receber `done` → `finishRun(runId, { status, intents, inputTokens, outputTokens, errorMessage })`
  - **Cálculo de `status`:** `'success'` se loop terminou voluntariamente sem erros; `'partial'` se `MAX_TOOL_ITERATIONS` atingido OU se algum `tool_error` ocorreu (manter critério simples — SF-5 documenta tech debt para revisitar com dados reais); `'failed'` se classifier ou executor lançaram excepção não capturada (AC9)
  - **AC valida apenas que o stream emite os payloads correctos** — não que o executor escreva em Dexie (não escreve)

- **AC9:** Em caso de excepção não capturada (classifier falha, SDK Anthropic erro de rede, etc.) — revisto pós-RESOLVED-2:
  - Emite evento SSE `tool_error { runId, toolName: 'executor', error: message PT-PT }` (sem stack trace — NFR11)
  - Emite evento SSE `done { runId, status: 'failed', intents: [], inputTokens: 0, outputTokens: 0, durationMs, errorMessage: message }` no `finally` do generator (garante client receber o evento de fecho — endereça SF-1)
  - Re-throw da excepção para o chamador (Story 1.8) poder retornar HTTP 500 adequado APÓS emissão do `done`
  - O client (Story 1.9), ao receber `done` com `status: 'failed'`, persiste o `AgentRun` com `errorMessage` via `startRun` + `finishRun`

- **AC10:** Tests Vitest + MSW em `tests/unit/agent/executor.test.ts` cobrem (revisto pós-RESOLVED-2 — testes do executor NÃO usam Dexie; persistência client é testada na Story 1.9):

  - Happy path sem tools (registry vazio): Sonnet responde com `text_delta` → `done`; stream emite `meta` (start + classified) → `text_delta`+ → `done` com `status: 'success'`, `totals.toolCalls: 0`

  - Multi-intent (benchmark Epic 1 AC1): `domains: ['calendar','finance']` → 2 tools de domínios distintos executadas SEQUENCIALMENTE (RESOLVED-1); ordem dos eventos `tool_complete` corresponde à ordem `tool_use` do Sonnet; `done.intents = ['calendar','finance']`

  - `getToolsForDomains` inclui sempre `meta` + desduplicação
  - NFR11 logger: `userPrompt` e `rawResponse` não aparecem em `console.info`/`console.error` calls
  - **Edge-safe (RESOLVED-2):** spy em `import` resolution — assert que `lib/agent/executor.ts` NÃO importa `@/lib/db/client` nem `@vercel/kv`; `ctx.db` e `ctx.kv` são `null` em todas as invocações de tools

export type ExecutorSSEEvent =
  // start: emitido logo no início, antes de classifier correr — client invoca startRun() ao receber
  | {
      type: 'meta';
      phase: 'start';
      runId: string;
      prompt: string;
      modelClassifier: string;
      modelExecutor: string;
      startedAt: number; // epoch ms
      classifierResult: null;

  | {
      type: 'meta';
      phase: 'classified';
      runId: string;
      classifierResult: ClassificationResult;

  | { type: 'tool_start'; runId: string; toolName: string; args: unknown }
  // tool_complete: payload COMPLETO — client invoca appendToolCall(runId, toolCall) directamente
  | {
      type: 'tool_complete';
      runId: string;
      toolName: string;
      args: unknown;
      result: unknown;

**Dexie em Edge runtime — RESOLVIDO via RESOLVED-2:**

- **API endpoint dedicado:** tool faz `fetch('/api/tasks/create')` para um endpoint Node runtime que tem acesso a server-side storage (caso venha a haver). Hoje, single-user com Dexie client-only, é overkill.

Story 1.5 entrega apenas a infraestrutura — Stories 2-7 escolhem o pattern.

## Open Questions — RESOLVIDAS por @architect (Aria) 07/05/2026

Decisões fechadas, alinhadas com os 5 ADRs canónicos (architecture-v2.md §1, 04/05/2026). NÃO reabrir sem nova validação Eurico.

### RESOLVED-1 — toolCalls: SEQUENCIAL com persistência incremental

**Decisão:** Tool calls dentro de uma iteração do loop são executadas **sequencialmente**, na ordem em que o Sonnet as emite. Cada `ToolCall` é persistido **incrementalmente** via `appendToolCall(runId, toolCall)` (Story 1.1 — já implementado em `lib/db/repos/agent-runs.ts:65-76`, com transacção Dexie `rw` que serializa concurrent appends e evita TOCTOU).

**Justificação técnica:**

1. **Determinismo do audit log (Story 1.1 contract):** `appendToolCall` (criado pela Story 1.1 AC8) é a API canónica para acumular tool calls. Já existe, é tipada, valida via Zod, e tem garantia transaccional. Re-implementar batch via `db.agent_runs.update({ toolCalls: [...] })` no fim seria **duplicação** e violaria a separação de concerns que a Story 1.1 estabeleceu.
2. **Undo (Story 1.7) precisa de ordem reversa determinística:** o `reverse()` de cada tool corre na ordem inversa do `execute()`. Execução paralela tornaria a ordem não-determinística, quebrando o invariant que Story 1.7 vai construir em cima.
3. **UX SSE limpa:** ordem `tool_start → tool_complete` por tool, intercalada com `text_delta`, é o que a UI Story 1.9 espera renderizar como cards sequenciais (arch §8 lines 700-703: "Cards de tools aparecem em tempo real (loading → success/error)").
4. **Side effects de write tools:** ~30 das 39 tools previstas (arch §7.4) são writes Dexie (criar_tarefa, criar_finança_*, etc.). Paralelizar criaria race conditions em transacções Dexie de tabelas relacionadas (ex: `criar_parcelada` toca `transactions` + `installments` simultaneamente).
5. **Multi-intent realista é pequeno:** o benchmark Epic 1 AC1 do PRD (linha 424) usa 2 tools. O `MAX_TOOL_ITERATIONS=5` (AC7) implica máximo ~5-10 tools totais por run. A latência sequencial é dominada pelo tempo do Sonnet (network), não pelas tools locais (Dexie sub-50ms NFR2). Optimização paralela é **prematura** sem dados reais (revisitável na Story 1.10).

**Trace:**
- ADR-2 (Dexie 4 desde dia 1) + arch §6.1 lines 410-416 — `ToolCall[]` é canonical, ordem importa
- arch §8 lines 700-703 — UX espera cards sequenciais
- Story 1.1 AC8 + `lib/db/repos/agent-runs.ts:65-76` — `appendToolCall` é a API canónica
- Story 1.7 (futura) — undo precisa de ordem reversa determinística

**Impacto em ACs:**
- **AC4 actualizado:** passo 5 do pipeline tool_use → "Acumula `ToolCall` via `appendToolCall(runId, toolCall)` ANTES de emitir `tool_complete`" (substitui "array interno" + write final).
- **AC8 simplificado:** remove a obrigação de "escrever via `db.agent_runs.update(runId, { toolCalls })` antes de `finishRun`" — `appendToolCall` já fez writes incrementais. `finishRun` apenas regista `status`/`intents`/tokens/`durationMs`.

### RESOLVED-2 — Persistência client-side; Story 1.5 NÃO usa Dexie em Edge

**Decisão:** A Story 1.5 entrega **apenas** o async generator `runAgent()` que **NÃO toca em IndexedDB**. Toda a persistência Dexie (criar `AgentRun`, `appendToolCall`, `finishRun`) acontece **no cliente**, depois do client receber o stream SSE — exactamente como a arch §8 line 689 declara: *"persist ChatMessage + AgentRun → IndexedDB (no client após receber stream)"*.

**O que muda concretamente:**
- `runAgent()` deixa de chamar `startRun`/`finishRun`/`appendToolCall` directamente
- O `runId` é gerado no início do generator com `crypto.randomUUID()` (Edge-safe — Web Crypto API)
- Os eventos SSE carregam toda a informação que o client precisa para reconstruir o `AgentRun` localmente:
  - `meta` carrega `runId` + `prompt` + `modelClassifier`/`modelExecutor` + `timestamp` (start)
  - `tool_complete` carrega `toolName`, `args`, `result`, `durationMs` (suficiente para `appendToolCall` no client)
  - `done` carrega `status`, `intents`, `inputTokens`, `outputTokens`, `durationMs` (final), `errorMessage?` (suficiente para `startRun`+`finishRun` no client)
- A consumer hook (Story 1.9) faz: ao receber `meta` → `startRun(...)`; ao receber cada `tool_complete` → `appendToolCall(...)`; ao receber `done` → `finishRun(...)`.

**Justificação técnica:**

1. **ADR-1 (Edge/Node split) é inegociável:** Story 1.8 (`/api/agent/prompt`) é declarada Edge na arch §4.1 line 188. Edge runtime Vercel **NÃO tem IndexedDB** — é Node-like com Web APIs limitadas (Crypto, Streams, fetch). Tentar importar `@/lib/db/client` em Edge falha em build (Dexie depende de `indexedDB` global).
2. **ADR-2 (Dexie 4 desde dia 1) é client-only por design:** o próprio `lib/db/client.ts:64-69` declara: *"Em SSR (RSC), `db` não deve ser usado directamente: queries Dexie só fazem sentido client-side"*. Isto é deliberado.
3. **Single source of truth do audit:** o cliente é onde o utilizador (Eurico) está e onde os widgets que consomem `agent_runs` correm. Server-side audit duplicaria storage e violaria NFR10 ("dados não saem do localStorage").
4. **Reconnect SSE (futura):** caso Story 1.8/1.9 venha a precisar de resumir um stream interrompido, a fonte de verdade é o `runId` que o cliente já registou — server stateless é a opção certa.

**Implicações para Story 1.5:**
- `lib/agent/executor.ts` torna-se **100% Edge-safe e stateless server-side**
- `ExecutionContext.db` passa de `NexusDB` real para `null as unknown as NexusDB` com JSDoc `@todo Stories 2-7 — tools que precisem de db delegam ao client via tool_result, ou Story 1.7 introduz client KV no server`. Stories 2-7 que precisem de Dexie têm de definir `execute` que **devolve um command para o client executar** (pattern já usado em apps PWA com SQLite remoto). A Story 1.5 não decide isto — Stories 2-7 verão.
- Os 23 tests da Story 1.5 podem testar `runAgent` puro com `fake-indexeddb` desligado — não precisam de Dexie. Apenas MSW + spy do `appendToolCall` (que NÃO deve ser chamado pelo executor).

**ACs movidas/alteradas:**
- **AC2 actualizado:** passos 2 (`startRun`), 9 (`finishRun`) e a interacção com `db.agent_runs.update` REMOVIDOS do executor. Substituídos por: emit `meta` com payload completo de start; emit `done` com payload completo de finish. Client (Story 1.9) faz a persistência.
- **AC4 actualizado (após RESOLVED-1):** passo 5 — `tool_complete` event leva `args`/`result`/`durationMs` no payload. Client invoca `appendToolCall` ao receber.

### RESOLVED-3 — VercelKV: `null` placeholder + Zod canonical para tipagem futura

**Decisão:** Em Story 1.5, `ExecutionContext.kv = null as unknown as VercelKV` com JSDoc `@todo Story 1.7`. **NÃO** adicionar `@vercel/kv` ao `package.json` nesta story — adiciona-se na Story 1.7 quando o cliente passa a ser usado. O tipo `VercelKV` é importado **só como tipo** via `import type` para satisfazer o TypeScript strict (já é o pattern usado em outros placeholders).

**Quando `@vercel/kv` for adicionado (Story 1.7):** seguir o **mesmo pattern do Tool Registry** (Story 1.3) — Zod schemas canónicos para serialize/parse de qualquer payload escrito em KV. Ou seja:

```typescript
// Story 1.7 — exemplo (NÃO implementar agora)
import { z } from 'zod';
const UndoSnapshotSchema = z.object({
  runId: z.string().uuid(),
  toolCalls: z.array(ToolCallSchema), // re-usa ToolCallSchema da Story 1.1
  expiresAt: z.number().int().positive(),
});
type UndoSnapshot = z.infer<typeof UndoSnapshotSchema>;
async function setUndoSnapshot(kv: VercelKV, snapshot: UndoSnapshot) {
  UndoSnapshotSchema.parse(snapshot); // fail-loud antes do write
  await kv.set(`nexus:undo:${snapshot.runId}`, JSON.stringify(snapshot), { ex: 30 });
}
```

**Justificação técnica:**

1. **ADR-5 (Tool Registry pattern com Zod):** o pattern canónico do projecto para validação de I/O é Zod canonical schema (`defineTool` em `lib/agent/tools/registry.ts:132-137` é a referência). KV é I/O — segue o mesmo pattern.
2. **Type drift é um risco real:** TypeScript-only types não validam runtime. Em KV (Redis), um schema mismatch após upgrade aparece em produção, não em CI. Zod canonical apanha em ambos.
3. **Consistência cross-story:** Story 1.1 usa Zod (`AgentRunSchema`, `ToolCallSchema`); Story 1.3 usa Zod (`ToolDefinitionShapeSchema`); Story 1.4 valida output Haiku contra Zod. KV não pode ser excepção.
4. **Branded types são overkill:** o ROI de branded types é em tipos primitivos partilhados (UserId, RunId). Em KV operations, a chave já é discriminada pelo prefixo (`nexus:undo:*`, `nexus:auth:session:*`) — Zod schema por prefix-namespace cobre o caso.
5. **Adiar `@vercel/kv` em Story 1.5 mantém a story focada:** AC1-AC13 não dependem de KV em runtime. Adicionar dep agora cria ruído sem benefício.

**Impacto em ACs:**
- **AC5 inalterado** quanto à decisão `kv: null` — apenas reforça o JSDoc: `/** @todo Story 1.7 — substituir por cliente Vercel KV real; tipagem segue pattern Zod canonical (ADR-5) tal como Tool Registry */`
