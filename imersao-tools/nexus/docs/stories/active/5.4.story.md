### `[GAP-5.4-RUNTIME]` — confirmar `@architect` antes de implementar

A 5.4 precisa de um endpoint server-side para a chamada ao Sonnet (a API key não pode ser exposta no browser). Há duas opções de arquitectura:

**Opção A** — Novo endpoint Edge `/api/diario/estruturar` (semelhante ao `/api/anthropic/proxy`):
- Recebe `{ bodyMarkdown: string }` via POST
- Faz chamada ao Sonnet com prompt de estruturação
- Devolve `{ whatHappened?: string; whatLearned?: string; whatFelt?: string }`
- Edge Runtime (sem SDKs Node-only, só fetch + Anthropic SDK)
- Simples, faz sentido para este fluxo (1 chamada AI, resposta JSON, sem streaming necessário)

**Opção B** — Reutilizar `/api/anthropic/proxy` com prompt específico no body:
- O proxy thin passa os headers e o body para a Anthropic API directamente
- O cliente constrói o payload completo (messages + model + prompt)
- Menos overhead de código, mas expõe o shape da request ao cliente

`@architect` decide entre A e B (e confirma se streaming é necessário ou se JSON síncrono chega). **[GAP-5.4-RUNTIME] escala `@architect`.**

> **[GAP-5.4-RUNTIME] RESOLVIDO (Architect Gate de entrada, Aria, 10/06/2026): Opção B — reutilizar `/api/anthropic/proxy`, sem endpoint novo; JSON síncrono; shape `{ whatHappened?; whatLearned?; whatFelt? }` 1:1 com `structuredAI?`.** A chamada AI vive num helper client-side `lib/diario/estruturar-cliente.ts` que espelha `InferenceTransport.classify`. Ver `[D-5.4-ENDPOINT]` + secção **Architect Gate (entrada)**. A Opção A (endpoint Edge dedicado) foi **declinada** — duplicaria auth+rate-limit+key sem benefício, e ADR-9 não se aplica (sem tools, sem Dexie server-side, sem multi-intent).

### Padrão de mock de protocolo AI (`mock-protocol-fidelity.md`)

A chamada ao Sonnet devolve uma resposta JSON com os 3 buckets (`whatHappened`, `whatLearned`, `whatFelt`). O mock MSW do endpoint de estruturação deve:
1. Reflectir o shape real da resposta da API Anthropic (não apenas fazer os testes passar)
2. Ter ≥1 teste que falharia se o shape da resposta divergisse (ex: campo renomeado, campo em falta)

[AUTO-DECISION] Como o endpoint é interno (não a API Anthropic directamente), o MSW pode interceptar `/api/diario/estruturar` — padrão consistente com ADR-8 (interceptar endpoint interno, não `api.anthropic.com`). Razão: mantém a mesma estratégia de mock já adoptada no projecto para endpoints internos que chamam a Anthropic; o endpoint interno é a fronteira natural do Nexus.

## User Story

Como utilizador do Nexus (o Eurico), quando estou a escrever uma entrada de diário com mais de 100 caracteres, quero que o cérebro AI me proponha uma estrutura organizada em "O que aconteceu", "O que aprendi" e "O que senti" — e possa aceitar ou ignorar essa proposta — para que as minhas entradas de diário se tornem mais úteis como instrumento de reflexão e continuidade pessoal, sem me forçar a escrever num formato rígido.

#### Escolha 3 — Shape da resposta AI (contrato que o mock reflecte)

Dois níveis de shape — o **wire** (resposta da Anthropic via proxy) e o **domínio** (o que o helper devolve à UI):

**Wire (o que o proxy devolve — Anthropic Messages API non-streaming):**
```jsonc
{
  "id": "msg_...",
  "type": "message",
  "role": "assistant",
  "model": "<sonnet>",
  "content": [ { "type": "text", "text": "<JSON de domínio, possivelmente com fences>" } ],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": <n>, "output_tokens": <n> }
}
```

**Domínio (o JSON que o Sonnet escreve dentro de `content[].text`, após `stripJsonMarkdownFences`):**
```ts
interface StructuredDiarioResponse {
  whatHappened?: string; // "o que aconteceu" — opcional (AI omite se o texto não tiver conteúdo)
  whatLearned?: string;  // "o que aprendi"  — opcional
  whatFelt?: string;     // "o que senti"    — opcional
}
```

Mapeia **1:1** ao `JournalEntry.structuredAI?` (`types/db.ts:228`, verificado): `{ whatHappened?: string; whatLearned?: string; whatFelt?: string }`. **Zero transformação de nomes** entre a resposta AI e o campo de persistência — `structuredAI = StructuredDiarioResponse` directamente. Os 3 campos são **todos opcionais**: a AI pode devolver `{}` ou só 1-2 buckets se o texto não suportar os 3 (ex: relato factual sem emoção → só `whatHappened`). O helper deve validar com Zod (`z.object({ whatHappened: z.string().optional(), ... }).strict()` — `strict()` para que um campo renomeado/extra falhe, satisfazendo AC5).

**Contrato de erro do helper (AC4):** `fetch` que devolve `!res.ok` → o helper **lança** `Error` com mensagem PT-PT (espelha `proxyErrorMessage` de `inference-transport.ts:184-198`). `content[].text` ausente ou JSON inválido após strip → **lança** (não devolve preview vazio silencioso). A UI apanha o throw → estado `error` (AC4). `response.ok` é verificado **antes** de ler o body (lição Epic 4 §5.1 / `internal-state-contract-gate.md` eixo c).
