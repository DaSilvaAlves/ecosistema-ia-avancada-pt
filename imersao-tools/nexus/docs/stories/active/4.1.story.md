### [GAP-4.1b] — `goal_milestones`: array embebido vs tabela separada (ESCALAR a `@architect`)

| Opção | A favor | Contra |
|-------|---------|--------|
| **Array embebido** (scaffold actual, `Goal.milestones`) | Sem join; milestones são parte do agregado Goal; pragmatismo consistente com o projecto; cascata trivial (morrem com o Goal) | Não permite query independente de milestones; PRD literal pede tabela |

**Recomendação `@sm` (não-vinculativa):** manter **array embebido** — FR40 ("vista meta: progress bar + histórico + milestones") consome milestones sempre no contexto do Goal, não isoladamente; e nenhum FR pede query global de milestones. ### CHECKPOINT @architect — AGUARDA RATIFICAÇÃO (antes de T5/T7)

> **FLAG @architect (Aria):** implementação dos repos (T5) e cascata (T7) BLOQUEADA até ratificação dos 2 pontos abaixo (condição §4 da `PO-VALIDATION-STORY-4.1.md`). T3/T4 do `Goal` também aguardam, pois o schema Zod do Goal depende do ponto 1.

**Ponto 1 — `[GAP-4.1b]` goal_milestones: recomendação Dara = EMBEBIDO.** Fundamentação técnica adicional:
- `Goal.milestones` já é array embebido no scaffold (`types/db.ts:194`) — caminho de zero-mudança de schema.
- **Cardinalidade:** um Goal tem ~2-5 milestones fixos → sub-agregado de baixa cardinalidade (padrão array embebido). Contraste deliberado com `habit_logs`, que cresce 1/dia/hábito sem limite → tabela com índice de range. A regra "alta cardinalidade + query por range → tabela; baixa cardinalidade + lido-com-o-pai → embebido" é coerente.
- Nenhum FR (FR39/FR40) pede query global de milestones; são sempre lidos no contexto do Goal.
- Tabela separada exigiria `version(5)` + índice + join em toda a leitura de Goal — custo sem benefício funcional.

**Ponto 2 — AC7 convenção de delete-cascata: proposta Dara.**
- Princípio: *cascade nos filhos sem vida própria; set null nas referências a entidades com vida própria.*
- `deleteHabit(id)` → cascade delete dos `habit_logs` do hábito (`db.transaction('rw', db.habits, db.habit_logs, ...)`). **Trade-off a confirmar:** logs como histórico vs órfãos — proposta é cascade (um log não tem significado sem o hábito). 
- `deleteReminder(id)` → cascade delete da `Recurrence` owned (`ownerType: 'reminder'`) se `recurrenceId != null` (padrão `deleteFinanceRecurrence`).
- `deleteGoal(id)` → milestones embebidos morrem com o registo (sem cascata explícita).
- **Hard-delete** (consistência com o codebase Epic 3), não soft-delete — confirmar.
- **Corolário D6** (`Task.projectId`): a Task TEM vida própria → **set null** ao apagar projecto (não cascade). Esta é a aplicação directa do princípio que resolve o débito D6.

### Ponto 1 — `[GAP-4.1b]` goal_milestones: **RATIFICADO EMBEBIDO**

**Decisão:** `Goal.milestones` mantém-se array embebido (`types/db.ts:194`). Sem tabela `goal_milestones`, sem `version(5)` por esta razão.

**Racional arquitectural:** a escolha embebido-vs-tabela rege-se por **cardinalidade + padrão de acesso**, não por preferência. `Goal.milestones` é um sub-agregado de **composição de baixa cardinalidade** (~2-5 por meta, fixos, lidos sempre no contexto do Goal — FR40; zero query global nos FR) → embebido. O contraste com `habit_logs` (tabela) é a **mesma regra aplicada coerentemente**: logs são alta cardinalidade (crescem 1/dia/hábito) com query por range (heatmap FR26) → tabela com índice `[habitId+date]`. Num store IndexedDB client-side single-user, o read-modify-write do Goal inteiro para marcar um milestone é trivial e sem concorrência real.

**Orientação para a implementação (não-bloqueadora):** documentar a semântica do campo `milestones[].at` no schema Zod — é o **valor-alvo numérico** do milestone (threshold em que `reached` vira true), coerente com `Goal.target`/`Goal.current`. Para `Goal.type === 'boolean'`, milestones são passos qualitativos (`note`) e a validação Zod **não** deve forçar `at` coerente com `target`. Permitir milestones para ambos os types sem acoplamento rígido.

### Ponto 2 — AC7 convenção de delete-cascata: **RATIFICADA**

**Princípio ratificado:** *cascade nos filhos sem vida própria (composição); set null nas referências a entidades com vida própria (associação).* É a distinção arquitectural correcta composição vs associação.

| Operação | Decisão | Racional |
|----------|---------|----------|
| `deleteHabit(id)` | **cascade** delete dos `habit_logs` (`db.transaction('rw', db.habits, db.habit_logs, ...)`) | HabitLog é observação de um Habit específico (composição forte) — órfão sem semântica sem o hábito. Padrão `deleteFinanceRecurrence`. |
| `deleteReminder(id)` | **cascade** delete da `Recurrence` owned (`ownerType: 'reminder'`) se `recurrenceId != null` | Recurrence owned pelo reminder (composição). Idêntico a `deleteFinanceRecurrence`. |
| `deleteGoal(id)` | milestones embebidos morrem com o registo | Trivial — são parte do agregado Goal. |
| Estratégia | **hard-delete** | Consistência com o codebase Epic 3 (`deleteFinanceRecurrence`/`deleteInstallmentCascade` são hard-delete). Introduzir soft-delete só aqui criaria inconsistência; auditoria não é NFR. |

**Resolução do trade-off histórico dos `habit_logs` (levantado pela Dara) — ao nível de UX, não de cascata:** o cascade está correcto para o delete *real*. O caso de uso "parar um hábito sem perder histórico" resolve-se com **archive/desactivar** (estado), não com soft-delete genérico. **Orientação para a Story 4.2 (CRUD hábitos):** oferecer "arquivar/desactivar hábito" como acção distinta de "apagar" — o utilizador que quer manter histórico arquiva; o delete (com cascade) é para remover mesmo. Isto NÃO entra na 4.1 (a 4.1 implementa o delete com cascade); é requisito a registar para a 4.2.

**Corolário D6 (`Task.projectId`) — RATIFICADO como referência:** a Task **tem vida própria** (FR30: "tarefas vinculam-se a 0 ou 1 projecto") → ao apagar um projecto, `Task.projectId` faz **set null** (não cascade, não bloquear). A convenção dá a resposta definitiva ao débito D6. Esta decisão fica registada como a resolução recomendada para a story técnica dedicada que tratar D6 pós-Epic-4 (ver `EPIC-4.md` §8 A7/D6).
