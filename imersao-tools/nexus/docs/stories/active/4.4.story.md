## User Story

**As a** utilizador do Nexus que acompanha hábitos com métricas (km corridos, páginas lidas, kg levantados),
**I want** registar o valor numérico cada vez que concluo um hábito e ver a minha evolução mensal e os meus recordes,
**so that** percebo se estou a melhorar ao longo do tempo, identifico os meus melhores dias e meses, e mantenho a motivação de superar os meus próprios limites.

- **AC1 — Helper puro `lib/habitos/metrics.ts` (tipos e funções base):** Existe `v2/lib/habitos/metrics.ts` exportando:
  ```ts
  export interface MonthlyMetricSummary {
    monthLabel: string;      // ex.: "Dez 2025" (PT-PT)
    totalValue: number;      // soma dos valores no mês
    daysCompleted: number;   // nº de dias com log no mês
    bestDayValue: number;    // melhor valor num único dia no mês
  }

  export interface MetricRecords {
    bestDayValue: number;    // maior valor num único dia (todos os logs históricos)
    bestMonthValue: number;  // maior soma num único mês (todos os logs históricos)
    bestDayDate: string;     // YYYY-MM-DD do dia com maior valor
  }
  ```
  Funções exportadas:
  - `getMonthlyEvolution(logs: HabitLog[], todayISO: string): MonthlyMetricSummary[]` — agrega os logs com `value` por mês, cobrindo os últimos 6 meses a partir de `todayISO` (usa `getLast6MonthsRange` da `heatmap.ts`). Meses sem logs aparecem com `totalValue: 0` e `daysCompleted: 0`. Ordenados do mais antigo para o mais recente.
  - `getMetricRecords(logs: HabitLog[]): MetricRecords` — calcula os recordes históricos sobre **todos** os logs passados (sem limite de range). Retorna `{ bestDayValue: 0, bestMonthValue: 0, bestDayDate: '' }` se não houver logs com `value`.
  - `getHeatmapLevel(value: number, target: number): 1 | 2 | 3 | 4` — mapeia um valor para um nível de intensidade (1 = ≤25% do target; 2 = 26-50%; 3 = 51-99%; 4 = ≥100%). Usado pelo `HabitHeatmap` com `metric`.
  Todas as funções são **puras e deterministas** (nenhuma chama `Date.now()`/`new Date()` sem argumento; recebem `todayISO` por parâmetro). Datas em `YYYY-MM-DD`, coerente com a convenção UTC da 4.2/4.3.
  _Trace: FR27, [AUTO-DECISION] A3/A4; padrão de `heatmap.ts` (4.3)._

### Gotcha crítico — logs sem `value` num hábito com métrica

A Story 4.2 criou `HabitLog`s sem `value` para todos os hábitos (incluindo os que acabaram de ter `metric` configurado). ### Gotcha — idempotência do registo de valor

A Story 4.2 estabeleceu que a idempotência do `createHabitLog` vive no handler da page, não no repo (o índice `[habitId+date]` não é unique — `client.ts:90`). A 4.4 mantém esta convenção: o handler `handleSubmitMetric` verifica se já existe log hoje para o hábito ANTES de chamar `createHabitLog`. Se já existir log com `value`, bloqueia (não duplica). Se existir log sem `value` (criado pela acção "Marcar concluído" da 4.2), o comportamento a definir: **[AUTO-DECISION] A1 implica** que para hábitos com `metric`, o registo de valor é a forma de marcar concluído — mas um log sem `value` pode já existir se o utilizador clicou "Marcar concluído" antes de a métrica ser configurada. Decisão do `@dev`: se já existe log hoje sem `value`, actualizar via `updateHabitLog(id, { value })` em vez de criar novo (o repo já deve ter `updateHabitLog` ou usar `db.habit_logs.update(id, { value })`). **Registar esta decisão no Dev Agent Record.** Se `updateHabitLog` não existir no repo, criar a função (`updateHabitLog(id: string, patch: Partial<HabitLog>): Promise<void>`) seguindo o padrão `updateHabit`.
