## Nota do `@sm` River — interpretação e resolução do [GAP-3.1]

### Contexto do [GAP-3.1]

`EPIC-3.md` §7 sinalizou explicitamente: "a Story 2.1 já criou uma tabela `recurrences` genérica — verificar em código se é reutilizável para finanças por `ownerType`, ou se precisa de extensão". Esta story resolve o gap com evidência directa do código.

### Evidência verificada (resolução do [GAP-3.1])

**Ficheiro:** `imersao-tools/nexus/v2/lib/db/client.ts` (linhas 76-79)
**Ficheiro:** `imersao-tools/nexus/v2/types/db.ts` (linhas 79-86)

```typescript
// client.ts:76-79 — Story 2.1 adicionou:
this.version(2).stores({
  recurrences: 'id, ownerType, ownerId, [ownerType+ownerId]',
  tags: 'id, name',
});

// types/db.ts:79-86 — interface Recurrence:
export interface Recurrence {
  id: string;
  rule: string; // RRULE string
  startDate: string;
  endDate: string | null;
  ownerType: 'task' | 'transaction' | 'habit' | 'reminder';
  ownerId: string;
}
```

**Conclusão do [GAP-3.1]: A tabela `recurrences` da Story 2.1 é REUTILIZÁVEL para finanças recorrentes (FR17) sem qualquer extensão de schema.**

O campo `ownerType` já contém o literal `'transaction'` (ver `types/db.ts:84`). A tabela foi desenhada explicitamente para ser genérica entre Epics 2/3/4 (`architecture-v2.md §6.2 L512-519`, `§16 L1128`; decisão registada na Story 2.1 Reconciliação R2 e Dev Notes). O motor de recorrência da Story 2.7 (`runRecurrenceEngine`) é igualmente genérico por `ownerType`.

**A Story 3.1 NÃO cria uma tabela `recurrences` separada para finanças.** Reutiliza a tabela `recurrences` existente com `ownerType: 'transaction'`. Não há duplicação nem extensão necessária.

### O que falta criar (version 3)

A `client.ts:28` já antecipa: "Epic 3 incrementa para version 3 (accounts, cards, installments, categories)". As interfaces `Account`, `Card`, `Transaction`, `Installment`, `Category` já existem em `types/db.ts:98-143` (criadas pela Story 0.3 para completar os tipos do domínio). O que falta é:

1. `this.version(3).stores({...})` com as 4 tabelas novas: `accounts`, `cards`, `installments`, `categories`
2. Notar que `transactions` JÁ EXISTE em `version(1)` (`client.ts:54`) com índices `id, accountId, cardId, category, date, recurrenceId, [accountId+date]` — não recriar
3. Repositórios tipados e schemas Zod para os 5 domínios financeiros (`accounts`, `cards`, `transactions`, `installments`, `categories`)
4. Hooks reactivos para os domínios principais

**[AUTO-DECISION] A1 — "version(3)" é o número correcto:** `version(1)` criou as tabelas base (Story 0.3/1.1); `version(2)` adicionou `recurrences` + `tags` (Story 2.1). Logo a próxima migração Dexie é `version(3)`. Decisão firme baseada no código actual — não requer escalação a `@architect`. (Razão: `client.ts:28` confirma explicitamente "Epic 3 incrementa para version 3".)

## User Story

Como `@data-engineer` (Dara), quero incrementar o schema Dexie para `version(3)` com as tabelas `accounts`, `cards`, `installments` e `categories`, confirmar que `transactions` já existe em `version(1)` com os índices correctos, e entregar schemas Zod + repositories tipados + hooks reactivos para os 5 domínios financeiros (`accounts`, `cards`, `transactions`, `installments`, `categories`), para que as Stories 3.2-3.11 do Epic 3 possam persistir/ler dados financeiros sem duplicar lógica de acesso a Dexie nem cair em invariantes inconsistentes.

## Contexto

`PRD-NEXUS-V2.md` §6.3 (FR16-FR19) e `EPIC-3.md` §4 definem o domínio Finanças. A Story 3.1 é a equivalente de schema para o Epic 3, seguindo o padrão já estabelecido pela Story 2.1 (Epic 2) e Story 1.1 (Epic 1): incremento Dexie aditivo + data access layer via repositórios tipados com validação Zod.

O helper de formatação monetária PT-PT (`formatCurrency`) é criado aqui para reutilização — trace ao risco R3 do `EPIC-3.md` §5 e ao AC5 do Epic 3 ("valores em formato PT-PT `€1.234,56`"). Todas as vistas (3.3/3.7/3.8/3.9) reutilizam este helper.

## Dev Notes

- **NÃO reescrever `version(1)` nem `version(2)`:** o padrão Dexie é aditivo. `this.version(1).stores({...})` e `this.version(2).stores({...})` mantêm-se literais; `this.version(3).stores({...})` adiciona apenas as tabelas novas. Reescrever `version(1)` ou `version(2)` corromperia o upgrade path dos dados do Eurico já em produção. [Source: `client.ts:21-29` + `architecture-v2.md §4.2`]

- **`formatCurrency` — implementação de referência:**
  ```typescript
  export function formatCurrency(cents: number): string {
    const negative = cents < 0;
    const abs = Math.abs(cents);
    const euros = Math.floor(abs / 100);
    const centavos = abs % 100;
    const formatted = euros.toLocaleString('pt-PT') + ',' + String(centavos).padStart(2, '0');
    return (negative ? '-' : '') + '€' + formatted;
  }
  ```
  Alternativa mais robusta via `Intl.NumberFormat('pt-PT', { style: 'currency', currency: 'EUR' })` — avaliar compatibilidade browsers (NFR23: Chrome 110+). Se `Intl.NumberFormat` produzir o formato exacto `€1.234,56`, preferir por correcção automática.
