## Nota do `@sm` River — verificação e contexto (Constitution Artigo IV)

Verificação 18/06/2026. A Story 6.7 **reutiliza, não recria**, a fundação OAuth da 6.1 e o token storage da 6.2. A ideia central é o **OAuth incremental**: o utilizador já autorizou o scope `calendar` (6.1); a 6.7 inicia um novo fluxo de consentimento para adicionar o scope `gmail.modify` à autorização existente. O Google suporta isto com o parâmetro `include_granted_scopes=true` no `generateAuthUrl` — o utilizador vê apenas o pedido do novo scope; a autorização anterior (`calendar`) é automaticamente preservada.

Esta story é deliberadamente mais pequena do que a 6.1: o fluxo OAuth (routes `start`/`callback`), o mecanismo de state HMAC (`verifyAndConsumeState`), o seam `token-store.ts`, e `getValidAccessToken()` já existem e não são alterados. O que é novo: (a) um novo scope no `generateAuthUrl`; (b) detecção de estado `gmail-ligado` na UI de definições; (c) extensão do MSW handler para o scope Gmail; (d) o `token-store.ts` pode precisar de persistir os dois scopes autorizados (ou é suficiente armazenar o token conjunto — `@architect` decide em `[D-6.7-SCOPE-STORE]`).

### 4 decisões `[D-6.7-*]` ratificadas

**[D-6.7-INCREMENTAL] = (B) modificada — nova função `generateGmailAuthUrl(state)` em `oauth.ts` + nova route `start/route.ts` parametrizada por scope, NÃO nova route dedicada.** Resolve SF-1. A tabela de reutilização (l.253) diz "não alterar a assinatura de `generateAuthUrl`" — e a `generateAuthUrl(state: string)` actual (`oauth.ts:117-125`) é Calendar-only com scope fixo `[GOOGLE_CALENDAR_SCOPE]`. Parametrizá-la (passar scope/`include_granted_scopes`) PARTIA a assinatura e arriscaria o caminho Calendar da 6.1 (que está Done em `main`). Decisão: **adicionar uma função NOVA `generateGmailAuthUrl(state: string)`** que encapsula `scope: [GMAIL_MODIFY_SCOPE]` + `include_granted_scopes: true` + `access_type: 'offline'` + `prompt: 'consent'`, deixando `generateAuthUrl` Calendar-only INTOCADA (zero risco de regressão na 6.1). A route de início (`start/route.ts`) discrimina pelo query param `?scope=gmail` (sub-opção da candidata A) e chama a função nova — uma só route, callback único (preserva `[D-6.1-CALLBACK]`), sem duplicar o boilerplate de sessão+state. Trade-off: uma função a mais em `oauth.ts` vs assinatura partida — escolho a função nova (princípio open-closed, a 6.1 não se toca).

**[D-6.7-SCOPE-STORE] = (A) — armazenar no mesmo `nexus:google:tokens`, sobrescrevendo via `saveTokens()` com o token novo combinado; SEM campo `authorizedScopes` no `GoogleTokenRecord`.** O Google emite no segundo consent (com `include_granted_scopes=true` + `prompt=consent`) UM token combinado que cobre `calendar` + `gmail.modify`, com um NOVO `refresh_token` (ver achado crítico — confirmado na spec). O `accessToken` combinado serve Calendar E Gmail. Não há dois tokens — há um. Persistir scopes separados (candidata B) seria enganoso: a revogação Google é tudo-ou-nada para o client OAuth (revogar Gmail revoga Calendar). O `GoogleTokenRecord {accessToken, refreshToken, expiresAt}` (`token-store.ts:57-61`) fica INTOCADO — zero version bump, zero alteração do seam AES-256-GCM da 6.2. Trade-off: a UI não distingue "calendar-só" de "ambos" a partir do KV (resolvido em `[D-6.7-STATUS]`).

**[D-6.7-STATUS] = (C) ajustada — `gmailConnected` é INFERIDO da presença de tokens em KV, com derivação de scope só-na-escrita (KV ganha `scopes?: string`), NÃO verificação à Google API.** O `[D-6.7-SCOPE-STORE]=(A)` significa que, após a 6.7, o token único cobre ambos os scopes; antes da 6.7, cobre só calendar. Para a UI distinguir "calendar-só" de "ambos", o status precisa de saber QUE scopes o token cobre. Como o `exchangeCode` actual (`oauth.ts:140-174`) DESCARTA o campo `scope` da resposta (não o devolve em `GoogleTokens`), a candidata (C) pura (só presença) é INSUFICIENTE para diferenciar calendar-só de gmail. Resolução mínima: **`exchangeCode` passa a devolver o `scope` (string espaço-separada) e `saveTokens` persiste-o como `scopes?: string` opcional no registo KV** (campo aditivo, retro-compatível — registos da 6.1 sem `scopes` → tratados como calendar-só). O endpoint `/api/google/oauth/status` (`status/route.ts:31`) EXPANDE de `{ connected: boolean }` para `{ connected: boolean, calendarConnected: boolean, gmailConnected: boolean }` — derivados de `scopes?.includes('gmail.modify')` / `scopes?.includes('calendar')`, com fallback: token presente sem campo `scopes` (legado 6.1) → `calendarConnected:true, gmailConnected:false`. Esta é uma extensão aditiva-relaxante (igual ao padrão `googleId?` opcional da 6.4): o campo `connected` legado mantém-se para não partir o `GoogleCalendarSettings.tsx` (que lê só `connected`). **Nota:** isto adiciona `scopes?` ao registo persistido — ver C2 (varredura de compatibilidade do `getTokens`/`isStoredRecord`).

**[D-6.7-UI-COMPONENT] = (A) — novo componente `GmailSettings.tsx`, paralelo e autónomo face a `GoogleCalendarSettings.tsx`; NÃO unificar.** O `GoogleCalendarSettings.tsx` está Done (6.1+6.2), tem 6 estados de render e a story manda explicitamente NÃO ALTERAR (l.259). ### Resolução SF-1 e SF-2

**SF-1 (tensão de assinatura) — RESOLVIDA por `[D-6.7-INCREMENTAL]`:** função NOVA `generateGmailAuthUrl(state)`, a `generateAuthUrl` Calendar-only fica intocada. Não há contradição com a tabela de reutilização. O `@dev` NÃO modifica a assinatura de `generateAuthUrl`.

Resolução mínima sem partir o HMAC: o `createSignedState` ganha um parâmetro opcional `flow: 'calendar' | 'gmail'` que é incorporado e devolvido pelo `verifyAndConsumeState` (o nonce assinado mantém-se HMAC-SHA256; o `flow` viaja como segmento adicional do payload assinado, NÃO como query param manipulável). **Alternativa mais simples e PREFERIDA (C5):** derivar o sinal do campo `scope` da resposta de token — se `exchangeCode` devolver scope com `gmail.modify`, o callback redirige `?connected=gmail`; senão `?connected=calendar`. ### Análise de ciclo de vida do estado OAuth incremental — `internal-state-contract-gate.md` (3 eixos)

**(a) Classes de estado.** Há 4 classes observáveis pela UI: `não-ligado` (sem tokens em KV) / `calendar-só` (token presente, `scopes` sem gmail ou ausente=legado 6.1) / `calendar+gmail` (token presente, `scopes` inclui `gmail.modify`) / `gmail-revogado-externo` (= calendar-revogado-externo, porque a revogação é tudo-ou-nada; `getValidAccessToken`→`TokenRevokedError`). O token NÃO é distinto do da 6.1 em quantidade — é UM registo singleton em `nexus:google:tokens`; o que muda é o conjunto de scopes que cobre. **Por camada:** `start` gera state + redirige (discrimina `?scope=gmail`); `callback` troca code → persiste token combinado → redirige `?connected=gmail|calendar` (deriva do scope); `status` devolve `{connected, calendarConnected, gmailConnected}` (deriva de `scopes`); `token-store` guarda/lê o registo único com `scopes?` (AES-256-GCM intacto); `GmailSettings.tsx` mostra `nao-ligado`/`ligado`/`erro` lendo `gmailConnected`; `GoogleCalendarSettings.tsx` continua a ler `connected` (inalterado — vê `ligado` em calendar-só E em calendar+gmail, correcto). Um utilizador que fez 6.1 mas não 6.7 → `calendarConnected:true, gmailConnected:false` (fallback de scope ausente).

**(b) Transição-já-ocorrida (CRÍTICO — refreshToken no 2.º consent).** ACHADO QUE INVERTE A DEV NOTES: o snippet (l.244) usa `prompt: 'consent'`. A spec oficial Google OAuth2 (developers.google.com/identity/protocols/oauth2/web-server) diz: *"the user must revoke the existing grant or you must use the `prompt=consent` parameter ... to ensure a new refresh token is issued"*. Logo, com `prompt=consent`, o segundo consent Gmail **DEVOLVE um NOVO `refresh_token`** que substitui o da 6.1 e cobre a autorização combinada (calendar+gmail). O `exchangeCode` actual já EXIGE `refresh_token` na resposta (`oauth.ts:162-166` lança `TokenExchangeError` se ausente) — portanto o caminho feliz do incremental tem sempre refresh_token, e o `saveTokens` deve **SOBRESCREVER** o registo (não preservar). Isto contradiz a Dev Notes l.302 ("o `saveTokens` ... nunca deve destruir o `refreshToken` existente") e a frase da l.148 do AC7 ("verifica que um `saveTokens` ... não apaga ... preserva o `refreshToken`"). **Reconciliação (C3):** o invariante correcto NÃO é "preserva o refreshToken antigo" — é "o registo resultante tem SEMPRE um refreshToken VÁLIDO e não-vazio (o novo combinado), nunca um registo sem refreshToken nem tokens parciais". O `exchangeCode` garante isto (rejeita resposta sem refresh_token). O teste de preservação (AC7/T6) deve reformular-se: *após o callback Gmail, `getTokens()` devolve um refreshToken não-vazio e o `scopes` inclui gmail.modify* — NÃO "o refreshToken é igual ao da 6.1" (seria FALSO com prompt=consent). Replay de code já usado → `token_exchange_failed` (igual 6.1, `oauth.ts:149-153`). Replay de state → `invalid_state` (single-use, `oauth-state.ts:114`).

**(c) Caminhos de falha.** `access_denied` no consent Gmail → o callback (`callback/route.ts:63-65`) já trata QUALQUER `?error=` do Google como `access_denied` e redirige ANTES de qualquer `saveTokens` → o token Calendar em KV NÃO é tocado (eixo c satisfeito, herdado da 6.1, sem alteração). `storage_failed` → `callback/route.ts:109-113` redirige sem persistir (mas atenção C3: com prompt=consent, se o `saveTokens` falhar a MEIO, o registo anterior pode ficar; como `kv.set` é uma escrita atómica de objecto único, não há estado parcial — ou o registo novo combinado entra inteiro, ou fica o antigo calendar-só; nunca um híbrido sem refreshToken). Token sem refresh → `exchangeCode` lança `TokenExchangeError` → `token_exchange_failed` (nunca persiste parcial). Scope parcialmente concedido (Google concede calendar mas não gmail) → o campo `scope` da resposta NÃO inclui `gmail.modify` → `[D-6.7-STATUS]` deriva `gmailConnected:false` e o callback redirige `?connected=calendar` → a UI Gmail mostra `nao-ligado` (honesto — o scope não foi concedido). `include_granted_scopes` não suportado em test mode → não aplicável: a spec confirma que funciona em test mode (single-user), e o pior caso degrada para um token só-gmail (sem calendar acumulado) — mitigado por `prompt=consent` que de qualquer forma re-autoriza; mas como medida de segurança o `@dev` NÃO deve assumir que o token novo perdeu o calendar: o `scope` da resposta é a fonte de verdade do que foi concedido.

### Scope `gmail.modify` — o que autoriza

`gmail.modify` dá acesso a:
- Ler emails e metadados da inbox
- Modificar labels (arquivar, marcar como lido)
- **Não** permite apagar emails permanentemente (exige `gmail.readonly` subset ou `mail.google.com` para full access)

É o scope correcto para FR64 (classificação AI em 4 buckets) e FR68 (tools `criar_draft_gmail`, `arquivar_email`). _[Source: Google Gmail API scopes spec]_

### `verifyAndConsumeState` — não alterar

Este mecanismo da 6.1 já é single-use (state apagado do KV após validação, HMAC-SHA256 com `SESSION_SECRET`). A 6.7 usa-o exactamente como a 6.1 — nenhuma alteração necessária. _[Source: `v2/lib/google/oauth-state.ts` (inferido da Task T2/T6 da 6.1 + D-6.1-PKCE ratificada)]_

### Revigar o que acontece em `access_denied` no fluxo Gmail

Se o utilizador cancelar o consentimento Gmail (`access_denied`), o callback deve:
1. **Não apagar** os tokens Calendar preexistentes em KV (eixo c do `internal-state-contract-gate.md`)
2. Redirigir para `/settings?error=access_denied`
3. A UI apresenta o erro mas continua a mostrar o estado Calendar como `ligado`

Isto é crítico — um `saveTokens` não deve ser chamado se o code é `access_denied` (a 6.1 já protege isto, mas verificar que o fluxo incremental não altera este comportamento).

### Runtime — Node (ADR-1)

Todas as routes `/api/google/oauth/*` correm em **Node runtime** — `googleapis`/`crypto`/`@vercel/kv` são Node-only. `export const runtime = 'nodejs'` (ou omitir, pois Node é o default quando se importa `googleapis`). _[Source: `architecture-v2.md` §4.1 tabela ADR-1]_

### `internal-state-contract-gate.md` — ciclo de vida do token OAuth incremental

O contrato de estado distribui-se por ≥2 camadas: KV (token com scopes acumulados) + callback route + componente UI (dois sub-estados de autorização). O `@architect` responde os três eixos no T0. Eixos específicos da 6.7:

- **(a)** O estado `não-ligado`/`ligado` da 6.1 é agora `não-ligado` / `calendar-ligado` / `gmail-ligado` / `ambos-ligados`. A UI deve reflectir estes sub-estados correctamente.
- **(b)** Um `saveTokens` no OAuth incremental **nunca deve destruir** o `refreshToken` existente — o Google emite um novo token que inclui os scopes acumulados, mas o `refreshToken` pode ou não ser renovado (comportamento a verificar com o `@architect`).
- **(c)** O `access_denied` no fluxo Gmail **não afecta** o token Calendar. O callback distingue o scope do fluxo antes de qualquer escrita em KV.
