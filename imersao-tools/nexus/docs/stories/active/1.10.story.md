### Decisões @po (resolvidas em PO-VALIDATION-STORY-1.10.md, 09/05/2026)

Fundamentação canónica:

**D2 — Pass rate threshold → `>= 43/50` (>= 86%) [RESOLVIDO via PRD]**

Pass rate threshold = `>= 43/50` (>= 86%) com zero falhas nos prompts canónicos `ac1-epic1`, `ac2-epic1`, `ac4-epic1`.

Fundamentação canónica:

- Zero falhas em prompts canónicos é não-negociável (validam directamente AC1, AC2, AC4 do Epic 1 — PRD linhas 424–427)

## Acceptance Criteria

- **AC1:** Ficheiro de fixtures `tests/fixtures/prompts-pt-pt.json` criado com exactamente 50 entradas PT-PT (caminho canónico — `architecture-v2.md` §5.3 linha 378 + §G4 linha 1065), cada uma com os campos:
  ```typescript
  interface RegressionPrompt {
    id: string;                    // ex: "R001"
    category: RegressionCategory;  // ver AC2
    prompt: string;                // texto PT-PT a submeter
    expectedIntents: string[];     // ex: ["criar_evento_calendar", "criar_finança_variavel"]
    expectedToolCount: number;     // nº mínimo de tool_complete esperados
    requiresPreview: boolean;      // true se deve entrar em preview-required
    expectUndo: boolean;           // true se deve aparecer UndoToast
    tags: string[];                // ex: ["ac1-epic1", "multi-intent", "real-api"]
  }
  ```
  Os 50 prompts cobrem todas as categorias definidas no AC2. **[GAP: se @po ou @analyst definirem os 50 prompts canónicos antes da implementação, usar esses; caso contrário, @qa pode derivar a lista a partir das categorias do AC2 e dos AC do Epic 1.]**

- **AC2:** Os 50 prompts estão distribuídos pelas seguintes categorias, com cobertura mínima por categoria:

  | Categoria | Descrição | Mínimo |
  |-----------|-----------|--------|
  | `simple-no-tools` | Prompt de texto puro sem tools (ex: "olá, estou bem") | 3 |
  | `single-intent-task` | Uma intent de tarefa (criar_tarefa, completar_tarefa) | 6 |
  | `single-intent-finance` | Uma intent financeira (variável, recorrente, cartão) | 6 |
  | `single-intent-calendar` | Uma intent de calendário (criar_evento_calendar) | 4 |
  | `single-intent-reminder` | Uma intent de lembrete (criar_lembrete) | 4 |
  | `multi-intent` | 2+ intents simultâneas (inclui o prompt canónico AC1 Epic 1) | 8 |
  | `preview-required` | Confidence < 70% — dispara `preview_request` SSE (AC2 Epic 1) | 5 |
  | `undo-flow` | Completa run + aciona UndoToast + clica "Anular" (AC4 Epic 1) | 4 |
  | `error-recovery` | Prompt que provoca `tool_error` e valida recuperação UI | 4 |
  | `abort-mid-stream` | Navegação durante stream ou rede dropada | 3 |
  | `performance-benchmark` | Prompts simples para medir latência p95 (AC5 Epic 1) | 3 |

  Conforme D1 (resolvido — Opção C híbrida), a distribuição acima corre em CI com MSW mocks; a categoria `performance-benchmark` mede latência da UI (não do LLM real) — para latência real do LLM, usar subset `@real-api` em staging.

- **AC3:** Suite Playwright em `tests/e2e/regression/regression.spec.ts` (ou equivalente Playwright) que:
  - Carrega a aplicação Nexus v2 num browser real (Chromium headless)
  - Autentica com password de teste (variável de ambiente `TEST_PASSWORD`)
  - Para cada um dos 50 prompts do fixture:
    1. Submete o prompt no `ChatInput`
    2. Aguarda os eventos SSE (via polling do DOM ou intercept de rede)
    3. Verifica que o número de ToolCards renderizados >= `expectedToolCount`
    4. Se `requiresPreview=true`: verifica que pelo menos um ToolCard entrou em estado `preview-required` (borda Gold visível)
    5. Se `expectUndo=true`: verifica que o `UndoToast` apareceu com o texto correcto
    6. Verifica que Dexie persistiu a `AgentRun` com `status` não-nulo (via `page.evaluate()` → `db.agentRuns.count()`)
    7. Regista duração da execução (do submit até ao evento `done`)
  - Gera output estruturado (JSON ou HTML) com resultado por prompt (PASS/FAIL + reason + durationMs)

- **AC4:** Validação dos AC do Epic 1 pelos prompts marcados com `"ac1-epic1"`, `"ac2-epic1"`, `"ac4-epic1"`:
  - **AC1 Epic 1:** prompt `"amanhã reunião 15h, paguei €78,70 supermercado"` (ou equivalente determinístico com mocks) produz exactamente 2 ToolCards `success` (criar_evento_calendar + criar_finança_variavel)
  - **AC2 Epic 1:** pelo menos 1 prompt da categoria `preview-required` verifica que o ToolCard entra em estado `preview-required` e, após confirmação via UI, transita para `success`
  - **AC4 Epic 1:** pelo menos 1 prompt da categoria `undo-flow` verifica que clicar "Anular" no UndoToast dentro de 30s reverte a run (Dexie `status = 'reverted'`)

- **AC5:** Relatório de regressão gerado automaticamente em `tests/e2e/regression/report/`:
  - `report.json`: resultados estruturados (por prompt: id, category, status PASS/FAIL, durationMs, reason se FAIL)
  - `report.html` (opcional mas recomendado): visualização legível com tabela de resultados e sumário
  - Sumário final impresso no stdout: `"Regression: N/50 PASS | P95 latência: Xms | Categoria failures: ..."`

- **AC6:** Pass rate threshold para fechar Epic 1: **`>= 43/50` (>= 86%)** com zero falhas nos prompts canónicos `ac1-epic1`, `ac2-epic1`, `ac4-epic1`. Fundamento canónico: `PRD-NEXUS-V2.md` §10 (linha 431) — `"benchmark intent accuracy >= 85% (não 90% como Jarvis — aceita tolerância em uso pessoal)"`. Cálculo: 85% × 50 = 42.5 → arredondamento conservador = 43/50 PASS. (D2 resolvido)

  - (D4 resolvido)

### Padrão Playwright para validação Dexie (referência para @qa)

```typescript
// helper: dexie-eval.ts
// Ler estado Dexie diretamente no browser context do Playwright
export async function getLastAgentRunStatus(page: Page): Promise<string | null> {
  return page.evaluate(async () => {
    // window.__nexusDB é o singleton Dexie exportado em lib/db/client.ts
    const db = (window as unknown as { __nexusDB: NexusDB }).__nexusDB;
    if (!db) return null;
    const last = await db.agentRuns.orderBy('startedAt').last();
    return last?.status ?? null;
  });
}
```

**Nota:** Verificar se `lib/db/client.ts` expõe o singleton em `window.__nexusDB` (common pattern em Next.js client). Se não, expor temporariamente em `app/layout.tsx` apenas em `NODE_ENV !== 'production'`.

## Testing Strategy

| Camada | Ferramenta | Âmbito |
|--------|-----------|--------|
| Unit (existente) | Vitest + MSW | Stories 1.1–1.9 — não alterados por esta story |
| E2E regression | Playwright (Chromium headless) | 50 prompts end-to-end via UI completa |
| Performance | Playwright `durationMs` por run | Validação AC5 Epic 1 (p95 < budget) |
| Relatório | JSON/HTML output | Evidência auditável para fechar Epic 1 |

**Sobre mock vs real API:** A decisão D1 determina o comportamento do Playwright em CI. Se Opção B (mocks), os MSW handlers de `POST /api/agent/prompt` já existem (definidos em Story 1.9 `tests/mocks/`) e podem ser reutilizados com payloads de resposta determinísticos para cada fixture. Se Opção A ou C, é necessário `ANTHROPIC_API_KEY` no ambiente de teste.

**Sobre fake timers:** A categoria `undo-flow` requer que o UndoToast apareça e o utilizador clique "Anular" dentro de 30s. Em Playwright não usar fake timers — o timeout real de 30s é suficientemente curto para E2E. Alternativamente, o `UNDO_TTL_SECONDS` pode ser configurável via env var `TEST_UNDO_TTL_SECONDS=5` para acelerar o teste.
