## Story

**As a** equipa de desenvolvimento do Nexus v2,
**I want** que os checks de CI (lint + typecheck + testes unitários + E2E) do Nexus v2 se tornem **bloqueantes** em pull requests para `main` — não apenas informativos como são hoje — mantendo o tempo total de execução credível abaixo de 5 minutos,
**so that** nenhum PR consiga ser mesclado com lint, erros de tipo ou testes a falhar, fechando a lacuna entre "o CI corre e passa" (estado actual) e "o CI impede a mesclagem se falhar" (NFR18, AC1 do epic), sem herdar o não-determinismo do full-suite (já resolvido pela 9.11) nem quebrar silenciosamente PRs que não tocam o Nexus v2.

**AC2 — Resolver o risco de required check "preso" por path-filter no trigger (achado real do `@sm`, não listado no `EPIC-9.md` §7 — descoberto neste draft) — CONDIÇÃO PRÉVIA a AC4**

> **Nota de sequência (fix do finding Major CodeRabbit, `@devops` Iter 1, 04/07/2026):** a **restructure** do YAML (remover `paths:` do trigger + job `changes` + condicionais) está FEITA nesta Fase 3 e valida-se por parse de sintaxe (Evidence Gate (b)) + precedente in-repo (`ci.yml` corre este padrão em produção). Mas a **prova empírica** de que um PR alheio ao Nexus não fica preso — e de que um job skipped satisfaz um required check — só é observável com o branch no remote sob branch protection real. Por isso essa prova (scratch-PR, T2.1/T2.3) é **pré-requisito explícito e deferido para depois de AC4 ser autorizado** (é a condição C2 do `@po`): a ordem correcta é (1) restructure [FEITA], (2) autorização do Eurico para AC4 [C3], (3) ligar branch protection [AC4], (4) scratch-PR não-Nexus confirma mesclabilidade [C2] — não se afirma o risco "resolvido de facto" antes do passo (4).

`nexus-v2-ci.yml` tem os filtros de `paths:` **ao nível do trigger** (`on.pull_request.paths: ['imersao-tools/nexus/v2/**', '.github/workflows/nexus-v2-ci.yml']`). Isto é um padrão de risco documentado do GitHub Actions: se um check for marcado como "required" em branch protection e o workflow que o produz **nunca dispara** para um PR (porque o PR não toca nenhum dos paths do filtro), o GitHub não sabe distinguir "não aplicável" de "ainda a correr" — o PR pode ficar preso indefinidamente em "Expected — Waiting for status to be reported", exigindo sempre `--admin` para mesclar, mesmo PRs legítimos que nada têm a ver com o Nexus v2 (ex: alterações só a `.aiox-core/`).

O próprio repositório já resolveu este problema para o CI raiz (`ci.yml`): o trigger não tem `paths:` (dispara em qualquer push/PR para `main`), e usa um job `changes` com `dorny/paths-filter` + jobs condicionais (`if: needs.changes.outputs.code == 'true'`) que **sempre correm e reportam um resultado** (mesmo que seja "skipped"), nunca deixando um required check por reportar.

`@devops` **antes de tocar em branch protection (AC4)**:
1. Confirma empiricamente o comportamento actual, criando um PR de rascunho (branch descartável) que **não** altera nenhum path de `imersao-tools/nexus/v2/**` nem o workflow — e observando se, hipoteticamente com os 3 checks marcados como required, o PR ficaria preso (o workflow simplesmente não aparece na lista de checks do PR, o que é o sintoma do problema).
2. Se confirmado o risco (esperado, dado o padrão de trigger actual), restrutura `nexus-v2-ci.yml` para o mesmo padrão já usado em `ci.yml`: remover os `paths:` do trigger (`on.push`/`on.pull_request` passam a disparar sempre para `main`), acrescentar um job `changes` com `dorny/paths-filter` a detectar alterações em `imersao-tools/nexus/v2/**`, e tornar os 3 jobs existentes condicionais (`needs: changes` + `if: needs.changes.outputs.nexus == 'true'`) — preservando o comportamento actual (só correm de facto quando há alterações relevantes) mas **sempre reportando um resultado** ao GitHub, mesmo que seja skip.
3. Regista a evidência do teste antes/depois (PR de rascunho fechado sem merge, ou `workflow_dispatch` de validação) na secção "Not-Tested Evidence Gate".

### Achado real — risco de required check preso por path-filter no trigger (AC2)

Este é o achado central desta story, **não listado no `EPIC-9.md` §7** (surgiu no diagnóstico deste draft, mesmo padrão de descoberta da Story 9.2 com o env de CI). `nexus-v2-ci.yml` filtra `paths:` **ao nível do `on:` do workflow** — isto significa que para um PR que não toque `imersao-tools/nexus/v2/**` nem o próprio ficheiro de workflow, o workflow **nunca dispara** — não aparece sequer na lista de checks do PR. Se estes 3 jobs forem marcados como "required" em branch protection sem resolver isto primeiro, qualquer PR alheio ao Nexus v2 (ex: uma alteração só a `.aiox-core/` ou a `docs/`) ficaria **preso indefinidamente** — o GitHub mostra "Expected — Waiting for status to be reported" para sempre, e o único caminho de mesclagem seria sempre `--admin` (contrariando o próprio objectivo desta story: tornar o gate real, não uma formalidade contornável).

O repositório já resolveu exactamente este problema no `ci.yml` (linhas 8-16, 26-46): o trigger dispara sempre (`on.push.branches: [main]`, `on.pull_request.branches: [main]`, sem `paths:`), e um job `changes` usa `dorny/paths-filter@v3` para popular outputs booleanos (`code`, `tests`, `config`, `stories`) que os restantes jobs consultam via `if: needs.changes.outputs.X == 'true'`. Quando a condição é falsa, o GitHub regista o job como **skipped** — que **conta como sucesso** para efeitos de required status check (comportamento documentado do GitHub Actions: um job com `if:` falso que nunca chega a correr ainda assim reporta um status de conclusão ao workflow, ao contrário de um workflow inteiro que nunca é despoletado). É este padrão exacto que `nexus-v2-ci.yml` precisa de adoptar antes de AC4.
