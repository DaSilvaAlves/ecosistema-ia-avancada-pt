### Veredicto por decisão GAP-5.4

#### GAP-5.4-A (runtime do endpoint) — `[D-5.11-RUNTIME]` RATIFICADO (proposta B1)

**Node runtime para `/api/conhecimento/web-search`** (path DDG); **path Anthropic reutiliza `/api/anthropic/proxy` (Edge) existente**. Justificação contra código real:
- O fetch DDG faz parsing de HTML grande (~50-200KB) em memória com regex/string ops. Edge tem limites de CPU/memória mais apertados e o ecossistema Edge não é o natural para HTML scraping. ADR-1 já estabelece o precedente exacto: "Node para SDKs/base64 ops grandes em OCR". HTML parsing grande é o mesmo padrão (V2).
- `getSession` funciona em Node (V3) — sem regressão de auth.
- O path Anthropic **não** precisa de endpoint novo: o proxy Edge aceita `tools` (V1) e devolve o JSON tal-qual. O endpoint `/api/conhecimento/web-search` (Node) chama internamente o proxy Edge via `fetch` server-to-server.

> Nota `[D-5.11-RUNTIME]`: a chamada Node→Edge (`/api/conhecimento/web-search` chama `/api/anthropic/proxy`) é um fetch interno same-origin. O `@dev` deve construir a URL absoluta a partir de `req.nextUrl.origin` (ou `new URL(req.url).origin`) e **propagar o cookie de sessão** (`req.headers.get('cookie')`) para o proxy não devolver 401. Verificar este detalhe — é o ponto onde a cascata pode partir silenciosamente.

#### GAP-5.4-B (tratamento de falha) — `[D-5.11-FALLBACK]` RATIFICADO COM CORRECÇÃO CRÍTICA (proposta B2 + V5)

A cascata B2 é aceite, **mas com uma correcção que a proposta não previu** e que é o coração desta story (lição 4.9 M4 + `internal-state-contract-gate.md` eixo c):

**Os erros da Anthropic web search NÃO são HTTP não-2xx — são HTTP 200 com `web_search_tool_result_error` no body (V5).** Logo, o gatilho de fallback Anthropic→DDG **não pode** ser `if (!response.ok)`. Tem de **inspeccionar o body**:

```
fallback para DDG quando QUALQUER de:
  (1) proxy devolve status != 200 (rede/auth/rate-limit do proxy — ex: 429, 502, 401)
  (2) status 200 MAS content[] contém um bloco { type: 'web_search_tool_result', content: { type: 'web_search_tool_result_error', error_code } }
  (3) status 200 MAS content[] não contém nenhum 'web_search_tool_result' com resultados (Claude respondeu sem pesquisar)
```

Cascata final ratificada (cada caminho → resposta explícita, NUNCA silenciosa):

| Caminho | Tratamento |
|---------|-----------|
| Timeout Anthropic (AbortController) | → tenta DDG |
| Proxy 429 (rate limit) | → tenta DDG (não passar 429 ao cliente enquanto houver fallback gratuito — R1/R12 favorece DDG quando Anthropic está limitado) |
| Proxy 401/502/5xx | → tenta DDG |
| Anthropic 200 + `web_search_tool_result_error` (qualquer `error_code`) | → tenta DDG |
| Anthropic 200 sem resultados de pesquisa | → tenta DDG |
| DDG timeout (AbortController) | → 503 PT-PT |
| DDG HTML inesperado/CAPTCHA (`parseDdgHtml`→`[]`) | → 503 PT-PT ("Não foi possível pesquisar agora. Tenta de novo mais tarde.") |
| Ambos falham | → 503 PT-PT |
| DDG devolve resultados | → 200 `{ results, source: 'duckduckgo' }` |

> `[D-5.11-FALLBACK]` Timeouts ratificados: **Anthropic 30s, DDG 10s** (proposta B2 aceite — Anthropic faz múltiplas sub-pesquisas server-side, precisa de margem; DDG é um GET simples). AbortController em ambos. Os códigos 502/422/429 que a proposta B2 sugeria expor ao cliente são **substituídos por `503` único** quando ambos os providers falham — do ponto de vista do utilizador o resultado é o mesmo ("pesquisa indisponível") e simplifica o contrato. O `WebSearchResults` mostra a mensagem PT-PT do 503. Mantém-se o princípio inegociável: **a falha nunca silencia**.

#### GAP-5.4-C (cache) — `[D-5.11-NO-CACHE]` RATIFICADO (proposta B3)

**Sem cache na 5.11.** Confirmo B3. Razões: (a) acção explícita do utilizador, volume baixo (single-user); (b) R1 (custo tokens) já mitigado por Anthropic-primeiro com `max_uses: 5` + acção explícita; (c) cache de pesquisa web tem invalidação não-trivial (resultados mudam) — adicionar agora é over-engineering (princípio "Progressive Complexity"). Cache fica como optimização pós-Epic 5 se o custo real o justificar.

#### GAP-5.4-D (guardar manual vs automático) — `[D-5.11-MANUAL-SAVE]` RATIFICADO (proposta B4)

**Guardar é acção manual na 5.11** (botão "Guardar como nota"); criação automática é a 5.12. Confirmo B4 — separação de scope correcta. O `@dev` reutiliza o padrão exacto de `handleSaveNote` (V9): `createKnowledgeNote({ id: crypto.randomUUID(), notebookId, title, bodyMarkdown, tags: [], sourceUrl, updatedAt: Date.now() })` dentro de try/catch com toast + re-throw. **Correcção de contrato (V7):** os AC referem `createNote` — o método real é `createKnowledgeNote` e exige `KnowledgeNote` completo (com `id`), não `Omit<...,'id'>`.

### Análise de ciclo de vida — `internal-state-contract-gate.md` (alimenta AC7)

> Esta é a 1.ª feature de fetch externo arbitrário. O estado distribui-se por: proxy Edge (Anthropic) ↔ endpoint Node (orquestração + DDG) ↔ componente client (`WebSearchResults`) ↔ Dexie (nota com `sourceUrl`). Os 3 eixos respondidos contra o código real:

**Eixo (a) — Classes de estado.** Classes distintas e o que cada camada faz:

| Classe | Endpoint Node | Componente client |
|--------|--------------|-------------------|
| `idle` (sem submit) | — | mensagem de convite |
| `searching` (fetch em curso) | a orquestrar cascata | skeleton; `aria-busy` |
| `results-anthropic` | 200 `{source:'anthropic'}` | lista + badge ANTHROPIC |
| `results-duckduckgo` | 200 `{source:'duckduckgo'}` | lista + badge DUCKDUCKGO |
| `empty` (provider OK, zero resultados) | 200 `{ results: [], source }` | mensagem "nenhum resultado" — **distinto de erro** |
| `error-both-failed` | 503 PT-PT | mensagem erro Magenta, `role="alert"` |

> Correcção de contrato `[D-5.11-EMPTY-VS-ERROR]`: **`results: []` com sucesso (provider respondeu, zero hits) é a classe `empty`, NÃO `error`.** O endpoint só devolve 503 quando ambos os providers falham (não quando devolvem zero resultados legítimos). O componente tem de distinguir `hasSearched && results.length===0 && error===null` (empty) de `error!==null` (error). A story já prevê isto nos 5 estados — confirmado correcto.

**Eixo (b) — Transição-já-ocorrida.** Cenários onde o estado mudou entre camadas:

| Cenário | Tratamento exigido |
|---------|-------------------|
| Utilizador clica "Guardar" em 2 resultados em rápida sucessão | Cada save é independente (UUID novo por nota) — sem colisão. NÃO de-duplicar por `sourceUrl` (o utilizador pode legitimamente querer 2 notas da mesma fonte). `[D-5.11-SAVE-INDEPENDENT]` |
| Nota com o mesmo `sourceUrl` já existe | **Permitido** — não é erro nem precisa de aviso. `sourceUrl` não é único (V7: schema não tem constraint unique) |
| Caderno seleccionado é eliminado entre a pesquisa e o guardar | `createKnowledgeNote` **lança** ("Caderno X não encontrado") (V7) → o save handler apanha, mostra toast PT-PT, re-throw. NUNCA cria nota órfã nem silencia. Reutiliza o padrão V9 |
| Utilizador submete nova pesquisa enquanto a anterior está em curso | Cancelamento de race via AbortController/flag `cancelled` (padrão 5.10 V9 já estabelecido) — só o último resultado actualiza o estado |

**Eixo (c) — Caminhos de falha.** (coberto por `[D-5.11-FALLBACK]` acima). Cada caminho → resposta explícita:
- Timeout/rede/proxy-5xx → cascata para DDG.
- Anthropic erro-no-body (HTTP 200) → cascata para DDG (o ponto cego que o `!response.ok` deixaria passar — exactamente o padrão M4 da 4.9).
- Ambos falham → 503 PT-PT visível.
- Falha ao guardar nota (Dexie/caderno removido) → toast PT-PT, sem silêncio.
- **Verificação obrigatória no gate de saída:** ≥1 teste prova que um `web_search_tool_result_error` (HTTP 200) dispara o fallback DDG — sem este teste, o ponto cego M4 repete-se.

## User Story

Como utilizador do Nexus (o Eurico), quando estou na página de Conhecimento, quero poder pesquisar na web a partir da interface do Nexus — e ver os resultados com título, excerto e URL de origem — para que consiga encontrar informação externa rapidamente e, se quiser, guardar os resultados como uma nota na minha hierarquia de conhecimento.
