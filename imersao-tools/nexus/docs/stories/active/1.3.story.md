## User Story

**As a** `@dev` (Dex) a implementar Stories 1.5 (executor) e Stories 2-7 (Epic-specific tools),
**I want** um Tool Registry tipado, validável e centralizado (`lib/agent/tools/registry.ts`) com `ToolDefinition` estendida, helpers Zod→JSON Schema e o método `toAnthropicTools()` canónico,
**so that** cada Epic possa registar tools concretas sem tocar no executor, o classifier (Story 1.4) e o executor (Story 1.5) consigam listar/filtrar/validar tools de forma uniforme, e a conversão Zod→JSON Schema falhe loud em vez de silently quando o shape produzido não é object.

## Contexto

PRD §10 line 414 (Epic 1 Story 1.3): "Tool registry: lista de tools disponíveis (vazia inicialmente, povoada por epics seguintes)". Architecture §7 (lines 550-673) é a fonte canónica do pattern: contract `ToolDefinition`, `ExecutionContext`, class `ToolRegistry`, singleton `toolRegistry`. AC6 do Epic 1 (PRD §10 line 429): "Tools registry suporta adicionar tools dinamicamente nos epics seguintes".

A Story 1.2 (`providers/types.ts`) definiu uma versão **mínima** de `ToolDefinition` com 3 campos (`name`, `description`, `argsSchema: z.ZodObject<z.ZodRawShape>`) — apertada para `z.ZodObject<z.ZodRawShape>` na Iter 3 (CodeRabbit Nitpick A). A Story 1.3 cria a versão **estendida canónica** em `lib/agent/tools/types.ts` adicionando `domain`, `resultSchema`, `requiresPreview`, `reversible`, `execute`, `reverse?` (arch §7.2 lines 565-576) PRESERVANDO os 3 campos base — `providers/types.ts` re-exporta o tipo estendido para retrocompat.

Tech debt OBRIGATÓRIO desta story (registado pela QA Iter 3 da Story 1.2 — CodeRabbit Nitpick #5): `toAnthropicTools` actualmente em `lib/agent/providers/anthropic.ts:188-205` retorna `{ type: 'object', properties: {} }` silenciosamente quando `zodToJsonSchema` produz shape sem `type === 'object'`. Story 1.3 move esta função para o registry (canonical home) e troca o fallback silencioso por **fail-loud** com erro útil em PT-PT identificando a tool culpada — protege Stories 1.5/2-7 contra schemas malformados em produção.

O registry **inicia vazio**: zero `register(...)` calls em código de produção desta story. Stories 2-7 chamam `toolRegistry.register(...)` para tools de domínio (39 tools previstas no inventário arch §7.4).

> `toAnthropicTools` em `lib/agent/providers/anthropic.ts:188-205` retorna `{ type: 'object', properties: {} }` silenciosamente quando `zodToJsonSchema` produz shape sem `type === 'object'`. Story 1.3 (Tool Registry) é o canonical home — mover para registry com **fail-loud**.

Implementação fail-loud (AC5):
```ts
// lib/agent/tools/registry.ts (helper interno usado por toAnthropicTools)
function convertToolToAnthropicShape(tool: ToolDefinition): AnthropicToolShape {
  const jsonSchema = zodToJsonSchema(tool.argsSchema, { target: 'openApi3' });

  // FAIL-LOUD — Story 1.3 endereça tech debt da Story 1.2 (CodeRabbit Nitpick #5)
  if (
    jsonSchema === null ||
    typeof jsonSchema !== 'object' ||
    !('type' in jsonSchema) ||
    jsonSchema.type !== 'object'
  ) {
    throw new Error(
      `Tool registry: zodToJsonSchema produziu shape inesperado para tool "${tool.name}" — ` +
      `esperado { type: "object", ... }, recebido: ${JSON.stringify(jsonSchema).slice(0, 200)}`
    );
  }

  return {
    name: tool.name,
    description: tool.description,
    input_schema: jsonSchema as AnthropicToolShape['input_schema'],
  };
}
```

**Decisão arquitectural — `ToolDefinition` mínima vs estendida:**

A Story 1.2 definiu `ToolDefinition` mínima em `providers/types.ts` para desbloquear o executor sem ter o registry. Story 1.3 cria a versão **estendida canónica** em `tools/types.ts`. Para retrocompat:

```ts
// lib/agent/providers/types.ts (Story 1.3 refactor)
export type { ToolDefinition } from '@/lib/agent/tools/types';
```

Justificação: o `AnthropicExecutor.execute(messages, tools, opts)` aceita `ToolDefinition[]` — o consumidor (Story 1.5) vai obter essas tools de `toolRegistry.byDomain(...)` que retorna a versão estendida. Como a estendida tem TODOS os campos da mínima (`name`, `description`, `argsSchema`), o executor não precisa de saber dos campos extra (`domain`, `execute`, etc.) — TypeScript estrutural permite passar a estendida onde mínima é esperada. Single source of truth = `tools/types.ts`.

**Decisão arquitectural — `convertToolToAnthropicShape` exportado vs privado:**

O helper privado serve dois consumidores:
1. `ToolRegistry.toAnthropicTools()` — converte todas/subset
2. `AnthropicExecutor` — convertia local; agora chama do registry

**Opção escolhida (pragmática):** exportar função pura `toolsToAnthropicShape(tools: ToolDefinition[]): AnthropicToolShape[]` do registry, que internamente chama `convertToolToAnthropicShape` por tool. A class method `ToolRegistry.toAnthropicTools(tools?)` delega ao mesmo helper. Assim:
- Executor é stateless (não depende do singleton)
- Registry pode oferecer atalho conveniente (`toolRegistry.toAnthropicTools()` sem args = todas)
- Testabilidade: `toolsToAnthropicShape([])` testável sem instanciar registry

```ts
// lib/agent/tools/registry.ts (assinatura final)
export function toolsToAnthropicShape(tools: ToolDefinition[]): AnthropicToolShape[];

class ToolRegistry {
  // ...
  toAnthropicTools(tools?: ToolDefinition[]): AnthropicToolShape[] {
    return toolsToAnthropicShape(tools ?? this.all());
  }
}

export const toolRegistry = new ToolRegistry();
```

```ts
export interface AnthropicToolShape {

```
