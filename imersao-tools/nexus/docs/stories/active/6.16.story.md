## Seam herdado — ponto de entrada desta story

### Seam 1 — Lembretes do Epic 4

O Epic 4 (FECHADO 10/10, `852449c7`) implementou o disparo server-side de lembretes via Web Push. O mecanismo é:

1. **Mirror KV** (`nexus:push:schedule`, hash Redis): o client espelha `{id, fireAt, text, status: 'pending'}` de cada lembrete pendente via `PUT /api/push/schedule` (`lib/push/schedule-client.ts:23`). A função `putReminderSchedule(reminder)` salta se `!reminder.channels.includes('push')` (`lib/push/schedule-client.ts:24`).
2. **Dispatcher** (`POST /api/push/dispatch`, `app/api/push/dispatch/route.ts`, `runtime='nodejs'`, Auth `CRON_SECRET` Bearer timing-safe): chama `listSchedules()` (lê o hash KV), filtra entradas `pending` com `fireAt <= now`, envia `sendPushNotification({title, body, data: {reminderId}})` e marca `sent` via `markScheduleSent`.
3. **Trigger externo**: o dispatcher é chamado por scheduler externo (padrão 4.8 e 6.5: `POST /api/push/dispatch` ou `POST /api/cron/sync` — a app é agnóstica à origem; o `vercel.json` NÃO declara `crons` nativas, conforme `[D-6.5-CRON-CONFIG]`).

**O que a 6.16 acopla aqui:** quando um lembrete tem `channels: [..., 'telegram']` (campo `Reminder.channels: Array<'push' | 'telegram'>` em `types/db.ts:215`), o dispatcher do Epic 4 IGNORA o canal `telegram` (o `putReminderSchedule` só espelha se `channels.includes('push')`). A 6.16 introduz o canal `telegram` no despacho.

**Símbolos reais confirmados por grep:**
- `Reminder.channels: Array<'push' | 'telegram'>` — `types/db.ts:215`
- `ReminderChannelSchema = z.enum(['push', 'telegram'])` — `lib/db/schemas.ts:332`
- `putReminderSchedule` filtra `!reminder.channels.includes('push')` — `lib/push/schedule-client.ts:24`
- `listSchedules()` — `lib/push/schedule-store.ts:73` (lê hash `nexus:push:schedule`)
- `sendPushNotification` — `lib/push/send-notification.ts:49`
- `dispatchDue` — `app/api/push/dispatch/route.ts:37` (filtra `pending`, `fireAt <= now`)

### Seam 2 — `sendMessage` da 6.13

`sendMessage(chatId, text)` existe em `lib/telegram/bot-api.ts` (criado na 6.13 via `callBotApi('sendMessage', { chat_id: chatId, text })`). A 6.16 reutiliza este helper para enviar lembretes e o briefing ao utilizador via Telegram.

### Seam 3 — Padrão de cron/bridge Node (4.8 + 6.5)

O padrão de endpoint protegido por `CRON_SECRET` Bearer timing-safe (`lib/push/cron-auth.ts`: `secretsMatch`, `extractBearer`) está em vigor nos endpoints `POST /api/push/dispatch` e `POST /api/cron/sync`. A 6.16 reutiliza este mesmo padrão para o(s) endpoint(s) novo(s).

**AC2 — Lembrete com canal `push` mantém o comportamento actual do Epic 4:**
Lembretes com `channels: ['push']` continuam a ser despachados pela lógica do Epic 4 sem alteração. O `git diff` da função `dispatchDue` (ou do `dispatch/route.ts`) é VAZIO se a opção GAP-6.16-A for endpoint separado, ou restrito ao bloco de adição do canal `telegram` se for estendido no dispatcher existente.

**Verificabilidade:** CI Vitest (suite existente do Epic 4 — tests de `dispatch.test.ts` — passa sem modificação).

**AC3 — Idempotência: lembrete não é despachado duas vezes via Telegram:**
Um lembrete já marcado `sent` (ou estado equivalente após decisão do GAP-6.16-D) não é despachado novamente via Telegram numa segunda execução do scheduler.

**Verificabilidade:** CI Vitest (mock `listSchedules` com entrada `{status: 'sent'}` → `sendMessage` NÃO chamado).

**AC4 — Fallback gracioso: `sendMessage` falha:**
Se `sendMessage` lançar ou devolver erro (Telegram Bot API indisponível, token inválido), o endpoint regista o erro em `console.error` e continua o despacho dos restantes lembretes (não aborta o lote). O endpoint responde sempre 200 (nunca 5xx — padrão dispatch/route.ts).

**Verificabilidade:** CI Vitest (mock de `sendMessage` que rejeita no 1.º lembrete → 2.º lembrete é tentado; endpoint responde 200).

**AC5 — AC epic AC5: lembrete agendado dispara push browser E mensagem Telegram (AC5 do EPIC-6.md §6):**
Dado um lembrete com `channels: ['push', 'telegram']`, o scheduler despacha AMBOS os canais: `sendPushNotification` para Web Push E `sendMessage` para Telegram. O utilizador recebe os dois.

**Verificabilidade:** Produção (P1-P5 reais; mocks em CI validam a lógica de duplo despacho; o timing real só é verificável em produção). Em CI: mock de `sendPushNotification` + mock de `sendMessage` → ambos chamados 1× para o mesmo lembrete.

**AC6 — Briefing matinal: endpoint chamável pelo scheduler externo:**
Existe um endpoint `POST /api/telegram/briefing` (ou equivalente, nome a confirmar no gate) com `runtime='nodejs'`, protegido por `CRON_SECRET` Bearer timing-safe (padrão `cron-auth.ts`). Quando chamado, gera e envia via `sendMessage` um briefing com o estado do dia (conteúdo conforme decisão do GAP-6.16-C).

**Verificabilidade:** CI Vitest (POST com `Authorization: Bearer {CRON_SECRET}` → `sendMessage` chamado 1× com chatId + texto não-vazio; POST sem auth → 401/503).

**AC7 — Briefing: janela horária 07h-09h (configurável):**
O endpoint de briefing rejeita ou ignora chamadas fora da janela `[07h, 09h[` (hora de Lisboa — fuso confirmado no gate GAP-6.16-B). A janela é configurável (env var ou parâmetro — conforme decisão do gate). Se chamado fora da janela, responde 200 com `{ok: false, reason: 'outside_window'}` (nunca 5xx — padrão 4.8/6.5).

**Verificabilidade:** CI Vitest (mock do relógio com hora fora da janela → `sendMessage` NÃO chamado, resposta `{ok:false, reason:'outside_window'}`; dentro da janela → `sendMessage` chamado).

**AC8 — Briefing: não duplica se já enviado no mesmo dia:**
O briefing matinal é enviado no máximo 1× por dia. Um mecanismo de estado (ex.: chave KV `nexus:telegram:briefing:last_sent` com data ISO) impede o re-envio se o scheduler chamar o endpoint múltiplas vezes na mesma janela (ex.: o scheduler externo chama de hora a hora entre 07h-09h).

**Verificabilidade:** CI Vitest (mock KV com `last_sent = today` → `sendMessage` NÃO chamado na 2.ª chamada; `last_sent = yesterday` → `sendMessage` chamado).

**AC9 — Segurança: fail-closed sem `CRON_SECRET`:**
Os endpoints novos da 6.16 (despacho Telegram + briefing) respondem 503 se `CRON_SECRET` estiver ausente do env, e 401 se o token não bater (padrão `dispatch/route.ts:73-86`). `TELEGRAM_CHAT_ID` ausente → `sendMessage` não chamado, `console.error`.

**Verificabilidade:** CI Vitest (request sem Authorization → 401; `CRON_SECRET` ausente → 503).

**AC10 — Briefing recebido no Telegram (produção):**
O utilizador recebe o briefing matinal no Telegram entre as 07h e as 09h (hora de Lisboa) num dia de semana. O texto inclui pelo menos o conteúdo mínimo verificável (ex.: menção de lembretes do dia ou tarefas pendentes, conforme decisão do GAP-6.16-C).

**Verificabilidade:** Manual em produção (P1-P5 provisionados + scheduler externo configurado).

**AC11 — Open-closed: guardas da 6.12/6.13/6.14 intactas:**
Os ramos `text`, `voice`, `photo`, `unknown` do handler `webhook/route.ts` e os bridges `process-text`/`process-voice` ficam byte-a-byte intocados. A 6.16 NÃO modifica o handler de webhook Edge. `git diff` do `webhook/route.ts` VAZIO (a 6.16 adiciona endpoints novos, NÃO modifica o webhook).
