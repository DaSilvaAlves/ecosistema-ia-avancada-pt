## User Story

**As a** utilizador do Nexus,
**I want** criar, editar, arquivar e apagar os meus hábitos (com nome, frequência, categoria e horário opcional), e registar de forma simples que completei um hábito hoje,
**so that** posso acompanhar as minhas rotinas diárias e pausar um hábito temporariamente sem perder o histórico de registos acumulado.

- **AC4 — funções `archiveHabit`/`restoreHabit` no repo `habits.ts`:** O ficheiro `v2/lib/db/repos/habits.ts` exporta:
  - `archiveHabit(id: string): Promise<void>` — faz `updateHabit(id, { archivedAt: Date.now() })`.
  - `restoreHabit(id: string): Promise<void>` — faz `updateHabit(id, { archivedAt: undefined })`.
  Nenhuma cascata envolvida. `deleteHabit` (cascade `habit_logs`) **não é modificado**. _Trace: Architect Gate Story 4.1 orientação archive; AC7 Story 4.1 (deleteHabit = hard-delete com cascade)._

- **AC5 — `HabitFormModal` (criar + editar):** Existe `components/habitos/HabitFormModal.tsx`. Props: `mode: 'create' | 'edit'`, `initialValue?: Partial<Habit>`, `onClose: () => void`, `onSubmit: (input: Partial<Habit>) => Promise<void>`. Campos obrigatórios: Nome (texto), Frequência (texto RRULE, ex.: `FREQ=DAILY`), Categoria (texto). Campos opcionais: Horário (`time`, string `HH:MM`). Validação Zod em submit (erros PT-PT por campo via `FormField`). Focus trap, `role="dialog"`, design system (glassmorphism, `#04040A`). - **AC7 — Registo de concluído (FR25):** A acção "Marcar concluído" no handler da página:

### Decisões de implementação e gotchas

1. **DEV-DECISION D-RESTORE (desvio justificado do AC4):** o AC4 especifica `restoreHabit` via `updateHabit(id, { archivedAt: undefined })`. A Dexie **ignora propriedades `undefined`** num patch de `update`, deixando o `archivedAt` antigo persistido na DB — o hábito continuaria a aparecer como arquivado. Implementado com `db.habits.where('id').equals(id).modify((h) => delete h.archivedAt)`, que remove mesmo a chave. O patch parcial é validado contra `HabitSchema.partial()` antes (campo `.optional()`). Teste não-tautológico com `Object.prototype.hasOwnProperty` prova a remoção real. Sem impacto noutros AC. **FLAG suave para `@qa`/`@architect`:** confirmar que a semântica (chave removida vs `null`) é aceitável — alternativa seria normalizar `archivedAt: null` no tipo, mas o tipo actual é `number | undefined`.

2. **Idempotência (AC7) vive no handler, não no repo:** o índice `[habitId+date]` **não é unique** (`client.ts:90`), por isso `createHabitLog` não dedupe por si. A dedup é feita no handler `handleMarkDone` da page (verifica `listHabitLogsByHabit(..., {from,to})` antes de criar). O teste de idempotência está no `HabitsPage.test.tsx` (prova que `createHabitLog` NÃO é chamado quando já há log), não no teste do repo — é onde o comportamento real vive.

3. **Header usa `/tasks` (EN) na linha 93, não `/tarefas`:** verifiquei que o `Header.tsx` tem `NavLink href="/tasks"` para Tarefas (divergente da rota real `(app)/tarefas`). O scope da story (FIX-2) é **apenas** corrigir o link de Hábitos (`/habits` → `/habitos`). Não toquei na linha 93 (`/tasks`) por estar fora de scope — possível débito separado a sinalizar.

4. **`react-component-test-criteria.md` aplicado:** os 3 componentes com ≥3 estados têm teste (modal 5 cenários, lista 7, page 6). `FormField`/`TabStrip` são triviais (1 estado) mas testei-os na mesma (AC11 exige-o explicitamente para a a11y do roving tabindex).

5. **Edit de horário:** no modo edit, quando o utilizador limpa o campo `time`, o modal omite a chave `time` do patch (string vazia falharia o regex HH:MM). O handler de edit não remove activamente um `time` previamente existente — limitação menor de scope (a 4.2 não tem caso de uso de "remover horário"); registado como possível refinamento futuro.
