**Campo de persistência — `bodyMarkdown: string`** (`types/db.ts`):

Os 3 consumidores guardam **markdown como string**, não JSON do Tiptap. **Serializador markdown — `[D-5.2-SERIALIZE]` (decisão do `@dev`):**

- `tiptap-markdown` (extensão community que embrulha markdown-it + serializer com suporte a task lists/GFM) **NÃO está instalado**.

A escolha entre (a) configurar `prosemirror-markdown` com serializers de nó custom para task lists, ou (b) adicionar `tiptap-markdown`, é do `@dev` (T2), documentada no Dev Agent Record com racional. Ambas são território `@dev` (dependência npm de produto, não infra/MCP). Ver AC2.

**Componentes partilhados** vivem em `components/ui/` (`FormField.tsx`, `TabStrip.tsx`, `Header.tsx`, `Sidebar.tsx`). O editor vai para `components/ui/MarkdownEditor.tsx` (PascalCase, padrão do directório).

## User Story

Como `@dev` (Dex), quero construir um componente de editor markdown partilhado (`MarkdownEditor`) baseado em Tiptap 2 (ADR-3 — editor já decidido), com config restrita (StarterKit + TaskList + TaskItem + Link + Placeholder), API de props controlada e round-trip fiável markdown ⇄ documento — para que as Stories 5.3 (diário), 5.6 (brain dump) e 5.9 (notas de conhecimento) tenham um único editor consistente, estilizado pelo design system, sem duplicar configuração de Tiptap nem arriscar perda de formatação ao guardar/carregar `bodyMarkdown`.

## Contexto

`PRD-NEXUS-V2.md` §6.8 (FR42 — diário texto livre markdown), §6.9 (FR47 — brain dump input texto livre) e §6.10 (FR51-52 — notas markdown) exigem entrada markdown. `EPIC-5.md` §5 (Story 5.2) e a ADR-3 fixam Tiptap 2 como o editor. Esta story constrói o componente UI por cima; **não** persiste nada (isso é das stories 5.3/5.6/5.9 que usam os repos da 5.1) nem implementa AI/heatmap/pesquisa.

O AC1 (nível epic) do `EPIC-5.md` §6 — "Diário aceita markdown com formatação preservada" — é satisfeito por esta story através do round-trip de serialização (AC2 abaixo). É também o risco **R5** do epic (serialização Tiptap ↔ Dexie, formatação perdida no round-trip).

## Acceptance Criteria

> Trace: FR42, FR47, FR51 (markdown), AC1 epic (`EPIC-5.md` §6 — formatação preservada), ADR-3, arch §4.3/§16, NFR15 (ESLint+TS strict), NFR17 (cobertura ≥60%), NFR18 (CodeRabbit CRITICAL bloqueia), `react-component-test-criteria.md`, `design-system-ia-avancada.md`. `external-contract-identifiers.md`: N/A (sem identificadores que cruzem contratos externos — os nomes de tools são da 5.13). `internal-state-contract-gate.md`: N/A (editor é componente controlado de 1 camada, sem estado de ciclo de vida distribuído — esse é da 5.8).

- **AC1:** Componente `MarkdownEditor` em `v2/components/ui/MarkdownEditor.tsx` (`'use client'`), baseado em Tiptap 2 com a config restrita **exactamente** dos 7 pacotes instalados: `StarterKit` + `TaskList` + `TaskItem` + `Link` + `Placeholder`. Sem extensões de conteúdo adicionais (sem images — Epic 8). _Trace: ADR-3; arch §4.3/§16; `package.json:27-33`._

- **AC2 (`[D-5.2-SERIALIZE]` — round-trip markdown, satisfaz AC1 epic + mitiga R5):** O editor faz round-trip fiável entre `bodyMarkdown: string` (contrato 5.1) e o documento Tiptap. O `@dev` ratifica e documenta no Dev Agent Record a estratégia de serialização escolhida (prosemirror-markdown com serializers de nó custom **ou** `tiptap-markdown`) com racional. O round-trip **preserva** ao guardar e recarregar: cabeçalhos, **negrito**, _itálico_, listas ordenadas/não-ordenadas, **task lists com checkboxes** (FR42/FR47 produzem checkboxes — arch §4.3), links e blocos de código. A lógica de serialização vive num helper puro testável (`v2/lib/editor/`), não acoplada ao componente. _Trace: AC1 epic; R5; GAP-5.2; FR42/FR47/FR51._

- **AC3:** API de props controlada e estável para os 3 consumidores (5.3/5.6/5.9):
  - `value: string` — markdown actual (controlado pelo pai)
  - `onChange: (markdown: string) => void` — emite markdown serializado em cada alteração
  - `placeholder?: string` — texto de placeholder quando vazio (extensão Placeholder)
  - `editable?: boolean` — default `true`; `false` torna o editor read-only
  - `ariaLabel: string` — rótulo acessível obrigatório (cada consumidor fornece o seu)
  
  Sem persistência, sem chamadas a repos/AI dentro do componente — é puramente apresentação + emissão. _Trace: FR42/FR47/FR51; reutilização Stories 5.3/5.6/5.9._

- **AC4:** SSR-safe no Next 15 App Router: componente `'use client'` com `immediatelyRender: false` no `useEditor` (evita hydration mismatch — gotcha Tiptap + Next). Não quebra o build (`next build`). _Trace: ADR-1; arch §4.1._

- **AC5 (design system — `design-system-ia-avancada.md`):** O editor respeita o design system: fundo escuro (`#04040A`), superfície do editor com glassmorphism (`rgba(255,255,255,0.025)` + `border 1px solid rgba(255,255,255,0.08)` + `border-radius` ≥ 8px), tipografia Inter no corpo + JetBrains Mono em blocos de código, cyan (`#00F5FF`) em links e estado de foco, placeholder em Grey2 (`#4A5568`). **Nunca** light mode. _Trace: `design-system-ia-avancada.md`._

- **AC6 (acessibilidade):** Navegação por teclado funcional (nativa do Tiptap/ProseMirror), foco visível, `aria-label` aplicado à área editável (via prop `ariaLabel`), e o editor não introduz armadilhas de foco. WCAG 2.1 AA. _Trace: EPIC-5 §8 A3 (a11y reforçada); NFR a11y._

- **AC7 (teste de componente — `react-component-test-criteria.md`):** O gate `@qa` conta os estados de render distintos do `MarkdownEditor` e regista a contagem na decisão. Estados candidatos: vazio (placeholder visível) / com conteúdo / read-only (`editable=false`). **Teste de componente obrigatório** cobrindo: (i) render de markdown inicial com formatação; (ii) emissão de `onChange` com markdown ao editar; (iii) placeholder quando `value` vazio; (iv) read-only quando `editable=false`. O round-trip de serialização (AC2) é testado **em separado no helper puro** (`lib/editor/`) ~100%. _Trace: `react-component-test-criteria.md`; EPIC-5 §8 A3; R6._

- **AC8:** lint + typecheck + vitest PASS; cobertura do helper de serialização ≥60% (NFR17, alvo ~100% por ser função pura); CodeRabbit sem CRITICAL (NFR18). Suite validada (ver Testing) — atenção: esta story **não** faz version bump Dexie, logo não toca testes de schema-upgrade (lição 5.1/1.10 não se aplica aqui, mas confirmar que nenhum teste existente quebra). _Trace: NFR15/NFR17/NFR18._

1. **Contrato de dados é markdown string** (`bodyMarkdown: string`, Story 5.1) → o editor faz round-trip markdown ⇄ documento Tiptap, obrigatoriamente.
2. **O nó mais frágil são as task lists** (`- [ ]`/`- [x]`, FR42/FR47). `tiptap-markdown` faz **serialize E parse** de task lists out-of-box. A alternativa `prosemirror-markdown` (instalada) exigiria: (a) serializers de nó custom para `taskList`/`taskItem` (os defaults snake_case não batem com os nomes camelCase do schema Tiptap), **e** (b) um plugin `markdown-it-task-lists` (também ausente) para o parse — mais código frágil para o mesmo resultado.
3. **Território `@dev`:** é dependência de produto (`dependencies`), não infra/MCP nem reabertura de ADR. Resolve a afirmação optimista da arch §4.3 ("markdown out-of-box", que o StarterKit sozinho não cumpre). **Não exigiu `FLAG @architect`** — sem impacto arquitectural além da lib bem-delimitada; peer `@tiptap/core ^2.0.3` compatível com a 2.10 instalada.
4. **Testabilidade preservada:** a serialização vive em `lib/editor/markdown.ts` (helper puro via editor headless `@tiptap/core`), testável em jsdom sem montar o componente — alinha com `react-component-test-criteria.md`.
