### AC1 — Parse seguro do body do update (FR70; `external-contract-identifiers.md`)

O handler Edge parseia o body do request com `req.json()` + try/catch e valida contra `TelegramUpdateSchema` (Zod) antes de qualquer outro processamento. O schema cobre:
- `update_id: z.number().int()` — obrigatório
- `message.chat.id: z.number().int()` — obrigatório quando `message` presente
- `message.text: z.string().optional()` — texto da mensagem
- `message.voice: z.object({ file_id: z.string() }).passthrough().optional()` — mensagem de voz
- `message.photo: z.array(z.object({ file_id: z.string() }).passthrough()).optional()` — array de fotos (Telegram envia múltiplas resoluções)
- `message` é opcional ao nível raiz (outros tipos de update não têm `message`)

Se `req.json()` lançar (body não é JSON) ou a validação Zod falhar → `Response('bad request', { status: 400 })`. O schema usa `.passthrough()` no nível raiz para tolerar campos extras do Telegram ([D-6.12-PARSE-STRATEGY]).

**Verificabilidade:** CI Vitest (testes com body não-JSON → 400; body JSON inválido-Zod → 400; body válido → processado).

### AC2 — Filtro `chatId === TELEGRAM_CHAT_ID` (FR70; C8 da 6.11; [D-6.11-CHATID])

Após o parse bem-sucedido, se `message.chat.id` (como string ou número — ver nota D-6.12-CHATID-TYPE) diferir de `process.env.TELEGRAM_CHAT_ID`, o webhook devolve imediatamente `Response(JSON.stringify({ok:true}), {status:200})` sem processar o update ([D-6.12-CHATID-REJECT]: resposta 200 silenciosa para chatId não autorizado, impedindo fingerprinting). Se `TELEGRAM_CHAT_ID` estiver ausente em env → rejeitar todos os updates com 200 silencioso (fail-closed para env ausente, coerência com C2 da 6.11).

**Nota D-6.12-CHATID-TYPE:** o `message.chat.id` da Bot API é um `number` (inteiro) no JSON; `TELEGRAM_CHAT_ID` é uma string em env. Comparar com coerção: `String(message.chat.id) === process.env.TELEGRAM_CHAT_ID`. O `@architect` confirma no gate.

**Verificabilidade:** CI Vitest (chatId correcto → processado; chatId errado → 200 `{ok:true}` sem processing; env `TELEGRAM_CHAT_ID` ausente → 200 silencioso).

### AC3 — Rate limiting Edge (FR70; REC-6.11-RATELIMIT; arch §9.3)

Antes do roteamento, o handler aplica rate limiting por `chatId` (para o chatId autorizado) usando KV com fixed window 60s ([D-6.12-RATELIMIT-ALGO]): chave `nexus:telegram:ratelimit:<chatId>:<window>`, `kv.incr`, TTL 70s. Se contador > 60 → `Response('rate limit exceeded', { status: 429 })` ([D-6.12-RATELIMIT-RESPONSE]). Sem `kv.keys()`/`kv.scan()` (D-KV-HASH). Se KV indisponível → comportamento conforme [D-6.12-RATELIMIT-KV-FAIL] ratificado pelo `@architect` (ver análise eixo b).

**Verificabilidade:** CI Vitest (mock KV: contador abaixo → processado; contador >= 60 → 429; KV indisponível → comportamento ratificado).

### AC4 — Detecção do tipo de update (FR70)

Após filtro `chatId` e rate limiting, o handler detecta o tipo de update:
- `message.text` presente e não-vazio → tipo `'text'`
- `message.voice` presente → tipo `'voice'`
- `message.photo` presente (array não-vazio) → tipo `'photo'`
- Nenhum dos anteriores (sticker, location, etc.) → tipo `'unknown'`

A detecção é mutuamente exclusiva por ordem de prioridade: `text` > `voice` > `photo` > `unknown`. O tipo é passado ao roteador (AC5).

**Verificabilidade:** CI Vitest (4 tipos de input → tipo detectado correcto; edge case: `message` ausente no update → tipo `'unknown'`).

### AC5 — Roteamento / fan-out <5s (FR70; ADR-1/arch §4.1; [D-6.12-FAN-OUT-SCOPE])

O roteador despacha conforme o tipo detectado:
- `'text'` → [conforme D-6.12-FAN-OUT-SCOPE ratificado pelo `@architect`]: stub `{ok:true, routed:false, type:'text'}` se a 6.13 ainda não estiver ligada, OU chamada ao handler de texto se a 6.12 e 6.13 forem implementadas em conjunto.
- `'voice'` → stub `{ok:true, routed:false, type:'voice'}` (6.14 não implementada)
- `'photo'` → stub `{ok:true, routed:false, type:'photo'}` (6.15 não implementada)
- `'unknown'` → stub `{ok:true, routed:false, type:'unknown'}` (ignorado silenciosamente)

Toda a resposta do webhook (parse + filtro + rate-limit + fan-out) tem de caber no orçamento Edge <5s (arch §4.1). O stub não tem latência adicional; a implementação real (6.13+) deve respeitar o mesmo orçamento.

**Verificabilidade:** CI Vitest (4 tipos → resposta 200 `{ok:true, routed:false, type:X}`). Produção: latência <5s — verificável após provisionamento P1-P4.

### AC6 — Mock MSW reflecte o shape real dos updates do Telegram (`mock-protocol-fidelity.md`)

### AC7 — Ordem de aplicação das guardas (segurança em profundidade)

A ordem de aplicação das guardas no handler é inegociável (defesa em profundidade):
1. **Validação `secret_token`** (herdada da 6.11, já implementada em `webhook/route.ts` — NÃO tocar)
2. **Parse do body + validação Zod** (AC1) — antes de aceder a qualquer campo
3. **Filtro `chatId`** (AC2) — antes de rate-limit (não desperdiçar KV writes em chatIds não autorizados)
4. **Rate limiting KV** (AC3) — após filtro `chatId`

Esta ordem garante que:
- Updates inautênticos (sem `secret_token`) são rejeitados antes do parse do body (sem parsing de JSON de origem desconhecida).
- ChatIds não autorizados não consomem KV writes de rate-limit.
- Rate-limit é aplicado apenas ao chatId autorizado.

**Verificabilidade:** Revisão de código (ordem das guardas inspeccionável em `webhook/route.ts`). Teste Vitest de integração que verifica a ordem: mock `kv.incr` e confirmar que NÃO é chamado quando chatId é inválido.

Toda a lógica KV da 6.12 (rate-limit) usa apenas `kv.incr`/`kv.get`/`kv.set` com chaves directas e conhecidas. `kv.keys()` e `kv.scan()` proibidos. [Trace: D-KV-HASH, precedentes 6.9/6.11]

**Verificabilidade:** CI Vitest + revisão CodeRabbit.

### Padrão de rate limiting Edge KV (arch §9.3)

```ts
// Fixed window 60s (confirmado por D-6.12-RATELIMIT-ALGO — aguarda ratificação @architect)
const RATE_LIMIT_WINDOW_MS = 60_000;
const RATE_LIMIT_MAX_REQUESTS = 60;
const RATE_LIMIT_TTL_S = 70; // 10s de margem sobre a janela

async function checkRateLimit(chatId: string): Promise<boolean> {
  const window = Math.floor(Date.now() / RATE_LIMIT_WINDOW_MS);
  const key = `nexus:telegram:ratelimit:${chatId}:${window}`;
  try {
    const count = await kv.incr(key);
    if (count === 1) {
      // Primeira invocação desta janela: definir TTL
      await kv.expire(key, RATE_LIMIT_TTL_S);
    }
    return count <= RATE_LIMIT_MAX_REQUESTS;
  } catch {
    // KV indisponível — comportamento conforme D-6.12-RATELIMIT-KV-FAIL
    // Ratificar com @architect: fail-open (return true) ou fail-closed (return false)
    return true; // Provisório — ratificar
  }
}
```

Nota: `kv.incr` é Edge-safe (`@vercel/kv` via Upstash REST — confirmado na 6.11 pelo `@architect`). Sem `kv.keys()`/`kv.scan()` (D-KV-HASH).
