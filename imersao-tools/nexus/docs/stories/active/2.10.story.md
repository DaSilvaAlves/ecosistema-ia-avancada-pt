O PRD §6.5 linha 164 confirma FR32:
> **FR32:** Tools cérebro: `criar_projecto`, `vincular_tarefa_projecto`, `consultar_projecto`.

A `architecture-v2.md` §7.3 fornece o exemplo canónico da tool `criar_tarefa` com o shape exacto esperado. A `architecture-v2.md` §7.4 lista as 7 tools do Epic 2. A Story 1.3 criou o `toolRegistry` singleton vazio — esta story é a primeira a populá-lo com tools de domínio `'tasks'`.

**Nota importante sobre `vincular_tarefa_projecto`:** esta tool aparece em ambas as FRs (FR15 + FR32). É uma única tool registada uma vez, no ficheiro `lib/agent/tools/tasks.ts` (domínio `'tasks'`), que serve os dois requisitos. Não há duplicação.

**Decisões autónomas do SM (para ratificação `@po`):**

[AUTO-DECISION A1] **3 ficheiros de tools** (não 1 ficheiro monolítico): `lib/agent/tools/tasks.ts` (5 tools: `criar_tarefa`, `completar_tarefa`, `listar_tarefas`, `listar_atrasadas`, `vincular_tarefa_projecto`) + `lib/agent/tools/projects.ts` (2 tools: `criar_projecto`, `consultar_projecto`) + `lib/agent/tools/index.ts` (ponto de entrada que importa ambos). Razão: separação por domínio — paralelo ao padrão `lib/db/repos/tasks.ts` vs `lib/db/repos/projects.ts`. A `architecture-v2.md` §7.3 usa `lib/agent/tools/tasks.ts` como path de exemplo para a `criar_tarefa`. Alternativa "1 ficheiro único" descartada — ficheiro com 7 tools register cresceria para >300 LOC, difícil de rever; Epic 3-7 vão adicionar mais tools e seguirão o mesmo padrão de ficheiro-por-domínio.

[AUTO-DECISION A2] **`requiresPreview: false`** para todas as tools excepto `vincular_tarefa_projecto` (A3). FR5 do PRD diz "Confidence < 70% → preview antes de persistir" — o preview é controlado pelo executor baseado em confidence score, não na flag `requiresPreview`. A flag é para tools que **sempre** requerem preview (ex: brain dump em Epic 5 segundo arch §1137). Create/complete/list são acções directas e reversíveis — não precisam de preview obrigatório. Trace: `architecture-v2.md` §7.3 exemplo — `criar_tarefa` tem `requiresPreview: false`.

[AUTO-DECISION A3] **`requiresPreview: false` para `vincular_tarefa_projecto`** também. Razão: a vinculação é reversível (`reverse` desfaz o vínculo) e a confidence do classifier determina o preview — não a flag. Trace: padrão arch §7.3.

[AUTO-DECISION A4] **`reversible: true`** para `criar_tarefa`, `completar_tarefa`, `vincular_tarefa_projecto`, `criar_projecto`. Razão: cada uma tem `reverse` definida que desfaz a acção (delete, set status anterior, set projectId anterior, set project status anterior). `listar_tarefas` e `listar_atrasadas` e `consultar_projecto` são read-only — `reversible: false`, `reverse: undefined`.

[AUTO-DECISION A5] **`listar_tarefas` retorna máximo 50 tarefas** (não o DEFAULT_LIMIT=200 do repo). Razão: o executor passa a lista como contexto para o LLM (Sonnet) no SSE stream — 200 tasks × ~100 tokens/task = 20K tokens de contexto desnecessários para uma consulta simples. O ceiling de 50 é suficiente para o uso conversacional ("que tarefas tenho hoje?"). Parâmetro `limite` no argsSchema permite o utilizador pedir mais explicitamente (max 100). Trace: architecture-v2.md §7.4 "optimização token economy: executor recebe só tools do domínio + meta".

[AUTO-DECISION A6] **`listar_atrasadas` usa `listTasks` com filtro de `dueDate < today`** aplicado no `execute`. O repo `listTasks` não tem filtro nativo de `overdue` — aplicado após fetch. Razão: repo não tem índice Dexie por `dueDate`; filtro client-side num array small (≤200 tasks) é trivial. Alternativa "criar helper `listOverdueTasks` no repo" descartada — a função seria usada apenas aqui, polui o repo; melhor inline no tool execute.

[AUTO-DECISION A7] **`consultar_projecto` retorna projecto + contagem de tasks** (`{ id, name, description, status, startDate, deadline, taskCount, doneTasks }`). Razão: para uma resposta do cérebro como "Como está o projecto X?" o utilizador quer o estado sem precisar de perguntar depois "e quantas tasks?". A contagem adiciona contexto sem custo significativo. `taskCount` e `doneTasks` calculados via `listTasks({ projectId })` após `getProject`. Alternativa "retornar apenas o projecto" descartada — incompleto para o caso de uso conversacional.

[AUTO-DECISION A8] **`criar_tarefa` constrói a `Task` completa inline** em vez de chamar o helper `createTask` do repo. Razão: o exemplo canónico `architecture-v2.md §7.3` usa `ctx.db.tasks.add({...})` directamente (tool `execute` recebe `ctx.db: NexusDB`). O repo `createTask` também valida via `TaskSchema.parse` — chamá-lo seria correcto, mas a arch §7.3 usa `ctx.db` directamente, pelo que seguimos o exemplo canónico para coerência. Trace: arch §7.3 linhas 688-710.

[AUTO-DECISION A9] **Activação dos registos via side-effect import** em `lib/agent/tools/index.ts`. O executor da Story 1.5 já importa as tools para passar ao classifier/executor (`byDomain`). A Story 2.10 exige que o `index.ts` seja importado no ponto de inicialização do servidor (Route Handler `/api/agent/prompt`). **Nota para Dex:** verificar onde o executor/provider são inicializados e adicionar `import '@/lib/agent/tools'` nesse ponto. [GAP menor] A Story 2.10 não sabe exactamente em que linha do Route Handler isto deve ser adicionado — Dex verifica durante T1 e documenta na secção Dev Agent Record.

[AUTO-DECISION A10] **Domínio `'tasks'` para as 5 tools de tarefas** (incluindo `vincular_tarefa_projecto`). `vincular_tarefa_projecto` poderia ser domínio `'meta'` (é cross-domain), mas o impacto é na entidade `Task` (modifica `Task.projectId`), portanto `'tasks'` é mais preciso para o filtro `byDomain('tasks')`. Alternativa `'meta'` descartada — a optimização `byDomain` do executor recebe os domínios do classifier; se o utilizador diz "vincula a tarefa X ao projecto Y", o classifier detecta intent `tasks` + `projects`, logo `byDomain('tasks')` apanha `vincular_tarefa_projecto`. Trace: FR15 — "vincular_tarefa_projecto" aparece explicitamente na lista de tools de tarefas.

**O que esta story entrega (resumo):**

1. **`lib/agent/tools/tasks.ts`**: 5 tools registadas no `toolRegistry` singleton (via `toolRegistry.register({...})`): `criar_tarefa`, `completar_tarefa`, `listar_tarefas`, `listar_atrasadas`, `vincular_tarefa_projecto`.
2. **`lib/agent/tools/projects.ts`**: 2 tools registadas no `toolRegistry` singleton: `criar_projecto`, `consultar_projecto`.
3. **`lib/agent/tools/index.ts`**: barrel de inicialização — `import './tasks'; import './projects';`. Importado no Route Handler `/api/agent/prompt` para activar registos.
4. **Testes Vitest** (`tests/unit/agent/tools/tasks.test.ts` + `tests/unit/agent/tools/projects.test.ts`): ~20-25 cenários cobrindo execute/reverse por tool, argsSchema validation, casos de erro PT-PT, e integração com `toolRegistry`.

## User Story

**As a** Eurico,
**I want** poder dizer ao cérebro "cria uma tarefa de X para amanhã", "completa a tarefa Y", "que tarefas tenho atrasadas?", "cria o projecto Z", "como está o projecto Z?", ou "vincula a tarefa W ao projecto Z" —,
**so that** o chat do Nexus executa acções reais de tarefas e projectos directamente a partir de linguagem natural, sem abrir formulários UI, cumprindo FR15 (tools `criar_tarefa`, `completar_tarefa`, `listar_tarefas`, `listar_atrasadas`, `vincular_tarefa_projecto`) e FR32 (tools `criar_projecto`, `vincular_tarefa_projecto`, `consultar_projecto`).

## Acceptance Criteria

- **AC1:** **`lib/agent/tools/tasks.ts`** criado com 5 `toolRegistry.register({...})` calls:

  **`criar_tarefa`** (FR15 — trace: PRD §6.2 L138, arch §7.3 L680-711):
  - `name: 'criar_tarefa'`, `domain: 'tasks'`, `requiresPreview: false`, `reversible: true`
  - `argsSchema`: `CriarTarefaArgs` (titulo, prioridade, prazo, projecto, tags, descricao) — shapes em §Contexto
  - `resultSchema`: `z.object({ id: z.string(), titulo: z.string() })`
  - `execute(args, ctx)`: cria `Task` com `crypto.randomUUID()` + campos derivados dos args + `ctx.db.tasks.add(...)`. Mapeia `prioridade` PT-PT → `priority` EN (`'alta'→'high'`, `'baixa'→'low'`, `'media'→'medium'`). `status: 'todo'`, `context: null`, `lastWorkedAt: null`, `recurrenceId: null`, `parentTaskId: null`, `createdAt: Date.now()`, `updatedAt: Date.now()`. Retorna `{ id, titulo: args.titulo }`.
  - `reverse(_args, result, ctx)`: `ctx.db.tasks.delete(result.id)`.

  **`completar_tarefa`** (FR15 — trace: PRD §6.2 L138):
  - `name: 'completar_tarefa'`, `domain: 'tasks'`, `requiresPreview: false`, `reversible: true`
  - `argsSchema`: `CompletarTarefaArgs` ({ id: UUID })
  - `resultSchema`: `z.object({ id: z.string(), statusAnterior: z.string() })`
  - `execute(args, ctx)`: `const task = await ctx.db.tasks.get(args.id)`. Se `task === undefined`, lança `Error('Tarefa "${args.id}" não encontrada')`. Guarda `statusAnterior = task.status`. Chama `ctx.db.tasks.update(args.id, { status: 'done', lastWorkedAt: Date.now(), updatedAt: Date.now() })`. Retorna `{ id: args.id, statusAnterior }`.
  - `reverse(args, result, ctx)`: restaura `ctx.db.tasks.update(args.id, { status: result.statusAnterior as TaskStatus, updatedAt: Date.now() })`.

  **`listar_tarefas`** (FR15 — trace: PRD §6.2 L138):
  - `name: 'listar_tarefas'`, `domain: 'tasks'`, `requiresPreview: false`, `reversible: false`
  - `argsSchema`: `ListarTarefasArgs` (status opcional, projectoId opcional, limite=20 max 100)
  - `resultSchema`: `z.object({ tarefas: z.array(z.object({ id, titulo, status, prioridade, prazo, projectoId })), total: z.number() })`
  - `execute(args, ctx)`: chama `listTasks({ status: args.status, projectId: args.projectoId ?? undefined, limit: args.limite })` do repo. Mapeia `priority` EN → `prioridade` PT-PT no resultado (`'high'→'alta'`, etc.). Retorna `{ tarefas: mapped[], total: mapped.length }`.
  - `reverse`: `undefined` (read-only, não reversível)

  **`listar_atrasadas`** (FR15 — trace: PRD §6.2 L138):
  - `name: 'listar_atrasadas'`, `domain: 'tasks'`, `requiresPreview: false`, `reversible: false`
  - `argsSchema`: `ListarAtrasadasArgs` ({ limite: 1-100, default 20 })
  - `resultSchema`: `z.object({ tarefas: z.array(z.object({ id, titulo, prazo, prioridade })), total: z.number() })`
  - `execute(args, ctx)`: `const today = new Date().toISOString().slice(0, 10)`. Chama `listTasks({ limit: 200 })`. Filtra `t.dueDate !== null && t.dueDate < today && t.status !== 'done'`. Aplica `slice(0, args.limite)`. Retorna `{ tarefas: filtered.slice(0, args.limite), total: filtered.length }`. Mapeamento `priority` → `prioridade` PT-PT igual a `listar_tarefas`.
  - `reverse`: `undefined`

  **`vincular_tarefa_projecto`** (FR15 + FR32 — trace: PRD §6.2 L138, §6.5 L164):
  - `name: 'vincular_tarefa_projecto'`, `domain: 'tasks'`, `requiresPreview: false`, `reversible: true`
  - `argsSchema`: `VincularTarefaProjectoArgs` ({ tarefaId: UUID, projectoId: UUID|null })
  - `resultSchema`: `z.object({ tarefaId: z.string(), projectoIdAnterior: z.string().nullable(), projectoIdNovo: z.string().nullable() })`
  - `execute(args, ctx)`: `const task = await ctx.db.tasks.get(args.tarefaId)`. Se undefined, lança `Error('Tarefa "${args.tarefaId}" não encontrada')`. import { toolRegistry, defineTool } from '@/lib/agent/tools/registry';

```typescript
toolRegistry.register(

    requiresPreview: false,
    reversible: true,
    execute: async (args, ctx) => { /* ... */ },
    reverse: async (_args, result, ctx) => { /* ... */ },
  })
);
```

### Uso do `defineTool` helper

`defineTool<TArgs, TResult>({...})` valida o shape em runtime antes do `register()`. Se o `argsSchema` não for `z.ZodObject`, lança antes de tentar registar. Recomendado para todas as tools desta story.

### `ctx.db` vs repos

As tools têm acesso a `ctx.db: NexusDB` (a instância Dexie). Para consistência com o exemplo canónico da arch §7.3, `criar_tarefa` e `criar_projecto` usam `ctx.db.tasks.add(...)` / `ctx.db.projects.add(...)` directamente. Para as operações de leitura complexas (`listar_tarefas`, `listar_atrasadas`, `consultar_projecto`), importar e usar os helpers do repo (`listTasks`, `getProject`) passando explicitamente os parâmetros — evita duplicação da lógica de filtro.

**ATENÇÃO:** `listTasks` do repo recebe `listTasks(opts)` com `opts.projectId?: string | null` — não `projectoId`. O argumento do argsSchema é `projectoId` (PT-PT), mas a chamada ao repo usa a key `projectId` (EN). Mapeamento explícito obrigatório.

### Inicialização dos side-effects

O `import '@/lib/agent/tools'` no Route Handler activa os `toolRegistry.register(...)` no arranque do processo. Em Next.js App Router (Vercel Edge/Node), o Route Handler é importado como módulo na primeira request — portanto os registos acontecem antes de qualquer chamada ao executor. Sem `import`, `toolRegistry.all()` retorna `[]` e o executor não tem tools disponíveis.

### Tipagem do `reverse` para tools read-only

Tools read-only (`listar_tarefas`, `listar_atrasadas`, `consultar_projecto`): `reversible: false`, e o campo `reverse` deve ser **omitido** (não `reverse: undefined` explícito — o TS pode reclamar dependendo da versão da interface). Verificar durante T1.2 se a interface `ToolDefinition` aceita omissão ou exige `undefined`.

## Dev Agent Record

*Preenchido por Dex (`@dev`) — implementação 20/05/2026*

### Decisões de implementação

**[DEV-DECISION D1] Leituras complexas inline com `ctx.db` em vez dos helpers de repo.**
A Dev Note sugeria usar `listTasks`/`getProject` de `lib/db/repos/` para as leituras
(`listar_tarefas`, `listar_atrasadas`, `consultar_projecto`). Decidi fazer as leituras
**inline com `ctx.db.tasks`/`ctx.db.projects`** em vez de chamar esses helpers. Razão
crítica: o Route Handler `route.ts` é **Edge runtime** (`export const runtime = 'edge'`).
Os helpers de repo importam o singleton `db` de `@/lib/db/client` (Dexie). Se as tools
chamassem os repos, o `import '@/lib/agent/tools'` no `route.ts` puxaria Dexie para o
bundle Edge — violação directa do ADR-1 (o próprio `executor.ts` L40-52 documenta:
"zero imports de Dexie em runtime; Stories 2-7 que precisem de operações Dexie em tools
devem fazê-lo via `ctx.db`"). Usar `ctx.db` (injectado, `import type` apenas) mantém o
módulo Edge-safe. A lógica de filtro inline é trivial (filter+sort+slice sobre array
pequeno) e replica fielmente o comportamento de `listTasks`. Build verde confirma a
Edge-safety: `/api/agent/prompt` compila sem erro de Dexie.

**[DEV-DECISION D2] `criar_tarefa`/`criar_projecto` usam `ctx.db.*.add()` directo.**
Conforme AUTO-DECISION A8 da story e o exemplo canónico arch §7.3. Os campos
obrigatórios de `Task` (`recurrenceId: null`, `parentTaskId: null`, `context: null`,
timestamps) são todos preenchidos no `execute` — PA-2 do architect-gate verificado.

**[DEV-DECISION D3] Helper `registar()` local para o cast de variância.**
`ToolRegistry.register(def: ToolDefinition)` aceita `ToolDefinition<unknown, unknown>`.
`defineTool<TArgs, TResult>` devolve `ToolDefinition<TArgs, TResult>` — não atribuível
ao tipo não-genérico porque o parâmetro `args` de `execute` é **contravariante**. Em
vez de 7 casts dispersos `as unknown as ToolDefinition`, criei um helper `registar()`
em cada ficheiro que encapsula o único cast, documentado. Mantém o registry (infra L2 —
não alterar) intacto e evita `any` (Constitution). `defineTool` valida o shape em
runtime, pelo que o cast é seguro.

**[DEV-DECISION D4] Mapeamento prioridade via objectos `as const satisfies`.**
`PRIORIDADE_PT_PARA_EN` e `PRIORIDADE_EN_PARA_PT` — dois sentidos do mapeamento
(PA-4 do architect-gate). `as const satisfies Record<...>` garante exaustividade
tipada sem perder os literais. T2 + T10 cobrem ambos os sentidos.

**[DEV-DECISION D5] Isolamento de testes — import do barrel, sem `clear()`.**
Os ficheiros de teste importam `@/lib/agent/tools` (o barrel), nunca `tasks.ts`/
`projects.ts` directos — evita dupla cadeia de registo e o erro "tool já registada".
Vitest isola cada ficheiro de teste em worker próprio, pelo que o singleton do
registry é populado 1x por ficheiro. `beforeEach` limpa apenas as tabelas Dexie
(`db.tasks.clear()`/`db.projects.clear()`), não o registry — espelha o estado real
de produção (PA-1). O `registry.test.ts` da Story 1.3, que faz `toolRegistry.clear()`,
corre noutro worker — sem leakage (verificado: 36 + 28 testes verdes em conjunto).

### GAP A9 / AC4 — Linha de `import '@/lib/agent/tools'` no Route Handler

**Resolvido em runtime (T1.6).** O `import '@/lib/agent/tools';` foi adicionado em
`app/api/agent/prompt/route.ts` **linha 11**, imediatamente após o bloco de imports
existente (após `import type { Logger, VercelKV }` na L7) e antes do JSDoc do módulo.
É o ponto correcto: é avaliado quando o Route Handler é carregado como módulo na
primeira request, antes de qualquer `runAgent(...)` — o executor invoca
`toolRegistry.byDomain(...)` e sem este import o registry estaria vazio.

**Nota Edge-safety (crítica):** o `route.ts` é Edge runtime. O import só é seguro
porque o barrel e os módulos `tasks.ts`/`projects.ts` **não** importam Dexie nem
`@vercel/kv` — apenas `import type { Task }`/`import type { Project }` (eliminados em
build) + o `registry.ts` (puro Zod + zod-to-json-schema). Ver DEV-DECISION D1. Build
de produção confirma: `/api/agent/prompt` compila sem erro.
