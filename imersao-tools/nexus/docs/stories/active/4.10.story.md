### `external-contract-identifiers.md` — aplicado no draft (eixo 2: contrato `ToolDomain`) — **[FLAG @architect]**

**Ponto crítico do draft.** O campo `ToolDefinition.domain` cruza um contrato externo: o **z.enum `ToolDomain`** (`types.ts:34-44` + `ToolDefinitionShapeSchema` em `registry.ts:43-54` — declarado em **dois** locais). Os valores válidos são:

```
tasks | finance | habits | journal | knowledge | calendar | gmail | telegram | receipt | meta
```

**Existe `habits`. NÃO existe `goals` nem `reminders`.** As 9 tools cobrem 3 áreas (hábitos, metas, lembretes). Isto é exactamente o tipo de identificador que `external-contract-identifiers.md` obriga a validar no draft, não na implementação.

**Evidência que resolve o gap (não suposição):** o classifier (`classifier-system.ts:30`) já agrupa as três áreas no mesmo domínio:
> `habits: 'hábitos diários, metas pessoais, lembretes recorrentes'`

O executor (Story 1.5) faz `toolRegistry.byDomain(d)` por cada domínio detectado pelo classifier (`registry.ts` comentário §7.4). Como o classifier roteia prompts de metas/lembretes para `'habits'`, registar as 9 tools com `domain: 'habits'` faz `byDomain('habits')` devolver as 9 → o executor envia-as ao Sonnet. **Internamente consistente, zero alteração de contrato.**

**Decisão proposta ao `@architect` (D-DOMAIN) — a ratificar no gate:**

| Opção | Descrição | Custo | Risco |
|-------|-----------|-------|-------|
| **A (recomendada)** | As 9 tools usam `domain: 'habits'`. Coerente com o classifier (linha 30) que já agrupa as 3 áreas. Sem alterar o enum. | Nenhum (zero contrato tocado) | Mínimo — `domain` fica como bucket de routing grosso, não label semântico fino |
| B | Estender `ToolDomain` com `'goals'`+`'reminders'` (enum em `types.ts` E `registry.ts`) + actualizar o classifier map + few-shots | Toca 3 contratos | Médio — divergência classifier↔registo; mais superfície de regressão |

> A story assume **Opção A** nos AC abaixo (todas as tools `domain: 'habits'`). Se o `@architect` ratificar a Opção B no gate, os AC de `domain` são reconciliados de forma rastreável (precedente do processo D-NAMES da 3.11) — `@dev` sinaliza, não corrige silenciosamente.

## User Story

**As a** Eurico a usar o cérebro do Nexus por linguagem natural,
**I want** que o cérebro saiba criar/registar/consultar os meus hábitos, metas e lembretes a partir de frases ("cria o hábito de ler todos os dias", "marca a meta de correr 100km", "lembra-me sexta às 10h de pagar a luz"),
**so that** posso operar todo o domínio de hábitos/metas/lembretes sem abrir a UI — o cérebro traduz a frase na tool certa e executa.

A decisão não se funda na recomendação herdada, mas no que o `domain` **é** no pipeline do cérebro, verificado em código:

| Consumo de `domain` | Ficheiro:linha | O que revela |
|---------------------|----------------|--------------|
| `getToolsForDomains` — `byDomain(d)` por domínio + sempre `byDomain('meta')` | `executor.ts:368-387` | `domain` é um **filtro de routing / economia de tokens** (39 tools → ~10 para o Sonnet), não um label semântico exposto. A semântica da tool vive em `name`+`description`. |
| `confidence[tool.domain]` para preview-threshold | `executor.ts:436,446,453` | `domain` é a **chave de lookup da confiança** do classifier. Só funciona se o classifier emitir confiança para esse domínio. |
| Classifier mapeia as 3 áreas → `'habits'` | `classifier-system.ts:30` | `confidence['habits']` é a chave populada para hábitos+metas+lembretes. `confidence['goals']`/`['reminders']` **nunca seriam emitidas** sem retreino do classifier. |
| `ALL_DOMAINS` + `DOMAIN_DESCRIPTIONS` exaustivos sobre `ToolDomain` | `classifier.ts:36` + `classifier-system.ts:27` | Estender o enum (Opção B) obriga a tocar **4 locais** (type + z.enum + ALL_DOMAINS + DOMAIN_DESCRIPTIONS) + few-shots. |
| **Precedente A10 — `projects.ts` usa `domain:'tasks'`** | `projects.ts:13,106,139` | **Decisão arquitectural já ratificada:** tools de projectos (semanticamente ≠ tarefas) partilham o bucket `'tasks'` para o `byDomain('tasks')` as apanhar. D-DOMAIN Opção A é o **mesmo padrão**. |

### Porque Opção A (e não B)

1. **Coerência com o consumo real:** `domain` é um bucket de routing + chave de confiança, não um eixo semântico fino. `domain:'habits'` faz o `byDomain('habits')` devolver as 9 tools sempre que o classifier detecta hábitos/metas/lembretes — e a `confidence['habits']` existe, alimentando a lógica de preview correctamente.
2. **Precedente A10 vinculativo:** `projects.ts` já estabeleceu que um bucket de domínio agrupa áreas semanticamente distintas quando o classifier as roteia juntas. D-DOMAIN é consistente com uma decisão já ratificada — não é uma decisão nova de risco.
3. **Opção B introduz regressão real:** sem retreinar o classifier para emitir `'goals'`/`'reminders'`, o lookup `confidence['goals']` devolveria `undefined` → a lógica de preview-threshold (`executor.ts:436`) partiria para as tools de metas/lembretes. Ganho funcional zero (o LLM já vê as 9 tools quando `'habits'` é detectado, e a semântica está em `name`+`description`). Custo: 4 locais + few-shots + risco. **Rejeitada.**
4. **Read-only consults também `'habits'` (não `'meta'`):** `consultar_metas`/`listar_lembretes`/`consultar_evolucao_habito` são domínio-específicas — disparadas quando o utilizador fala de hábitos/metas/lembretes (classifier → `'habits'`). Devem ser `'habits'` para entrarem via `byDomain('habits')`. Pô-las em `'meta'` (sempre incluído) inflaria **todos** os requests. Precedente directo: `consultar_balanco`/`consultar_categoria` são `domain:'finance'`, não `'meta'` (`finance.ts:574,610`).
