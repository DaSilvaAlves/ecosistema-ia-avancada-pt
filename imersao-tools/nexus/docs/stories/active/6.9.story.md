### Contrato real entregue pela Story 6.8 (verificado em código)

**Helper `v2/lib/google/gmail.ts`:**
- Tipos exportados: `GmailBucket = 'importante' | 'responder_hoje' | 'pode_esperar' | 'descartavel'`, `GmailClassifyCacheValue = { bucket: GmailBucket, classifiedAt: number }`, `ClassifyResult = { classified: number, fromCache: number, total: number }`
- Função exportada: `classifyInboxEmails(accessToken: string): Promise<ClassifyResult>`
- Constante exportada: `GMAIL_BUCKETS = ['importante', 'responder_hoje', 'pode_esperar', 'descartavel'] as const`
- Helper exportado: `classifyCacheKey(msgId: string): string` — chave `nexus:cache:gmail:classify:<msgId>`
- Schema Zod exportado: `GmailClassifyWireSchema` — `{ importante: string[], responder_hoje: string[], pode_esperar: string[], descartavel: string[] }` (`.strict()`)

**Route `POST /api/google/gmail/classify`:**
- Sucesso: `{ ok: true, classified: number, fromCache: number, total: number }`
- Erros: 401 `{ error: 'not_connected' }`, 401 `{ error: 'token_revoked' }`, 503 `{ error: 'refresh_failed' | 'gmail_unavailable' | 'classify_failed' }`
- Auth DUAL: sessão cookie OU `Authorization: Bearer <CRON_SECRET>`
- **NÃO devolve os emails classificados com metadados** — apenas telemetria do run. Os detalhes dos emails (subject, from, date, bucket) vivem EXCLUSIVAMENTE na cache KV `nexus:cache:gmail:classify:<msgId>` com valor `{ bucket, classifiedAt }`.

**Schema KV (arch §6 linha 599):**
```text
nexus:cache:gmail:classify:<msgId>  →  { bucket: GmailBucket, classifiedAt: number }  TTL 7d
```

### GAP crítico identificado — [GAP-6.9-READ-ENDPOINT]

A route POST classify **não devolve a lista de emails classificados com metadados** (subject, from, date). Só devolve a telemetria `{ classified, fromCache, total }`. A cache KV armazena `{ bucket, classifiedAt }` por `msgId` — NÃO armazena subject/from/date.

Para a vista mostrar "Importantes + Para responder hoje" com informação legível (remetente, assunto), existem três abordagens possíveis:

| Opção | Descrição | Implicação |
|-------|-----------|------------|
| (A) Nova route `GET /api/google/gmail/inbox` | Lê a KV para os buckets `importante`+`responder_hoje` e faz `users.messages.get` para buscar subject/from dos msgIds classificados | Route nova Node — fora do scope da 6.8 |
| (B) Classificação + exibição em pipeline: trigger classify → ler diretamente da KV + Gmail API no cliente | Mais chamadas do lado cliente; expõe accessToken ao cliente (má prática) | Violação do padrão Node-only para Gmail API |
| (C) Estender a route POST classify para também devolver a lista `{ importante: EmailSummary[], responder_hoje: EmailSummary[] }` na resposta | Alteração da 6.8 (story fechada) | Rompe o contrato da 6.8 (breaking change em story Done) |

**[GAP-6.9-READ-ENDPOINT]** — `@architect`/`@po` decidem no gate de entrada da 6.9 qual a abordagem. A história não pode começar sem esta decisão. A opção (A) parece mais alinhada com o padrão existente (route Node fina) e com o princípio "gmail API só no servidor". Se (A) é escolhida, a 6.9 cria uma route `GET /api/google/gmail/inbox` que: (i) valida sessão; (ii) lê KV para os buckets pretendidos; (iii) busca metadados Gmail API para cada msgId; (iv) devolve lista `{ emails: EmailSummary[] }`. Esta route seria consumida pelo componente via SWR/fetch do cliente.

### [GAP-6.9-TRIGGER] — trigger de classificação na vista

FR66 especifica a vista, não o trigger. A route POST classify já existe (6.8) e pode ser chamada manualmente. A questão é: a vista 6.9 inclui um botão "Actualizar" que dispara a classify POST e depois lê os resultados? Ou assume que a KV já tem resultados do cron (6.5) e só os lê?

[AUTO-DECISION] Proposta: o componente inclui um botão "Actualizar inbox" que chama `POST /api/google/gmail/classify` e, após sucesso, relê os dados para actualizar a lista. O estado de loading durante a actualização é um dos estados de render. Se `@architect`/`@po` decidirem que só o cron alimenta a KV (sem trigger manual), o botão é removido e o estado `loading` passa a ser só do fetch inicial.

### [GAP-6.9-EMPTY-VS-NOT-CONNECTED] — distinção entre "sem emails" e "Gmail não ligado"

A vista pode estar num estado "sem emails importantes" por duas razões distintas: (a) o Gmail está ligado mas não há emails nos buckets `importante`/`responder_hoje`; (b) o Gmail não está ligado (token ausente ou revogado). A UI deve distinguir estes dois casos para o utilizador saber se precisa de ligar o Gmail ou se a inbox está realmente limpa.

O endpoint `/api/google/oauth/status` já devolve `{ gmailConnected: boolean }` (6.7). A 6.9 pode consultá-lo no mount para distinguir os dois casos. `@architect`/`@po` confirmam se esta consulta extra ao `/status` deve ser feita pelo componente ou se a route de leitura (opção A do `[GAP-6.9-READ-ENDPOINT]`) já devolve o estado de ligação.

### Confirmação de `external-contract-identifiers.md`

A 6.9 é puramente de UI — não introduz tools, identificadores de API externa, nem enums novos. Os bucket names já foram validados pela 6.8 (`importante`, `responder_hoje`, `pode_esperar`, `descartavel` — ASCII, validados contra o contrato interno). A 6.9 exibe estes valores na UI com a grafia PT-PT humana (labels, títulos), seguindo o padrão D-FUZZY (3.11/4.10/5.13): o identificador técnico está na KV; a grafia humana vive na camada semântica da UI.

### Confirmação de `internal-state-contract-gate.md`

A 6.9 lê estado de camadas distintas: KV (cache de classificação) + Gmail API (metadados por msgId, se opção A) + status OAuth. O gate `@dev` faz a análise de ciclo de vida antes do merge:
- (a) Classes de estado: `gmail-nao-ligado` / `loading` / `empty` / `content-com-emails` / `erro-oauth` / `erro-fetch`
- (b) Transição-já-ocorrida: a KV pode ter TTL expirado entre a classificação e a leitura; um msgId pode ter sido eliminado do Gmail depois de classificado
- (c) Caminhos de falha: `GET /api/google/gmail/inbox` → 401 (não ligado / token revogado) → estado `erro-oauth`; 503 (Gmail indisponível) → estado `erro-fetch`

### Decisões ratificadas

#### `[D-6.9-READ-ENDPOINT]` (a-1 — re-derivação por `messages.list` + `kv.get` por id; opções a-2/b/c REJEITADAS)

A vista lê os buckets `importante`+`responder_hoje` COM metadados através de uma **nova route Node `GET /api/google/gmail/inbox`** que **re-deriva** a lista de candidatos exactamente como a 6.8 já faz internamente:

1. `GET /gmail/v1/users/me/messages?labelIds=INBOX&maxResults=50` (1 chamada) → `msgId[]` — replica o padrão de `listInboxMessageIds` (6.8 l.219). A route reimplementa este passo (helper privado), **não importa nem altera** o helper 6.8.
2. Para cada `msgId`: `kv.get(classifyCacheKey(msgId))` (O(1) por id) → lê `{bucket, classifiedAt}`. **Filtra** os que estão em `importante` OU `responder_hoje`; descarta `pode_esperar`/`descartavel` e os `null` (não-classificados / TTL expirado).
3. Para os `msgId`s filtrados: `messages.get?format=metadata&metadataHeaders=Subject,From,Date` em **lotes ≤10 com `Promise.all`** ([D-6.8-BATCH], reimplementado).
4. Devolve `{ emails: EmailSummary[] }`.

**Porquê (a-1) e não as outras:**

| Opção | Razão de rejeição |
|-------|-------------------|
| (a-2) índice por bucket em KV (hash) | Exigiria escrita NOVA no caminho da 6.8 (Done/main) → viola open-closed; a 6.8 não escreve esse índice, logo a vista só funcionaria após reclassificação. Sobre-engenharia para single-user com ~50 emails. |
| (b) fetch client-side da Gmail API | Expõe access token ao browser → viola NFR6 (token server-only) e o padrão Node-only 6.2-6.8. PROIBIDA. |
| (c) estender route classify | Breaking change em story Done; mistura telemetria com display. PROIBIDA. |
| `kv.keys('...classify:*')` dentro de (a) | Anti-pattern proibido pela D-KV-HASH (`schedule-store.ts:17-19`). PROIBIDO. |

**Runtime:** `export const runtime = 'nodejs'` (ADR-1 / §4.1 l.199 — `@vercel/kv` + fetch Gmail server-side + `getValidAccessToken` são Node-only). Confirmado contra arquitectura, não reaberto.

**Shape de resposta (vinculativo):**
```typescript
interface EmailSummary {
  id: string;            // msgId (chave da cache KV)
  bucket: 'importante' | 'responder_hoje'; // só estes 2 (FR66)
  subject: string;       // header Subject (string vazia se ausente — eixo b)
  from: string;          // header From (string vazia se ausente)
  date: string;          // header Date (string vazia se ausente)

}
// Sucesso:  200 { emails: EmailSummary[] }   (lista vazia = inbox limpa)
// Erros:    401 { error: 'not_connected' }   (getValidAccessToken null OU sessão inválida)
//           401 { error: 'token_revoked' }   (TokenRevokedError OU GmailAuthError do Gmail)

//           503 { error: 'gmail_unavailable' } (Gmail 429/5xx / rede)
```
