## Story

**As a** utilizador do Nexus v2 em qualquer dispositivo (desktop ou mobile, com ou sem rede instável),
**I want** que a app tenha uma estratégia de cache resiliente via Service Worker — assets estáticos servidos do cache primeiro, chamadas a `/api/*` a tentarem a rede primeiro com um sinal honesto de "sem rede" quando falham,
**so that** a app carregue rapidamente em repetidas visitas e comunique claramente quando não consegue falar com o servidor, sem nunca partir as notificações Web Push já entregues no Epic 4 e sem fingir sucesso quando a rede falha (NFR21, R4/R5 de `EPIC-9.md`).

## Acceptance Criteria

**AC1 — Extensão do SW existente, não um SW novo**

`public/sw.js` é **estendido**, nunca reescrito nem substituído. Os handlers `push` (linhas 34-59) e `notificationclick` (linhas 131-171), a função `postAction` (linhas 73-97) e `reshowNotification` (linhas 99-111) ficam **byte-a-byte intactos** — zero linhas alteradas nessas secções. Os handlers `install` e `activate` existentes são **estendidos** (skipWaiting/clients.claim mantidos), não substituídos.

[Trace: `EPIC-9.md` Risco R4 "SW parte o Web Push do Epic 4"; GAP-9.3 §7 "(a) o SW actual e o que a 9.3 acrescenta ... sem partir o handler push do Epic 4"]

**AC2 — Fetch strategy network-first para `/api/*`, fallback honesto `503 {offline:true}`**

O novo handler `fetch` intercepta pedidos `GET` (e, no mínimo, também trata correctamente pedidos não-`GET` deixando-os passar sem cache — ver AC3) para paths que começam por `/api/`. Estratégia: tenta a rede primeiro (`fetch(event.request)`); se a rede responder (mesmo com erro HTTP como 4xx/5xx do próprio servidor), essa resposta do servidor é devolvida tal e qual — **não** é convertida em `503 {offline:true}` (distinção entre "sem rede" e "erro real do servidor", exigida por `internal-state-contract-gate.md` eixo (c) e anti-padrão M4 da Story 4.9). Só quando o `fetch()` **falha** (rejeita — TypeError de rede, timeout, DNS, offline real) é que o handler devolve uma `Response` sintética: status `503`, `Content-Type: application/json`, body `{"offline":true}`. Este AC pára aqui — o **consumo** desse sinal pela UI (banner, distinção visual) é âmbito da Story 9.5, não desta (ver AC9, delimitação explícita).

[Trace: `EPIC-9.md` §5 linha 9.3 "network-first para `/api/*` (fallback `503 {offline:true}`)"; arch §11; `internal-state-contract-gate.md` eixo (c) "o cliente distingue sucesso de erro HTTP/rede?"]

**AC3 — Cache-first para assets estáticos, sem interferir com navegação/documentos HTML**

Pedidos `GET` same-origin para assets estáticos (`/_next/static/**`, e quaisquer ficheiros servidos de `public/` quando existirem — ícones/manifest da 9.4, fora do âmbito desta story) usam estratégia cache-first: se existir no cache, devolve do cache imediatamente; caso contrário, vai à rede, devolve a resposta e (se `response.ok`) grava uma cópia no cache para o próximo pedido. **Não** intercepta navegações de documento HTML (`event.request.mode === 'navigate'`) nem qualquer outro path fora de `/_next/static/**`/`public/` — deixa esses pedidos passar para a rede sem intervenção do SW (evita reintroduzir por acidente o "offline shell" de página HTML, que é âmbito da 9.5, não desta story).

[Trace: `EPIC-9.md` §5 linha 9.3 "cache-first para assets"; arch §11 "fetch (network-first para `/api/*` ... cache-first para assets)"]

**AC4 — Cache versionado com limpeza no `activate`**

Introduz uma constante de versão de cache (ex: `const CACHE_NAME = 'nexus-static-v1'`) usada por `caches.open()` no handler `fetch` (AC3). O handler `activate` (estendido, não substituído — AC1) acrescenta, além de `clients.claim()` já existente, uma limpeza de caches obsoletos: itera `caches.keys()` e apaga (`caches.delete()`) qualquer cache cujo nome não seja o `CACHE_NAME` corrente. Uma subida de versão futura (`nexus-static-v2`) purga automaticamente o cache antigo no próximo `activate`, sem crescimento ilimitado.

[Trace: `EPIC-9.md` §5 linha 9.3 arch §11 "activate (limpeza de caches antigos)"]

**AC5 — Registo do SW a nível de app, independente de push**

Hoje o SW só é registado dentro de `usePushSubscription.subscribe()` (`hooks/usePushSubscription.ts` linha 80) — um utilizador que nunca activa notificações nunca tem o SW instalado, logo nunca beneficia da fetch strategy desta story. A 9.3 acrescenta o registo do SW a nível de bootstrap da app: um client component (`<ServiceWorkerRegister />`, seguindo o padrão já estabelecido de `<DailyEngineProvider>` em `app/(app)/layout.tsx`, Story 3.10) que chama `navigator.serviceWorker.register('/sw.js', { scope: '/' })` uma vez, com guarda `'serviceWorker' in navigator` (graceful degradation, mesmo padrão de `isPushSupported()` no hook — NFR23). Esta chamada **não substitui** nem altera a chamada existente em `usePushSubscription.ts` linha 80 — o teste `tests/unit/hooks/usePushSubscription.test.ts:102` (`expect(registerSpy).toHaveBeenCalledWith('/sw.js', { scope: '/' })`) continua a passar sem alteração. As duas chamadas ao mesmo script/scope são idempotentes por spec (ver Inventário).

[Trace: Inventário `@sm` — achado real "o SW só é registado dentro de subscribe()"; `EPIC-9.md` §5 linha 9.3; padrão `DailyEngineProvider` Story 3.10]

**AC6 — Zero regressão nos testes existentes do SW e do hook de push**

`tests/unit/sw/push-handler.test.ts` e `tests/unit/sw/notificationclick-handler.test.ts` continuam a passar **sem nenhuma alteração ao próprio ficheiro de teste**. Como estes testes fazem `vi.stubGlobal('self', {...})` sem expor `caches` (ver Inventário), o novo código de `fetch`/`activate`/`install` que usa `caches.open()`/`caches.keys()`/`caches.delete()` **não pode correr no module-load** (top-level) — tem de estar dentro dos handlers (`self.addEventListener('fetch', ...)`, etc.), nunca invocado incondicionalmente ao importar o módulo. `tests/unit/hooks/usePushSubscription.test.ts` também continua a passar sem alteração.

[Trace: Inventário `@sm` — risco concreto de quebra de testes existentes por `caches` não-stubbed]

**AC7 — Testes novos para a fetch strategy (D-SW-TEST-FRAMEWORK)**

Cria `tests/unit/sw/fetch-handler.test.ts`, seguindo o mesmo padrão D-SW-TEST-FRAMEWORK dos testes existentes (`vi.stubGlobal` para `self`, `clients`, `fetch`, e agora também `caches` com um mock mínimo — `open`/`match`/`put`/`keys`/`delete`). Cenários mínimos:
1. `/api/*` com rede OK → devolve a resposta de rede tal qual (incluindo um 4xx/5xx do servidor, **não** convertido em `503 {offline:true}` — prova o eixo (c) do `internal-state-contract-gate.md`).
2. `/api/*` com rede a falhar (fetch rejeita) → devolve `503`, `Content-Type: application/json`, body `{"offline":true}`.
3. Asset estático já em cache → devolve do cache sem chamar `fetch`.
4. Asset estático ausente do cache → chama `fetch`, devolve a resposta, e grava-a no cache (`cache.put`) só se `response.ok`.
5. `activate` com um cache antigo (`nexus-static-v0`) presente → é apagado; o `CACHE_NAME` corrente não é tocado.
6. Navegação de documento (`request.mode === 'navigate'`) → não é interceptada pelo cache-first (passa directa para a rede, sem chamada a `caches`).

[Trace: `not-tested-trailer-rules.md` (test-runner/config não se aplica aqui — é ficheiro de teste de aplicação, mas a rigor de testabilidade é exigida pelo gate `@architect`); `internal-state-contract-gate.md`]

**AC10 — Análise de ciclo de vida do estado offline (gate `@architect`, GAP-9.3)**
