### [GAP-5.1b] — `brain_dumps`: tabela Dexie vs estado transitório (ESCALAR a `@architect`)

O Brain Dump (FR47-49) é fundamentalmente diferente das outras 3 áreas:
- **FR47:** input texto livre.
- **FR48:** AI estrutura em 4 buckets (tarefas propostas / projectos propostos / ideias soltas / decisões).
- **FR49:** utilizador **aprova item-a-item antes de persistir** — os itens aprovados viram tarefas/projectos/notas.

| Opção | A favor | Contra |
|-------|---------|--------|
| **Tabela `brain_dumps`** (PRD literal) | Historial do brain dump; o utilizador pode rever sessões anteriores; trace de "o que foi gerado e aprovado" | Items aprovados persistem como Tasks/Projects/Notes — o brain dump em si é input/processo, não output final; tabela pode crescer sem limite |
| **Estado transitório (sem tabela)** | Brain dump é uma sessão de processo, não um documento para guardar; consistente com o modelo "sem persistência de sessões" | Perde o historial; PRD §10 lista explicitamente `brain_dumps` como tabela |

**Recomendação `@sm` (não-vinculativa):** tendo em conta que o PRD lista `brain_dumps` explicitamente e que o historial de sessões de brain dump pode ter valor (saber "o que já foi descarregado"), inclinamo-nos para a **tabela** — mas a decisão é do `@architect` por ser arquitectural (impacto no ciclo de vida, gestão de dados, índices). **Se o `@architect` decidir tabela, a story faz `version(5)` aditivo com a tabela `brain_dumps`. Se decidir estado transitório (sem tabela), sem version bump.**

**A decisão do `@architect` em AC2 desbloqueia o caminho da story.**

## Dev Notes

- **Não recriar tabelas.** `journal_entries`, `knowledge_areas`, `knowledge_notebooks`, `knowledge_notes` vivem em `version(1)` (`client.ts:93-96`). Só re-declarar uma tabela num `version()` posterior se for para **adicionar índice** (mecanismo aditivo Dexie).
- **Versão Dexie actual:** `version(4)` em `client.ts:145`. A próxima aditiva seria `version(5)` — usada SÓ se `brain_dumps` for tabela (AC2) OU se o gate descobrir índice em falta (AC1 sub-task).
- **Tags:** `KnowledgeNote.tags` é `string[]` de IDs (padrão `Task.tags` do Epic 2, `types/db.ts:249`). NÃO criar sistema de tags separado — reutilizar a tabela `tags` de `version(2)`. A unicidade de tags é verificada no repo de tags existente (Epic 2).
- **`sourceUrl`:** campo já presente em `KnowledgeNote` (`types/db.ts:250`) — antecipado para suportar FR55/FR56 (pesquisa web cria nota com URL de origem). O repo de notas pode indexar por `sourceUrl` no futuro se necessário; por agora, sem índice (não há FR que peça query por URL).
- **Cascata 2 níveis:** a hierarquia Área→Caderno→Nota é mais profunda que qualquer cascata anterior (Epic 4 tinha Hábito→Log, 1 nível). O `deleteKnowledgeArea` deve ser `db.transaction('rw', db.knowledge_areas, db.knowledge_notebooks, db.knowledge_notes, ...)` — os 3 stores na mesma transacção.
- **Padrão de atomicidade no repo** (Stories 3.4/4.1): toda a cascata via `db.transaction('rw', ...)` dentro do repo; as pages nunca chamam `db.*` directamente.
- **Brain Dump:** se AC2 ratificar tabela, a interface `BrainDump` vai para a secção "Epic 5" de `types/db.ts`. O `parsedOutput` (4 buckets AI) deve ser `unknown` ou interface própria para evitar coupling com a Story 5.7 (parser AI) nesta story de schema; a Story 5.7 define o tipo exacto.
- **`internal-state-contract-gate.md`:** NÃO se aplica a esta story. O estado distribuído proposta→aceite/rejeitado→persistido é da Story 5.8 (approval flow), não da 5.1 (schema). A Story 5.1 apenas cria a camada de persistência; o ciclo de vida do Brain Dump approval é gerido na 5.8.
- **Convenção A5 (`story-lifecycle.md`):** contagens de teste vivem só no Change Log/Dev Agent Record como snapshot datado — **nunca** em headers de secção ou File List.
- **D-4.2-1 (NavLink `/tasks` EN):** se esta story tocar o `Header.tsx` (improvável para uma story de schema puro), absorver o débito D-4.2-1 de caminho. Se não tocar, o débito aguarda a 5.3 ou 5.9 (que certamente adicionam NavLinks ao Header).
- **Não implementar UI, editor, pesquisa web ou tools** — fora de scope da 5.1.

### Recomendação [GAP-5.1b] — `brain_dumps`: tabela Dexie vs estado transitório

**Recomendação Dara: tabela Dexie em `version(5)` aditivo.** Fundamentação a partir do código real e dos FR:

1. **Ciclo de vida atravessa sessões e exige máquina de estados persistida.** O FR48 (AI estrutura em 4 buckets) e o FR49 (aprovação item-a-item) implicam um estado intermédio `parsed → partially_approved → fully_approved` que NÃO é instantâneo: o utilizador pode parsear o brain dump, fechar o tab e voltar mais tarde para aprovar itens. Um estado transitório (React state / `useLocalStorage`) perde-se ou fica frágil entre sessões. A Story 5.8 (approval flow) precisa de ler/escrever esse estado de forma fiável — uma tabela Dexie dá-lhe o mesmo modelo ACID que todas as outras entidades do app.

2. **Coerência com o padrão do codebase.** Todas as 14+ entidades persistentes do Nexus v2 vivem em Dexie com repo tipado + Zod + hooks. O Brain Dump é a única que ficaria fora desse padrão se fosse transitória — criando uma excepção arquitectural sem ganho claro. O `agent_runs` (Epic 1) já estabelece o precedente de persistir "processos" (corridas do agente), não só "documentos finais".

3. **O PRD §10 lista `brain_dumps` explicitamente como tabela** — e nenhum ADR a contradiz. Pela regra de reconciliação do `EPIC-5.md` §7, sem divergência arquitectural que justifique desviar do PRD, o PRD prevalece.

4. **Custo baixo, aditivo, reversível.** `version(5).stores({ brain_dumps: 'id, createdAt, status' })` é um incremento aditivo que não toca dados de produção (Dexie preserva as 20 tabelas existentes). Índice `createdAt` serve `listBrainDumps` ordenado DESC (historial — FR47); `status` serve filtros do approval flow (5.8).

**Trade-off do crescimento (contra-argumento mitigado):** a tabela pode crescer sem limite. Mitigação: brain dumps são de baixa frequência (sessões pontuais de descarga mental, não input contínuo); se o volume crescer, uma retenção/limpeza pode ser adicionada numa story futura sem alterar o schema. O risco de crescimento é menor que o risco de perder o estado de aprovação a meio.

**Forma proposta da interface `BrainDump`** (a ratificar; `parsedOutput` deliberadamente `unknown` para evitar coupling com a Story 5.7 que define o tipo exacto do parser):

```typescript
export interface BrainDump {
  id: string;
  createdAt: number;          // epoch ms — índice para historial DESC
  bodyMarkdown: string;       // input original (FR47)
  parsedOutput?: unknown;     // 4 buckets AI (FR48); tipo exacto definido na Story 5.7
  status: 'pending' | 'parsed' | 'partially_approved' | 'fully_approved';
}
```

### AC2 / `[GAP-5.1b]` — DECISÃO `D-BRAINDUMP-STORE`: tabela Dexie `version(5)` aditivo

**Ratifico `brain_dumps` como tabela Dexie**, não estado transitório. Fundamentação (rastreável, não palpite):

2. **Coerência arquitectural.** As 20 tabelas do Nexus v2 vivem em Dexie com repo+Zod+hooks (`client.ts:85-147`). Tornar o Brain Dump a única excepção transitória cria uma divergência sem ganho. 3. **PRD prevalece sem ADR em contrário.** `PRD-NEXUS-V2.md:521` lista `brain_dumps` como tabela; nenhum dos 5 ADRs base a contradiz. Pela regra de reconciliação `EPIC-5.md` §7, sem divergência arquitectural justificada, o PRD manda.
4. **Custo baixo, aditivo, reversível.** `version(5)` aditivo preserva as 20 tabelas existentes (Dexie não toca dados de produção). Crescimento ilimitado é o único contra — mitigado: brain dumps são de baixa frequência (acção explícita pontual); retenção/limpeza pode ser adicionada numa story futura sem alterar schema. O risco de perder estado de aprovação a meio supera o risco de crescimento.
