### Análise de Ciclo de Vida — 3 eixos obrigatórios (`internal-state-contract-gate.md`)

> A ser preenchida pelo `@architect` no Architect Gate de Entrada. Os 3 eixos são verificados contra o código real.

| Eixo | Pergunta | Resposta (`@architect` Aria — ratificada no Gate de Entrada, 18/06/2026, contra código real) |
|------|---------|-------------------------------|
| **(a) Classes de estado** | Quais as classes de estado que o cron orquestra? O pull e o push mantêm a coerência dos seus cursores KV e do índice `&googleId` Dexie quando chamados em sequência pelo cron? | **RATIFICADO.** Quatro classes confirmadas no código: (1) **pendente-pull** — evento Google ainda não em Dexie; o pull traz via `syncCalendarEvents(accessToken, currentSyncToken)` e faz upsert (`sync/route.ts:85,115`). (2) **local-pendente** — evento Nexus sem `googleId`; o push lê-os por `db.calendarEvents.filter(e => !e.googleId)` (`push/route.ts:96`) e empurra (produtor é a 6.6 `criar_evento_calendar`, Done em main). (3) **sincronizado** — com `googleId`; o push persiste `googleId` na mesma cadeia `await` após insert 2xx (`push/route.ts:116-119`). (4) **falha-push** — 404 conta como `failed` sem persistir `googleId` (`push/route.ts:129-132`); 429/5xx/401 abortam o lote com 503/401. **O cron NÃO toca nenhuma destas classes directamente** — é orquestrador fino: delega 100% da mutação de estado às routes 6.3/6.4. O cursor KV `nexus:google:calendar:syncToken` é gerido exclusivamente pelo `sync/route.ts` (linhas 104-111); o índice `&googleId` Dexie exclusivamente pelo `push/route.ts`. O cron lê apenas os **contadores de resposta**, nunca o estado persistido. Coerência preservada por composição: cada route mantém a sua própria atomicidade-só-no-fim. |
| **(b) Transição-já-ocorrida** | O cron é re-executado antes do anterior terminar (overlap entre execuções). O pull é chamado duas vezes com o mesmo `syncToken`. O push encontra eventos já sincronizados (já têm `googleId`). | **RATIFICADO — idempotência por composição confirmada, com 1 caveat de corrida documentado.** Pull: idempotente por `syncToken` — o cursor só é persistido no fim de um sync bem-sucedido (`sync/route.ts:104-111`); duas chamadas seguidas com o mesmo cursor de partida trazem o mesmo delta na 2ª só se a 1ª ainda não persistiu o cursor (re-processa, mas o upsert no helper é idempotente por id Google). Push: idempotente por `!googleId` — eventos já sincronizados (com `googleId`) saem do filtro `filter(e => !e.googleId)` (`push/route.ts:96`); o `&googleId` único esparso garante que um re-insert não cria duplicado em Dexie. **Caveat de corrida real (overlap push-push):** se cron1.push e cron2.push correm sobrepostos, ambos podem ler o mesmo evento local-pendente (sem `googleId`) ANTES de qualquer um persistir o `googleId` → **dois `events.insert` no Google → evento duplicado no Google Calendar** (o `&googleId` esparso protege o Dexie, mas NÃO o lado Google, que ainda não tem `googleId` para deduplicar). **Mitigação ratificada:** a decisão **D-6.5-ORCHESTRATION (serial intra-cron)** elimina a corrida pull→push *dentro* de uma execução; a corrida *entre execuções sobrepostas* é eliminada pela cadência conservadora de **D-6.5-CRON-CONFIG (1×/dia)** — a janela de uma execução (pull+push de poucos eventos) é de segundos, muito inferior ao intervalo de 24h, tornando overlap virtualmente impossível na operação de utilizador único (Eurico). Um lock distribuído (KV `nexus:cron:sync:lock` com TTL) é registado como **follow-up opcional pós-Epic-6** caso a cadência aumente para sub-horária — NÃO é requisito desta story dada a cadência diária. |
| **(c) Caminhos de falha** | Pull OK + push falha (token revogado a meio, 429, 5xx): o cron devolve erro? O estado fica consistente? Pull falha + push não corre: o cursor `syncToken` foi actualizado? | **RATIFICADO.** Pull falha: o `sync/route.ts` devolve 401 (`token_revoked`/`not_connected`), 503 (`refresh_failed`/`calendar_unavailable`) **sem persistir cursor parcial** (linhas 64-96 — o `setCalendarSyncToken` só corre no caminho de sucesso, linhas 104-111). Logo o cursor antigo permanece intacto → o próximo cron retoma do mesmo ponto (idempotente). Push falha: 404 por-evento conta `failed` sem persistir `googleId` (re-tentado no próximo cron); 429/401/5xx abortam o lote com 503/401, e os `googleId` já persistidos antes do erro mantêm-se válidos (atomicidade por-evento, `push/route.ts:116`). **Decisão do cron perante estes erros: ver D-6.5-PARTIAL-FAILURE abaixo** — o cron NUNCA propaga 5xx (devolve sempre 200 com o detalhe parcial), porque um 5xx faria o scheduler (cron-job.org ou Vercel) re-agendar com backoff não controlado, multiplicando chamadas a um Google já em falha. O estado fica sempre consistente porque ambas as routes são fail-safe (nunca `200 { ok:false }` com estado parcial — herança do anti-padrão M4 da 4.9). |

A idempotência é garantida pelos mecanismos das routes 6.3 e 6.4 reutilizados — o cron não introduz novo estado.

#### D-6.5-ORCHESTRATION — RATIFICADO

**Decisão:** **(1) sequência serial pull→push** (candidata C) + **(2) chamada interna por import directo dos handlers** (Opção B), **não** por `fetch` HTTP com cookie.

**Justificação — sequência serial:** trazer eventos novos do Google (pull) antes de empurrar locais (push) reduz a janela de conflito e é a semântica natural do sync 2-way. Serial também elimina a corrida pull→push intra-cron (eixo b). O custo de latência é irrelevante a 1×/dia. `[Source: análise eixo b acima; Story 6.3 AC5 + 6.4 AC5]`

**Justificação — import directo (resolve a descoberta material + SSRF):** as routes exigem `getSession(req)` (cookie) e o middleware bloqueia sem cookie. Um `fetch` interno teria de forjar cookie de sessão — inviável e inseguro. O import directo dos handlers (`import { POST as calendarPull } from '@/app/api/google/calendar/sync/route'`) chamados com um `Request` sintético **continua a bater no `getSession(req)` que devolve 401 sem cookie** — portanto a route do cron tem de construir um `Request` que satisfaça o contrato de auth dessas routes. **Via ratificada:** o handler do cron, após validar o seu próprio `CRON_SECRET` Bearer, invoca os handlers pull/push passando um `Request` que inclui um **cookie de sessão de serviço** — MAS isto reabre o problema de forjar sessão. **Decisão final para evitar qualquer forja de sessão e o risco SSRF (lição 5.11 CR --base main):** o `@devops` deve **extrair a lógica de sync de cada route para um helper de serviço chamável sem `Request`** OU, em alternativa mínima-invasiva sem refactor de 6.3/6.4, **chamar os handlers com um `Request` cujo cookie é a sessão do próprio Eurico recriada server-side** não é aceitável. Portanto a via limpa é: **a route do cron NÃO chama as routes HTTP; importa directamente os helpers de domínio que as routes já usam** — `syncCalendarEvents` (de `lib/google/calendar.ts`) para o pull e `pushCalendarEvent` (de `lib/google/calendar-push.ts`) para o push, mais `getValidAccessToken()` para o token e a gestão do cursor KV (`lib/google/calendar-sync-token.ts`) e `db.calendarEvents` para o push — replicando o orquestração das routes mas **sem `getSession`** (a auth do cron É o `CRON_SECRET`, não a sessão de browser).

> **FLAG DE SCOPE para `@devops` (ratificada por `@architect`):** a story assumia que o cron "chama as routes HTTP internas" e é "fino, zero lógica". O código real torna isso impossível sem forjar sessão. A via correcta é o cron importar os **helpers de domínio** (`syncCalendarEvents`, `pushCalendarEvent`, `getValidAccessToken`, cursor KV, `db.calendarEvents`) — os mesmos que as routes 6.3/6.4 usam — e replicar a coordenação fina (ler cursor → sync → persistir cursor; filtrar `!googleId` → push → persistir `googleId`). Isto NÃO é "lógica de sync duplicada" no sentido proibido (o cálculo de diff continua 100% dentro de `syncCalendarEvents`/`pushCalendarEvent`); é a **coordenação de orquestração** que as routes fazem e que o cron tem de repetir porque não as pode invocar via HTTP. **Risco mitigado:** zero round-trip HTTP interno → zero superfície SSRF (a lição 5.11 era sobre chamadas server-side a URLs; aqui não há URL nenhuma). O `@devops` deve manter a coordenação do cron alinhada linha-a-linha com a das routes (mesma ordem de persistência do cursor, mesma atomicidade-só-no-fim) para não divergir o contrato de estado. `[Source: sync/route.ts:79-111; push/route.ts:96-150; session.ts:73-99; middleware.ts:25,58]`

#### D-6.5-PARTIAL-FAILURE — RATIFICADO

**Decisão:** **candidata (c) — o cron devolve sempre 200 com detalhe de erros parciais; pull e push são independentes (push corre mesmo que o pull falhe), mas com curto-circuito de token revogado.** Contrato:
1. **Pull falha por token revogado/não-ligado (`token_revoked`/`not_connected`, 401):** o push também vai falhar pela mesma causa (ambos usam `getValidAccessToken()`). Curto-circuito: se o pull devolve erro de classe-token, o cron **marca o push como `skipped`** e devolve `200 { ok: false, calendar: { pull: { error: 'token_revoked' }, push: { skipped: true } } }`. Evita uma segunda chamada inútil a um token que se sabe revogado.
2. **Pull falha por causa transitória (`refresh_failed`/`calendar_unavailable`, 503):** o token pode ainda ser válido (foi a Calendar API que falhou, não o refresh). O push **corre na mesma** (pode haver eventos locais para empurrar com token válido). Resposta: `200 { ok: false, calendar: { pull: { error: 'calendar_unavailable' }, push: { pushed, updated, failed } } }`.
3. **Push falha (parcial ou total):** o cron recolhe `{ pushed, updated, failed }` ou o erro de classe (`rate_limited`/`token_revoked`/`calendar_push_unavailable`) e devolve `200` com o detalhe. **Nunca 5xx** — um 5xx faria o scheduler re-agendar com backoff não controlado contra um Google já em falha.
4. **`ok` é `true` apenas se pull E push terminaram sem erro de classe** (contadores de `failed` por-evento não derrubam `ok`, porque são falhas esperadas e idempotentemente re-tentadas no próximo cron). Liga ao **AC4**.

`[Source: sync/route.ts:62-96 (classes de erro do pull); push/route.ts:129-145 (classes de erro do push); anti-padrão M4 4.9 via internal-state-contract-gate.md]`
