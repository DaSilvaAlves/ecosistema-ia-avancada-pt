## Story

**Como** utilizador do Nexus (Eurico),
**quero** importar um ficheiro ZIP de backup (gerado pela Story 9.6) a partir da página de definições e restaurar todos os meus dados,
**para que** consiga recuperar o estado completo da minha conta (tarefas, finanças, hábitos, diário, notas, etc.) se perder o browser/dispositivo, ou mover os meus dados para outro dispositivo — fechando o ciclo de continuidade pessoal aberto pela 9.6.

## Acceptance Criteria

1. A secção "Backup" existente em `/settings` (Story 9.6) ganha um novo componente `RestoreSettings.tsx` (mesmo padrão visual dos cartões existentes `BackupSettings.tsx`/`GoogleCalendarSettings.tsx`) com um input de ficheiro (`accept=".zip"`) e um botão "Importar dados", junto do botão de exportar já existente.
2. Ao seleccionar um ZIP e confirmar a importação, o sistema desempacota-o (`fflate.unzipSync`) e procura **exactamente** a entrada `nexus-db-export.json` (nome fixo do contrato da Story 9.6, `DB_EXPORT_FILENAME` em `lib/backup/export.ts`). Se essa entrada não existir (ZIP de outra origem, corrompido, ou vazio), a importação **falha honestamente antes de tocar em Dexie** — nenhuma tabela é lida nem escrita.
3. O JSON extraído é validado como um export `dexie-export-import` reconhecível (`formatName === 'dexie'`) antes de qualquer escrita. Se o conteúdo não for um JSON válido no formato esperado (ZIP malicioso/corrompido com um ficheiro `nexus-db-export.json` que não é realmente um export Dexie), a importação falha honestamente sem tocar em Dexie.
4. **[GAP-9.4 eixo (c) — compatibilidade de versão de schema]:** a importação usa `importInto(db, jsonBlob)` da `dexie-export-import` **sem** `acceptNameDiff: true` nem `acceptVersionDiff: true`. Se o `databaseName` do backup for diferente de `nexus_v2` (nome da DB, `lib/db/client.ts`) OU a `databaseVersion` do backup for diferente da versão de schema actual (`db.verno`, hoje `6`), a importação é **rejeitada** com uma mensagem honesta PT-PT (ex.: "Este backup foi feito com uma versão incompatível da app. Restauro cancelado, os teus dados actuais não foram alterados.") — política MVP explícita: falha honesta, sem tentativa de migração automática entre versões de schema.
5. **[GAP-9.4 eixo (a) — substituir, decisão explícita]:** antes de disparar a importação, o utilizador vê uma confirmação destrutiva explícita em PT-PT (`window.confirm`, mesmo padrão de `TaskKebabMenu.tsx` L145) do tipo: *"Isto vai substituir TODOS os teus dados actuais pelos dados deste backup. Esta acção não pode ser desfeita. Continuar?"*. Só após confirmação positiva a importação prossegue; cancelar não faz qualquer alteração e o componente volta a `idle`.
6. A importação usa `importInto(db, jsonBlob, { clearTablesBeforeImport: true, overwriteValues: true })` — os dados actuais das 22 tabelas Dexie são **substituídos** pelos do backup, não fundidos. Decisão registada (GAP-9.4 eixo a): "restaurar" significa reverter ao estado exacto do backup. Como consequência directa desta política, reimportar o **mesmo** backup duas vezes seguidas é idempotente por construção (as tabelas são sempre limpas antes de reescritas — não há duplicação possível).
7. **[GAP-9.4 eixo (b) — all-or-nothing]:** a importação **não** usa `noTransaction: true` — corre dentro da transacção atómica nativa do `importInto` (comportamento default da lib quando `noTransaction` não é definido). Se ocorrer qualquer erro a meio da importação (JSON corrompido a meio dos dados, falha de escrita numa tabela), a transacção reverte por completo — a base de dados fica exactamente no estado anterior ao restore, nunca com um subconjunto de tabelas escritas e outras não. Coberto por teste com JSON corrompido a meio das tabelas (ver Testing).
8. Após importação bem-sucedida, a UI reflecte os novos dados sem exigir reload manual — os ecrãs que já usam `useLiveQuery` (dashboard, tarefas, finanças, hábitos, projectos, tags, etc. — ver Dev Notes) re-renderizam automaticamente porque o observable Dexie dispara ao committar a transacção de import. O componente `RestoreSettings.tsx` mostra uma confirmação de sucesso PT-PT (Lime) com a contagem de tabelas restauradas (derivada dos metadados do backup, `peakImportFile`) e oferece um botão explícito "Recarregar página" (não reload automático — evita perder trabalho não relacionado que o utilizador tenha noutro separador/estado local fora de Dexie).
9. O componente `RestoreSettings.tsx` tem pelo menos 4 estados de render distintos (`idle` / `a-importar` / `sucesso` / `erro`) — `react-component-test-criteria.md` aplica-se: teste de componente obrigatório, 1 cenário por estado de render React, mais 1 cenário adicional que prova que cancelar a confirmação destrutiva **não** chama a lógica de import (fica em `idle`).
10. Testes unitários (Vitest + `fake-indexeddb`) cobrem, no mínimo: (a) round-trip completo `buildBackupZip()` → `restoreFromZip()` prova que os dados batem certo após o restore; (b) ZIP sem a entrada `nexus-db-export.json` falha honestamente sem tocar Dexie; (c) JSON com `databaseName` diferente falha honestamente sem escrever; (d) JSON com `databaseVersion` diferente da actual falha honestamente sem escrever; (e) importar sobre uma DB com dados existentes demonstra substituição total (dados antigos deixam de existir, só ficam os do backup); (f) falha a meio da importação (JSON corrompido/truncado) não deixa a DB parcialmente escrita — o estado antes da tentativa é idêntico ao estado depois da falha; (g) reimportar o mesmo backup duas vezes seguidas não duplica registos (idempotência).
11. **Delimitação (não-âmbito):** esta story não reabre nem altera a Story 9.6 (o export permanece inalterado — `lib/backup/export.ts` não é modificado, exceto import das suas constantes exportadas); não implementa migração automática de schema entre versões de backup diferentes (política MVP é falha honesta, AC4); não toca produção/deploy; não introduz um botão de "apagar tudo" independente do restore.

### API `dexie-export-import` — `importInto` (a API que esta story consome)

[Source: `node_modules/dexie-export-import/dist/import.d.ts`; `node_modules/dexie-export-import/README.md`; `node_modules/dexie-export-import/dist/dexie-export-import.js` L2354, L3418-3420, L3501-3502 — comportamento confirmado por leitura directa do código-fonte da lib instalada, não da documentação apenas]

```ts
import { importInto, peakImportFile } from 'dexie-export-import';

interface ImportOptions {
  acceptMissingTables?: boolean;
  acceptVersionDiff?: boolean;   // default false — NÃO usar (AC4)
  acceptNameDiff?: boolean;      // default false — NÃO usar (AC4)
  acceptChangedPrimaryKey?: boolean;
  overwriteValues?: boolean;     // true (AC6) — permite bulkPut sobre chaves existentes
  clearTablesBeforeImport?: boolean; // true (AC6) — limpa cada tabela antes de escrever (= substituir)
  skipTables?: string[];
  noTransaction?: boolean;       // default false/undefined — NÃO definir (AC7, mantém atomicidade)
  chunkSizeBytes?: number;
  filter?: (table, value, key) => boolean;
  progressCallback?: (progress: ImportProgress) => boolean;
}

await importInto(db, jsonBlob, {
  clearTablesBeforeImport: true,
  overwriteValues: true,
});
```

**Comportamento nativo confirmado no código-fonte da lib (`dexie-export-import.js`, versão instalada 4.4.0):**

- **Validação de nome/versão acontece ANTES de qualquer escrita** (L3418-3420, dentro do generator de `importInto`, antes do loop de `clearTablesBeforeImport`): `if (!options.acceptNameDiff && db.name !== dbExport.databaseName) throw new Error("Name differs...")` e `if (!options.acceptVersionDiff && db.verno !== dbExport.databaseVersion) throw new Error("Database version differs...")`. Isto significa que, **sem** passar `acceptNameDiff`/`acceptVersionDiff` (o default é `false`/`undefined`), a lib já rejeita nome/versão incompatíveis por si só, antes de tocar em qualquer tabela — a Task 1 só precisa de capturar e reclassificar estes `Error` nativos em `RestoreError`, não reimplementar a validação.
- **Atomicidade é o comportamento default:** o README descreve a lib como "Atomic - import / export within one database transaction (optional)" — a atomicidade é o caminho por omissão; só se perde se `noTransaction: true` for passado explicitamente. Esta story **nunca** passa essa opção.
- **`peakImportFile(blob)`** lê só os metadados (`formatName`, `databaseName`, `databaseVersion`, `tables[]` com `rowCount`) **sem** importar — usado para a validação de formato (AC3) e para a contagem apresentada no sucesso (AC8), sem custo de uma segunda leitura completa do ficheiro (é a mesma leitura em streaming truncada aos metadados).

### Análise de ciclo de vida para o gate `@architect` (`internal-state-contract-gate.md`) — ponto de partida factual

O `@dev` implementa e o `@architect` confirma contra o código real implementado (não é suficiente aceitar este ponto de partida sem verificação):

| Eixo | Análise (baseada no design desta story) |
|------|------------------------------------------|
| **(a) Classes de estado** | Duas classes de entrada possíveis: DB local vazia (primeira utilização) vs DB local com dados reais existentes. A política de substituição total (`clearTablesBeforeImport: true`) faz as duas classes convergirem para o **mesmo** resultado final (o estado do backup) — é o comportamento **desejado** de um "restore" (não é um bug de colapso de classes, é a semântica correcta da operação). O `@architect` confirma que nenhum caminho de código trata estas duas classes de forma diferente por engano (ex.: um `if (tabelaVazia)` acidental que só limparia em certas condições). |
| **(b) Transição-já-ocorrida** | O que acontece se o browser fechar/o separador fechar a meio da transacção `importInto`? A transacção IndexedDB é gerida pelo motor do browser — uma transacção que não commitou nunca persiste parcialmente (garantia da spec IndexedDB, não código nosso). O `@architect` confirma que a story não introduz nenhum passo de escrita **fora** da transacção do `importInto` (ex.: nenhum `db.someTable.put()` manual antes/depois da chamada) que pudesse quebrar essa garantia. |
| **(c) Caminhos de falha** | Ficheiro sem a entrada esperada (AC2), JSON não reconhecido (AC3), nome de DB diferente (AC4), versão de schema diferente (AC4), transacção falha a meio por corrupção de dados (AC7) — todos têm de resultar em **zero escrita** e uma mensagem PT-PT honesta e distinta (não um "erro genérico" que esconda qual das 5 causas ocorreu). O `@architect` verifica que o mapeamento `RestoreError.reason` → mensagem PT-PT no componente cobre as 5 causas sem ambiguidade, e que os testes da Task 3 provam — por execução real, não por leitura do código — que a DB fica inalterada em cada um destes 5 casos. |
