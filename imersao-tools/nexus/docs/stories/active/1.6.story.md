## User Story

**As a** Eurico (utilizador único do Nexus v2) a interagir com o chat multi-intent,
**I want** que o sistema me mostre uma prévia das acções que vai executar e peça confirmação quando o classifier tem confiança < 70% ou quando a tool marcada com `requiresPreview: true` for invocada,
**so that** nunca sejam persistidas acções irreversíveis baseadas em interpretações ambíguas do meu prompt PT-PT, cumprindo o FR5 do PRD ("Confidence < 70% → preview antes de persistir") e o AC2 do Epic 1 ("Prompt ambíguo dispara preview de confirmação").

## Contexto

**PRD §6.1 FR5** (linha 125): `"Confidence < 70% → preview antes de persistir"` — fonte canónica do threshold.
**PRD §10 linha 417**: `"1.6 Preview-then-confirm para confidence < 70%"` — scope exacto da story.
**Epic 1 AC2** (PRD §10 linha 425): `"Prompt ambíguo dispara preview de confirmação"`.

A Story 1.4 (Done) garante que `ClassificationResult.confidence` é um `Record<string, number>` per-domain com valores calibrados em [0, 1] via few-shot prompt. A Story 1.5 (Done) implementou `runAgent()` como async generator stateless que emite eventos SSE. A Story 1.3 (Done) definiu `ToolDefinition.requiresPreview: boolean` como campo obrigatório em cada tool.

**Dois gatilhos independentes para preview:**

| Gatilho | Fonte | Condição |
|---------|-------|----------|
| Confidence baixa | `ClassificationResult.confidence[domain]` | Qualquer domain com confidence < 0.7 |
| Tool marcada | `ToolDefinition.requiresPreview` | `requiresPreview === true` na tool a executar |

**Fluxo preview:**

```
runAgent() a correr normalmente
  │
  ├─ Antes de executar tool:
  │    SE confidence[domain] < 0.7 OU tool.requiresPreview === true:
  │       1. NÃO executa a tool ainda
  │       2. Emite evento SSE `preview_request` com payload { toolName, args, reason }
  │       3. Suspende o loop aguardando resposta
  │    SENÃO:
  │       Executa imediatamente (comportamento Story 1.5)
  │
  ├─ Client recebe `preview_request`:
  │    Mostra UI de confirmação ao utilizador
  │    Utilizador confirma → envia POST /api/agent/confirm { runId, toolName, action: 'confirm' }
  │    Utilizador cancela → envia POST /api/agent/confirm { runId, toolName, action: 'cancel' }
  │
  └─ Executor recebe resposta via mecanismo de sinalização (ver AC3):
       confirm → executa tool → continua loop
       cancel  → emite `tool_error { toolName, error: 'Cancelado pelo utilizador' }` → continua loop
```

**Nota de scope — stateless executor (RESOLVED-2 da Story 1.5):**
O executor é Edge-safe e stateless. A suspensão do loop enquanto aguarda confirmação requer um mecanismo de sinalização compatível com Edge Runtime. A implementação canónica usa Vercel KV (introduzido na Story 1.7 para undo) ou uma abordagem alternativa como callback via Promise. [GAP — confirmar com @architect: mecanismo de sinalização preferido entre (a) Vercel KV poll, (b) Promise/AbortController in-process, (c) separar em dois endpoints sem suspenção real]. Abordagem default desta story: **callback via Promise in-process** — simples, Edge-safe, funciona se o confirm chegar pelo mesmo Edge process. Se o Vercel distribuir a request de confirm para outro process, Story 1.8 terá de introduzir KV para coordenação.

**Anti-padrões críticos desta story:**
- NÃO criar o endpoint `/api/agent/prompt` — é Story 1.8
- NÃO criar UI de confirmação — é Story 1.9
- NÃO implementar undo — é Story 1.7
- NÃO alterar `ToolDefinition` (Story 1.3) — `requiresPreview` já existe
- NÃO alterar `ClassificationResult` schema (Story 1.2) — `confidence` já existe

## Acceptance Criteria

- **AC1:** `runAgent()` em `lib/agent/executor.ts` é estendido (NÃO recriado) com gate de preview antes de cada `tool.execute()`:
  - Avalia condição: `hasConfidenceBelowThreshold(classifierResult, tool.domain) || tool.requiresPreview`
  - Função auxiliar `hasConfidenceBelowThreshold(result: ClassificationResult, domain: ToolDomain): boolean` — interna, não exportada — retorna `true` se `result.confidence[domain] !== undefined && result.confidence[domain] < PREVIEW_CONFIDENCE_THRESHOLD`
  - Constante `PREVIEW_CONFIDENCE_THRESHOLD = 0.7` exportada de `lib/agent/executor.ts` (permite override em testes + documentada como knob de tuning, traçada ao FR5)

- **AC2:** Novo evento SSE `preview_request` adicionado ao tipo `ExecutorSSEEvent` em `lib/agent/executor.ts`:
  ```typescript
  | {
      type: 'preview_request';
      runId: string;
      toolName: string;
      args: unknown;           // args validados por argsSchema — o client mostra ao utilizador
      reason: 'low_confidence' | 'requires_preview' | 'both';
      confidence?: number;     // valor de confidence[domain] se reason inclui low_confidence
      domain: ToolDomain;
    }
  ```
  Este evento é emitido **antes** de executar a tool quando o gate é activado. Após emitir `preview_request`, o loop suspende-se.

- **AC3:** Mecanismo de suspensão e retoma do loop:
  - `runAgent()` aceita novo campo opcional em `RunAgentOpts`: `confirmationProvider?: ConfirmationProvider`
  - Interface `ConfirmationProvider` exportada de `lib/agent/executor.ts`:
    ```typescript
    export interface ConfirmationProvider {
      requestConfirmation(runId: string, toolName: string): Promise<'confirm' | 'cancel'>;
    }
    ```
  - Se `opts.confirmationProvider` fornecido: o executor invoca `confirmationProvider.requestConfirmation(runId, toolName)` e **aguarda** (`await`) a Promise. Resultado `'confirm'` → executa a tool. Resultado `'cancel'` → emite `tool_error { runId, toolName, error: 'Cancelado pelo utilizador' }` + continua loop.
  - Se `opts.confirmationProvider` não fornecido (default): emit `preview_request` e **executa imediatamente a tool** (comportamento "auto-confirm" para compatibilidade retroactiva com Story 1.5 e para testes que não injectam provider). Isto mantém o output SSE completo para o client, que pode usar o `preview_request` como informação (e.g., destacar a acção na UI), sem bloquear o fluxo.
  - **Justificação do auto-confirm default:** Story 1.8 (endpoint) e Story 1.9 (UI) são as histórias que constroem a experiência real de confirmação. Nesta story, o executor expõe a abstracção correcta sem bloquear desenvolvimento paralelo.

- **AC4:** Novo evento SSE `preview_confirmed` adicionado ao tipo `ExecutorSSEEvent`:
  ```typescript
  | {
      type: 'preview_confirmed';
      runId: string;
      toolName: string;
      action: 'confirm' | 'cancel';
    }
  ```
  Emitido **após** `confirmationProvider.requestConfirmation()` resolver (seja auto-confirm ou provider real), antes de executar ou cancelar. Permite ao client actualizar o estado da UI em tempo real.

- **AC5:** Rastreio de `hadPreviewGate` no output `done`:
  - Evento `done` passa a incluir campo `previewCount: number` — número de tools que passaram pelo gate de preview neste run (incluindo auto-confirmed e cancelled). Permite ao client saber se o run teve ambiguidade.
  - Campo é adicionado ao tipo `done` em `ExecutorSSEEvent` (campo opcional para retrocompat com consumers que não o usam).

- **AC6:** Novas sequências de testes em `tests/unit/agent/executor.test.ts` cobrem:
  - Gate de preview activado por `confidence < 0.7`: mock classifier retorna `confidence: { tasks: 0.55 }` → `preview_request` emitido com `reason: 'low_confidence'`, `confidence: 0.55`; auto-confirm (sem provider) → `preview_confirmed { action: 'confirm' }` → `tool_complete`; `done.previewCount === 1`
  - Gate de preview activado por `tool.requiresPreview === true` (confidence >= 0.7): `preview_request` emitido com `reason: 'requires_preview'`; auto-confirm → `tool_complete`
  - Gate activado por ambos: `reason: 'both'`
  - Com `confirmationProvider` mock que resolve `'cancel'`: `preview_request` → `preview_confirmed { action: 'cancel' }` → `tool_error { error: 'Cancelado pelo utilizador' }` → loop continua; `done.status: 'partial'`; `done.previewCount === 1`
  - Com `confirmationProvider` mock que resolve `'confirm'`: flow normal como auto-confirm
  - Confidence >= 0.7 e `requiresPreview: false`: gate **não** activado, `preview_request` nunca emitido
  - `PREVIEW_CONFIDENCE_THRESHOLD` exportado e igual a `0.7`

- **AC7:** Coverage `lib/agent/executor.ts` mantém-se ≥ 80% lines após adição do código de preview.

**Decisão de design — auto-confirm default (AC3):**
O `confirmationProvider` é opcional. Sem ele, o gate emite `preview_request` + `preview_confirmed { action: 'confirm' }` e continua imediatamente. Isto:
1. Mantém retrocompatibilidade com consumers da Story 1.5 que não conhecem preview
2. Permite Stories 1.8/1.9 injectarem o provider real sem reescrever executor
3. Facilita testes unitários do executor sem precisar de provider mock a não ser para testar o path `cancel`

**Decisão de design — `reason` discriminado:**
Quando ambos os gatilhos estão activos (`confidence < 0.7` AND `requiresPreview === true`), `reason: 'both'` permite ao client UI mostrar mensagem mais informativa. O campo `confidence?` só é incluído quando `reason` inclui `'low_confidence'`.

**Fluxo dos eventos SSE para um preview confirmado (com provider):**
```
meta (start) → meta (classified) → tool_start → preview_request → [aguarda] → preview_confirmed { action: 'confirm' } → tool_complete → done
```

**Fluxo dos eventos SSE para um preview cancelado:**
```
meta (start) → meta (classified) → tool_start → preview_request → [aguarda] → preview_confirmed { action: 'cancel' } → tool_error → done (status: partial)
```

**Nota: `tool_start` antes de `preview_request`:**
O `tool_start` serve para a UI mostrar loading state da tool. O `preview_request` interrompe antes do `tool.execute()`. Esta ordem está alinhada com o fluxo da Story 1.5 (AC4 passos 3-5) onde `tool_start` precede a execução. A Story 1.9 (UI) interpretará `preview_request` como "parar loading, mostrar diálogo de confirmação".

**[GAP — confirmar com @architect]:** Se o Vercel distribuir a request de confirm (`POST /api/agent/confirm` da Story 1.8) para um Edge process diferente do que está a correr o stream SSE, a Promise in-process não vai resolver. Nesse caso a Story 1.8 precisará de introduzir Vercel KV como mecanismo de coordenação. Esta decisão está fora do scope da Story 1.6 — o executor expõe a abstracção `ConfirmationProvider` que permite a Story 1.8 implementar qualquer mecanismo sem alterar o executor.

### Completion Notes

**Pontos-chave da implementação:**

1. **Estrutura modular** — Gate isolado em duas funções puras (`hasConfidenceBelowThreshold` e `evaluatePreviewGate`) facilmente testáveis. `evaluatePreviewGate` retorna `null` quando o gate não dispara (caminho rápido, zero overhead para Story 1.5 backwards compat) ou um objecto `{ reason, confidence? }` rico em informação.

2. **Auto-confirm default elegante** — Sem provider, o gate emite na mesma `preview_request` + `preview_confirmed { confirm }` para o client poder mostrar UI informativa, mas executa imediatamente. AC4 garante `previewCount: 0` quando NENHUM gate é activado (vs `previewCount: 1` quando há gate auto-confirmed).

3. **Gate dentro do `handleSdkEvent`** — Coloquei o gate entre `tool_start` e `tool.execute()` (linha ~792 do `executor.ts`). Reusa a estrutura existente do `handleSdkEvent` (que já era `async`) e propaga o counter via `previewGated: boolean` em `SdkEventHandled`.

4. **Provider error handling robusto (AC6)** — Provider que rejeita Promise é tratado como erro de tool individual (não fatal): emite `tool_error` PT-PT com causa do provider + injecta `tool_result` para o modelo continuar o loop. NÃO emite `preview_confirmed` (semanticamente o provider não resolveu).

5. **Schema discriminação** — `confidence` no payload `preview_request` é incluído condicionalmente apenas quando `reason` inclui `'low_confidence'` (consistência com AC2 spec). O TS narrowing valida isto automaticamente porque o tipo é `confidence?: number`.

6. **MSW mock unificado** — Os 3 cenários (LOW_CONFIDENCE, REQUIRES_PREVIEW, BOTH_GATES) partilham o mesmo SSE handler 2-turn. A diferenciação está no classifier response (que retorna confidence diferente). A tool `tool_preview` é registada pelo test com config adequada (`domain` + `requiresPreview`) — esta separação permite os 4 cenários de gate testáveis com 1 só handler SSE.
