## Acceptance Criteria

> Traço directo a FR51, FR52, FR54 (EPIC-5.md §4 + PRD §6.10). AC numerados e testáveis.

### FR51 — Hierarquia Áreas → Cadernos → Notas

**AC1** — A rota **`/knowledge`** (rota canónica — ver [D-5.9-LAYOUT] C1; NÃO `/conhecimento`) mostra a vista de Conhecimento como **modal fullscreen** (paradigma `/tarefas`), com layout **master-detail de 2 painéis** (front-end-spec-v2.md §3.6): painel esquerdo = árvore Áreas→Cadernos com expand/collapse (cada área expande para os seus cadernos in-place); painel direito = nota seleccionada. Seleccionar uma área expande os seus cadernos; seleccionar um caderno popula a lista de notas; seleccionar uma nota popula o painel direito. Em mobile (<768px) colapsa para drill-down (a árvore é a vista; tocar numa nota abre-a fullscreen). _[FR51 + front-end-spec-v2.md §3.6/§8]_

**AC2** — A lista de áreas é ordenada alfabeticamente por nome (PT-PT — `localeCompare('pt-PT')`), a lista de cadernos de uma área é ordenada alfabeticamente, a lista de notas de um caderno é ordenada descendentemente por `updatedAt` (mais recente primeiro). _[FR51 — convenção já no repo]_

**AC3** — A vista de nota mostra o título e o corpo em markdown renderizado (leitura) e permite alternar para modo de edição com o `MarkdownEditor.tsx` (Story 5.2). A edição actualiza `updatedAt` via `updateKnowledgeNote`. _[FR51/FR52]_

### FR52 — CRUD de áreas, cadernos, notas

**AC4** — Criar área: formulário com campos `name` (obrigatório), `color` (selector de cor, obrigatório), `icon` (campo de texto ou picker de emoji, obrigatório). Ao submeter, chama `createKnowledgeArea` e actualiza a lista. Validação Zod do repo lança `ZodError` PT-PT se campos inválidos — a UI mostra a mensagem de erro. _[FR52]_

**AC5** — Editar área: inline ou via modal — altera `name`/`color`/`icon` via `updateKnowledgeArea`. **A área de sistema (`SYSTEM_AREA_ID`) não é renomeável** (botão editar disabled + tooltip "Área de sistema") — [D-5.9-SYSTEM-ENTITY-VISIBILITY] C3. _[FR52 + contrato D-5.8]_

**AC6** — Eliminar área: confirmação **quantificada** ([D-5.9-DELETE-CASCADE-UX] Opção B) — antes do diálogo, contar cadernos (`listNotebooksByArea`) e notas (somar `listNotesByNotebook` por caderno) e mostrar *"Vais apagar a área «X», N caderno(s) e M nota(s). Esta acção é irreversível."*. A contagem é **informativa** — passa-se ao texto do diálogo, **nunca** ao `deleteKnowledgeArea` (o delete usa o id, é atómico). A eliminação é em cascata (Área → Cadernos → Notas) via `deleteKnowledgeArea` numa transacção atómica. **Entidades de sistema não-elimináveis** (`SYSTEM_AREA_ID`): botão eliminar desactivado (disabled + tooltip "Área de sistema") quando `area.id === SYSTEM_AREA_ID`. _[FR52 + contrato D-5.8-INBOX]_

**AC7** — Criar caderno: requer área seleccionada; campos `name` (obrigatório). `createKnowledgeNotebook` valida que a área pai existe — a UI lança erro se a área entretanto desapareceu. _[FR52]_

**AC8** — Editar caderno: altera `name` via `updateKnowledgeNotebook`. **O caderno de sistema (`INBOX_NOTEBOOK_ID`) não é renomeável** (botão editar disabled + tooltip "Caderno de sistema") — [D-5.9-SYSTEM-ENTITY-VISIBILITY] C3. _[FR52 + contrato D-5.8]_

**AC9** — Eliminar caderno: confirmação **quantificada leve** ([D-5.9-DELETE-CASCADE-UX]) — contar só notas (`listNotesByNotebook`, 1 read) e mostrar *"Vais apagar o caderno «X» e M nota(s)."*. Cascata (Caderno → Notas) via `deleteKnowledgeNotebook`. **Entidades de sistema não-elimináveis** (`INBOX_NOTEBOOK_ID`): botão desactivado (disabled + tooltip "Caderno de sistema") quando `notebook.id === INBOX_NOTEBOOK_ID`. _[FR52 + contrato D-5.8-INBOX]_

**AC10** — Criar nota: requer caderno seleccionado; campos `title` (obrigatório) e `bodyMarkdown` (editor Tiptap 2, pode estar vazio no momento de criação). `updatedAt` definido como `Date.now()` na criação. _[FR52]_

**AC11** — Editar nota: altera `title` e/ou `bodyMarkdown` via `updateKnowledgeNote`; actualiza `updatedAt = Date.now()`. _[FR52]_

**AC12** — Eliminar nota: confirmação **simples** ([D-5.9-DELETE-CASCADE-UX] — sem contagem, não há cascata). Hard-delete via `deleteKnowledgeNote` (folha da hierarquia). Nota: notas *dentro* do `_inbox` de sistema **são** elimináveis (a nota não é entidade de sistema — só o caderno o é). _[FR52]_

### FR54 — Tag system global partilhado com tarefas

**AC13** — Na vista de nota (edição), existe um picker de tags que reutiliza `useTags` (hook do Epic 2) e a tabela `tags` existente. O utilizador pode adicionar ou remover tags **de uma nota** (altera o array `tags` da nota, não a tabela `tags`). As tags são gravadas no campo `tags: string[]` da nota (IDs de tags). **Proibido qualquer delete de tag da tabela `tags` nesta story** ([D-5.9-SYSTEM-ENTITY-VISIBILITY] C4 — gestão de tags é do Epic 2 / `/tags`). Se o picker permitir "criar tag", usa `createTag` (Epic 2). _[FR54]_

**AC14** — A tag de sistema `decisao` (`DECISAO_TAG_ID = '00000000-0000-4000-8000-000000000003'`) é apresentada no picker como qualquer outra tag (não há UI especial para ela — é uma tag normal). _[FR54 + contrato D-5.8-TAG-DECISAO]_

**AC15** — As notas podem ser filtradas por tag a partir da vista de caderno (usando `listNotesByTag`). _[FR54]_

## Decisões deferidas ao `@architect` (Aria)

> Padrão das Stories 5.7/5.8: decisões não-triviais são deferidas ao architect antes da implementação, em vez de serem inventadas no draft. O `@dev` não implementa até estas decisões estarem registadas na story.

**[D-5.9-LAYOUT]** Modelo de layout da vista de 3 níveis:
- PRD §6.10 (FR51) diz "hierarquia Áreas → Cadernos → Notas" mas não especifica o padrão de layout.
- Opção A: Painel lateral com 3 colunas (master-detail-detail) — nativo em desktop, complexo em mobile.
- Opção B: Navegação drill-down (clica área → abre cadernos; clica caderno → abre notas) — simples, familiar (padrão ficheiros).
- Opção C: Tabs superiores por nível com breadcrumb.
- `@architect` decide: qual o padrão de layout que melhor serve o modelo mobile-first do Nexus (ADR-1 Edge/Node + `front-end-spec-v2.md`)? Esta decisão afecta a estrutura de componentes e o roteamento.

**[D-5.9-DELETE-CASCADE-UX]** Experiência de confirmação de eliminação em cascata:
- `deleteKnowledgeArea` apaga N cadernos e M notas numa transacção atómica. Quantificação prévia ao diálogo de confirmação?
- Opção A: Confirmação simples ("Tens a certeza? Esta acção é irreversível.") — sem quantificação.
- Opção B: Antes de confirmar, contar cadernos e notas da área e mostrar ("Vais apagar 3 cadernos e 12 notas permanentemente.") — exige 2 reads Dexie antes do delete.
- `@architect` decide: qual o comportamento de confirmação para cascade delete? Afecta AC6 e AC9.

**[D-5.9-SYSTEM-ENTITY-VISIBILITY]** Visibilidade da área de sistema no CRUD:
- A área "Sistema" (`SYSTEM_AREA_ID`) e o caderno "Caixa de entrada" (`INBOX_NOTEBOOK_ID`) existem desde o 1.º approval do Brain Dump. O utilizador vê-os na lista de áreas/cadernos?
- Opção A: Visíveis mas não-elimináveis (botão disabled) — o utilizador sabe que existem, pode navegar e ver as notas/ideias do brain dump.
- Opção B: Ocultos da UI de CRUD de Conhecimento (filtrados no `listKnowledgeAreas`) — aparecem só no contexto do Brain Dump.
- Opção C: Visíveis mas numa secção separada "Sistema" (fora da lista principal de áreas do utilizador).
- `@architect` decide: qual a visibilidade das entidades de sistema? Esta decisão afecta AC6 (já desenhado para Opção A) e pode alterar AC1/AC2.

### [D-5.9-LAYOUT] — RATIFICADA: master-detail de 2 painéis (não 3 colunas, não drill-down, não tabs)

A vista é um **modal fullscreen** invocado pela navegação (paradigma das vistas `/tarefas`, `/financas`), não uma página de 3 colunas independentes.

**Fonte (a decisão já estava tomada no spec aprovado):**

### [D-5.9-DELETE-CASCADE-UX] — RATIFICADA: quantificada (Opção B) para ÁREAS; simples para cadernos e notas

**Decisão:**
- **Eliminar ÁREA (cascata 2 níveis):** confirmação **quantificada** (Opção B). Antes do diálogo, contar cadernos (`listNotebooksByArea`) e notas (somar `listNotesByNotebook` por caderno) e mostrar: *"Vais apagar a área «X», N caderno(s) e M nota(s). Esta acção é irreversível."*
- **Eliminar CADERNO (cascata 1 nível):** confirmação quantificada **leve** — contar só notas (`listNotesByNotebook`, 1 read): *"Vais apagar o caderno «X» e M nota(s)."*
- **Eliminar NOTA (folha):** confirmação **simples** (sem contagem — não há cascata).

**Justificação (peso UX vs custo):**
- O custo das reads é **baixo e local** (Dexie IndexedDB, índices `areaId`/`notebookId` já existentes — `listNotebooksByArea` e `listNotesByNotebook` usam `where(...).equals(...)`). _[VERIFICADO: knowledge-notebooks.ts:48-56, knowledge-notes.ts:49-57]_ Não há round-trip de rede. O custo de 1+N reads por confirmação de área é desprezável face ao risco.
- O peso UX é **alto**: a cascata de 2 níveis é **hard-delete irreversível** (sem soft-delete no codebase — `deleteKnowledgeArea` apaga 3 tabelas atomicamente). _[VERIFICADO: knowledge-areas.ts:70-91]_ Apagar uma área "Trabalho (28)" sem quantificar destrói 28 notas sem o utilizador perceber a magnitude. A quantificação é a salvaguarda proporcional ao dano.
- Para a **nota** (folha, sem filhos), quantificar não acrescenta informação — confirmação simples basta. Evita-se cerimónia desnecessária no caso de 90% das eliminações.

**Edge (transição-já-ocorrida, `internal-state-contract-gate` eixo b):** a contagem é lida **fora** da transacção de delete; entre a leitura e o delete, o nº real pode mudar (ex: brain dump cria nota no `_inbox` da área de sistema — mas a área de sistema não é eliminável, ver D-5.9-SYSTEM-ENTITY-VISIBILITY). Para áreas de utilizador, a janela é o tempo do diálogo modal; o delete é atómico e usa o id, não a contagem — a contagem é **informativa**, nunca um parâmetro do delete. Aceitável: a divergência só afecta o texto mostrado, nunca a correcção do delete. **O `@dev` não deve passar a contagem ao `deleteKnowledgeArea` — só ao texto do diálogo.**

### [D-5.9-SYSTEM-ENTITY-VISIBILITY] — RATIFICADA: Opção A (visíveis, não-elimináveis)

**Decisão:** As entidades de sistema (área "Sistema" `SYSTEM_AREA_ID`, caderno "Caixa de entrada" `INBOX_NOTEBOOK_ID`) são **visíveis** na árvore de Conhecimento, mas **não-elimináveis** (botão eliminar disabled + tooltip) e **não-renomeáveis** (ver C3). Sem filtro em `listKnowledgeAreas`, sem secção separada.

**Justificação traçada ao código:**
- O `_inbox` é o destino real das **ideias soltas** do Brain Dump (bucket `ideias` → `createKnowledgeNote({ notebookId: INBOX_NOTEBOOK_ID })`). _[VERIFICADO: approval-persistencia.ts:184-192]_ A spec §1 (linha 242) confirma: *"ideias soltas → db.knowledge_notes (caderno default `_inbox`)"_. _[VERIFICADO: front-end-spec-v2.md:242]_ Ocultá-lo (Opção B) **esconderia conteúdo real do utilizador** — as ideias capturadas pelo brain dump ficariam inacessíveis na vista de Conhecimento, o que é uma perda de capacidade (viola o princípio "nunca perder capacidade"). Rejeitada.
- A área de sistema é criada **lazy** — só existe depois do 1.º brain dump com ideias. _[VERIFICADO: garantirInbox() em approval-persistencia.ts:101-119, só chamado se `precisaInbox`]_ Num utilizador novo, não existe de todo, logo não polui a árvore. Quando existe, é porque tem conteúdo do utilizador — visível faz sentido.
- Opção C (secção separada "Sistema") adiciona um conceito de UI (duas listas) sem precedente no Nexus e contradiz o wireframe §3.6 (uma única árvore de áreas). Rejeitada por sobre-engenharia. _[JUÍZO ancorado em VERIFICADO §3.6]_

**Fronteira de sistema — cascade delete NUNCA apaga entidades de sistema (verificação obrigatória do spawn):**
- A relação real no código: o `_inbox` (`INBOX_NOTEBOOK_ID`) é **sempre filho da área de sistema** (`SYSTEM_AREA_ID`) — `garantirInbox()` cria a área primeiro e o caderno com `areaId: SYSTEM_AREA_ID`. _[VERIFICADO: approval-persistencia.ts:101-118]_ **Não existe** no código qualquer caminho que crie um caderno de sistema dentro de uma área de utilizador. O cenário hipotético do spawn ("caderno de sistema noutra área de utilizador") **não ocorre** — o `_inbox` está, por construção, dentro da área de sistema.
- Logo, basta o guard `area.id === SYSTEM_AREA_ID` (eliminar área disabled) e `notebook.id === INBOX_NOTEBOOK_ID` (eliminar caderno disabled). Como a área de sistema é não-elimável, o `_inbox` nunca é apanhado por uma cascata de área. **Não há via indirecta** de o apagar. AC6/AC9 cobrem-no.
- **CONDIÇÃO C3 (mover/renomear):** o guard cobre *eliminar*. Mas a spec não prevê *mover* notas entre cadernos nesta story, e a área/caderno de sistema **não devem ser renomeáveis** (o brain dump reencontra-os por id, não por nome — `getKnowledgeNotebook(INBOX_NOTEBOOK_ID)`, logo renomear não quebra o contrato, mas confunde o utilizador). Recomendação: o guard `SystemEntityGuard` desactiva **eliminar E editar** (rename) para entidades de sistema. Editar uma nota *dentro* do `_inbox` é permitido (a nota não é de sistema). Ver ajuste AC5/AC8.

**Contrato de estado multi-camada (`internal-state-contract-gate` — verificação obrigatória do spawn):**

Eixo de risco identificado: a **tag de sistema `decisao`** (`DECISAO_TAG_ID`) é usada por **tarefas** (`createTask({ tags: [DECISAO_TAG_ID] })`) _[VERIFICADO: approval-persistencia.ts:194-209]_ **e** pode ser usada por **notas** (AC14 apresenta-a no picker).
