### Decisões ratificadas pelo Eurico e/ou pelo `@architect` antes do draft

As seguintes decisões foram ratificadas antes do draft e NÃO são reabertas nesta story:

**[DECISÃO-RATIFICADA-1] SDK Telegram = Bot API por `fetch` directo.**
Sem `node-telegram-bot-api`, sem `grammY`, sem `telegraf`. Todas as chamadas à Telegram Bot API (`setWebhook`, `getMe`, `sendMessage`, etc.) são efectuadas via `fetch` nativo para `https://api.telegram.org/bot<token>/<method>`. Justificação: (a) elimina as 2 vulnerabilidades critical do `npm audit` (cadeia `request` via `node-telegram-bot-api` — roadmap §1 P0.1) sem introduzir dependência nova; (b) `fetch` nativo é Edge-safe (ADR-1: `/api/telegram/webhook` corre em Edge — SDKs Node-only não são permitidos em Edge); (c) a Telegram Bot API é um contrato HTTP simples e estável. Verificação: após a 6.11, `npm audit` não deve reportar novos criticals por causa do sub-módulo Telegram.

**[DECISÃO-RATIFICADA-2] Token BotFather NÃO provisionado em Vercel env (ainda).**
O pipeline CI corre com mock MSW (`tests/mocks/handlers/telegram.ts` — stub existente a ser expandido nesta story; ver secção [MSW-TELEGRAM] abaixo). Os AC que dependem de token/chat real ficam marcados como "verificável só em produção após provisionamento" (padrão AC13 da 4.9, P1-Gmail). O provisionamento do `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` e `TELEGRAM_WEBHOOK_SECRET` em Vercel env é **pré-requisito de produção explícito** documentado nesta story — não bloqueia o merge.

### Análise de Ciclo de Vida — `internal-state-contract-gate.md`

A story 6.11 introduz estado distribuído: o token/chatId vivem em Vercel env (server-only); o estado `webhookSet` e `webhookUrl` vivem em KV `nexus:telegram:bot`; o estado real do webhook registado vive em `api.telegram.org`. São 3 camadas.

| Eixo | Pergunta obrigatória | Análise `@sm` (Gate de Entrada — `@architect` ratifica) |
|------|----------------------|-------------------------------|
| **(a) Classes de estado** | Quais as classes de estado do bot? O que cada camada faz a cada classe? | **3 classes:** (1) **Não-configurado** — `TELEGRAM_BOT_TOKEN` ausente ou inválido; KV `nexus:telegram:bot` inexistente ou `webhookSet:false`. O endpoint `/api/telegram/webhook` recusa todos os updates com 401 (não tem `secret_token` para validar). (2) **Configurado/registado** — `TELEGRAM_BOT_TOKEN` válido; `setWebhook` chamado com sucesso; KV `nexus:telegram:bot.webhookSet=true`. O endpoint valida o header `x-telegram-bot-api-secret-token` e responde 200 (stub 6.11) ou roteia (6.12+). (3) **Configurado/desregistado** — token em env mas webhook foi apagado/substituído externamente (ex: Eurico criou outro bot). KV `nexus:telegram:bot.webhookSet=true` mas estado real no Telegram é `deleteWebhook`. Divergência possível. |
| **(b) Transição-já-ocorrida** | O que acontece se `setWebhook` já foi chamado com o mesmo URL? Com URL diferente? Se KV diz `webhookSet:true` mas Telegram não tem webhook activo? | (1) `setWebhook` com mesmo URL → idempotente (Telegram devolve `ok:true`); KV actualiza `webhookSetAt` (timestamp). (2) `setWebhook` com URL diferente (ex: re-deploy) → Telegram substitui silenciosamente; KV actualiza `webhookUrl` + `webhookSetAt`. (3) KV `webhookSet:true` mas webhook não activo no Telegram (ex: token trocado externamente) → `getMe` ou `getWebhookInfo` podem detectar; no MVP a 6.11 não valida proactivamente — o Architect decide se é obrigatório um check de coerência. |
| **(c) Caminhos de falha** | `setWebhook` com token inválido; `secret_token` errado no header do webhook; `TELEGRAM_BOT_TOKEN` ausente em env; webhook recebe request sem header `x-telegram-bot-api-secret-token` | (1) Token inválido → `getMe` devolve `{ok:false, description:"Not Found"}` → setup aborta com erro descritivo PT-PT, KV não é actualizado. (2) Header `x-telegram-bot-api-secret-token` ausente ou errado no webhook → 401 imediato (arch §9.5). (3) `TELEGRAM_BOT_TOKEN` ausente em env → o helper `bot-api.ts` não consegue construir a URL; abortar com `BotApiTokenMissingError` antes de qualquer `fetch`. (4) `setWebhook` devolve `{ok:true, result:false}` (Telegram não actualizou) → erro descritivo, KV não actualizado. |

## User Story

Como Eurico (utilizador do Nexus), quero configurar o bot Telegram (token BotFather em Vercel env, webhook registado em `api.telegram.org` com `secret_token`) e ter um endpoint `/api/telegram/webhook` Edge que rejeite imediatamente requests inautênticos, para que o sub-módulo Telegram fique pronto a receber e processar updates nas stories 6.12+.

## Acceptance Criteria

> Trace: FR69 + FR70 (PRD §6.13). AC epic-level: AC4 (bot Telegram responde a "olá" em < 3s) é da 6.12/6.13 — deferido. Cada AC abaixo é traçado a FR e ao AC de epic onde aplicável.

### AC1 — Helper Bot API por `fetch` (FR69)

O módulo `lib/telegram/bot-api.ts` expõe pelo menos as funções `callBotApi<T>(method: string, params?: Record<string, unknown>): Promise<T>` (helper genérico), `getMe(): Promise<TelegramUser>` e `setWebhook(url: string, secretToken: string): Promise<void>`. Todas as chamadas são via `fetch` nativo para `https://api.telegram.org/bot${token}/<method>` — sem SDK Node (`node-telegram-bot-api`, `grammY`, `telegraf` não entram). O helper é Edge-safe (só `fetch`, sem Node APIs). [DECISÃO-RATIFICADA-1]

**Verificabilidade:** CI mock MSW (handler `telegram.ts` actualizado para `getMe`/`setWebhook` com shape real `{ok:true, result:{...}}` — ver AC6). Produção deferida (P1).

### AC2 — `getMe` valida token antes de `setWebhook` (FR69)

A lógica de setup (script npm `setup:telegram` ou route Node, conforme D-6.11-SETUP-SCRIPT) chama `getMe` primeiro e aborta com erro descritivo PT-PT se o token for inválido (`{ok:false}` da Bot API) — sem prosseguir para `setWebhook`. Se `getMe` devolver `{ok:true, result:{username:...}}` o setup regista no log o nome do bot e prossegue.

**Verificabilidade:** CI mock MSW (handler que devolve `{ok:false, description:"Not Found"}` para token inválido + `{ok:true, result:{id:123, username:"nexus_test_bot",...}}` para token válido). Produção deferida (P1).

### AC3 — `setWebhook` regista o webhook com `secret_token` e persiste em KV (FR69)

`setWebhook(webhookUrl, TELEGRAM_WEBHOOK_SECRET)` chama `POST https://api.telegram.org/bot<token>/setWebhook` com body `{ url: webhookUrl, secret_token: TELEGRAM_WEBHOOK_SECRET, allowed_updates: ["message"] }`. Se `{ok:true}`, persiste em KV `nexus:telegram:bot → { token: tokenShape, chatId: TELEGRAM_CHAT_ID, webhookSet: true, webhookUrl: webhookUrl, webhookSetAt: ISO8601 }` (schema conforme D-6.11-KV-SCHEMA ratificado por `@architect`). Se `{ok:false}` ou erro de rede, KV não é actualizado e a função lança erro descritivo.

**Verificabilidade:** CI mock MSW (handler `setWebhook` devolve `{ok:true, result:true}`) + Vitest que verifica o KV mock é escrito com o schema correcto. Produção deferida (P1+P3+P4).

### AC4 — Endpoint `/api/telegram/webhook` Edge valida `secret_token` e rejeita requests inválidos (FR70; relacionado com AC epic AC4 indirecto)

`app/api/telegram/webhook/route.ts` tem `export const runtime = 'edge'`. Qualquer request **sem** o header `x-telegram-bot-api-secret-token` ou com valor diferente de `process.env.TELEGRAM_WEBHOOK_SECRET` recebe imediatamente `Response('forbidden', { status: 403 })` — sem processar o body (conforme arch §9.5). **Status fixado em 403 por [D-6.11-401-VS-403]** (ratificado no Gate de Entrada — vinculativo, sem oscilação). Adicionalmente, **fail-closed explícito** (C2 CRÍTICA): se `TELEGRAM_WEBHOOK_SECRET` estiver ausente/vazio em env, o webhook devolve 403 incondicional ANTES de comparar headers — nunca aceitar sem segredo configurado (anti-padrão M4 da 4.9).

**Verificabilidade:** CI Vitest (mock da env var `TELEGRAM_WEBHOOK_SECRET` presente) — teste com header ausente → 403, header errado → 403, header correcto → 200 (stub).

### AC5 — Endpoint responde 200 a updates válidos autenticados (stub para 6.12) (FR70)

Após validar o `secret_token`, o endpoint devolve `Response(JSON.stringify({ok:true}), { status: 200, headers: {'Content-Type':'application/json'} })` sem parsear o body do update. O parse completo de texto/voz/foto e o fan-out são da story 6.12. O body não é lido na 6.11 (stub mínimo — apenas 200 OK para que o Telegram não re-tente).

**Verificabilidade:** CI Vitest (request com header correcto + body qualquer → 200 `{ok:true}`).

### AC6 — Mock MSW Telegram reflecte o shape real da Bot API (FR69/FR70; `mock-protocol-fidelity.md`)

O handler `tests/mocks/handlers/telegram.ts` é expandido com handlers para `getMe` e `setWebhook` que reflectem o shape real das respostas da Telegram Bot API:
- `getMe` → `{ ok: true, result: { id: 7654321, is_bot: true, first_name: "Nexus Test Bot", username: "nexus_test_bot", can_join_groups: true, can_read_all_group_messages: false, supports_inline_queries: false } }`
- `setWebhook` → `{ ok: true, result: true, description: "Webhook was set" }`
- Caso token inválido (query param ou header de teste) → `{ ok: false, error_code: 401, description: "Unauthorized" }` (o `description` REAL da Bot API para token inválido é `"Unauthorized"`; `"Not Found"` é para um método inexistente — C5/D-6.11-GET-ME)

Existe ≥1 teste Vitest que falharia se o shape divergisse do protocolo real (ex: `result` ausente num `getMe` válido). [Trace: `mock-protocol-fidelity.md` (A1 Epic 1)]

**Verificabilidade:** CI Vitest (testes incluem asserção de shape estrita com Zod ou `.toMatchObject` exaustivo).

### AC7 — `npm audit` não reporta NOVOS criticals introduzidos pela 6.11 (FR69; Risco R3)

**REFORMULADO por [D-6.11-AUDIT-REMOVE] (achado decisivo do Architect Gate) + CR Iter 2 (#2, realismo do alvo).** Após a implementação, a 6.11 **não introduz nenhum critical novo** e **elimina as 2 criticals da cadeia `node-telegram-bot-api`/`request`** (via remoção da dependência). Concretamente, `npm audit --audit-level=critical` no directório `v2/` passa de **5 → 3 criticals**:
- As **2 criticals da cadeia `node-telegram-bot-api`** (`form-data` + `request`) são ELIMINADAS. Estas criticals NÃO desaparecem só por usar `fetch` — a dependência continua DECLARADA em `package.json` e o `npm audit` analisa a árvore de dependências, não os imports do código. Portanto a 6.11 DEVE **REMOVER** `node-telegram-bot-api` (e `@types/node-telegram-bot-api` se existir) do `package.json` + actualizar o lockfile. A 6.11 não adiciona nenhuma dependência Telegram nova (usa `fetch` nativo).
- As **3 criticals remanescentes** são devDeps do `vitest` (`@vitest/coverage-v8`, `@vitest/ui`, `vitest`), **pré-existentes e fora do scope da 6.11** (não-runtime; não chegam a produção). Um alvo de "0 criticals absoluto" seria insatisfazível nesta story porque estas 3 não pertencem ao sub-módulo Telegram. Ficam registadas como dívida fora-scope.

**Verificabilidade:** evidência local ANTES (5 criticals, das quais 2 da cadeia `node-telegram-bot-api`) e DEPOIS (3 criticals, todas devDeps vitest) anexada ao Change Log. `package.json` é path bloqueador (`not-tested-trailer-rules.md`) → `Not-tested:` NÃO é waiver válido; exige a evidência de `npm audit` real. Falsificável: se a dependência `node-telegram-bot-api` permanecer, as 2 criticals dela persistem (5 no total) e o AC falha. [C7]

### AC8 — Estilo KV: sem `kv.keys()`/`scan` (padrão D-KV-HASH)

A lógica de KV para `nexus:telegram:bot` usa `kv.get()`/`kv.set()` directamente sobre a chave conhecida — jamais `kv.keys()` ou `kv.scan()`. [Trace: D-KV-HASH, precedente 6.9]

### Padrão do helper Bot API (`lib/telegram/bot-api.ts`)

O padrão segue `lib/google/gmail.ts` e `lib/google/calendar.ts` — helper puro, sem imports de framework Next.js, Edge-safe, testável em isolamento com MSW.

**Diferença crítica vs helpers Google:** os helpers Google usam `googleapis` SDK (Node-only, `lib/google/*.ts` correm Node). O helper Telegram usa `fetch` nativo — Edge-safe, sem dependência Node. Consequência: `lib/telegram/bot-api.ts` pode ser importado pelo Edge webhook sem violar ADR-1. [DECISÃO-RATIFICADA-1]

**Convenção de chamada Bot API:**
```ts
// URL pattern Telegram Bot API
const BASE_URL = `https://api.telegram.org/bot${process.env.TELEGRAM_BOT_TOKEN}`;

async function callBotApi<T>(method: string, params?: Record<string, unknown>): Promise<T> {
  if (!process.env.TELEGRAM_BOT_TOKEN) throw new BotApiTokenMissingError();
  const resp = await fetch(`${BASE_URL}/${method}`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: params ? JSON.stringify(params) : undefined,
  });
  const data = await resp.json() as { ok: boolean; result?: T; description?: string };
  if (!data.ok) throw new BotApiError(method, data.description ?? 'Unknown error');
  return data.result as T;
}
```

### Decisões ratificadas — D-6.11-*

**[D-6.11-401-VS-403]** (resolve [GAP-6.4b]) — **403 Forbidden** (NÃO 401). Ratifico o que a arch §9.5 já usa.
Justificação: 401 Unauthorized implica semanticamente um desafio de autenticação (`WWW-Authenticate`) e convida o cliente a re-tentar com credenciais — o que NÃO se aplica ao Telegram (o `secret_token` é um segredo fixo partilhado, não uma credencial negociável; um chamador sem o segredo é um intruso, não um cliente por autenticar). 403 ("conheço o pedido, recuso-o") é a semântica correcta para "origem não reconhecida, sem caminho de remediação para o chamador". Acresce coerência: a arch §9.5 (snippet canónico l.838-842) já especifica 403, e a Telegram não re-tenta com base no status de erro de um webhook não-2xx da mesma forma para 401 vs 403 — qualquer não-2xx provoca re-tentativa. **Decisão vinculativa: o `@dev` usa 403 e NÃO oscila.** Reconciliar AC4 e T4.2 para fixar 403 (remover a frase "ou 401" e a indecisão).

**[D-6.11-TIMING-SAFE]** (sub-decisão de segurança do webhook) — comparação do `secret_token` **NÃO precisa de ser timing-safe** nesta story, com justificação registada.
Justificação: (a) o Edge runtime **não** dispõe de `crypto.timingSafeEqual` de `node:crypto` (Node-only) — usá-lo violaria a Edge-safety, que é o pilar de toda a 6.11; (b) o vector de timing attack sobre um segredo de ≥32 chars de alta entropia, sobre a rede pública com jitter de latência muito superior à diferença de timing de uma comparação de strings, é **impraticável** (o sinal afoga-se no ruído de rede); (c) o `secret_token` Telegram é um segredo simétrico longo e aleatório, não um MAC derivado de input do atacante. A comparação `!==` directa de strings é aceitável e é o que a arch §9.5 mostra. NOTA: isto contrasta deliberadamente com o `CRON_SECRET` (que usa `secretsMatch` timing-safe em `lib/push/cron-auth.ts`) — aí o handler corre em **Node**, onde `timingSafeEqual` está disponível sem custo de portabilidade. Débito opcional REC-6.11-TIMING: se a Web Crypto (`crypto.subtle`) for adoptada noutra story Edge, considerar uma comparação de tempo-constante via subtle; não obrigatório aqui.

**[D-6.11-SETUP-SPLIT]** (resolve D-6.11-SETUP-SCRIPT + Edge-safety C) — **split runtime obrigatório**: o **setup corre em Node**, o **webhook receiver corre em Edge**.
A invocação do setup é a **candidata (b): route Node protegida** `POST /api/google/... ` — NÃO; corrijo: `POST /api/telegram/setup/route.ts` com `export const runtime = 'nodejs'` e auth `getSession` (padrão de `validate-token/route.ts:11,18-21` e `gmail/classify/route.ts:59-85`). Razões para Node no setup: (i) o setup persiste em KV e chama a Bot API por `fetch` — ambos Edge-safe — MAS (ii) é uma operação one-time interactiva, sem orçamento de latência crítico, e a coerência com TODAS as outras routes de setup/admin do repo (`/api/google/oauth/*`, `validate-token`) é Node; (iii) reutiliza `getSession` directamente, o padrão de auth de admin já estabelecido. O `npm run setup:telegram` (arch §13 l.1145) é **rejeitado como superfície primária** porque um script `tsx` fora do runtime Vercel não tem acesso garantido às env vars de produção nem ao KV de produção da mesma forma que uma route deployada — a route é mais fiável e ergonómica (invocável da UI definições, padrão `POST /api/google/oauth/start`). Se o `@dev` quiser MANTER também o script npm como conveniência local, é aceitável como wrapper fino que faz `fetch` à própria route — mas a **fonte de verdade do setup é a route Node**. O webhook receiver (`app/api/telegram/webhook/route.ts`) é **Edge** (`export const runtime = 'edge'`, ADR-1/arch §4.1 l.194). Não há `node:crypto`, `googleapis` nem qualquer API Node-only no webhook — só leitura de header + comparação de string + `Response`.

**[D-6.11-WEBHOOK-STUB]** — **candidata (a): stub 200 puro, sem parsear o body**. Ratifico.
Após validar o `secret_token`, o webhook devolve `Response(JSON.stringify({ok:true}), {status:200, headers:{'Content-Type':'application/json'}})` SEM ler nem parsear o body. O parse do `update_id`, do tipo de mensagem (texto/voz/foto), o fan-out e o filtro de `chatId` são da 6.12. Parsear o `update_id` na 6.11 (candidata b) seria invadir o âmbito da 6.12 sem benefício: um `update_id` válido não acrescenta segurança (a autenticação é o `secret_token`) e cria acoplamento ao schema de update que a 6.12 vai definir. **A 6.11 é setup + porteiro de origem; a 6.12 é o handler.** Corte limpo (resolve ponto D do gate).

**[D-6.11-KV-SCHEMA]** — schema ratificado, com o token NUNCA em claro em KV.
```ts
interface TelegramBotKvRecord {
  tokenHint: string;     // ÚLTIMOS 4 chars do token, só para debug. NUNCA o token completo.
  chatId: string;        // TELEGRAM_CHAT_ID (não-sensível; é o destino, não credencial)
  webhookSet: boolean;
  webhookUrl: string;
  webhookSetAt: string;  // ISO 8601
}
const KV_KEY = 'nexus:telegram:bot'; // arch §6 — nome exacto, prefixo nexus: (ADR-6)
```
Ratifico o campo extra `webhookUrl` + `webhookSetAt` proposto pelo `@sm` (necessários para a análise de coerência do eixo b — saber QUE url está registado e QUANDO). **Renomeio `token` → `tokenHint`** para tornar inequívoco no código que NÃO é o token completo (a nota de segurança do `@sm` é correcta: o token vive em env server-only; duplicá-lo em KV aumenta a superfície de exposição e contradiz NFR6/R1). O `secret_token` NÃO entra em KV (é env var — não duplicar; guardar um hash do segredo em KV não traz valor porque a validação do webhook compara contra `process.env.TELEGRAM_WEBHOOK_SECRET` directamente, não contra KV). A arch §6 (l.598) lista `{ token, chatId, webhookSet }` — esta story EXPANDE esse schema; débito documental REC-6.11-ARCH-SCHEMA: actualizar arch §6 para reflectir `tokenHint`/`webhookUrl`/`webhookSetAt` (não-bloqueante; a story é a fonte de verdade até lá).

**[D-6.11-GET-ME]** — **candidata (a): `getMe` PRIMEIRO, abortar se `{ok:false}`**. Ratifico.
O setup chama `getMe()` para validar o token antes de `setWebhook`. Se `{ok:false}` (token inválido — Bot API devolve `{ok:false, error_code:401, description:"Unauthorized"}`), aborta com erro descritivo PT-PT e **NÃO escreve KV**. Razão: mensagem de erro clara ao Eurico ("token BotFather inválido") em vez de uma falha opaca de `setWebhook`; e o `getMe` é o ponto canónico de validação de token da Bot API. Custo: 1 chamada HTTP extra no setup one-time — irrelevante. NOTA de fidelidade de protocolo: o `description` real da Bot API para token inválido é `"Unauthorized"` (não `"Not Found"` — `"Not Found"` é o que se obtém para um *método* inexistente, não para token inválido). O AC6/AC2/T5.1 da story usam `description:"Not Found"` — **corrigir para `"Unauthorized"`** no handler MSW de token inválido (ver C5). É um detalhe de `mock-protocol-fidelity.md`: o mock deve espelhar o protocolo REAL.

**[D-6.11-IDEMPOTENCIA]** — confirmada: `setWebhook` é idempotente por design na Bot API.
`setWebhook` com o mesmo URL devolve `{ok:true, result:true, description:"Webhook is already set"}` ou `"Webhook was set"`; com URL diferente, substitui silenciosamente o anterior (o Telegram só mantém UM webhook por bot). A lógica de setup é idempotente por design: re-registar = actualizar `webhookUrl`+`webhookSetAt` em KV; nenhum erro se já registado. **Não é obrigatório** um check proactivo `getWebhookInfo` de coerência no MVP da 6.11 (ver eixo b da análise abaixo para a divergência KV↔Telegram e porque é aceitável diferir) — mas registo como débito REC-6.11-COHERENCE.

**[D-6.11-CHATID]** (resolve ponto F do gate, Risco R2) — o filtro por `chatId` do Eurico é da **6.12, NÃO da 6.11**.
Justificação de fronteira: o filtro `update.message.chat.id === TELEGRAM_CHAT_ID` exige **parsear o body do update** — exactamente o que [D-6.11-WEBHOOK-STUB] difere para a 6.12. Na 6.11 o webhook ainda não lê o body. A defesa de origem na 6.11 é o `secret_token` (que já impede que terceiros sem o segredo cheguem ao endpoint — e o segredo só é conhecido pelo Telegram e pelo Nexus). O `chatId` é uma **segunda camada** (defesa em profundidade: garante que mesmo um update legítimo do Telegram, mas de OUTRO chat que não o do Eurico, é descartado) e pertence naturalmente à camada de parse (6.12). **Condição de continuidade:** a 6.12 DEVE implementar o filtro `chatId` (registar como pré-requisito explícito da 6.12 — ver C8). Rate limiting Edge (§9.3) — **diferido**: o `middleware.ts` actual (corre em Edge) NÃO implementa o rate limiting por KV descrito em §9.3 (é um GAP arch-vs-código pré-existente, não introduzido pela 6.11). O `secret_token` já corta o grosso do tráfego inautêntico no webhook antes de qualquer processamento. Diferir o rate limiting para a 6.12/Epic 8 (hardening) é coerente; registar débito REC-6.11-RATELIMIT.

**[D-6.11-AUDIT-REMOVE]** (achado decisivo — reforça AC7) — para eliminar as 2 criticals, a dependência `node-telegram-bot-api` tem de ser **REMOVIDA do `package.json`**, não apenas não-usada.
Achado: `package.json:39` ainda declara `"node-telegram-bot-api": "^0.66.0"`. As 2 criticals (`npm audit`, cadeia `request`) vêm desta dependência DECLARADA — `npm audit` analisa a árvore de dependências do `package.json`/lockfile, não o que o código importa. Usar `fetch` em vez do SDK NÃO remove as criticals enquanto a entrada existir no `package.json`. **A 6.11 DEVE remover `node-telegram-bot-api` (e quaisquer `@types/node-telegram-bot-api`) do `package.json` + actualizar o lockfile.** Verificar por `grep` que nenhum ficheiro a importa antes de remover (é stub vazio hoje, risco nulo). ### Análise de Ciclo de Vida do estado distribuído — `internal-state-contract-gate.md` (3 eixos, contra o código real)

Estado distribuído por **3 camadas**: (1) env server-only (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_WEBHOOK_SECRET`); (2) KV `nexus:telegram:bot` (`webhookSet`/`webhookUrl`/`webhookSetAt`/`tokenHint`); (3) estado real do webhook registado em `api.telegram.org`. É o padrão "callback/registo externo ↔ store ↔ config" que a regra marca como alvo principal do Epic 6.

**(a) Classes de estado** — quais as classes e o que cada camada faz a cada uma:
- **Não-configurado:** `TELEGRAM_BOT_TOKEN` ausente/inválido em env; KV inexistente ou `webhookSet:false`; Telegram sem webhook. → O helper `callBotApi` lança `BotApiTokenMissingError` ANTES de qualquer `fetch` se o token estiver ausente (eixo c). O webhook Edge, se `TELEGRAM_WEBHOOK_SECRET` ausente em env, **tem de FALHAR-FECHADO** (rejeitar TODOS os requests com 403 — nunca aceitar sem segredo configurado; ver eixo c ponto 3). Isto é a classe mais perigosa: um webhook que aceita sem segredo é o anti-padrão M4 da 4.9 (tratar ausência como permissão).
- **Configurado/registado:** token válido; `setWebhook` OK; KV `webhookSet:true`+`webhookUrl`+`webhookSetAt`; Telegram com webhook activo. → Webhook valida `x-telegram-bot-api-secret-token` e responde 200 stub (6.11) / roteia (6.12).
- **Configurado/desregistado (divergência):** token em env, KV `webhookSet:true`, MAS o webhook real foi apagado/substituído externamente (ex: Eurico criou outro bot, ou outra deployment fez `setWebhook` com outro URL). → KV mente face ao Telegram. No MVP da 6.11 esta divergência **não é detectada proactivamente** (aceitável — ver eixo b). A consequência é benigna: o Nexus deixa de receber updates (não há corrupção de dados, não há silent loss de uma ACÇÃO do utilizador — o utilizador percebe que o bot "não responde" e re-corre o setup). Difere de um silent loss de estado de aplicação.

**(b) Transição-já-ocorrida** — o que acontece quando a transição já ocorreu entre camadas:
- **`setWebhook` com o MESMO URL (re-registo):** idempotente. Telegram devolve `{ok:true}`; KV actualiza `webhookSetAt` (e `webhookUrl` igual). Sem erro, sem duplicação — o Telegram mantém UM só webhook por bot ([D-6.11-IDEMPOTENCIA]). **Condição C6:** o teste de idempotência (T3.3) tem de provar que invocar o setup 2× não lança e que o KV fica coerente (mesmo `webhookUrl`, `webhookSetAt` actualizado).
- **`setWebhook` com URL DIFERENTE (re-deploy):** Telegram substitui silenciosamente o webhook anterior; KV actualiza `webhookUrl`+`webhookSetAt`. Coerente.
- **KV diz `webhookSet:true` mas Telegram não tem webhook (divergência da classe c):** detectável por `getWebhookInfo` se chamado; o MVP da 6.11 NÃO valida proactivamente. **Ratifico que diferir é aceitável** porque: (i) é single-user, baixa frequência de re-config; (ii) a recuperação é trivial (re-correr setup, que é idempotente); (iii) não há perda de dados nem acção do utilizador silenciosamente engolida (contraste com M1/M2 da 4.9). A ordem de escrita do setup tem de ser **Telegram PRIMEIRO, KV DEPOIS** (escrever KV só após `{ok:true}` confirmado do `setWebhook`) — assim o KV nunca afirma `webhookSet:true` sem o Telegram ter realmente aceitado. **Condição C3** cobre isto. Débito REC-6.11-COHERENCE (check `getWebhookInfo` opcional numa story futura de observabilidade).

**(c) Caminhos de falha** — erros entre camadas tratados como falha (nunca sucesso silencioso):
1. **`getMe` com token inválido** → Bot API `{ok:false, error_code:401, description:"Unauthorized"}` → `callBotApi` lança `BotApiError`; o setup aborta com mensagem PT-PT clara; **KV NÃO é escrito** ([D-6.11-GET-ME]).
2. **`setWebhook` devolve `{ok:false}` ou `{ok:true, result:false}`** (Telegram não actualizou) → o helper `setWebhook` lança erro descritivo; **KV NÃO é escrito** (a escrita só ocorre após `result===true` confirmado). Anti-padrão a evitar: escrever KV `webhookSet:true` quando `result:false`.
3. **Webhook recebe request mas `TELEGRAM_WEBHOOK_SECRET` ausente em env (fail-closed):** se `process.env.TELEGRAM_WEBHOOK_SECRET` for `undefined`, a comparação `secretHeader !== undefined` é `true` para QUALQUER header não-undefined — MAS um atacante pode enviar SEM header (header = `null`), e `null !== undefined` é `true` → 403. PERIGO SUBTIL: se o atacante enviar header vazio e o segredo for `undefined`... `"" !== undefined` = `true` → 403. Parece seguro por acidente, mas é **frágil**. **Condição C2 (CRÍTICA):** o webhook tem de verificar EXPLICITAMENTE que `TELEGRAM_WEBHOOK_SECRET` está presente e não-vazio ANTES de comparar; se ausente → 403 incondicional (fail-closed explícito, nunca depender da coincidência `x !== undefined`). NUNCA aceitar um request quando o segredo não está configurado. Este é exactamente o ponto cego que `internal-state-contract-gate.md` existe para apanhar (a regra nasceu do M4 da 4.9: tratar ausência/erro como sucesso).
4. **Erro de rede no `fetch` (Telegram indisponível a meio):** `callBotApi` propaga a rejeição do `fetch`; o setup aborta; **KV NÃO é escrito**. Estado anterior preservado.
5. **`TELEGRAM_BOT_TOKEN` ausente em env durante o setup:** `BotApiTokenMissingError` antes de qualquer `fetch` (eixo a). Mensagem clara.
