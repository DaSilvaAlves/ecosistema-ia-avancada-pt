## Story

**As a** utilizador do Nexus v2 numa ligação instável ou sem rede,
**I want** que a app me diga honestamente quando está sem rede — um indicador visível sempre que offline, o dashboard/páginas a continuarem a mostrar os meus dados locais sem esperar pela rede, e o chat a recusar-se claramente a fingir que enviou uma mensagem que não chegou a lado nenhum,
**so that** eu confie no que a app mostra mesmo sem ligação, sem nunca ser enganado por um "sucesso" que na realidade é uma mensagem perdida (NFR21, R5 de `EPIC-9.md`, continuação directa do princípio D-SNOOZE-CONTRACT/M4 da Story 4.9).

## Acceptance Criteria

**AC1 — Hook `useOnlineStatus`**

Cria `hooks/useOnlineStatus.ts`: hook `'use client'` que devolve `boolean` (`true` = online, `false` = offline). Estado inicial SSR-safe (`typeof navigator === 'undefined' ? true : navigator.onLine` — assume online até o browser confirmar o contrário, mesmo padrão de guarda usado em `useLocalStorage.ts` para `typeof window`). Regista listeners `window.addEventListener('online', ...)` e `('offline', ...)` no mount, remove-os na cleanup do `useEffect`. Fonte única de verdade para qualquer componente que precise de saber se a app está online — reutilizado pelo `Header` (AC2) e pelo `OfflineBanner` (AC3).

**AC3 — `OfflineBanner`: banner "sem rede" com estados de render**

Montado em `Header.tsx` (mesmo padrão de cobertura app-wide do AC2 — um único ponto de montagem cobre as 10 páginas), **imediatamente a seguir ao `</header>`** (irmão, não filho, para não interferir com o `position: sticky` do header).

**AC6 — Chat: mensagem honesta e específica de "sem rede" (distinta de outros erros)**

`hooks/useAgentStream.ts`, função `networkErrorMessage(e)` (L76-81): estende para distinguir a classe de sinal (2) do contrato da 9.3 — quando `e instanceof TypeError` (o sinal nativo de falha de rede do `fetch`, emitido para o POST não-GET a `/api/anthropic/proxy` conforme o contrato ratificado no Architect Gate da 9.3), devolve uma mensagem específica e honesta: **"Sem rede — a tua mensagem não foi enviada. Tenta novamente quando a ligação voltar."** — distinta da mensagem genérica actual ("Erro de rede: {message}") que se mantém para outros tipos de erro (falhas de parsing, erros do proxy reportados como `Error` não-`TypeError` via `proxyErrorMessage`). O `stream.error` continua a ser renderizado pelo `ChatPanel.tsx` (L319-335, inalterado) — só a *função* de formatação da mensagem muda, não o mecanismo de exibição. Nenhuma run é marcada como sucesso quando isto acontece (comportamento já correcto, preservado — ver Inventário).

[Trace: Inventário `@sm` — "chat já falha honestamente hoje" + "o chat é sempre não-GET"; `EPIC-9.md` Risco R5 "offline finge sucesso — anti-padrão M4 da 4.9"; `docs/stories/completed/9.3.story.md` C1 "contrato de dois sinais"]

**AC7 — Sinal `503 {offline:true}` (GET): tratamento defensivo, sem consumidor actual**

Como nenhum GET client-side a `/api/*` existe hoje (Inventário — grep exaustivo confirma), esta story **não cria um novo consumidor artificial** para este sinal (evitaria inventar uso — Constitution Artigo IV). Regista-se em Dev Notes, para consumo futuro: qualquer código cliente que venha a fazer `fetch` GET a `/api/*` deve tratar `res.status === 503 && (await res.clone().json()).offline === true` como sinal de "sem rede" (discriminado pelo corpo, não só pelo status — um 503 real do servidor é uma classe diferente, conforme AC10 eixo (a) já ratificado pela 9.3), e não como erro genérico. Este AC é de **documentação/contrato**, não de código novo — `@architect` confirma no gate que nenhum consumidor GET foi omitido por engano.

[Trace: `docs/stories/completed/9.3.story.md` AC2/AC10; Inventário `@sm` — "Não existem consumidores GET a /api/* no client hoje"]

**AC8 — Navegação offline (app-shell): fora de âmbito, delimitação explícita [D-9.5-NO-APP-SHELL]**

**[AUTO-DECISION D-9.5-NO-APP-SHELL]**: esta story **não** implementa precache do app-shell nem uma página de fallback de navegação (`navigation-fallback`/`offline.html`) para [D-9.3-NO-PRECACHE] (a decisão da 9.3 de não pré-cachear assets hashed). Razão: (a) o layout autenticado (`app/(app)/layout.tsx`) faz `await cookies()` + `redirect('/login')` server-side em **cada** navegação — não existe um "shell" estático seguro para pré-cachear sem risco de servir uma página autenticada desactualizada a um utilizador cuja sessão expirou entretanto; (b) uma página de fallback offline exigiria conteúdo/design novo não especificado no PRD/arch (risco de invenção, Constitution Artigo IV); (c) o âmbito NFR21 é "modo offline **degradado**" para uma sessão **já carregada** que perde rede a meio — não "app instalável que arranca a frio sem rede nenhuma alguma vez" (essa ambição pertenceria a uma decisão de arquitectura maior, fora do PRD §10 Epic 9). **Consequência prática:** se o utilizador recarregar a página (F5) ou abrir a app pela primeira vez estando completamente offline, a navegação falha normalmente (comportamento actual do browser, inalterado) — o modo degradado desta story cobre apenas o caso "app já aberta, rede cai a meio da sessão" (banner + Header + dashboard local + chat honesto, AC1-AC7). Esta é uma decisão a **ratificar ou reverter** pelo `@architect` no gate — não bloqueia o arranque da implementação.
