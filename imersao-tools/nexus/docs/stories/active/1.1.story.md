## User Story

Como `@dev` (Dex), quero um data access layer tipado para `agent_runs` e `chat_messages` com helpers, validação Zod e hooks reactivos, para que as Stories 1.2-1.10 do Epic 1 possam persistir/ler audit logs sem duplicar lógica de acesso a Dexie nem cair em invariantes inconsistentes (ex: AgentRun sem `toolCalls` array, ChatMessage sem `conversationId`).

## Contexto

PRD §10 Epic 1 define `agent_runs` como **fonte canónica de auditoria** de cada execução do cérebro multi-intent (FR48 — audit log). Cada execução do cérebro persiste um `AgentRun` com status, tool calls, tokens consumidos. Story 1.7 (Undo) lê os runs recentes (≤30s) para permitir reverter. Story 1.9 (UI) renderiza cards baseados em runs.

`chat_messages` é fonte canónica do histórico de conversas (one conversation = `conversationId='main'` no MVP single-user). Cada mensagem do utilizador, cada resposta do executor e cada tool result são `ChatMessage` distintos.

Schema actual (Story 0.3 Done):
- `agent_runs: 'id, timestamp, [timestamp+status]'` — index composto permite filtrar por janela temporal + status
- `chat_messages: 'id, conversationId, timestamp, [conversationId+timestamp]'` — index composto permite scroll cronológico por conversation

Interfaces TypeScript já existentes em `types/db.ts` (Story 0.3) — confirmar que estão completas conforme arch §6.1.

## Dev Notes

- **Schema NÃO muda nesta story:** Story 0.3 já criou as tabelas correctas. Não incrementar `this.version()` em `client.ts`. Se descobrires query lenta sem index, abrir issue separado. Coverage threshold (25%) mantém-se — Story F.1 trata de subir global.

- **Zod schemas vão ser reutilizados pela Story 1.4 (classifier) e 1.5 (executor):** o classifier vai validar JSON do Anthropic Haiku contra `AgentRunSchema['intents']`; o executor vai validar tool args contra schema da tool específica (definido em arch §7.2). Manter `lib/agent/schemas.ts` como fonte canónica.

- **`run-builder.ts` é açúcar sintáctico:** opcional para Stories 1.5-1.7, mas evita boilerplate "lê timestamp antigo, calcula delta, faz update". Implementação 30 linhas. Documentado como "preferred path" em Dev Notes da 1.5.

- **Hooks reactivos `useRecentAgentRuns`:** Story 1.9 (UI cards de acções criadas) e Story 1.7 (toast undo) precisam de auto-refresh quando novo run aparece. `useLiveQuery` da Dexie já dá isto grátis — apenas embrulhar.

- **Anti-invenção:** Esta story NÃO implementa classifier, executor, tool registry, UI, SSE streaming, integração Anthropic. São Stories 1.2-1.9. A tentação de "adiantar" deve ser resistida.

- **Persistência de `messages` (chat real):** Story 0.3 criou `chat_messages` mas até agora nada escreve. Story 1.9 vai começar a escrever. Esta story 1.1 prepara o caminho com helpers tipados — Story 1.9 não precisa de re-inventar.

- **Validação PT-PT em `ZodError`:** Zod permite custom error messages. Para AC4, usar mensagens PT-PT em campos obrigatórios (ex: `z.string().min(1, 'Prompt é obrigatório')`). Não complicar — só onde o utilizador final vai ver o erro (Story 1.6 preview-then-confirm).

- **Convenção de import:** seguir Constitution Article VI — sempre `@/...` absoluto. Excepção: imports dentro de `lib/db/repos/` podem ser relativos entre si.

- **Naming convention:** repos vão para `lib/db/repos/{tabela}.ts` (kebab-case singular sem `s` final). Schemas Zod em `lib/agent/schemas.ts` (singular `schemas` plural OK porque é colecção). Hooks em `hooks/use{Algo}.ts` PascalCase do `Algo`.

### Completion Notes

1. **Fix técnico durante implementação — Dexie compound index `between`:** A primeira versão de `listRecentRuns(opts)` usava `db.agent_runs.where('[timestamp+status]').between([sinceTs, status], [Date.now() + 1, status])` mas o `between` em Dexie 4 só limita o primeiro elemento do array — o status no segundo elemento serve apenas como tiebreaker para timestamps iguais. Resultado: filter por status não funcionava (test "filtra por status via index composto" falhou). Refactorizei para `where('timestamp').aboveOrEqual(sinceTs)` + `.filter((r) => r.status === status)`. Mesma estratégia aplicada em `listConversation` (where simples + filter).

2. **Fix técnico — Zod `z.unknown()` infere campo opcional:** `ToolCall.args: unknown` em `types/db.ts` é obrigatório, mas `z.unknown()` em Zod gera `unknown | undefined` (campo opcional). Isto causou typecheck error (`Property 'args' is optional in type [parsed] but required in type 'ToolCall'`). Solução: validar com `Schema.parse(input)` (lança ZodError se inválido) MAS retornar/persistir o `input` original tipado, em vez do resultado do parse. Mantém validação runtime + tipos correctos compile-time.

3. **Endereçado should-fix #2 da PO Validation:** Criado `tests/unit/hooks/useAgentRuns.test.tsx` (extra, fora do plano original) com 2 casos `renderHook` + insert + `waitFor` confirmando re-render reactivo dos hooks. Crítico para Stories 1.7 (toast undo) e 1.9 (UI cards).

4. **Should-fix #1 (`run-builder.ts` "opcional" no Dev Notes):** Não toquei na secção Dev Notes da story (regra: @dev só edita Dev Agent Record). AC6 garante que é entregável obrigatório, e o ficheiro foi criado e testado.
