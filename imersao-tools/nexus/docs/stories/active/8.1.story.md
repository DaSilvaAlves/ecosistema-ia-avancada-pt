### DESIGN-DECISION D-8.1-FACTORY — Branch por `LLM_PROVIDER` com `OpenAIExecutor`/`OpenAIClassifier` ainda inexistentes

**Pergunta:** A S1 adiciona o branch `openai` na factory, mas o `OpenAIExecutor`/`OpenAIClassifier` só chegam na S2/S3. O que faz o branch `openai` na S1?

**Decisão:** O branch `LLM_PROVIDER === 'openai'` **falha loud com mensagem PT-PT clara de "ainda não implementado (chega em S2/S3)"** — não devolve `null`, não cai silenciosamente para Anthropic. É exactamente o AC do ADR-10 §8 row S1: *"`LLM_PROVIDER=openai` sem impl ainda → fail-loud claro"*.

**Justificação com trace:**
1. ADR-10 §8 row S1 lista o fail-loud do branch `openai` sem impl como AC explícito.
2. Princípio de fail-loud já estabelecido na factory actual (`factory.ts:26-34` — `readApiKey()` lança Error PT-PT se key ausente). A S1 estende o mesmo padrão.
3. Cair silenciosamente para Anthropic quando o operador pediu `openai` mascararia um erro de configuração (anti-silent-loss, padrão `internal-state-contract-gate.md` eixo c). O fail-loud é debugável; o silent-fallback não.
4. Quando a S2/S3 entregam `OpenAIExecutor`/`OpenAIClassifier`, o branch passa de `throw` para `new OpenAIExecutor(...)` — extensão limpa, sem refactor.

**Alternativa rejeitada:** branch `openai` cai para Anthropic com warning. Razão: silent-fallback mascara má configuração; viola o "fail-loud claro" do AC.

### DESIGN-DECISION D-8.1-FLAGS — Duas flags (`LLM_PROVIDER` server-only + `NEXT_PUBLIC_LLM_PROVIDER` público) e asserção de concordância

**Pergunta:** Porquê duas flags? Como evitar o mismatch entre elas?

**Decisão:** Duas flags por necessidade arquitectural (ADR-10 §3.4): `LLM_PROVIDER` é **server-only** (lida na factory/proxy, escolhe o upstream e a impl server-side); `NEXT_PUBLIC_LLM_PROVIDER` é **pública** (o `client-executor.ts` corre no browser e precisa de escolher o transport — S4). A S1 introduz **ambas** e adiciona uma **asserção de concordância no boot do server** (`NEXT_PUBLIC_LLM_PROVIDER === LLM_PROVIDER`), que falha loud em mismatch.

**Justificação com trace:**
1. ADR-10 §3.4: *"O `client-executor.ts` corre no browser, logo a sua selecção de transport precisa de uma flag pública: `NEXT_PUBLIC_LLM_PROVIDER`. O proxy (Edge, server) usa a flag server-only `LLM_PROVIDER` [...] As duas têm de concordar."*
2. ADR-10 §3.4 (mitigação): *"Adicionar uma asserção de arranque (`NEXT_PUBLIC_LLM_PROVIDER === LLM_PROVIDER`) no boot do server é barato e elimina a classe."*
3. Convenção Next.js (verificada em `lib/shared/env.ts:8-10`): variáveis `NEXT_PUBLIC_*` são acessíveis ao client por design; as restantes são server-only. `OPENAI_API_KEY` **NUNCA** é `NEXT_PUBLIC_*` (NFR5 — secret nunca no bundle client). Ver D-8.1-SECRET.
4. A asserção é uma só verificação no boot — não distribui estado por camadas; `internal-state-contract-gate.md` não exige análise de ciclo de vida multi-camada nesta dimensão (a flag é config estática, não estado mutável).

**Alternativa rejeitada:** uma só flag pública partilhada. Razão: tornaria `LLM_PROVIDER` exposto ao client desnecessariamente e não resolve o facto de o proxy (server) e o transport (client) lerem contextos diferentes; a asserção de concordância é a mitigação canónica do ADR.

### DESIGN-DECISION D-8.1-SECRET — `OPENAI_API_KEY` server-only (NFR5)

**Pergunta:** Onde vive a `OPENAI_API_KEY` e como se garante que nunca chega ao bundle client?

**Decisão:** `OPENAI_API_KEY` é validada no **`ServerEnvSchema`** de `lib/shared/env.ts` (server-only, espelhando `ANTHROPIC_API_KEY`), **nunca** com prefixo `NEXT_PUBLIC_`. A leitura na factory é pontual via `process.env.OPENAI_API_KEY` dentro de `readApiKey('openai')` (mesmo padrão Edge-safe da key Anthropic, `factory.ts:26-34`). É opcional em dev/test (resolve só quando `LLM_PROVIDER=openai`), provisionada em prod via Vercel UI.

**Justificação com trace:**
1. NFR5 (citado no prompt de arranque + ADR-10 §5 tabela `lib/shared/env.ts` "validar `OPENAI_API_KEY`"): a key é secret e nunca pode entrar no client bundle.
2. Padrão real verificado: `ANTHROPIC_API_KEY` está em `ServerEnvSchema` (`env.ts:14`), nunca em `PublicEnvSchema` (`env.ts:63-65`). A `OPENAI_API_KEY` segue exactamente o mesmo lugar.
3. `factory.ts:11-13` documenta que a key Anthropic é lida via `process.env.X` directo (não via `getServerEnv()`) "para evitar parse global em Edge runtime — apenas a key é lida pontualmente". A `OPENAI_API_KEY` segue o mesmo padrão Edge-safe em `readApiKey('openai')`.
4. Apenas `NEXT_PUBLIC_LLM_PROVIDER` (o **nome** do provider, não um secret) é público — é seguro expor qual provider está activo.

**Alternativa rejeitada:** `OPENAI_API_KEY` lida via `getServerEnv()` no caminho quente. Razão: `getServerEnv()` faz parse global de todo o schema; o padrão estabelecido na factory é leitura pontual da key para compatibilidade Edge (`factory.ts:11-13`).

A camada de inferência já isola o provider atrás de `ClassifierProvider`/`ExecutorProvider` (`lib/agent/providers/types.ts`). A factory (`factory.ts`) é hoje **hard-coded Anthropic**. A migração é uma **adição de implementações** atrás das mesmas interfaces — não um refactor do executor.

```text
ClassifierProvider / ExecutorProvider   (lib/agent/providers/types.ts — INTERFACES, não tocar)

            factory.ts getClassifier()/getExecutor()
                  │  hoje: hard-coded new AnthropicClassifier/Executor(apiKey)
```

## Acceptance Criteria

> Traçados directamente ao **ADR-10 §8 row S1** (âmbito + AC) + §3.2/§3.4 (factory + flags) + §4.2 (`toolsToOpenAIShape`) + §4.5 (defaults) + §7.1 (nomes ≤64) + NFR5 (secret server-only). Wording preservado do ADR; nenhum AC inventado.

**AC1 (Feature flag `LLM_PROVIDER` resolve o provider; default `anthropic`)** — `lib/shared/env.ts` valida `LLM_PROVIDER` como enum `'anthropic' | 'openai'` com **default `'anthropic'`** quando ausente. O valor é lido pela factory para escolher a implementação. Sem a flag definida, o comportamento é idêntico ao de hoje (retrocompatibilidade total).

Trace: ADR-10 §1.2.1 + §3.2 ("`process.env.LLM_PROVIDER` (default `anthropic`)") + §8 row S1.

**AC2 (Factory devolve a impl certa por `LLM_PROVIDER`)** — `getClassifier()` e `getExecutor()` em `factory.ts` passam a fazer branch por `LLM_PROVIDER`:
- `'anthropic'` (default) → `new AnthropicClassifier/Executor(apiKey)` — **byte-a-byte o comportamento actual**;
- `'openai'` → como `OpenAIClassifier`/`OpenAIExecutor` ainda **não existem** (S2/S3), o branch **falha loud** com mensagem PT-PT clara de "provider OpenAI ainda não implementado (chega em S2/S3)" — **não** cai silenciosamente para Anthropic.

Trace: ADR-10 §3.2 + §8 row S1 ("`LLM_PROVIDER=openai` sem impl ainda → fail-loud claro") + D-8.1-FACTORY.

**AC3 (Leitura de key por-provider, fail-loud PT-PT)** — `readApiKey(provider)` lê `process.env.ANTHROPIC_API_KEY` ou `process.env.OPENAI_API_KEY` consoante o provider activo, com `Error` PT-PT claro se a key do provider activo estiver ausente (mesmo padrão do `readApiKey()` actual, `factory.ts:26-34`). A leitura é pontual (`process.env.X` directo, não `getServerEnv()`) para compatibilidade Edge.

Trace: ADR-10 §3.2 ("`readApiKey(provider)`, com fail-loud PT-PT se a key do provider activo estiver ausente") + `factory.ts:11-13,26-34` (padrão Edge-safe).

**AC4 (`OPENAI_API_KEY` server-only — NFR5)** — `OPENAI_API_KEY` é validada no `ServerEnvSchema` de `lib/shared/env.ts` (opcional em dev/test, resolvida só quando `LLM_PROVIDER=openai`), **nunca** com prefixo `NEXT_PUBLIC_`. A key nunca entra no client bundle. Apenas `NEXT_PUBLIC_LLM_PROVIDER` (o nome do provider, não um secret) é público.

Trace: NFR5 + ADR-10 §5 (tabela `lib/shared/env.ts`) + D-8.1-SECRET + `env.ts:14` (padrão `ANTHROPIC_API_KEY`).

**AC5 (Asserção de concordância de flags)** — Existe uma asserção no boot do server que verifica `NEXT_PUBLIC_LLM_PROVIDER === LLM_PROVIDER`; um mismatch falha loud com `Error` PT-PT claro (não silencioso). `NEXT_PUBLIC_LLM_PROVIDER` é validada no `PublicEnvSchema`.

Trace: ADR-10 §3.4 ("asserção de arranque (`NEXT_PUBLIC_LLM_PROVIDER === LLM_PROVIDER`) no boot do server [...] elimina a classe") + D-8.1-FLAGS.

**AC6 (`toolsToOpenAIShape` produz o envelope OpenAI correcto)** — Em `lib/agent/tools/registry.ts`, `toolsToOpenAIShape(tools: ToolDefinition[]): OpenAIToolShape[]` (irmão de `toolsToAnthropicShape`) produz, por tool, o envelope **`{ type: 'function', function: { name, description, parameters } }`**, onde `parameters` é o resultado do **mesmo** `zodToJsonSchema(tool.argsSchema, { target: 'openApi3' })` usado pelo caminho Anthropic. Aplica o **mesmo fail-loud**: se `zodToJsonSchema` produzir shape sem `type === 'object'`, lança `Error` identificando a tool culpada. `OpenAIToolShape` é adicionado a `lib/agent/tools/types.ts` (irmão de `AnthropicToolShape`). O `toolsToAnthropicShape` e o `AnthropicToolShape` ficam **intocados**.

Trace: ADR-10 §4.2 ("adicionar `toolsToOpenAIShape(tools)` [...] reusa o mesmo `zodToJsonSchema` [...] embrulhando o resultado em `{ type:'function', function:{ name, description, parameters } }`") + decisão "dois helpers irmãos" (§4.2) + `registry.ts:88-123`.

**AC7 (`parameters` idêntico ao `input_schema` do caminho Anthropic)** — Para qualquer tool, o `function.parameters` produzido por `toolsToOpenAIShape` é **igual** ao `input_schema` produzido por `toolsToAnthropicShape` (ambos vêm do mesmo `zodToJsonSchema(argsSchema, {target:'openApi3'})`). Um teste falsificável afirma esta igualdade — falharia se as duas conversões divergissem no JSON Schema.

Trace: ADR-10 §4.2 ("Schema dos args [...] `function.parameters` (JSON Schema) — mesmo `zodToJsonSchema`") + `registry.ts:91` (conversão única partilhada).

**AC8 (Guard de comprimento de nome ≤64 ASCII)** — O `register()` do Tool Registry ganha um guard que rejeita nomes de tool com **> 64 caracteres** (limite OpenAI `^[a-zA-Z0-9_-]{1,64}$`), com `Error` PT-PT. O `TOOL_NAME_PATTERN` actual (`/^[a-z][a-z0-9_]*$/`, snake_case lowercase ASCII) já é **subconjunto estrito** do padrão OpenAI → os nomes actuais passam inalterados; o único guard novo é o de comprimento. Um teste confirma que um nome >64 é rejeitado e que os nomes actuais (≤64) passam.

### Ponto de atenção — Edge-safe (não usar `getServerEnv()` no caminho quente)

A factory documenta (`factory.ts:11-13`) que lê a key via `process.env.X` directo, **não** via `getServerEnv()`, "para evitar parse global em Edge runtime". O `readApiKey(provider)` da 8.1 mantém este padrão: lê `process.env.ANTHROPIC_API_KEY`/`process.env.OPENAI_API_KEY` pontualmente. A validação Zod em `env.ts` é para o arranque/boot (e para a asserção de concordância), não para o caminho quente da factory.

### Ponto de atenção — Default que preserva o comportamento Anthropic

`LLM_PROVIDER` ausente **tem** de resolver para `'anthropic'` (não `undefined`, não erro). Usar `z.enum([...]).default('anthropic')` em `env.ts` **e** um fallback equivalente na leitura directa da factory (`process.env.LLM_PROVIDER ?? 'anthropic'`), porque a factory lê `process.env` directo (não o objecto Zod parseado). Garante AC1/AC12 mesmo sem `getServerEnv()` no caminho quente.

### Ponto de atenção — Asserção de concordância: onde corre

A asserção `NEXT_PUBLIC_LLM_PROVIDER === LLM_PROVIDER` (AC5) corre no **boot do server**. Implementar como helper exportado (ex: `assertProviderFlagsAgree()`) e invocá-lo no ponto de arranque server-side adequado (ex: instrumentação/boot, ou lazy na primeira chamada da factory) — **não** num componente client (onde `LLM_PROVIDER` server-only não está disponível). O `@architect` confirma o ponto de invocação exacto no gate de entrada.

### [AUTO-DECISION] Modelos default OpenAI

ADR-10 §4.5 recomenda `gpt-4.1-mini` (classifier) e `gpt-4.1` (executor) como **pontos de partida configuráveis**, não contrato. A 8.1 adopta-os como `DEFAULT_OPENAI_*`. O Eurico pode trocar por env sem alterar código (ADR-10 §4.5). Sem invenção — os nomes vêm da tabela de pricing validada do ADR (§4.5).

### [AUTO-DECISION] Versão da dependência `openai`

O ADR-10 escreve `"openai": "^<latest>"`. A versão exacta **não** está fixada no ADR. O `@dev` confirma a última versão estável no momento da implementação (npm/context7) e fixa-a com caret. Isto não é invenção — é resolução de um placeholder explícito do ADR.
