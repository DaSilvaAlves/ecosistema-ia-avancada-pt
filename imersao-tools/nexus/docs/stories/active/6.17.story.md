**Por que é recomendado:** a 6.17 introduz a primeira tool do cérebro com efeito externo via canal Telegram. O ADR-9 (architecture-v2.md) estabelece que o executor de tools corre **client-side** (browser) com `ctx.kv` como `noKvStub` (LANÇA) e `getValidAccessToken()` Node-only inacessível. Logo, `enviar_telegram` **não pode** chamar `sendMessage` directamente (que faz `fetch` a `api.telegram.org` com o token — server-only). O padrão da 6.10/6.13 é que a tool usa `ctx.fetch` para uma route server-side same-origin que executa a operação Node-only. O `@architect` ratifica esta decisão antes da implementação.

### Análise de Ciclo de Vida — `internal-state-contract-gate.md` (a preencher no gate)

A 6.17 distribui estado por 2 fronteiras: (1) tool client-side (argumento `{ text }`) → (2) route Node `POST /api/telegram/send` → `sendMessage` → `api.telegram.org`. A preenchimento dos 3 eixos fica para o `@architect`:

| Eixo | Pergunta obrigatória para gate |
|------|-------------------------------|
| **(a) Classes de estado** | Que estados observáveis existem? Tool invocada / route chamada / `sendMessage` OK / `sendMessage` falhou. A tool sabe se a mensagem foi entregue ou não? |
| **(b) Transição-já-ocorrida** | `sendMessage` com token expirado? Route com `TELEGRAM_CHAT_ID` ausente? Mensagem vazia? |
| **(c) Caminhos de falha** | 401 (sem sessão na route) / 400 (`text` vazio) / 5xx (Telegram down) → a tool distingue sucesso de falha? Nenhum caminho devolve sucesso mascarando falha. |

## Story

**As a** utilizador do Nexus v2,
**I want** que o cérebro multi-intent possa enviar mensagens Telegram para mim directamente (via tool `enviar_telegram`),
**so that** a IA possa comunicar pro-activamente e responder a pedidos que implicam notificação ou mensagem no canal Telegram, sem eu precisar de abrir o bot manualmente.

## Acceptance Criteria

> Traçados directamente a `PRD-NEXUS-V2.md` §6.13 FR76 + `EPIC-6.md` §5 row 6.17. Não inventados.

**AC1** — A tool `enviar_telegram` está registada no `toolRegistry` com `domain: 'telegram'`, `name: 'enviar_telegram'` (ASCII `[a-z0-9_]`, validado contra `TOOL_NAME_PATTERN` — `external-contract-identifiers.md`).

**AC2** — O `argsSchema` da tool contém obrigatoriamente `text: z.string().min(1).max(4096)` e NÃO contém `chat_id` (o destinatário é sempre o utilizador autenticado via `TELEGRAM_CHAT_ID` server-side — prevenção SSRF).

**AC3** — A tool invoca por `ctx.fetch` a route server-side `POST /api/telegram/send` (runtime `nodejs`, `export const runtime = 'nodejs'`) que lê `TELEGRAM_CHAT_ID` do env e chama `sendMessage` de `lib/telegram/bot-api.ts`. A tool NUNCA chama `sendMessage` directamente (Node-only).

**AC4** — A route `POST /api/telegram/send` tem autenticação `getSession` (auth obrigatória — a tool só é invocada no contexto de uma sessão browser autenticada; a route não está em `PUBLIC_PATHS`). Se sessão ausente → 401.

**AC5** — A route valida `{ text }` com Zod: `text` ausente ou vazio → 400; `text` > 4096 chars → 400. A tool propaga os erros da route como `Error` PT-PT descritivo (nunca trata 4xx/5xx como sucesso — anti-M4 da Story 4.9).

**AC6** — `TELEGRAM_CHAT_ID` ausente em env → a route devolve 503 com mensagem descritiva. A tool recebe 503 e lança erro PT-PT (não sucesso silencioso).

**AC7** — `requiresPreview` e `reversible` definidos conforme `[D-6.17-REVERSIBLE]` ratificado pelo `@architect`.

**AC8** — A tool `enviar_telegram` está exportada no barrel `lib/agent/tools/index.ts` (para registo automático no boot via `import '@/lib/agent/tools'`).

**AC9** — Testes Vitest cobrem: (a) tool registada no registry com `domain='telegram'` e schema correcto; (b) invocação da tool → `ctx.fetch` chamado para `/api/telegram/send`; (c) route `POST /api/telegram/send` — sucesso (200, `sendMessage` chamado); (d) route — 401 (sem sessão); (e) route — 400 (`text` vazio); (f) route — 503 (`TELEGRAM_CHAT_ID` ausente); (g) mock MSW de `sendMessage` reflecte o protocolo real da Bot API (`{ok:true, result:{...}}`/`{ok:false,...}`) — `mock-protocol-fidelity.md`.

**AC10** — Suite Vitest completa mantém-se verde (baseline 2316 PASS pós-6.16; zero regressões).

**AC11 (produção — diferido)** — O cérebro responde a "envia-me uma mensagem no Telegram a dizer bom dia" via Telegram em < 3s. Verificável só com env Telegram provisionado em produção (P1-P4 herdados das stories anteriores).

### Decisões ratificadas

**[D-6.17-RUNTIME] — RATIFICADA: candidata (a).**
A tool `enviar_telegram` corre client-side (ADR-9: `noKvStub` lança, `TELEGRAM_BOT_TOKEN` é server-only). Chama por `ctx.fetch` uma route Node **nova**: `POST /api/telegram/send`, com `export const runtime = 'nodejs'`, que lê `TELEGRAM_CHAT_ID` de `getServerEnv()` e invoca `sendMessage(chatId, text)` de `@/lib/telegram/bot-api.ts` (Story 6.13, INTOCADO — open-closed).
- **Reuso vs nova route:** route NOVA. Candidata (b) (`/api/telegram/process-text`) é rejeitada — corre o cérebro completo, não é uma route de envio standalone; reutilizá-la acoplaria o envio à orquestração e duplicaria a auth do bridge webhook. Candidata (c) é impossível (token server-only). Precedente directo: 6.10 criou 2 routes Node novas (`draft`, `archive`) em vez de forçar a tool a fazer Node-only no browser.
- **Path exacto:** `app/api/telegram/send/route.ts`. **Método:** `POST`. **Runtime:** `nodejs` (lê `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` do env — Node-only).
- A tool replica o helper `gmailRouteFetch` de `gmail.ts:102-112`: um `ctx.fetch` que rejeita (rede caída) é convertido em `Error` PT-PT, nunca propaga rejeição crua nem sucesso silencioso.

**[D-6.17-CHATID] — RATIFICADA: candidata (a) (anti-SSRF). Vinculativa.**
O `chat_id` **NUNCA** é argumento da tool nem campo do body da route. A route lê **sempre** `getServerEnv().TELEGRAM_CHAT_ID` server-side e passa-o a `sendMessage`. O `argsSchema` da tool contém **apenas** `{ text }`. Justificação de segurança: se o `chat_id` fosse argumento, o LLM do cérebro poderia construir um `chat_id` arbitrário (alucinação ou prompt injection) e a tool tornar-se-ia um primitivo de envio para destinatários arbitrários (SSRF/abuso). O destinatário é um invariante do contrato de segurança server-side, fora do alcance do modelo. CodeRabbit Primary Focus desta story confirma este eixo.

**[D-6.17-REVERSIBLE] — RATIFICADA: `requiresPreview: false`, `reversible: false`.**
Justificação (mapeada ao precedente real `gmail.ts`):
- `reversible: false` — uma mensagem entregue no Telegram não pode ser retirada. Igual a todas as tools de efeito externo do Epic 6 (`criar_draft_gmail` l.252, `arquivar_email` l.310 = `reversible:false`). Não existe `reverse`.
- `requiresPreview: false` — DIVERGE de `criar_draft_gmail`/`arquivar_email` (que são `true`), e alinha com `listar_emails_importantes` (`false`) e com as notificações do Epic 4. Razão: `criar_draft_gmail` exige preview porque o LLM **compõe conteúdo novo dirigido a um terceiro** (destinatário arbitrário `to`) — o utilizador tem de rever antes. Em `enviar_telegram` o destinatário é fixo (o próprio utilizador, via `TELEGRAM_CHAT_ID` — `[D-6.17-CHATID]`) e o efeito é uma notificação self-directed em resposta a um pedido explícito ("envia-me uma mensagem a dizer X"); a conversa no chat Nexus é, ela própria, o preview. Forçar `requiresPreview: true` degradaria a UX de respostas simples sem ganho de segurança (não há terceiro a proteger). O risco residual (LLM envia texto ligeiramente diferente do pedido) é baixo e self-contained — vai para o próprio utilizador.

**[D-6.17-CONTRACT] — RATIFICADA: contrato único tool↔route.**
Resolve o Should-Fix S2 do `@po`. Fixa-se um contrato coerente, sem reconciliação a meio da implementação:
- **Route → sucesso (200):** `{ ok: true }`. (Espelha o padrão minimalista da route; `sendMessage` devolve `void`, não há `message_id` a propagar — a 6.13 já ignora o `result` da Bot API por design, `bot-api.ts:273-275`.)
- **Route → falha:** **NUNCA** `200 { ok: false }`. Status HTTP é o sinal de verdade (anti-M4 da 4.9): 401 / 400 / 503 / 502, cada um com corpo `{ error: '<code>' }` descritivo (padrão `draft/route.ts`).
- **Tool `resultSchema`:** `z.object({ sent: z.boolean() })`. A tool mapeia `200 → { sent: true }`. O nome `sent` (semântica da tool: "foi enviado?") é distinto de `ok` (semântica HTTP da route: "pedido bem-sucedido?") — separação deliberada e documentada, não acidental. A tool valida `resp.ok` E parseia `{ ok: true }` do corpo (defesa em profundidade, padrão `DraftCreatedResponseSchema.safeParse`); corpo malformado num 2xx → `Error` (não `{ sent: true }` mascarado).
- **Tabela de mapeamento de erros da route (vinculativa para T3):**

  | Condição | Status | corpo `{ error }` | Origem |
  |----------|--------|-------------------|--------|
  | `getSession` inválida/ausente | 401 | `not_authenticated` | `draft/route.ts:136-139` |
  | `text` ausente/vazio/>4096 | 400 | `invalid_request` | Zod na route |
  | `TELEGRAM_CHAT_ID` ausente | 503 | `chat_id_missing` | `env.ts:24` `.optional()` |
  | `BotApiTokenMissingError` | 503 | `bot_token_missing` | `bot-api.ts:56` |
  | `BotApiError` / `BotApiTimeoutError` / rede | 502 | `telegram_unavailable` | `bot-api.ts:69-95` |

  Nota: 502 (e não 503) para `BotApiError` porque a falha é do upstream Telegram (bad gateway), distinta de 503 (config server-side ausente). A tool mapeia ambos para `Error` PT-PT distinto; nenhum é sucesso.
