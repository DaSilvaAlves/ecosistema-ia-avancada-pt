**`[D-5.7-MECHANISM]` = RATIFICADA Opção (A)** — reutilizar `/api/anthropic/proxy`, JSON síncrono, Sonnet `DEFAULT_EXECUTOR_MODEL`, `temperature: 0`.
Fundamentos: (1) precedente `[D-5.4-ENDPOINT]` validado em produção para a mesma classe de operação (texto livre → JSON estruturado one-shot); (2) o overlay "A estruturar…" (FE [4]) é um estado binário loading→done — SSE/streaming não melhora a UX de um parse atómico; (3) zero superfície nova (sem rota Edge nova, sem contrato SSE para manter); (4) a FE spec §1.4 [4] ("POST `/api/agent/brain-dump` (Edge, SSE)") é anterior ao `[D-5.4-ENDPOINT]` — fica **reconciliada**: a fonte de verdade de UI são os estados visuais ([4] overlay, [5] secções), o transporte é decisão de arquitectura.
Consequências para `@dev`: (a) actualizar o comentário `[D-5.6-SEAM]` em `BrainDumpLauncher.tsx:18-19` (refere o endpoint SSE que não vai existir); (b) `DEFAULT_MAX_TOKENS = 2048` no `parser-cliente.ts` — os 1024 do diário cobrem 3 buckets curtos; 4 buckets com N itens cada precisam de folga (AC2 <8s mantém-se com Sonnet síncrono).

**`[D-5.7-SHAPE]` = RATIFICADA com separação wire/domínio** — dois schemas no `ai-parser.ts`, ambos `.strict()`:
- **Wire (resposta AI):** `BrainDumpWireSchema` — 4 buckets **obrigatórios** (`tarefas`, `projectos`, `ideias`, `decisoes` — ASCII, `external-contract-identifiers.md`), cada um `z.array(z.string().min(1))`. A AI devolve **textos, não ids** — um LLM não é fonte fiável de unicidade de identificadores.
- **Domínio (persistido — seam 5.8):** `BrainDumpParsedSchema` — mesmos 4 buckets obrigatórios, itens `{ id: string; texto: string }`. Tipo exportado `BrainDumpParsed = z.infer<...>`.
- **Enriquecimento puro:** `enrichWithIds(wire, idFn = () => crypto.randomUUID())` — atribui ids no cliente após parse; `idFn` injectável para testes determinísticos.
Divergência deliberada face ao diário (campos opcionais): aqui os 4 buckets são **sempre presentes** (arrays vazios permitidos) porque a 5.8 itera os 4 e o display mostra contador "(N)" — arrays garantidos eliminam guards no consumo.

**`[D-5.7-TOOLS]` = RATIFICADA Opção (A)** — JSON estruturado ad-hoc (padrão 5.4), **sem** Tool Registry nesta story.
O arch §16 (`architecture-v2.md:1138` — "Sonnet com tools `criar_tarefa`/`criar_projecto`/`criar_nota` em modo `requiresPreview: true`") aplica-se ao fluxo de **persistência aprovada** — ou seja, à 5.8 (aprovação item-a-item) com tools registadas na 5.13. Invocar tools `criar_*` no parse da 5.7 contradiria o próprio `requiresPreview` (não existe aprovação nesta story). Não há divergência real com o arch: o parse é transformação read-only; as tools entram quando os itens se tornam entidades. O `parsedOutput` persistido é o contrato entre as duas fases.

**`[D-5.7-SCOPE]` = CONFIRMADA** — 5.7 entrega FE [4]-[5] **sem controlos de item**: os ☐/✏️/✗ e o botão "Guardar N itens" visíveis no mock do [5] pertencem aos passos [6]-[8] (= Story 5.8). Decisão menor de UI fixada: as 4 secções aparecem sempre; buckets **não-vazios** default expandidos (FE [5]); buckets **vazios** mostram "(0)" e ficam colapsados (feedback de que a AI considerou o bucket, sem roubar espaço).

**`[D-5.7-PERSIST]` = CONFIRMADA** — `createBrainDump({ id, createdAt, bodyMarkdown, parsedOutput, status: 'parsed' })` **apenas** após parse + enrich com sucesso; qualquer falha (rede, `!res.ok`, JSON inválido, shape inválido) → throw PT-PT → estado `error`, **zero writes**. `pending` nunca é persistido pela 5.7. `internal-state-contract-gate.md`: eixo (c) coberto por AC2/AC4; eixos (a)/(b) só ganham superfície multi-camada na 5.8 — o gate completo aplica-se lá.

**Decisão AC8 (`types/db.ts`) = MANTER `unknown`** — `parsedOutput?: unknown` em `types/db.ts` e `z.unknown()` no `BrainDumpSchema` ficam **intocados**. O comentário da 5.1 (`D-BRAINDUMP-STORE`) previa explicitamente "sem coupling nesta camada". O tipo forte (`BrainDumpParsed`) vive em `lib/brain-dump/ai-parser.ts`; a escrita (AC3) só persiste output já validado; a leitura (5.8) revalida com o parse de domínio. Evita import `types/db.ts` → `lib/brain-dump/` e qualquer toque na suite schema-upgrade. `types/db.ts` e `lib/db/schemas.ts` saem da File List.

## User Story

Como Eurico (utilizador do Nexus), quero que, ao clicar "Estruturar com AI" no Brain Dump, a AI reorganize o meu texto livre em **4 buckets** — tarefas propostas, projectos propostos, ideias soltas e decisões a tomar — mostrados em secções colapsáveis, para eu ver a estrutura que saiu do meu despejo de ideias (a aprovação item-a-item e a persistência como tarefas/projectos/notas ficam para a Story 5.8).

`PRD-NEXUS-V2.md` §6.9 (FR48 — "AI estrutura output em: tarefas propostas, projectos propostos, ideias soltas, decisões a tomar") é o requisito raiz. `EPIC-5.md` §5 (row 5.7) atribui à 5.7 o **parser AI** (texto → 4 buckets), distinto da 5.6 (UI de input) e da 5.8 (aprovação item-a-item). A `front-end-spec-v2.md` §1.4 (Flow 4) passos [4]-[5] são a fonte de verdade de UI: clicar "Estruturar" → overlay "A estruturar…" → 4 secções colapsáveis (default expandidas) com os itens por bucket.

Esta story entrega os passos **[4]-[5]**: ligar o seam `onStructure` da 5.6 ao pipeline AI, parsear a resposta nos 4 buckets, **persistir** o brain dump (`status: 'parsed'`), e **mostrar** os 4 buckets em read-only. Os passos [6]-[8] (desmarcar/editar/rejeitar item-a-item, "Guardar N itens", persistência em `db.tasks`/`db.projects`/`db.knowledge_notes`, toast, mensagem retroactiva) são da **Story 5.8** (`internal-state-contract-gate.md` aplica-se lá — estado distribuído proposta→aceite→persistido).

Reutiliza o padrão validado da estruturação AI do diário (5.4): helper puro com Zod `.strict()` + client `/api/anthropic/proxy` JSON síncrono (`[D-5.4-ENDPOINT]`), sujeito à ratificação do `@architect` (`[D-5.7-MECHANISM]`).

Mesma filosofia: helper puro Zod `.strict()` (falsificável) + client edge-safe sem SDK/key + throw PT-PT + `stripJsonMarkdownFences`. [Source: `lib/diario/ai-estrutura.ts`, `lib/diario/estruturar-cliente.ts`]
- **`mock-protocol-fidelity.md` (A1 Epic 1) — obrigatório.** O mock da resposta Sonnet reflecte o protocolo real (`content[].text` com JSON dos 4 buckets); ≥1 teste falha se o shape divergir. O `.strict()` é o mecanismo que o garante. [Source: `.claude/rules/mock-protocol-fidelity.md`; EPIC §8 A1]
- **`external-contract-identifiers.md`:** os nomes de campo dos buckets (`tarefas`/`projectos`/`ideias`/`decisoes`) são identificadores de contrato interno do `parsedOutput` — ASCII, sem acentos/cedilha (validar no schema). As tools `criar_tarefa`/`criar_projecto`/`criar_nota` (se usadas — `[D-5.7-TOOLS]`) cruzam o Tool Registry e são da 5.13 (nomes já ASCII no EPIC row 5.13). [Source: `.claude/rules/external-contract-identifiers.md`]
- **`internal-state-contract-gate.md` — parcial na 5.7, completo na 5.8.** Na 5.7 aplica-se o eixo (c) falhas: rede/`!res.ok`/JSON inválido tratados como erro (nunca sucesso silencioso). O ciclo completo proposta→aceite/rejeitado→persistido (eixos a/b) é da 5.8. [Source: `.claude/rules/internal-state-contract-gate.md`; EPIC §8 A1 Epic 4]
- **`status: 'parsed'` é a única transição da 5.7.** `pending` nunca é persistido (parse falhado não cria dump); `partially/fully_approved` são da 5.8. [Source: `types/db.ts:261`; FR48/FR49]
- **Edge-safety (ADR-1/NFR5):** os helpers não importam `@anthropic-ai/sdk` nem `ANTHROPIC_API_KEY`. A key vive só no proxy server-side. [Source: `estruturar-cliente.ts:20-22`]
- **AC2 latência (<8s/200 palavras):** validação manual/perf, não unit. Sonnet `temperature:0`, `max_tokens` suficiente para 4 buckets (rever vs os 1024 do diário — 4 buckets podem precisar de mais). [Source: EPIC §10 AC2]
- **Display read-only é o seam para a 5.8.** Os checkboxes ☐/✏️/✗ e "Guardar N itens" do FE [6]-[8] são da 5.8; a 5.7 lista os itens sem acções. [Source: FE §1.4 [5]-[8]]
- **A2 Epic 4 (varredura de classe):** se o CR/gate apanhar um bug de protocolo/parse, verificar a mesma classe no parser do diário (5.4) e na pesquisa web (5.11 futura) no mesmo ciclo. [Source: EPIC §8 A2]
- **Sem version bump Dexie.** A tabela `brain_dumps` existe (5.1). Só o **tipo** de `parsedOutput` se concretiza — não toca `client.ts`/schema. Confirmar que nenhum teste schema-upgrade quebra. [Source: `brain-dumps.ts:10`]
