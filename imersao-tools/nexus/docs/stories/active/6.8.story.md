### Análise de ciclo de vida do estado — `internal-state-contract-gate.md` (obrigatória no gate de entrada)

> O estado distribui-se por ≥2 camadas: Gmail API (fonte de emails) + cache KV (resultados de classify) + proxy AI (inferência) + route (coordenador). Aplica-se a regra `internal-state-contract-gate.md` (A1 Retro Epic 4).

| Eixo | Perguntas obrigatórias a responder no gate de entrada |
|------|------------------------------------------------------|
| **(a) Classes de estado** | Um `msgId` pode estar: `não-classificado` (não em KV) / `classificado` (em KV com TTL válido) / `TTL-expirado` (KV hit mas expirado — tratado como não-classificado?). O que acontece quando o email já foi eliminado do Gmail mas ainda está em KV (msgId deletado)? O classifier deve só classificar mensagens que ainda existem na inbox? |
| **(b) Transição-já-ocorrida** | O que acontece se o cron disparar duas vezes em paralelo para o mesmo lote de 50 emails? A cache KV `kv.set` é atómica por chave — mas N escritas paralelas para N chaves são seguras? E se o AI proxy falhar a meio da classificação (ex: timeout): os emails classificados antes do timeout ficam em KV, os restantes ficam sem classificar — estado parcial aceitável? Ou deve ser tudo-ou-nada? |
| **(c) Caminhos de falha** | `getValidAccessToken()` lança `TokenRevokedError` — route devolve 401; emails não são classificados (correcto). Gmail API devolve 429 (rate limit) ou 5xx — a route devolve 503? O proxy AI falha (Anthropic 5xx) — a route devolve 503 e nenhum email é classificado (nenhuma escrita em KV)? Se o helper classificar só 30 dos 50 emails antes de falhar, o estado parcial é preservado ou revertido? |

## Débito Herdado — REC-6.7-REFRESH-SCOPES (Baixa)

> Registo preventivo conforme instrução do `@sm` (spawn prompt). O débito **REC-6.7-REFRESH-SCOPES** (Baixa prioridade) foi diferido da Story 6.7: verificar se o fluxo de refresh do `getValidAccessToken()` preserva o array `scopes` ao renovar o `accessToken` com o `refreshToken`. Actualmente, o refresh repõe `accessToken` + `expiresAt` mas pode ou não repor `scopes` (dependendo de se o Google inclui `scope` na resposta de refresh).

**Impacto na 6.8:** a 6.8 usa `getValidAccessToken()` cujo token pode ter sofrido refresh depois da 6.7. Se o refresh não preservar `scopes`, o `gmailConnected` derivado de `scopes?.includes('gmail.modify')` pode passar a `false` após refresh — fazendo a 6.8 recusar chamadas Gmail de forma incorrecta (falso negativo). A 6.8 não resolve este débito (é responsabilidade do `token-store.ts`), mas regista-o explicitamente e o `@architect` decide se bloqueia esta story ou é tratado como waiver documentado.

**Acção no draft:** `@architect` verifica no gate de entrada se o refresh em `token-store.ts` preserva `scopes`. Se não preservar, o débito sobe de Baixa para Média e deve ser tratado em T0 como pré-condição desta story (antes de T1).

### `getValidAccessToken()` — único ponto de entrada

`getValidAccessToken()` de `lib/google/token-store.ts` (criado pela 6.2) é o único ponto de entrada de access token para todas as stories Google autenticadas. O token retornado serve tanto o Calendar como o Gmail (token combinado da 6.7). NÃO chamar `getTokens().accessToken` directamente — pode devolver um token expirado sem refresh. _[Source: EPIC-6.md §5 row 6.2; 6.3 Dev Notes]_

### `internal-state-contract-gate.md` — ciclo de vida do classifier

O estado distribui-se por ≥2 camadas: Gmail API (fonte) + KV cache (resultado por msgId) + proxy AI (inferência) + route (coordenador). O `@architect` responde os três eixos no T0. Eixos específicos da 6.8:
- **(a)** `não-classificado` / `classificado-em-cache` / `TTL-expirado` / `email-eliminado-mas-em-cache`. Um email eliminado do Gmail cujo `msgId` ainda está em KV (TTL válido) — o helper serve o bucket da cache mesmo que o email já não exista (aceitável: a UI da 6.9 tentará mostrar o email e não o encontrará na inbox).
- **(b)** Runs paralelas do cron: N escritas KV paralelas para N chaves distintas são seguras (KV é atómica por chave). Estado parcial após AI timeout: emails classificados antes do timeout ficam em KV (aceitável — o próximo run classifica o resto).
- **(c)** `TokenRevokedError` → 401; Gmail 429 → 503; Anthropic 5xx → 503; escrita KV falhada → throw (nenhuma classificação parcial reportada como sucesso).

_[Source: `.claude/rules/internal-state-contract-gate.md`; EPIC-6.md §8 A1 Epic 4]_

### Análise de ciclo de vida do estado — `internal-state-contract-gate.md` (3 eixos)

> O estado distribui-se por Gmail API (fonte) + cache KV por `msgId` (resultado) + Anthropic API (inferência) + helper/route (coordenação). Resposta vinculativa do gate de entrada (AC7).

**Eixo (a) — Classes de estado e transições.** Um `msgId` tem 4 classes:
1. `não-classificado` — chave KV `nexus:cache:gmail:classify:<msgId>` ausente. Transição → é incluído no lote de leitura + AI.
2. `classificado` — chave KV presente com `{ bucket, classifiedAt }`. O `@vercel/kv` aplica o TTL nativamente: uma chave expirada **não é devolvida** pelo `kv.get` (devolve `null`), logo "TTL-expirado" colapsa em `não-classificado` no plano de leitura — **não há leitura de valor stale-mas-expirado** (o TTL é server-side no KV, não uma comparação de `classifiedAt` no helper). Transição → re-classificado no próximo run (re-leitura Gmail + AI). Custo aceitável: 7 dias é uma janela larga; um email ainda na inbox ao fim de 7d é raro e o re-classify é barato (1 email).
3. `email-eliminado-do-Gmail-mas-msgId-ainda-em-KV` (TTL válido) — o `messages.list` já NÃO devolve esse `msgId` (não está na inbox), logo o helper nunca o re-lê; a chave KV expira sozinha por TTL. A 6.9 (vista) que ler buckets agregados pode listar um bucket com um `msgId` que já não existe na inbox — **aceitável e documentado**: a 6.9 tentará abrir/mostrar e tratará o 404 do Gmail graciosamente (responsabilidade da 6.9, fora do scope da 6.8). A 6.8 NUNCA serve um email que não veio do `messages.list` corrente — o `list` é a fonte de verdade da inbox; o KV é só o cache da classificação.
4. `classificação-em-curso` — estado transitório intra-helper (lido do Gmail, ainda não escrito em KV). Não é persistido; uma falha aqui deixa o `msgId` em `não-classificado` (eixo c).

**Eixo (b) — Transição-já-ocorrida.**
- **Runs paralelas do cron sobre o mesmo lote:** o `kv.set` é atómico **por chave**. N escritas paralelas para N chaves distintas (`<msgId>` distintos) são independentes e seguras — não há chave partilhada nem read-modify-write (o helper faz `set`, não `incr`/`append`). Duas runs concorrentes podem classificar o mesmo `msgId` em duplicado (desperdício de 1 chamada AI) mas o resultado é idempotente: a última escrita vence e o bucket é determinístico (`temperature: 0`). Sem corrupção, sem lock necessário. A cadência cron da 6.5 é diária — overlap é improvável na prática.
- **Cache parcial após sucesso de N de M:** se o helper classificar e escrever 30 de 50 antes de uma falha, esses 30 ficam **persistidos** (cada `set` é commit imediato). O próximo run lê esses 30 do cache (`fromCache`) e classifica só os 20 restantes. **Estado parcial é aceitável e desejável** — é progresso, não corrupção (espelha `[D-6.5-PARTIAL-FAILURE]` do cron calendário: progresso parcial > tudo-ou-nada num batch de leitura idempotente). **Condição C5:** a escrita em KV de cada email classificado é feita assim que o seu bucket é válido — NÃO acumular tudo em memória e escrever no fim (isso transformaria uma falha tardia em perda total do lote).

**Eixo (c) — Caminhos de falha.**
- `getValidAccessToken()` → `null` (sem tokens) → route 401 `not_connected`; helper nunca é chamado. Nenhuma escrita KV.
- `getValidAccessToken()` lança `TokenRevokedError` → route 401 `token_revoked`. `TokenRefreshError` → route 503. (Mesma taxonomia do cron 6.5 `runPull`, `cron/sync/route.ts:104-108`.)
- **Gmail `messages.list`/`get` 401 (`invalid_grant`)** → o helper propaga um erro tipado (classe-token) → route 401. Nenhuma escrita KV.
- **Gmail 429 (rate limit) ou 5xx** → o helper propaga erro tipado transitório → route 503. Os `msgId`s já escritos antes da falha permanecem (eixo b); os restantes ficam `não-classificado`.
- **Anthropic 5xx / timeout** → o helper lança; **nenhum dos emails do lote AI falhado é escrito em KV** (a escrita só acontece após Zod `.strict()` validar o bucket). Os emails de lotes anteriores já escritos permanecem. Route 503.
- **Resposta AI com shape inválido** (bucket renomeado / campo extra / `msgId` desconhecido) → Zod `.strict()` throw → nenhuma escrita do lote inválido. **Falsificável (AC6).** Defesa adicional **C2**: a resposta AI só pode conter `msgId`s que estavam no lote enviado (a AI não inventa ids) — um `id` devolvido que não estava no input é descartado/rejeitado.
- **Escrita KV falhada** (`kv.set` rejeita) → o helper propaga; o `classified` reportado conta só os emails efectivamente escritos (nenhuma classificação não-persistida é reportada como sucesso). Route 503.

### Decisão REC-6.7-REFRESH-SCOPES (Baixa)
