- **AC1 (helper push puro `lib/google/calendar-push.ts` — testável ~100%):**
  Existe `lib/google/calendar-push.ts` com uma função exportada (ex: `pushCalendarEvent(accessToken: string, event: CalendarEvent): Promise<PushResult>`) que: (i) para eventos **local-pendente** (sem `googleId`, classe que será produzida pela 6.6) — chama `POST https://www.googleapis.com/calendar/v3/calendars/primary/events` com o corpo `{ summary, start, end }` mapeado a partir do modelo Nexus (epoch ms → `dateTime` ISO 8601 ou `date` para all-day); (ii) para eventos com `googleId` (classe "sincronizado") — chama `PUT https://www.googleapis.com/calendar/v3/calendars/primary/events/{googleId}` (full replace — decisão D-6.4-INSERT-OR-UPDATE); (iii) devolve `{ googleId: string, etag: string, updatedAt: number }` em sucesso, para persistência em Dexie; (iv) não chama `getValidAccessToken()` directamente — recebe o `accessToken` como parâmetro (desacopla do store de tokens, maximiza testabilidade). **Nota de scope (D-6.4-SCOPE):** o ramo `update` (PUT) existe no helper por completude e é testado por MSW, mas a route não o exerce no scope actual (insert-only — não há produtor de eventos alterados-após-sync nesta story). `[Source: EPIC-6.md §5 row 6.4; handoff RETOMA-20260617-story-6.4 §push scope; decisões D-6.4-INSERT-OR-UPDATE, D-6.4-SCOPE]`
  _Onde é verificável: CI (Vitest + MSW mock — insert, update, 404, 429, 5xx)._

- **AC2 (persistência do `googleId` em Dexie após insert bem-sucedido — idempotência anti-Risco R6):**
  Após `events.insert` bem-sucedido, o `googleId` devolvido pelo Google é persistido no registo `calendarEvents` do evento em Dexie. A persistência ocorre na **mesma cadeia `await` imediatamente após** o insert (janela mínima de crash — decisão C3). Um evento que já tem `googleId` nunca é re-inserido no Google: a lógica discrimina por `googleId` (ausente = local-pendente → insert; presente = sincronizado → update, fora do scope actual da route). **`googleId` é opcional no modelo** (`googleId?: string` em `types/db.ts` e `z.string().min(1).optional()` em `schemas.ts`) — esta alteração é aditiva-relaxante, SEM version bump Dexie (decisão D-6.4-SYNCSTATUS, Condição C2). A fronteira anti-loop é estrutural: scope insert-only + `&googleId` único esparso (D-6.4-LOOP, ratificado pelo `@architect`).
  _Onde é verificável: CI (Vitest + MSW mock — insert com persistência, re-push de evento com googleId = update não insert, falha de insert não persiste googleId)._

- **AC3 (mapeamento CalendarEvent Nexus → Google Event — epoch ms → ISO 8601):**
  O helper converte correctamente os campos do modelo Nexus para o protocolo Google Calendar API v3: `title → summary`; `startAt` (epoch ms) → `start.dateTime` (ISO 8601 com timezone, ex: `2026-06-20T15:00:00.000Z`) ou `start.date` (YYYY-MM-DD se `allDay: true`); `endAt` → `end.dateTime`/`end.date` (idem). O mapeamento reverso (resposta Google → persistência Dexie) preserva o `id` Nexus existente. Os campos de data suportam tanto events com hora (`dateTime`) como dias inteiros (`allDay: true`).
  _Onde é verificável: CI (Vitest + MSW mock — evento com hora, evento all-day, mapeamento inverso da resposta)._

- **AC4 (tratamento de falhas Google — 404, 429, 5xx — sem estado parcial):**
  O helper trata explicitamente: (i) 404 no `events.update` (evento apagado no Google entre o read e o `PUT`) — devolve `CalendarPushNotFoundError` (erro tratável, não excepção genérica); a route **conta o evento como `failed` e não faz re-insert nem apaga o registo local automaticamente nesta story** (decisão C4 — a decisão de re-insert pertence a uma story de conflito futura); (ii) 429 rate limit — propaga como `CalendarPushRateLimitError`, a route devolve 503 `rate_limited` (não persistir estado inconsistente); (iii) 5xx Google → `CalendarPushError`, route devolve 503 `calendar_push_unavailable` (nunca `200 { ok: false }` — anti-padrão M4 da 4.9 evitado). Em qualquer falha, o `googleId` não é persistido em Dexie (sem estado parcial).
  _Onde é verificável: CI (Vitest + MSW mock — handler 404: evento em `failed`, handler 429, handler 5xx; cada cenário tem teste)._

- **AC5 (fronteira anti-loop Risco R6 — ratificada pelo `@architect` no Gate de Entrada):**
  A estratégia anti-loop (D-6.4-LOOP) está implementada de forma **estrutural**: (i) a route `/push` actua exclusivamente em eventos **sem `googleId`** (local-pendente, D-6.4-SCOPE insert-only) — nunca re-empurra eventos de origem-Google; (ii) após `insert` bem-sucedido, o `googleId` é persistido em Dexie, transitando o evento para a classe "sincronizado"; (iii) o pull (6.3) subsequente que traga o mesmo evento reconhece o `googleId` por `where('googleId').equals(...)` e faz upsert idempotente, preservando o `id` Nexus existente sem re-disparar push (as routes `/sync` e `/push` são independentes; o cursor KV do pull não é tocado pelo push). A unicidade `&googleId` esparsa em Dexie impede duplicados locais. Loop estruturalmente impossível no scope desta story (insert-only, sem produtor de alterações locais).
  _Onde é verificável: CI (Vitest — teste de loop: push cria googleId, pull subsquente com o mesmo evento não re-dispara push; eixo b do ciclo de vida)._

POST https://www.googleapis.com/calendar/v3/calendars/primary/events
Authorization: Bearer <accessToken>
Content-Type: application/json

Corpo:

Resposta 201 Created:

  "id": "google_event_id_abc",   // ← guardar em Dexie como googleId

  "status": "confirmed",
  "updated": "2026-06-17T12:00:00.000Z",

  "start": { "dateTime": "2026-06-20T15:00:00.000Z" },
  "end":   { "dateTime": "2026-06-20T16:00:00.000Z" }
}

# Actualizar evento existente (update — PUT full replace)
PUT https://www.googleapis.com/calendar/v3/calendars/primary/events/<googleId>
Authorization: Bearer <accessToken>
Content-Type: application/json

Corpo: evento completo (mesmo formato do insert)
Resposta 200 OK: mesmos campos do insert

HTTP/1.1 404 Not Found
{ "error": { "code": 404, "message": "Resource Not Found: events" } }
→ Tratar explicitamente (não como 5xx); decisão da route: re-insert ou reportar falha

HTTP/1.1 429 Too Many Requests
Retry-After: 60
→ Propagar como CalendarPushRateLimitError; route devolve 503 rate_limited
