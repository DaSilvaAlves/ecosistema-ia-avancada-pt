## User Story

**As a** Eurico (utilizador único do Nexus v2) a interagir com o chat,
**I want** que o sistema exponha um endpoint Edge `POST /api/agent/prompt` que receba o meu prompt PT-PT, o classifique, execute as tools correspondentes em SSE streaming e entregue ao browser os eventos em tempo real,
**so that** a UI (Story 1.9) possa renderizar cards de acções, texto streaming e o toast de undo em tempo real — cumprindo o FR1/FR2/FR3 do PRD ("chat-first", "classifica em 1+ intents", "executa todas e devolve resumo agregado"), o AC1 do Epic 1 ("Prompt multi-intent cria entidades correctas numa única execução") e o AC5 do Epic 1 ("Latência p95 < 6s em batch de 50 prompts"), integrando os mecanismos das Stories 1.1–1.7 numa única superfície de entrada.

**GAP cross-process ConfirmationProvider (herdado de Story 1.6 + routado em ADR-6 Story 1.7):**

A Story 1.6 implementou `ConfirmationProvider` interface (in-process, via Promise). A Story 1.6 identificou o GAP: se o Vercel distribuir o `POST /api/agent/confirm` (confirmação do utilizador) para um Edge process diferente do que está a correr o SSE stream, a Promise in-process nunca resolve. A Story 1.7 diferiu esta decisão explicitamente (RESOLVED-3 + ADR-6) para a Story 1.8.

Esta story é responsável por:
1. Criar o endpoint `POST /api/agent/confirm` que recebe `{ runId, toolName, action }` do browser
2. Implementar `KvConfirmationProvider` que realiza polling KV (`nexus:agent:confirm:<runId>:<toolName>`) para coordenar entre processos Edge
3. Injectar `KvConfirmationProvider` como `confirmationProvider` no `runAgent()` call dentro do `POST /api/agent/prompt`

**Fluxo cross-process (ADR-7 desta story):**

```text
Browser → POST /api/agent/prompt
  Edge A: runAgent() com KvConfirmationProvider
  Edge A: emite preview_request SSE → aguarda KvConfirmationProvider.requestConfirmation()
  KvConfirmationProvider: polling KV nexus:agent:confirm:<runId>:<toolName> (TTL ~60s)

Browser → POST /api/agent/confirm { runId, toolName, action: 'confirm'|'cancel' }
  Edge B (pode ser diferente de A): escreve KV nexus:agent:confirm:<runId>:<toolName> = action
  Edge B: responde 200

Edge A: polling KV encontra action → resolve Promise → executa ou cancela tool → continua SSE
```

**Anti-padrões críticos desta story:**
- NÃO criar UI de chat — é Story 1.9
- NÃO criar regression suite — é Story 1.10
- NÃO alterar `runAgent()`, `classifyPrompt()`, `toolRegistry` — apenas consumir
- NÃO implementar `markRunReverted` server-side — é client-side Dexie (RESOLVED-2 Story 1.5)
- NÃO alterar o rate limiting global (já em middleware) — este endpoint está automaticamente abrangido
- NÃO incluir conteúdo de prompts em logs (NFR11)

- **AC5:** SSE protocol — cada evento emitido como:
  ```
  data: <JSON.stringify(event)>\n\n
  ```
  Onde `event` é do tipo `ExecutorSSEEvent` (Stories 1.5/1.6/1.7: `meta`, `tool_start`, `tool_complete`, `tool_error`, `text_delta`, `preview_request`, `preview_confirmed`, `undo_registered`, `done`). O encoding é UTF-8. Sem `event:` prefix field (apenas `data:`). Sem `id:` field. O stream termina com `data: [DONE]\n\n` após o evento `done`.

- **AC6:** Telemetria mínima (NFR11 + NFR12) — o handler deve logar via `logger.info` (Edge runtime, Vercel logs):
  - Início do request: `{ runId, promptHash: sha256(prompt).slice(0,8), conversationId? }` — NÃO logar o prompt em claro
  - Fim do request: `{ runId, durationMs, intents: classifierResult.intents, toolCallCount, status: done.status }`
  - Erros: `logger.error({ runId, error })` — NÃO incluir prompt
  - `sha256` implementado via `crypto.subtle.digest('SHA-256', encoder.encode(prompt))` (Edge-safe, sem `crypto.createHmac`)

- **AC7:** Novo módulo `lib/agent/kv-confirmation-provider.ts` exporta `KvConfirmationProvider` que implementa a interface `ConfirmationProvider` (Story 1.6 — `executor.ts` L112: `requestConfirmation(runId: string, toolName: string)`) usando KV polling:
  ```typescript
  export class KvConfirmationProvider implements ConfirmationProvider {
    constructor(
      private readonly kvClient: VercelKV,
    ) {}

    async requestConfirmation(
      runId: string,
      toolName: string,
    ): Promise<'confirm' | 'cancel'> {
      // polling KV nexus:agent:confirm:<runId>:<toolName>
      // TTL 60s (CONFIRM_TTL_SECONDS exportado)
      // polling interval 250ms (CONFIRM_POLL_INTERVAL_MS exportado)
      // timeout após CONFIRM_TTL_SECONDS × 1000ms → retorna 'cancel' (safe default)
    }
  }

  export const CONFIRM_TTL_SECONDS = 60;      // TTL da entrada KV de confirmação
  export const CONFIRM_POLL_INTERVAL_MS = 250; // intervalo de polling
  export const KV_CONFIRM_NAMESPACE = 'nexus:agent:confirm'; // prefixo do namespace
  ```
  - Construtor recebe apenas `kvClient: VercelKV` — `runId` vem como argumento de `requestConfirmation` (interface canónica Story 1.6)
  - O provider é construído **uma vez por request** antes do `for await`, sem necessidade de aguardar `meta(start)` event
  - Chave KV: `nexus:agent:confirm:<runId>:<toolName>`
  - KV value: `'confirm'` ou `'cancel'` (string)
  - O polling corre dentro da Edge function com `await new Promise(r => setTimeout(r, CONFIRM_POLL_INTERVAL_MS))`
  - Timeout seguro: se `CONFIRM_TTL_SECONDS` expirar sem resolução → `logger.warn` + retornar `'cancel'`
  - Se `kvClient.get(key)` retorna valor não-null: `await kvClient.del(key)` (cleanup imediato) + retornar o valor
  - Constantes exportadas permitem override em testes e documentam knobs de tuning

### ADR-7 (NOVO — registado nesta story, não modifica architecture-v2.md que está fixed em 04/05/2026)

> **ADR-7: Cross-process ConfirmationProvider — KV polling com TTL 60s**
>
> **Status:** PROPOSED (a confirmar por `@architect` Aria antes de implementação)
> **Context:** Story 1.6 expôs `ConfirmationProvider` interface in-process (Promise). Story 1.7 ADR-6 diferiu a implementação cross-process para esta story. O Vercel Edge pode distribuir o `POST /api/agent/prompt` (Edge A, SSE stream) e o `POST /api/agent/confirm` (Edge B, resposta ao clique) para instâncias distintas.
>
> **Decision proposta:** `KvConfirmationProvider` implementa `ConfirmationProvider` via KV polling com intervalo de 250ms e TTL 60s.
>
> **Namespace:** `nexus:agent:confirm:<runId>:<toolName>` — distinto de `nexus:undo:run:<runId>` (ADR-6).
>
> **Rationale:**
> - **Pub/sub Redis (PUBSUB):** `@vercel/kv` v3 não expõe PUBSUB na surface pública — usa Upstash REST API que não suporta streaming pub/sub.
> - **Polling é sufficientemente rápido:** 250ms de latência máxima de confirmação é imperceptível para uma interacção human-in-the-loop onde o utilizador leva 1-5s a confirmar.
> - **TTL 60s:** mais que suficiente para o utilizador confirmar ou cancelar; após expiração o provider retorna `'cancel'` (safe default).
> - **Alinhamento com ADR-6:** partilha cliente `kv` singleton, namespace independente.
>
> **Alternatives considered:**
> - **Vercel PUBSUB/Redis Streams:** não disponível via `@vercel/kv` REST API surface.
> - **Long-polling endpoint separado:** complexidade desnecessária (SSE stream já existe no prompt handler).
> - **WebSocket:** requer infra separada, viola C2 (zero custos).
> - **In-process Promise (Story 1.6 default):** não funciona cross-process (razão deste ADR).
>
> **Consequences:**
> - Polling a cada 250ms não usa `kv` de forma ineficiente (< 240 reads/min por confirmação activa — dentro do free tier 10k req/dia).
> - Se `@architect` recusar polling: alternativas são (1) ignorar cross-process (usar auto-confirm default da Story 1.6, racionalizando que Vercel numa única instância para single-user) ou (2) revisitar PUBSUB em versão futura.

### Contexto técnico de arch — implementação SSE em Edge Runtime

**ReadableStream com generator:**

```typescript
// Padrão recomendado para SSE em Next.js 15 Edge:
// runAgent(userPrompt, opts) — assinatura canónica (executor.ts L464)
// executor gera runId internamente, classifica e filtra tools internamente
const kvProvider = new KvConfirmationProvider(kv);
const stream = new ReadableStream({
  async start(controller) {
    const encoder = new TextEncoder();
    let runId: string | undefined;
    try {
      for await (const event of runAgent(prompt, { confirmationProvider: kvProvider })) {
        // Capturar runId do primeiro meta(start) para logging
        if (event.type === 'meta' && event.phase === 'start') {
          runId = event.runId;
        }
        controller.enqueue(encoder.encode(`data: ${JSON.stringify(event)}\n\n`));
      }
      controller.enqueue(encoder.encode('data: [DONE]\n\n'));
    } catch (err) {
      // catch apenas se o próprio for-await lançar (raro — runAgent emite done.status='failed' internamente)
      // NÃO emitir type:'error' (não existe no ExecutorSSEEvent union — executor.ts L159-255)
      // Fechar stream limpo; o caller retorna 200 (stream já iniciado) e o cliente detecta via ausência de done
      logger.error('stream fatal', { runId, error: String(err) });
      controller.enqueue(encoder.encode('data: [DONE]\n\n'));
    } finally {
      controller.close();
    }
  },
});
return new Response(stream, {
  headers: {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  },
});
```

**SHA-256 hash PT-PT para logger (Edge-safe, sem Node `crypto`):**

```typescript
async function promptHash(prompt: string): Promise<string> {
  const encoder = new TextEncoder();
  const data = encoder.encode(prompt);
  const hashBuffer = await crypto.subtle.digest('SHA-256', data);
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  return hashArray.map(b => b.toString(16).padStart(2, '0')).join('').slice(0, 8);
}
```

**KvConfirmationProvider — polling pattern:**

```typescript
async requestConfirmation(runId: string, toolName: string): Promise<'confirm' | 'cancel'> {
  const key = `${KV_CONFIRM_NAMESPACE}:${runId}:${toolName}`;
  const deadline = Date.now() + CONFIRM_TTL_SECONDS * 1000;

  while (Date.now() < deadline) {
    const value = await this.kvClient.get<string>(key);
    if (value === 'confirm' || value === 'cancel') {
      await this.kvClient.del(key);
      return value;
    }
    await new Promise<void>(resolve => setTimeout(resolve, CONFIRM_POLL_INTERVAL_MS));
  }

  logger.warn('KvConfirmationProvider timeout', { runId, toolName });
  return 'cancel';
}
```

### Critical Issues (must-fix antes de @dev)

**Crit-1: AC4 redefine `runAgent()` — assinatura inventada (Article IV violado).**

A assinatura real em `lib/agent/executor.ts` L464 é:
```typescript
export async function* runAgent(
  userPrompt: string,
  opts: RunAgentOpts = {}
): AsyncGenerator<ExecutorSSEEvent>
```

`RunAgentOpts` (L121) tem APENAS: `model?`, `maxTokens?`, `maxToolIterations?`, `classifyOpts?`, `confirmationProvider?`. Não aceita `classifierResult`, `toolRegistry`, `executorProvider`, `ctx`.

AC4 actual (passos 3, 4, 6) prescreve:
```text
3. Chamar classifyPrompt(prompt, provider) ...
4. Construir ExecutionContext com kv real ...
6. Chamar runAgent(prompt, classifierResult, toolRegistry, executorProvider, ctx, { confirmationProvider })
```

Erros materiais:
- `runAgent` chama `classifyPrompt` **internamente** (L518 do executor) — handler NÃO deve invocar separadamente.
- `runId` é gerado **dentro** de `runAgent` (L473 `const runId = crypto.randomUUID()`) e exposto via `meta(start)` event — handler NÃO gera runId externamente.
- `toolRegistry` é importado e usado **internamente** pelo executor via `getToolsForDomains` (L272-295) — não passado como argumento.
- `ExecutionContext` é construído pelas tools no momento da execução, não passado a `runAgent` — executor é stateless por design (RESOLVED-2 Story 1.5).
- `executorProvider` não é argumento de `runAgent` — `AnthropicExecutor` é instanciado internamente.

**Implicação:** o handler real de `app/api/agent/prompt/route.ts` é muito mais simples do que AC4 sugere — basicamente `for await (const event of runAgent(prompt, { confirmationProvider }))`. A complexidade de AC4 não existe; @dev confundir-se-ia ao tentar implementar a assinatura inventada.

**Fix sugerido (a aplicar em AC4 + Tasks 3.5/3.6/3.8 + Dev Notes ReadableStream snippet):**
```text
4. Fluxo principal do handler:
   1. Parse + validar body (AC2) → 400 PT-PT em falha
   2. Auth via getSession(req) (AC3) → 401 PT-PT em falha
   3. Construir KvConfirmationProvider (AC7) — runId será correlacionado via meta(start) event
   4. Iterar `for await (const event of runAgent(prompt, { confirmationProvider: kvProvider }))`
   5. Capturar runId do primeiro evento (meta phase=start) para logging + correlação com KvConfirmationProvider
   6. Serializar cada event como `data: ${JSON.stringify(event)}\n\n`
   7. Terminar stream com `data: [DONE]\n\n` após `done`
```

**Subnota:** O `KvConfirmationProvider` precisa do `runId` no construtor (AC7). Mas `runId` só é conhecido após o `meta(start)` event do `runAgent`. Há 2 caminhos válidos:
- (a) `KvConfirmationProvider` aceita `runId` no método `requestConfirmation(runId, toolName)` em vez do constructor — **respeita a interface canónica de Story 1.6 L107** que já tem `runId` como argumento.
- (b) Provider é construído com closure sobre uma `Promise<string>` que resolve no primeiro `meta(start)`.

Caminho (a) é o correcto e já está alinhado com `ConfirmationProvider` interface. AC7 deve refactorar: o construtor recebe **apenas** `kvClient` (não `runId` — esse vem por argumento como na interface).

**Crit-2: AC10 mock de `runAgent` inventa shape do `done` event.**

Dev Notes linha 441 escreve:
```typescript
yield { type: 'done', runId: 'test-run-id', status: 'success', previewCount: 0, durationMs: 100, toolCallCount: 0 } as ExecutorSSEEvent;
```

Shape canónico do `done` event (executor.ts L238-255):
```typescript
{
  type: 'done';
  runId: string;
  status: 'success' | 'partial' | 'failed';
  intents: string[];          // OBRIGATÓRIO — em falta no mock
  inputTokens: number;        // OBRIGATÓRIO — em falta no mock
  outputTokens: number;       // OBRIGATÓRIO — em falta no mock
  durationMs: number;
  errorMessage?: string;
  totals: { intents: number; toolCalls: number };  // OBRIGATÓRIO — em falta no mock
  previewCount?: number;      // OPCIONAL
}
```

`toolCallCount` NÃO é campo do `done` event — o campo correcto é `totals.toolCalls`.

**Fix sugerido:** Substituir mock por shape canónico:
```typescript
yield {
  type: 'done', runId: 'test-run-id', status: 'success',
  intents: [], inputTokens: 0, outputTokens: 0, durationMs: 100,
  totals: { intents: 0, toolCalls: 0 },
  previewCount: 0,
};
```

E em AC10 (`tests/unit/api/agent/prompt.test.ts`), substituir o teste `'done' event inclui durationMs > 0` por `'done' event tem shape canónico (intents, inputTokens, outputTokens, totals, durationMs)`.

**Crit-3: AC4 passo 1 inverte ordem auth-vs-body do precedente Story 1.7.**

Story 1.7 endpoint (route.ts L124-159) faz **auth primeiro, body depois**. AC4 actual diz "1. Validar body (AC2) + auth (AC3)" sem especificar ordem, mas Tasks 3.2 e 3.3 listam body antes de auth.

Inverter para body antes de auth permite a um cliente sondar `prompt: ""` recebendo 400 sem ter sessão válida, divergindo do Story 1.7.

**Fix sugerido:** Reorder AC4 step 1 explicitamente: "1.a Auth via `getSession(req)` (AC3) → 401 em falha; 1.b Parse + validate body via `PromptRequestSchema` (AC2) → 400 em falha". Reorder Tasks 3.2 ↔ 3.3 conforme.

### Should-Fix Issues (não bloqueiam mas reduzem risco)

**SF-1:** AC3 escreve `Auth via getSession()` mas a assinatura real é `getSession(req: Request)` (auth/session.ts L73). Story 1.7 usa correctamente `getSession(req)`. Clarificar AC3 para `getSession(req)`.

**SF-2:** AC7 prescreve KvConfirmationProvider construtor com `(runId, kvClient)`. Como Crit-1 nota, o `runId` vem por argumento ao método `requestConfirmation` (interface Story 1.6 L107). Isto também simplifica a injecção no handler — o provider é construído UMA vez por request (antes do `for await`), sem precisar de aguardar o `meta(start)` event.

Stories 1.5/1.6/1.7 fazem o `runAgent` consumir excepções internamente e emite `done.status = 'failed'` com `errorMessage`. O snippet em Dev Notes "Contexto técnico de arch" (linhas 364-371) tem `catch (err) { controller.enqueue ... 'type: error' ... }` — esse `type: 'error'` NÃO existe no `ExecutorSSEEvent` union (executor.ts L159-255). Precisa de ser substituído por captura defensiva: o catch só dispara se o **próprio `for await` lançar** (caso raro).
