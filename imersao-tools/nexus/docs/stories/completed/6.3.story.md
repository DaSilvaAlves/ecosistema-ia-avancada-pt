## Nota do `@sm` River — verificação e contexto (Constitution Artigo IV)

Verificação 17/06/2026. A Story 6.3 implementa a **direcção PULL do sync de calendário** (FR59): eventos criados ou actualizados no Google Calendar são trazidos para o Nexus via sync incremental baseado em `syncToken`. O fluxo oposto (Nexus → Google) é a Story 6.4, fora do scope desta story.

**Ponto de entrada de access token:** `getValidAccessToken()` exportado por `lib/google/token-store.ts` (Story 6.2, já em `main`). Esta é a **única** função que a 6.3 deve chamar para obter um access token válido — nunca `getTokens().accessToken` directo. Esta regra é explícita no epiclevel (EPIC-6.md §5 row 6.2): "`getValidAccessToken()` é o único ponto de entrada de access token para 6.3/6.4/6.6/6.7".

**Helper puro:** toda a lógica de reconciliação vive em `lib/google/calendar.ts`. A route `POST /api/google/calendar/sync` é fina — apenas coordena: chama `getValidAccessToken()`, invoca o helper, trata erros de sessão. A lógica testável (~100%) fica no helper.

**Protocolo `events.list` Google Calendar API:** o sync incremental usa `syncToken` (devolve apenas alterações desde a última sincronização). Quando o `syncToken` expira (Google devolve `410 Gone`), é necessário um full resync (sem `syncToken`, iterar com `pageToken` até ao fim). O helper deve tratar ambos os casos.

**Modelo Nexus para eventos de calendário:** o PRD §6.11 não define explicitamente o schema Dexie para eventos de calendário. A 6.3 mapeia os campos do Google Event para um modelo Nexus — a estrutura exacta deve ser ratificada pelo `@architect` no draft. Marcado como `[GAP-6.3-SCHEMA]`.

**Estado distribuído (aplicação leve de `internal-state-contract-gate.md`):** o pull sync distribui estado por Google API + helper + Dexie + persistência do `nextSyncToken`. O gate `@qa` valida as classes de estado do ciclo de vida: evento novo / actualizado / cancelado (`status:cancelled`) / syncToken válido vs expirado (410). Não tem o peso de estado multi-camada da 6.2 ou 6.4, mas a análise de ciclo de vida é obrigatória.

## User Story

Como Eurico (utilizador do Nexus), quero que os eventos do meu Google Calendar apareçam automaticamente no Nexus através de sync incremental eficiente, para que as minhas obrigações de calendário estejam sempre visíveis no sistema de continuidade pessoal sem necessitar de entrada manual duplicada.

- **AC1 (helper puro `lib/google/calendar.ts` — lógica de reconciliação, testável ~100%):**
  Existe `lib/google/calendar.ts` com uma função exportada (ex: `syncCalendarEvents(accessToken: string): Promise<SyncResult>`) que: (i) chama `GET https://www.googleapis.com/calendar/v3/calendars/primary/events` com o `syncToken` guardado (se existir), ou full resync (sem `syncToken`) na primeira chamada ou após 410 Gone; (ii) itera por `pageToken` até não haver mais páginas (`nextPageToken` ausente); (iii) devolve a lista de alterações (novos, actualizados, cancelados) e o `nextSyncToken` para persistência; (iv) não chama `getValidAccessToken()` directamente — recebe o `accessToken` como parâmetro (desacopla do store de tokens, maximiza testabilidade). `[Source: EPIC-6.md §5 row 6.3; architecture-v2.md §3 tree]`
  _Onde é verificável: CI (Vitest + MSW mock — todos os cenários do helper)._

- **AC2 (persistência do `nextSyncToken` — `[GAP-6.3-SCHEMA]` — `@architect` decide onde guardar):**
  O `nextSyncToken` devolvido pelo Google após cada sync é persistido de forma que o próximo sync o utilize como `syncToken`. `[GAP-6.3-SCHEMA]`: `@architect` decide no draft se o syncToken vive em: (a) Vercel KV (chave `nexus:google:calendar:syncToken`) — consistente com o padrão de server-side storage do Epic 6; (b) no próprio registo de tokens KV (campo adicional em `nexus:google:tokens`); (c) outro mecanismo. A decisão impacta quem persiste (a route ou o helper) e o schema KV. **Não implementar sem esta decisão ratificada.** Após a decisão, o AC é actualizado com a forma correcta.
  _Onde é verificável: CI (Vitest + MSW mock — teste de persistência e reutilização do syncToken)._

- **AC3 (eventos novos e actualizados — reconciliação em Dexie — `[GAP-6.3-SCHEMA]`):**
  Eventos com `status: 'confirmed'` retornados pelo sync são guardados/actualizados em Dexie com um mapeamento canónico dos campos Google Event → modelo Nexus. `[GAP-6.3-SCHEMA]`: `@architect` define o schema Dexie para eventos de calendário (ex: tabela `calendarEvents` com `{ id: string, googleId: string, title: string, startAt: number, endAt: number, allDay: boolean, updatedAt: number }`). O mapeamento é idempotente: re-sincronizar o mesmo evento não cria duplicados (idempotência por `googleId`/`id` do evento Google). Os campos de data suportam tanto `dateTime` (com hora) como `date` (dia inteiro / `allDay: true`).
  _Onde é verificável: CI (Vitest + MSW mock — upsert idempotente)._

- **AC4 (eventos cancelados — remoção de Dexie):**
  Eventos com `status: 'cancelled'` retornados pelo sync incremental são removidos de Dexie (ou marcados como eliminados, conforme decisão de `@architect`). O tratamento de `status: 'cancelled'` é explícito no helper e testado separadamente. Um evento cancelado que não existe em Dexie (nunca foi sincronizado) não causa erro — é ignorado graciosamente.
  _Onde é verificável: CI (Vitest + MSW mock — remoção de evento cancelado)._

- **AC5 (caso 410 Gone — syncToken expirado → full resync automático):**
  Quando o Google devolve `410 Gone` (syncToken expirado), o helper: (i) apaga o syncToken guardado; (ii) reinicia automaticamente o sync com full resync (sem `syncToken`, `singleEvents=true`); (iii) a route devolve `{ ok: true, fullResync: true, eventsProcessed: N }` em vez de um erro (o 410 é um caso operacional normal, não um bug). O comportamento é explicitamente testado com um MSW handler que devolve 410.
  _Onde é verificável: CI (Vitest + MSW mock — cenário 410 Gone)._

- **AC6 (route `POST /api/google/calendar/sync` — Node runtime, fina):**
  Existe `app/api/google/calendar/sync/route.ts` com `export const runtime = 'nodejs'`. A route: (i) verifica sessão com `getSession()` — devolve 401 sem sessão; (ii) chama `getValidAccessToken()` (de `lib/google/token-store.ts`) — se devolver `null`, devolve 401 `{error: 'not_connected'}`; se lançar `TokenRevokedError`, devolve 401 `{error: 'token_revoked'}`; se lançar `TokenRefreshError`, devolve 503; (iii) invoca o helper `syncCalendarEvents(accessToken)` com o token válido; (iv) devolve `{ ok: true, eventsProcessed: N, fullResync: boolean }`. A route é fina — zero lógica de reconciliação (tudo no helper).
  _Onde é verificável: CI (Vitest + MSW mock — cenários de auth e delegação ao helper)._

- **AC7 (MSW handlers — fidelidade de protocolo, `mock-protocol-fidelity.md`):**

### Completion Notes

- **DEV-DECISION D-6.3-FETCH-DIRECT:** o helper usa `fetch` global directo contra `https://www.googleapis.com/calendar/v3/calendars/primary/events` (não o SDK `googleapis`), seguindo o precedente estabelecido em `token-store.ts` (`getValidAccessToken` usa `fetch` directo). Razão: o MSW intercepta `fetch` global de forma fiável; o SDK `googleapis` pode não passar por MSW e quebra a fidelidade de protocolo (AC7). Confirmei o shape camelCase real (`nextSyncToken`/`nextPageToken`/`dateTime`) contra `node_modules/googleapis/build/src/apis/calendar/v3.d.ts` — a Calendar API v3 JSON usa **camelCase** (distinto do snake_case do OAuth2 token endpoint). O handler MSW e o teste falsificável (AC7) provam-no: um teste com `next_sync_token` (snake_case errado) resulta em `nextSyncToken: null`.
- **Atomicidade do cursor (AC2/AC5):** a route persiste o `nextSyncToken` SÓ NO FIM do sync bem-sucedido, nunca por página. Falha a meio da paginação (5xx) propaga ANTES de devolver o cursor → a route não persiste cursor parcial (teste `falha a meio da paginação...`).
- **410 Gone (AC5):** tratado dentro do helper — sentinela interna `SyncTokenExpired` → reinicia full resync automático (sem syncToken) → devolve `fullResync: true`. A route apaga o cursor antigo antes de gravar o novo.
- **Caminhos de falha (AC8 eixo c):** 401 do Google → `CalendarAuthError` → route 401 `token_revoked`; 5xx → `CalendarSyncError` → route 503 `calendar_unavailable` (anti-padrão M4 da 4.9 evitado — NUNCA `200 {ok:false}`); `TokenRevokedError` → 401 `token_revoked`; `TokenRefreshError` → 503 `refresh_failed`.
- **IDS protocol:** REUSE de `getValidAccessToken()` (token-store 6.2), `getSession()` (auth/session), padrão de repo Dexie (transacção `rw`), `CalendarEventSchema` (schemas.ts Zod). CREATE justificado: `calendar.ts` (helper puro novo), `calendar-sync-token.ts` (store KV dedicado — D-6.3-SYNC-TOKEN), route nova. ADAPT: handlers MSW google.ts (expandido com `events.list`).
- **Regra `dexie_version_bump_full_suite`:** version(6) obrigou a actualizar 2 ficheiros de schema-upgrade test (`schema-upgrade.test.ts` + `schema-upgrade-v3.test.ts`): verno 5→6, contagem 21→22 tabelas, asserção `calendarEvents`. Suite COMPLETA corrida (1990 PASS), não scoped.
- **DEV-DECISION D-6.3-POSITIVE-EPOCH (CR Iter 1, 17/06/2026 — Opção A):** o CodeRabbit `--base main` (gate de saída `@devops`) apanhou 1 Major: `CalendarEventSchema` usava `.nonnegative()` em `startAt`/`endAt`/`updatedAt`, mas toda a convenção do codebase usa `.positive()` para epoch ms (11+ ocorrências: `Reminder.fireAt`, `Task/Account.createdAt/updatedAt`, etc.) — o `CalendarEventSchema` era a única excepção. Apliquei a **Opção A** (recomendada): `.nonnegative()` → `.positive()` (alinha com a convenção; epoch 0 nunca é timestamp legítimo). Componente acoplada tratada na mesma passagem: `toEpochMs(undefined)` deixou de devolver `{ms:0}` (que com `.positive()` lançaria `ZodError` não tratado → 500 na route) e passa a devolver `{ms:NaN}`; `mapEvent` detecta epoch não-positivo/NaN (start/end/updatedAt) e devolve `null`; `reconcilePage` trata o `null` como **skip gracioso** — exactamente o padrão já usado para `!event.id` (não persiste, contabiliza, NÃO lança). Adicionei o contador `skipped` ao `SyncResult` (precedente do codebase: `recurrence.ts`, `v1-to-v2.ts`), propagado por `runSync`/`syncCalendarEvents` e exposto na resposta da route para observabilidade. Teste novo prova o caminho: evento `confirmed` sem `start`/`end` (shape real do Google) → `skipped:1`, não persistido, sem throw. Varredura de classe (A2): `toEpochMs` era o único ponto produtor de epoch 0; o único outro `.parse()` de shape externo no helper é o do upsert, agora protegido pelo filtro de `mapEvent`. Verificação: lint EXIT 0, typecheck EXIT 0, vitest 1991 PASS/0 FAIL (+1 teste novo).
