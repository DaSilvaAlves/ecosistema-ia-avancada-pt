### `[D-6.1-PKCE]` — RATIFICADA: Opção (A) state opaco assinado HMAC-SHA256 + (PKCE como débito da 6.2)

**Decisão:** state opaco assinado com `crypto.createHmac('sha256', SESSION_SECRET)`, armazenado em KV com TTL curto (`nexus:google:oauth-state:<state>`, TTL 600s) e validado no callback. **PKCE NÃO é exigido na 6.1.**

**Justificação (traça à arch + RFC):**
- O cliente OAuth do Nexus é um **confidential server-side client** — o `GOOGLE_OAUTH_CLIENT_SECRET` vive server-only em Vercel env (`env.ts:20`; arch §9.2:789) e nunca chega ao browser. PKCE (RFC 7636) foi desenhado para **public clients** (SPA/mobile) que não conseguem guardar um secret. Para confidential clients o `client_secret` na troca de code já fornece a prova de posse que o PKCE replicaria.
- A arch §16 (`architecture-v2.md:1142`) prescreve explicitamente "OAuth state é **assinado** com `SESSION_SECRET` para CSRF protection". A Opção (A) é o que a arch já decidiu — escolher (B) seria inventar para além da arch (Artigo IV).
- O state assinado + TTL + single-use (apagar no callback) cobre integralmente a ameaça de CSRF no callback, que é a ameaça real aqui. RFC 9700 §2.1 aceita o state assinado como mitigação suficiente de CSRF para confidential clients.
- **Trade-off:** PKCE acrescentaria defesa-em-profundidade marginal (protege contra interceptação do code num canal já TLS) mas adiciona um `code_verifier`/`code_challenge` a transportar e armazenar — complexidade desproporcional para single-user, test mode permanente. **Registado como REC-6.1-PKCE (débito não-bloqueador):** se a 6.2 reavaliar a postura de segurança, PKCE S256 pode ser adicionado sem refactor (o state-store já existe).

**Condições vinculativas (gate de saída):**
1. O HMAC usa o `SESSION_SECRET` lido via `getServerEnv()` — **nunca** `process.env` raw.
2. O state é **single-use**: o callback apaga a entrada KV (`kv.del`) após validação bem-sucedida, ANTES da troca de code (eixo b do ciclo de vida — evita replay do state).
3. O state assinado inclui nonce aleatório (`crypto.randomUUID()`) — o HMAC é sobre o nonce, não sobre valor previsível.
4. Comparação do HMAC em **tempo constante** (`crypto.timingSafeEqual`) — padrão já usado em `lib/push/cron-auth.ts`.

### `[D-6.1-CALLBACK]` — RATIFICADA: Opção (A) `app/api/google/oauth/callback/route.ts` (path literal dedicado). RESOLVE a divergência da arch.

**Decisão:** o callback vive em `v2/app/api/google/oauth/callback/route.ts` (path literal `/callback`). O **início** do fluxo vive em `v2/app/api/google/oauth/start/route.ts`. **NÃO** se usa a rota dinâmica `[provider]`.

**Resolução da divergência da arch (sinalizada pelo `@po`):**
- A arch tem uma incoerência real entre **§3:102** (`google/oauth/[provider]/route.ts`) e **§9.2:790 + §9.4** (`GOOGLE_OAUTH_REDIRECT_URI = …/api/google/oauth/callback`).
- **§9.2:790 prevalece** porque o redirect URI é um **identificador de contrato externo** (`external-contract-identifiers.md`): tem de bater **ao caracter** com o valor registado no Google Cloud Console (P1), caso contrário o Google rejeita com `redirect_uri_mismatch`. O path literal `/callback` é o que está documentado como o valor a registar — é a fonte de verdade do contrato.
- A rota dinâmica `[provider]` resolveria `…/oauth/callback` com `params.provider === 'callback'` — semanticamente **errado** ("callback" não é um provider) e frágil (qualquer caminho sob `/oauth/*` cairia no mesmo handler). O padrão `[provider]` da §3 foi uma generalização prematura: o Nexus tem **um único provider** (Google) e o scope incremental Gmail da 6.7 reutiliza o **mesmo** cliente OAuth Google (mesma rota de callback, scope diferente no `generateAuthUrl`) — não precisa de um segmento `[provider]` distinto.
- **Acção sobre a arch:** a §3:102 deve ser corrigida para `google/oauth/callback/route.ts` + `google/oauth/start/route.ts`. Esta correcção da arch é registada como **REC-6.1-ARCH** (não-bloqueadora da implementação; a story usa já o path correcto). A arch é L2/documentação — a correcção pode acompanhar esta story ou ser feita pelo `@architect` em doc separado.

**Condições vinculativas:**
1. `GOOGLE_OAUTH_REDIRECT_URI` (env + Google Cloud Console P1) = `https://nexus-eurico.vercel.app/api/google/oauth/callback` — exactamente, sem trailing slash.
2. Ambas as rotas (`start`, `callback`) correm em **Node** (ADR-1; arch §4.1:197) — `export const runtime = 'nodejs'` explícito ou omissão (Node é default ao importar `googleapis`).

### `[D-6.1-ERROR]` — RATIFICADA: máquina de estados com erro tipado + redirect com `?error=<tipo>` (sem dump silencioso)

**Decisão:** o callback **nunca** devolve um erro cru ao browser nem faz throw não-tratado. Mapeia cada falha para um tipo de erro fechado e redirige para `/settings?error=<tipo>`. A UI (`GoogleCalendarSettings`) lê o query param e apresenta mensagem PT-PT + CTA de retentar. Tipos de erro fechados:

| `?error=` | Causa | Origem |
|-----------|-------|--------|
| `access_denied` | Utilizador cancelou/negou o consent | query param `error` do Google no callback |
| `invalid_state` | State ausente, inválido, expirado ou já usado (CSRF) | validação HMAC/KV falha → **também 403 antes do redirect** (ver AC6) |
| `token_exchange_failed` | `getToken` devolveu erro (`invalid_grant`, etc.) | excepção/erro de `exchangeCode` |
| `storage_failed` | Escrita em KV falhou após troca bem-sucedida | excepção de `kv.set` |
| `account_mismatch` | (reservado) conta Google ≠ esperada — opcional, single-user | verificação futura |

**Justificação:** `internal-state-contract-gate.md` eixo (c) exige que **cada** caminho de falha entre camadas seja tratado explicitamente como falha, nunca como sucesso silencioso (lição M1/M4 da 4.9). O conjunto fechado de tipos torna a UI testável (AC4: estado `erro` por tipo) e impede que detalhes do Google (que podem conter dados sensíveis) vazem para a URL/UI.

**Condições vinculativas:**
1. `invalid_state` produz **403** no handler (AC6) E o redirect didáctico — a troca de code **nunca** ocorre com state inválido.
2. Nenhum tipo de erro inclui o `code`, o `state`, ou qualquer token na query string ou em logs (NFR11 adaptado).
3. Strings de erro PT-PT vivem no componente, não no handler (o handler só passa o tipo).

### `[D-6.1-SCOPE]` — RATIFICADA: Opção (A) 6.1 armazena tokens em KV SEM encriptação at-rest; encriptação é da 6.2

**Decisão:** a 6.1 escreve `nexus:google:tokens → { accessToken, refreshToken, expiresAt }` em KV **sem encriptação at-rest**, via `@vercel/kv` (padrão `subscriptions-store.ts`). A camada de encriptação at-rest, refresh flow e revogação são da **6.2** (GAP-6.2). O seam é um **token-store** (`lib/google/token-store.ts`) com interface `saveTokens/getTokens/deleteTokens` que a 6.2 reimplementa por dentro **sem mudar a interface** — zero refactor dos callers.

**Justificação (decisão de segurança):**
- Separação de responsabilidades: a 6.1 prova o fluxo OAuth end-to-end (authorize → callback → tokens em KV) testável sem a complexidade criptográfica da 6.2. GAP-6.2 (`EPIC-6.md` §7) é **explicitamente** a encriptação — invadir esse scope na 6.1 violaria a fronteira definida no epic.
- **Avaliação de risco da janela desencriptada:** o Vercel KV (Upstash) é encriptado at-rest **ao nível do fornecedor** e o acesso exige `KV_REST_API_TOKEN` (server-only). A app é single-user, test mode permanente. A janela em que os tokens vivem sem encriptação **aplicacional** (até a 6.2) é aceitável para este perfil de risco — não há multi-tenancy nem exposição pública do KV. O `refreshToken` é o activo mais sensível; fica protegido pelo token de acesso ao KV e pelo TLS Upstash.
- **Trade-off vs Opção (B):** encriptar já na 6.1 evitaria a janela, mas (i) acopla 6.1 à decisão criptográfica que pertence à 6.2, (ii) torna os testes da 6.1 dependentes de gestão de chave, (iii) GAP-6.2 ficaria sem objecto. O seam por interface (`token-store.ts`) dá o melhor dos dois: a 6.1 entrega simples, a 6.2 adiciona a cifra por dentro sem tocar nos callers.

**Condições vinculativas:**
1. O seam é a interface `token-store.ts` (`saveTokens/getTokens/deleteTokens`) — os callers (callback route, status check) **nunca** acedem ao `kv` directamente para tokens; usam o store. Isto garante que a 6.2 troca a implementação sem refactor.
2. `saveTokens` só é chamado após `access_token` presente e não-vazio (AC3 — nunca persiste tokens parciais; eixo b/c).
3. Esta janela desencriptada é registada como **REC-6.1-ENCRYPT (débito explícito da 6.2)** na story — não é uma omissão, é uma fronteira deliberada.

### Análise de ciclo de vida do token — `internal-state-contract-gate.md` (obrigatória; Epic 6 é o alvo principal da regra)

O contrato de estado do token OAuth distribui-se por ≥2 camadas (KV `nexus:google:tokens` + KV `nexus:google:oauth-state` + callback route + componente UI). Os três eixos, respondidos contra o desenho ratificado:

| Eixo | Resposta para a 6.1 | Major que previne |
|------|---------------------|-------------------|
| **(a) Classes de estado** | Token: `não-existente` / `válido`. A 6.1 entrega **apenas** a transição `não-existente → válido`. `expirado→renovado` e `válido→revogado` são da 6.2 — o componente UI **não** deve afirmar `ligado` baseado só na presença da chave sem considerar `expiresAt` (mas a renovação em si é da 6.2; a 6.1 pode mostrar `ligado` se a chave existe e documentar que a validade fina é da 6.2). State: `não-existente`/`válido`/`usado`/`expirado`. | UI afirmar `ligado` sobre token inexistente |
| **(b) Transição-já-ocorrida** | O `code` do Google é **single-use** (Google invalida após troca) — replay do code → `token_exchange_failed`, nunca silent overwrite. O **state** é single-use: apagado do KV após validação, ANTES da troca — replay do state → `invalid_state`/403. | Replay de code/state tratado como sucesso |
| **(c) Caminhos de falha** | `access_denied`, `invalid_state` (403), `token_exchange_failed`, `storage_failed` — cada um redirige com `?error=<tipo>` (D-6.1-ERROR). Falha de `kv.get`/`kv.set` é tratada (não assume sucesso). Sessão inválida no `start` → 401. | Falha-como-sucesso (M4 da 4.9) |

Esta análise é **condição de saída**: o gate de saída re-verifica os três eixos contra o código real antes do PASS.

## User Story

Como Eurico (utilizador do Nexus), quero poder iniciar o fluxo de autorização Google (scope `calendar`) a partir das definições da app, e que o Nexus complete o callback OAuth e armazene os tokens necessários, para que as integrações de calendário das stories seguintes (6.2-6.6) possam aceder ao Google Calendar em meu nome.

## Contexto

`PRD-NEXUS-V2.md` §6.11 (FR58: "OAuth flow Google (scope `calendar`) iniciado pelo utilizador nas definições") é o requisito raiz. `EPIC-6.md` §5 (row 6.1) atribui a esta story o fluxo completo de autorização — UI de definições + handler de início + callback Node + armazenamento em KV. Esta é a **fundação de toda a integração Google**: Calendar + Gmail partilham o mesmo cliente OAuth (`googleapis`), pelo que o que se constrói aqui é reutilizado pela 6.7 (Gmail scope incremental).

É a primeira vez que o Nexus v2 delega autenticação a um terceiro. O endpoint `/api/google/oauth/*` corre em **Node runtime** (ADR-1, arch §4.1) porque `googleapis` SDK precisa de `http`/`crypto` Node — não pode correr em Edge. A app fica em **test mode permanente** (PRD §11 R4, AR5 arch §18): single-user, < 100 utilizadores, sem verification Google.

**Relação com 6.2:** a 6.1 entrega o fluxo OAuth end-to-end (authorize → callback → tokens em KV). A 6.2 adiciona a camada de segurança server-side (encriptação at-rest, refresh flow, revogação). A fronteira exacta é decidida por `[D-6.1-SCOPE]` no Architect Gate de Entrada.

O ciclo de vida do token OAuth distribui-se por ≥2 camadas (KV + route de callback + componente de UI). Os três eixos a cobrir no quality gate:

- **(c) Caminhos de falha:** `access_denied`, state inválido, code inválido, falha KV — cada um tratado explicitamente (não como sucesso silencioso).

### 1. Adjudicação do FLAG F2 (CodeRabbit Iter 1, Major) — DECISÃO: RECONCILIAR AC6 → 302 (com distinção forjado vs expirado)

**O CodeRabbit tem razão na substância.** Verifiquei a verdade técnica contra a especificação HTTP (MDN/RFC 9110): o header `Location` só desencadeia navegação automática do browser em respostas **3xx** (e `201 Created`). Num **403 Forbidden** o `Location` é **ignorado** pelo user-agent — o browser renderiza o corpo da resposta. No código actual (`callback/route.ts:72-75`) o corpo é `null`, logo o utilizador vê **página em branco**, nunca `?error=invalid_state`. O AC4 (estado `erro` com mensagem PT-PT + CTA "Tentar novamente") fica **inalcançável** para o caso mais comum e legítimo: state expirado (TTL 600s ultrapassado entre o início do fluxo e o regresso do consent screen).

**A tensão real** (que o gate de entrada não desambiguou e por isso é minha responsabilidade resolver agora): `[D-6.1-ERROR]` cond.1 e AC6 prescreveram "403 imediato" tratando **toda** a falha de state como uma só classe. Mas o eixo (a) do ciclo de vida distingue duas sub-classes com perfis opostos:

| Sub-classe de state inválido | Quem a causa | Resposta correcta |
|------------------------------|--------------|-------------------|
| **expirado** / **já-consumido** (single-use) / **ausente** | **utilizador legítimo** (demorou no consent, refrescou, clicou 2x) | **302** → `/settings?error=invalid_state` (alcança a UI, pode retentar) |
| **assinatura HMAC inválida** (forjado) | **atacante** (CSRF, state fabricado) | manter rigor de segurança; **não** é um fluxo de UX a recuperar |

O ponto crítico: em **ambas** as sub-classes a troca de code **nunca ocorre** (a segurança de AC6 — "sem troca de code com state inválido" — é preservada na íntegra independentemente do status HTTP). O status 403 vs 302 **não** é o que protege contra CSRF; o que protege é o short-circuit `verifyAndConsumeState` → não-trocar. O 403 era uma escolha de *forma* que, por uma propriedade do browser, **quebra a recuperabilidade sem acrescentar segurança real** — porque um atacante CSRF nunca vê a UI de qualquer forma (não tem sessão/browser do Eurico no fluxo), e o utilizador legítimo é penalizado com um ecrã morto.

**DECISÃO ratificada:** reconciliar AC6 e `[D-6.1-ERROR]` cond.1 — o callback redirige com **302** para `/settings?error=invalid_state` em **todas** as classes de state inválido. A garantia de segurança mantém-se literal: **a troca de code nunca ocorre com state inválido** (já é o caso — `verifyAndConsumeState` short-circuita antes de `exchangeCode`). Mantém-se o registo de que nenhum token/code/state aparece na query nem em logs.

**Por que não manter 403 + clarificar AC6 (a outra opção):** manter 403 só seria defensável se o 403 comprasse segurança que o 302 não tem. Não compra — a propriedade de não-trocar-code é o que dá a segurança, e essa é ortogonal ao status. Manter 403 preservaria a letra de um AC à custa de um caminho de falha real do contrato de estado (utilizador legítimo sem UI). Entre a letra de um AC frozen e a regra `internal-state-contract-gate.md` (eixo c: caminhos de falha entre camadas têm de ser tratados como falha *recuperável e visível*, não como ecrã morto), a regra prevalece — e por isso reconcilia-se o AC, de forma rastreável, em vez de o contornar.

> **RECONCILIAÇÃO DE AC RASTREÁVEL (padrão D-NAMES 3.11 / external-contract-identifiers.md):**
> - **AC6, bullet 1** — ANTES: *"State inválido ou ausente no callback → 403 imediato, sem troca de code."* — DEPOIS (reconciliado por Architect Gate de saída 16/06/2026): *"State inválido, ausente, expirado ou já-usado no callback → **redirect 302** para `/settings?error=invalid_state`, **sem troca de code** (a troca nunca ocorre com state inválido — garantia de CSRF preservada; o status passa de 403 a 302 para que o utilizador legítimo com state expirado alcance a UI de erro, RFC 9110: `Location` só é honrado em 3xx)."*
