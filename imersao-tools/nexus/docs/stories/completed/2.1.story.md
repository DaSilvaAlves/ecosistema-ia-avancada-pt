## User Story

Como `@data-engineer` (Dara), quero incrementar o schema Dexie para `version(2)` com as tabelas `recurrences` e `tags`, e entregar schemas Zod + repositories tipados + hooks reactivos para `tasks`, `projects`, `recurrences` e `tags`, para que as Stories 2.2-2.10 do Epic 2 possam persistir/ler tarefas, projectos, recorrências e etiquetas sem duplicar lógica de acesso a Dexie nem cair em invariantes inconsistentes.

## Contexto

`PRD-NEXUS-V2.md` §6.2 (FR9, FR10, FR14) e §6.5 (FR29, FR30) definem o domínio Tarefas/Projectos. `EPIC-2.md` §2 enquadra o ângulo de continuidade: o campo `context` ("onde parei") + `lastWorkedAt` da `Task` é o que distingue isto de uma to-do list genérica — alinhado à visão Nexus.

`architecture-v2.md` ADR-2 decidiu **Dexie 4 IndexedDB desde o dia 1** (o PRD falava em "localStorage" — superado). `architecture-v2.md` §16 linha 1121 é explícita: **"Story 2.1 schema vai para Dexie version 2 (incremento ao schema base)"**. Cada Epic adiciona `this.version(N+1).stores({...})` sem reescrever o anterior — Dexie preserva os dados existentes no upgrade.

A Story 1.1 (Epic 1) estabeleceu o padrão de data access layer que esta story replica para o domínio Tarefas: `lib/db/repos/{tabela}.ts` (repos tipados com validação Zod), `lib/*/schemas.ts` (schemas Zod canónicos), `hooks/use{Algo}.ts` (wrappers `useLiveQuery`).

## Resoluções (`@po` 15/05/2026)

> As 3 perguntas abertas do draft original foram **decididas pela `@po`** no `PO-VALIDATION-STORY-2.1.md` §1 (15/05/2026) com fundamentação canónica directa — sem escalação a `@architect`. As decisões abaixo são **firmes** e estão baked-in nos AC3/AC6/AC9. Histórico das perguntas originais ver `PO-VALIDATION-STORY-2.1.md` §1.

| # | Decisão firme `@po` | Fundamentação |
|---|---------------------|---------------|
| Q1 | `Task.tags: string[]` guarda **ids** de tag (não nomes). Rename-safe. | `Tag.id` explícito em `architecture-v2.md §6.2` + `types/db.ts:88-92` (seria vestigial se não usado). Rename-safety é crítica numa ferramenta de continuidade pessoal — o utilizador vai reorganizar taxonomia ao longo do uso. |
| Q2 | Tabela `tags` **sem** índice único `&name`. Em vez disso, **verificação repo-level com normalização case-insensitive** (`name.trim().toLowerCase()` para comparação; persiste `name` com a capitalização original escolhida). Lança `Error('Já existe uma tag com o nome "{name}"')` em PT-PT se duplicado. | UX: mensagem PT-PT clara vs `ConstraintError` opaco do Dexie. Apanha "Urgente"/"URGENTE"/"urgente" como duplicados. Tabela de tags é pequena — `db.tags.toArray()` + filter é trivial. |
| Q3 | Índice `recurrences: 'id, ownerType, ownerId, [ownerType+ownerId]'`. Composto `[ownerType+ownerId]` serve `getRecurrenceByOwner` (lookup dominante). | Derivação directa de `architecture-v2.md §6.2` (campos `ownerType` + `ownerId` da `Recurrence`) + padrão consistente com `[habitId+date]` / `[conversationId+timestamp]` em `architecture-v2.md §4.2`. Não-invenção. `@architect` pode sanity-check em qa-gate (não-bloqueante). |

## Acceptance Criteria

- **AC1:** `lib/db/client.ts` incrementa para `this.version(2).stores({ recurrences: '...', tags: '...' })` **sem reescrever** o bloco `version(1)`. As 13 tabelas de `version(1)` (incl. `tasks`, `projects`) ficam intactas — Dexie preserva os dados existentes no upgrade. Apenas as 2 tabelas novas (`recurrences`, `tags`) são adicionadas.
- **AC2:** A classe `NexusDB` declara `recurrences!: Table<Recurrence, string>` e `tags!: Table<Tag, string>` (importando `Recurrence`/`Tag` de `@/types/db`, que já existem).
- **AC3:** Índices: `recurrences: 'id, ownerType, ownerId, [ownerType+ownerId]'` e `tags: 'id, name'`. **Decisão firme `@po` (Q2 + Q3) — baked-in.**
- **AC4:** O comentário incorrecto em `client.ts:22` ("Epic 2 incrementa para version 2 (adiciona installments, accounts, cards)") é corrigido — `installments`/`accounts`/`cards` são Epic 3. O comentário passa a descrever `recurrences` + `tags` para Epic 2.
- **AC5:** Existe `lib/db/schemas.ts` com schemas Zod `TaskSchema`, `ProjectSchema`, `RecurrenceSchema`, `TagSchema` que espelham fielmente as interfaces de `types/db.ts:54-92`. Campos obrigatórios com mensagem PT-PT (ex: `z.string().min(1, 'Título é obrigatório')`). Nenhum `any`. (Rationale do ficheiro: schemas de domínio DB, paralelo a `lib/agent/schemas.ts` que é domínio agente.)
- **AC6:** Existe `lib/db/repos/tasks.ts` que exporta funções tipadas: `createTask(input)`, `getTask(id)`, `listTasks(opts?)`, `updateTask(id, patch)`, `setTaskStatus(id, status)`, `deleteTask(id)`. Validam input via Zod antes de `db.tasks.*`. `listTasks` suporta filtros por `status`, `projectId`, `tag` via os índices de `version(1)`. Default: ordenado desc por `createdAt`. **Filtro por tag recebe `tagId` (string)** — decisão firme `@po` Q1: `db.tasks.where('tags').anyOf([tagId])` via índice multi-entry `*tags`. `Task.tags: string[]` guarda **ids**, não nomes.
- **AC7:** Existe `lib/db/repos/projects.ts` que exporta: `createProject(input)`, `getProject(id)`, `listProjects(opts?)`, `updateProject(id, patch)`, `archiveProject(id)` (atalho que define `status: 'paused'` ou `'done'` — confirmar semântica de "arquivar" com a interface `Project.status: 'active'|'paused'|'done'`; `EPIC-2.md` §5 usa "arquivar" para Story 2.8 — aqui só o helper base).
- **AC8:** Existe `lib/db/repos/recurrences.ts` que exporta: `createRecurrence(input)`, `getRecurrence(id)`, `getRecurrenceByOwner(ownerType, ownerId)`, `deleteRecurrence(id)`. `getRecurrenceByOwner` usa o índice composto `[ownerType+ownerId]`.
- **AC9:** Existe `lib/db/repos/tags.ts` que exporta: `createTag(input)`, `listTags()`, `getTag(id)`, `deleteTag(id)`. `createTag` **rejeita duplicados via normalização case-insensitive** (decisão firme `@po` Q2): comparação faz `name.trim().toLowerCase()` contra todas as tags existentes; se já existir, lança `Error('Já existe uma tag com o nome "{name}"')` em PT-PT. Persiste o `name` com a capitalização original escolhida pelo utilizador. Implementação via `db.tags.toArray()` + filter (tabela pequena — performance trivial).
- **AC10:** Hooks reactivos: `hooks/useTasks.ts` exporta `useTasks(opts?)` (wrapper `useLiveQuery` sobre `listTasks`, retorna `Task[] | undefined`); `hooks/useProjects.ts` exporta `useProjects()`. Seguem o padrão de `hooks/useAgentRuns.ts` (Story 1.1).
- **AC11:** Tests Vitest em `tests/unit/db/repos/` cobrem CRUD roundtrip de cada repo (`tasks`, `projects`, `recurrences`, `tags`), `listTasks` com cada filtro, `getRecurrenceByOwner` via índice composto, e `createTag` a rejeitar duplicado. Usam `fake-indexeddb` (já em `tests/setup.ts`).
- **AC12:** Tests Vitest em `tests/unit/db/schemas.test.ts` cobrem casos negativos: `Task` sem `title` rejeitada; `Task.status` fora do enum rejeitado; `Recurrence.ownerType` inválido rejeitado; `Project` sem `name` rejeitado.
- **AC13:** Teste de upgrade de schema: abrir a DB, inserir dados com `version(1)` activo, confirmar que após upgrade para `version(2)` os dados de `tasks`/`projects` persistem e as tabelas `recurrences`/`tags` estão disponíveis e vazias.
- **AC14:** Quality gates locais passam em `imersao-tools/nexus/v2/`: `npm run lint`, `npm run typecheck`, `npm run test:unit` (todos os existentes + novos), `npm run build`.
- **AC15:** Coverage de `lib/db/repos/**` e `lib/db/schemas.ts` é **>= 80% lines** medido via `npm run test:coverage`. **NÃO** alterar o threshold global em `vitest.config.ts` (é caminho bloqueador — ver Not-Tested Evidence Gate; subir o global é Story F.1, fora de scope).

## Dev Notes

- **NÃO reescrever `version(1)`:** o padrão Dexie é aditivo. `this.version(1).stores({...})` mantém-se literal; `this.version(2).stores({...})` adiciona apenas as tabelas novas. Dexie só re-processa o que muda. Reescrever `version(1)` corromperia o upgrade path dos dados do Eurico já em produção. [Source: `architecture-v2.md` §4.2 linhas 237-255 + §16 linha 1121]

- **Interfaces já existem — não recriar:** `Task`, `Project`, `Recurrence`, `Tag` estão em `types/db.ts:54-92`, criadas pela Story 0.3 e traçadas a `architecture-v2.md` §6.2. Os schemas Zod (AC5) espelham-nas; se houver divergência entre interface e schema Zod, a interface manda (é a fonte canónica). [Source: `types/db.ts:54-92`, `architecture-v2.md` §6.2 linhas 482-526]

- **`recurrences` é genérica, partilhada entre Epics:** `ownerType: 'task'|'transaction'|'habit'|'reminder'`. O Epic 3 (Finanças) e o Epic 4 (Hábitos/Lembretes) vão reutilizar esta tabela. Não criar nada específico de tarefas aqui. O *motor* de geração de instâncias recorrentes é a Story 2.7 (`lib/shared/recurrence.ts`, wrapper sobre `rrule`) — **fora do scope da 2.1**, que só persiste a definição. [Source: `architecture-v2.md` §6.2 linhas 512-519 + §16 linha 1128]

- **Tags denormalizadas:** não há tabela de junção `task_tags`. `Task.tags: string[]` + índice multi-entry `*tags` em `tasks` (`client.ts:46`). A tabela `tags` guarda apenas as definições (`id, name, color`). Ver Q1 (ids vs nomes no array) antes de implementar o filtro `listTasks({ tag })`. [Source: `architecture-v2.md` §4.2 linha 240, §6.2 linhas 521-525]

- **Padrão de repo herdado da Story 1.1:** repos em `lib/db/repos/{tabela}.ts` (kebab-case singular), validação Zod no input antes de `db.*.add()`, throw `ZodError` com mensagem PT-PT. Ver `lib/db/repos/agent-runs.ts` e `lib/db/repos/chat-messages.ts` como referência directa. Atenção à lição da Story 1.1: usar `Schema.parse(input)` para validar mas persistir o `input` original tipado (Zod `z.unknown()` infere campo opcional e quebra o typecheck) — só relevante se algum campo for `unknown`, o que não é o caso em Task/Project/Recurrence/Tag, mas manter o padrão consistente. [Source: `stories/completed/1.1.story.md` Dev Notes + Completion Notes #2]

- **Migration NÃO é desta story:** `lib/db/migrations/v1-to-v2.ts` já existe (skeleton da Story 0.3) e já mapeia `V1Task` → `Task`. A Story 2.2 vai refiná-la para usar os repos desta story em vez de `db.tasks.bulkAdd` directo. Não tocar na migration na 2.1. [Source: `lib/db/migrations/v1-to-v2.ts`]

- **Hooks fora do coverage:** tal como na Story 1.1, `vitest.config.ts` `coverage.include` cobre `lib/**` mas não `hooks/`. Os hooks `useTasks`/`useProjects` correm em testes (opcional, mas recomendado um smoke `renderHook` se houver tempo) mas não contam para o número de coverage. AC15 mede `lib/db/**`. [Source: `stories/completed/1.1.story.md` Completion Notes #7]

- **Import convention:** Constitution Article VI — sempre `@/...` absoluto. Excepção: imports entre ficheiros dentro de `lib/db/repos/` podem ser relativos entre si (padrão da Story 1.1).

- **`archiveProject` (AC7):** a interface `Project.status` é `'active'|'paused'|'done'` — não há estado `'archived'` literal. O helper `archiveProject` na 2.1 é só o atalho base de mudança de estado; a semântica completa de "arquivar projecto" (UI, filtros) é a Story 2.8. Não inventar um estado `'archived'`.
