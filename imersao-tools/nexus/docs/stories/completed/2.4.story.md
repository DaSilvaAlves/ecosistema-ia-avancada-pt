## Nota do `@sm` River sobre escopo e dependência

A Story 2.4 no `EPIC-2.md` §5 é descrita como **"Colunas customizáveis + drag-and-drop com `dnd-kit`"**, traçando a FR11 e FR12. O termo "customizáveis" refere-se à possibilidade de as colunas reflectirem qualquer valor de `TaskStatus` — não a customização via UI pelo utilizador (reordenação de colunas ou criação de colunas personalizadas está fora do scope desta story). As 4 colunas são fixas: **TODO / EM CURSO / BLOQUEADAS / FEITO** (mapeiam `'todo'`, `'in-progress'`, `'blocked'`, `'done'`).

A Story 2.3 entregou:
1. O scaffold da página `/tarefas` (`app/(app)/tarefas/page.tsx`).
2. O header sticky com tabs "Lista | Kanban | Calendário" — tab Kanban está `aria-disabled="true"` com tooltip "Disponível na Story 2.4".
3. O componente `TaskRow.tsx` (React.memo) com a shape final de Task pós-Iter 2.
4. Os helpers `lib/tarefas/isOverdue.ts` e `hooks/useDebounced.ts`.
5. O componente `OverdueSection.tsx` — reutilizável entre as 3 vistas.

A Story 2.4:
- Activa o tab Kanban (remove `aria-disabled`, conecta à vista Kanban).
- Cria `KanbanBoard`, `KanbanColumn`, `KanbanCard` (novo componente, distinto de `TaskRow`).
- Integra `@dnd-kit/core` + `@dnd-kit/sortable` para drag entre colunas.
- Persiste mudanças de status via `setTaskStatus()` (repo Story 2.1) — optimistic UI com rollback em erro.
- Herda filtros do mesmo estado de página (status filter no Kanban filtra colunas visíveis; pesquisa/tag/projecto reduzem cards visíveis por coluna).
- Mantém a `OverdueSection` no topo (fora das colunas Kanban) — atrasadas ainda visíveis em modo Kanban.

**[AUTO-DECISION A1] Drag dentro da mesma coluna (reordenação) fora-de-scope nesta story.** FR12 especifica "drag-and-drop entre colunas (Kanban)" — não reordenação intra-coluna. O campo `Task` não tem `order` ou `position`. Reordenação intra-coluna exigiria novo campo no schema (Story 2.1) e migration — futura story se necessário. Alternativa "implementar reordenação intra-coluna agora" foi descartada — scope creep, exige schema change fora deste epic.

**[AUTO-DECISION A2] Coluna "FEITO" não oculta automaticamente tarefas feitas há >N dias.** Scope não contemplado em FR11/FR12. A coluna FEITO mostra todas as tarefas `status='done'`. Limpeza de arquivo é futura story ou será abordada quando o volume justificar.

**[AUTO-DECISION A3] O filtro de Status da barra de filtros, quando activo no Kanban, oculta a coluna correspondente em vez de mostrar só uma coluna.** Exemplo: filtrar "Em curso" mostra apenas a coluna EM CURSO; as outras são ocultadas (não removidas do DOM — mantêm-se mas com `display:none`/`hidden`). Comportamento coerente com a spec §3.2 que mostra os filtros acima do Kanban. Alternativa "filtro de status desactivado em modo Kanban" foi descartada — utilizador precisa de foco.

**[AUTO-DECISION A4] Botão "+ Nova Tarefa" no header fica em construção (disabled) nesta story.** A criação de tarefa via UI (Flow 1.3 do spec §1.3) é funcionalidade separada — não está nos FRs alvo desta story (FR11, FR12). O botão mantém-se visível mas `disabled` com tooltip "Em construção". Consistente com D4 da Story 2.3.

## User Story

**As a** Eurico,
**I want** a vista Kanban na página `/tarefas` com as minhas tarefas organizadas em 4 colunas (Por fazer, Em curso, Bloqueadas, Feitas) e drag-and-drop entre colunas para mudar o status,
**so that** possa reorganizar visualmente as minhas prioridades sem precisar de abrir menus — uma interacção directa e rápida de gestão de estado (cumpre FR11 vista Kanban + FR12 drag-and-drop entre colunas, persiste via Dexie sem reload).

## Decisões autónomas (River — para ratificação `@po`)

1. **[AUTO-DECISION A1]** Reordenação intra-coluna fora-de-scope. Trace: FR12 especifica "entre colunas", não intra-coluna. Campo `order` não existe no schema. Razão: schema change exigiria migration adicional — décadas de débito técnico vs scope entregável agora. Alternativa "adicionar campo `order` e drag intra-coluna" descartada.

2. **[AUTO-DECISION A2]** Coluna "Feitas" não tem limite temporal ou arquivamento automático. Razão: não está nos FRs — evita scope creep. Futura story se o volume justificar.

3. **[AUTO-DECISION A3]** Filtro Status em modo Kanban oculta colunas em vez de desactivar o filtro. Razão: UX mais directa; "filtrar por Em curso" = ver só EM CURSO. Alternativa "desactivar filtro status em Kanban" descartada — perde funcionalidade.

4. **[AUTO-DECISION A4]** Botão "+ Nova Tarefa" permanece disabled nesta story. Razão: criação UI (Flow 1.3) é story futura não incluída nos FRs 2.4.

5. **[AUTO-DECISION A5]** Keyboard navigation para drag usa `@dnd-kit` built-in keyboard sensor (`KeyboardSensor`) + `sortableKeyboardCoordinates`. Não implementar keyboard shortcuts custom. Razão: `dnd-kit` já fornece WAI-ARIA Authoring Practices para D&D com teclado (Space/Enter para pegar, Arrow Keys para mover, Enter/Space para largar, Escape para cancelar). Documentar ARIA attrs nos ACs.

## Acceptance Criteria

- **AC1:** O tab "Kanban" na header strip da página `/tarefas` está **activo** (não mais `aria-disabled`). Ao clicar no tab Kanban, a vista muda para o layout Kanban; ao clicar em "Lista", regressa à tabela. O estado activo do tab persiste via `useState` na page (não em URL params nesta story).

- **AC2:** A vista Kanban apresenta exactamente **4 colunas fixas** na ordem: **Por fazer** (`todo`) · **Em curso** (`in-progress`) · **Bloqueadas** (`blocked`) · **Feitas** (`done`). Cada coluna tem:
  - Header com label PT-PT em JetBrains Mono 0.95rem weight 700.
  - Cor de accent no header alinhada ao mapeamento §Contexto: Por fazer (cyan), Em curso (gold), Bloqueadas (magenta), Feitas (lime).
  - Badge contador de cards `(N)` em JetBrains Mono 0.65rem.
  - Área de drop visualmente distinta quando card está a ser arrastado sobre ela (border subtle glow da cor da coluna).

- **AC3:** Cada **KanbanCard** apresenta:
  - Título da tarefa (Inter 0.95rem).
  - Badge prioridade (Alta/Média/Baixa — magenta/cyan/grey, JetBrains Mono 0.65rem) — igual às badges de `TaskRow.tsx` da Story 2.3 para consistência visual.
  - Due date formatado `DD/MM/YYYY` via `formatDueDate()` (corrigido na Story 2.3 Iter 2) ou `—` se null.
  - Tags: até 2 chips horizontais; se mais, mostra "+N".
  - Se tarefa atrasada (via `isOverdue(task)`): tinting magenta subtil `rgba(255,0,110,0.05)` no card e due date em `#FF006E`.
  - Nome do projecto se `projectId !== null` (lookup via `useProjects()`).

- **AC4:** **Drag-and-drop entre colunas** com `@dnd-kit/core` + `@dnd-kit/sortable`:
  - Arrastar um card de qualquer coluna para outra coluna muda o `status` da tarefa.
  - **Optimistic UI**: o card move-se visualmente para a nova coluna imediatamente (antes de confirmar Dexie).
  - **Rollback em erro**: se `setTaskStatus(id, novoStatus)` lançar erro, o card regressa à coluna original com toast de erro PT-PT ("Erro ao mover tarefa — tenta novamente").
  - A operação chama apenas `setTaskStatus(id, novoStatus)` do repo `@/lib/db/repos/tasks` — não `db.tasks.update` directamente.
  - Após `setTaskStatus` com sucesso, `useLiveQuery` re-renderiza automaticamente (Dexie reactivo) — não é necessário setState manual para sincronizar.

- **AC5:** **Drag com teclado** (WAI-ARIA D&D Authoring Practices):
  - `KeyboardSensor` do `@dnd-kit/core` activo.
  - Space/Enter para iniciar drag do card focado; Arrow Keys para mover entre colunas; Space/Enter para largar; Escape para cancelar.
  - Card tem `role="button"` e `aria-grabbed` durante drag.
  - Cada coluna tem `aria-label` PT-PT (ex: `aria-label="Coluna Por fazer, 12 tarefas"`).
  - Anúncios de acessibilidade via `announcements` prop do `DndContext` (PT-PT: "A mover [título] de [coluna origem] para [coluna destino]", "Tarefa [título] movida para [coluna]").

- **AC6:** A secção **Atrasadas** (`OverdueSection.tsx`, herdada de Story 2.3) mantém-se visível acima das colunas Kanban quando `overdueTasks.length > 0`. Comportamento idêntico ao da vista Lista (max 5 listadas, link "Mostrar todas").

- **AC7:** Os **filtros** (`TasksFilters.tsx` da Story 2.3) mantêm-se funcionais em modo Kanban:
  - Filtro **Projecto**, **Tag**, **Prioridade** e **Pesquisa** reduzem os cards visíveis dentro das colunas (filtros client-side sobre o array de tasks por coluna).
  - Filtro **Status**: quando seleccionado (ex: "Em curso"), oculta as outras 3 colunas (A3). Coluna filtrada permanece visível mesmo que vazia.
  - Pesquisa por título: debounce 200ms, `useDebounced` (herdado de Story 2.3).

- **AC8:** **Estados de carregamento e vazio**:
  - Quando `useTasks()` devolve `undefined` (Dexie a carregar): skeleton de 4 colunas com 3 cards placeholder cada (animated pulse glass).
  - Quando coluna tem `length === 0`: empty state por coluna — text "Sem tarefas" em grey `#8892A4`, Inter 0.9rem italic, centrado na coluna.
  - Quando todas as tarefas filtradas são 0: mensagem global "Nenhuma tarefa corresponde aos filtros activos." — igual ao estado vazio da lista.

- **AC9:** **PT-PT** consistente: nenhum texto em PT-BR ou inglês onde PT-PT existe. Termos canónicos: "Por fazer", "Em curso", "Bloqueadas", "Feitas", "Tarefas", "Projecto", "Prioridade", "Atrasadas", "Erro ao mover tarefa", "A mover", "Tarefa movida para".

- **AC10:** **Testes Vitest + Testing Library** cobrem:
  - **T1 — Render base com dados**: 8 tasks mock distribuídas pelas 4 colunas. Verifica que cada coluna renderiza o número correcto de cards e o badge contador correcto.
  - **T2 — Estado loading**: `useTasks` devolve `undefined` → 4 colunas skeleton visíveis, cards reais ausentes.
  - **T3 — Estado vazio por coluna**: array com tasks só em 2 colunas → colunas vazias mostram "Sem tarefas"; colunas com tasks mostram cards.
  - **T4 — Atrasadas visíveis**: 1 task `dueDate=ontem, status='todo'` → `OverdueSection` visível acima das colunas com contador "(1)"; card na coluna "Por fazer" tem tinting magenta.
  - **T5 — Filtro projecto**: select projecto X → cards sem `projectId === X` desaparecem de todas as colunas (spy sobre useTasks opts ou render check).
  - **T6 — Filtro status oculta colunas**: select status "Em curso" → apenas coluna EM CURSO visível (`hidden` ou removida do DOM nas outras 3).
  - **T7 — setTaskStatus chamado no drag**: simular `onDragEnd` com `active.id = taskId` e `over.id = 'in-progress'` → `setTaskStatus(taskId, 'in-progress')` chamado 1x (spy via `vi.spyOn(tasksRepo, 'setTaskStatus')`).
  - **T8 — Rollback em erro**: `setTaskStatus` rejeita → card regressa à coluna original (verificar via estado do componente ou DOM após `await act`).
  - **T9 — Tab switch**: clicar tab "Lista" em modo Kanban → lista visível, colunas Kanban ausentes. Clicar tab "Kanban" → colunas Kanban visíveis, tabela ausente.
  - **T10 — Acessibilidade smoke**: colunas têm `aria-label` PT-PT; cards têm `role="button"` (ou equivalente dnd-kit); `DndContext` presente no DOM.

  - `npm run test:unit` — todos os testes existentes (>= 418 pré-existentes) + os ~10 novos da 2.4 passam.

### Padrão dnd-kit para drag entre colunas (não intra-coluna)

```typescript
// KanbanBoard.tsx — estrutura mínima
import { DndContext, PointerSensor, KeyboardSensor, useSensor, useSensors, DragEndEvent } from '@dnd-kit/core';
import { sortableKeyboardCoordinates } from '@dnd-kit/sortable';

const sensors = useSensors(
  useSensor(PointerSensor),
  useSensor(KeyboardSensor, { coordinateGetter: sortableKeyboardCoordinates })
);

function handleDragEnd(event: DragEndEvent) {
  const { active, over } = event;
  if (!over) return;
  const taskId = active.id as string;
  const novoStatus = over.id as TaskStatus;
  if (taskId === novoStatus) return; // mesmo id → ignorar (não deve acontecer)
  // Verificar se mudou de coluna: encontrar task actual e ver se status é diferente
  const task = tasks?.find(t => t.id === taskId);
  if (!task || task.status === novoStatus) return;
  // Optimistic UI
  setOverrides(prev => ({ ...prev, [taskId]: novoStatus }));
  setTaskStatus(taskId, novoStatus).catch(() => {
    setOverrides(prev => { const next = { ...prev }; delete next[taskId]; return next; });
    // mostrar toast de erro
  });
}

// KanbanColumn.tsx — useDroppable com id = TaskStatus
import { useDroppable } from '@dnd-kit/core';
const { setNodeRef, isOver } = useDroppable({ id: columnId }); // columnId = 'todo' | 'in-progress' | ...

// KanbanCard.tsx — useSortable com id = task.id
import { useSortable } from '@dnd-kit/sortable';
const { attributes, listeners, setNodeRef, transform, transition, isDragging } = useSortable({ id: task.id });
```

> **IMPORTANTE:** Não usar `SortableContext` com `items` em cada coluna se o objectivo é apenas drag between colunas (não intra-coluna). Neste caso, `KanbanColumn` usa `useDroppable` e `KanbanCard` usa `useSortable` para o handle. Esta é a configuração mínima para "cross-container drag" sem reordenação intra-coluna. Verificar a documentação `@dnd-kit` se houver conflito.

### Anti-padrões a evitar

| Anti-padrão | Correcto |
|-------------|----------|
| `db.tasks.update(id, { status: novoStatus })` no componente | `await setTaskStatus(id, novoStatus)` do repo |
| Sem rollback quando `setTaskStatus` falha | Sempre: try/catch + restaurar `overrides` + toast PT-PT |
| `useTasks({ status: 'todo' })` separado por coluna (4 queries Dexie) | Um único `useTasks()` sem filtro de status → dividir por coluna client-side com `useMemo` |
| Objecto de opts recriado em cada render (`useTasks({ status: filter })`) | Extrair `statusFilter` como primitiva e passar directamente |
| Importar de `@dnd-kit/core` sem instalar | Verificar `package.json` antes de implementar (T1.2) |
| Drag intra-coluna com campo `order` inexistente | Não implementar — ver A1 |
| Toast com biblioteca nova não aprovada | Usar primitivo simples ou verificar se existe pattern no projecto |
