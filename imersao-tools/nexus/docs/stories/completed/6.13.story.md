A 6.12 fechou com o handler Edge `POST /api/telegram/webhook/route.ts` a fazer o dispatch stub no passo (5):

```ts

// (5) Detecção de tipo + dispatch stub (AC4/AC5 — [D-6.12-FAN-OUT-SCOPE]).
// A 6.12 faz APENAS dispatch stub: `routed:false`. A chamada ao cérebro para
```

A 6.13 substitui esta linha final **apenas para `type === 'text'`** — transformando `routed: false` em `routed: true` e entregando a resposta ao utilizador via `sendMessage` do helper `lib/telegram/bot-api.ts`. Os outros tipos (`voice`, `photo`, `unknown`) continuam com o stub `routed: false` (são da 6.14/6.15).

**Variáveis disponíveis no ponto de dispatch (contexto garantido pela 6.12):**
- `update`: `TelegramUpdate` (validado por Zod) — contém `update.message.text` para tipo `text`
- `authorizedChatId`: `string` (env `TELEGRAM_CHAT_ID` validado — o filtro chatId já passou)
- `type`: `UpdateType` — já detectado como `'text'` para este ramo

### Achado de auth CENTRAL (define `[D-6.13-RUNTIME]`)

O `/api/anthropic/proxy/route.ts` é **Edge + cookie-gated**: `getSession(req)` na linha 90, devolve **401 se `!session.valid`** (l.91-93). O webhook Telegram é cookieless (não traz `nexus_session` — é por isso que está em `PUBLIC_PATHS`, `middleware.ts:41`, C6b da 6.12). **Conclusão:** se o bridge invocasse o cérebro por um caminho que falasse com `/api/anthropic/proxy` (o `InferenceTransport` do `client-executor.ts`), receberia **401** e o cérebro nunca chamaria o Sonnet — bot mudo. Este é o paralelo EXACTO do hotfix 4.8 / C6b da 6.12, um nível acima.

A saída segura é: o **bridge Node importa `runAgent` SEM injectar `executor`/`classifier`**. Nesse caso o `runAgent` resolve o provider via `resolveServerExecutor()` (`executor.ts:496-499`) → `getExecutor()` (`providers/factory.ts:43-46`), que lê `ANTHROPIC_API_KEY` do env e instancia `AnthropicExecutor` com o SDK directo a `api.anthropic.com` — **NÃO toca no proxy nem em cookie**. O classifier idem (`getClassifier()`, factory:36-41, via `classifyPrompt` sem `opts.classifier`). Isto é Node-safe e cookieless por construção. O `@dev` NÃO deve, em circunstância alguma, fazer o bridge chamar `/api/anthropic/proxy` (regredia para 401).

### Análise `internal-state-contract-gate.md` — 3 eixos do estado distribuído

- **Eixo (a) — particionamento de estados:** o estado distribui-se por 3 fronteiras: (1) Edge webhook (recebe update, valida, ACK), (2) bridge Node (corre o cérebro), (3) `api.telegram.org` (entrega `sendMessage`). Estados terminais distintos e observáveis: `routed:true` (ACK dado) ≠ cérebro concluído ≠ resposta entregue. Como é fire-and-forget, o ACK `routed:true` significa apenas "aceite para processamento", NÃO "respondido" — semântica honesta (AC4). Os 3 sub-casos do filtro chatId da 6.12 continuam a resolver ANTES do dispatch (C7 da 6.12 intacto).
- **Eixo (b) — sem estado órfão / sem janela de inconsistência crítica:** o bridge é stateless (não escreve KV/Dexie no caminho da 6.13 — `db:null`, tools de DB inertes). Não há registo a meio para deixar órfão. Se o bridge crashar a meio do generator, o `catch` envia mensagem de erro; se o próprio processo morrer, o utilizador não recebe nada — aceitável single-user (sem retry, sem fila). NÃO introduzir persistência de "mensagem em processamento" (over-engineering para single-user).
- **Eixo (c) — cada falha tem status distinto, zero erro-como-sucesso:** webhook nunca devolve 5xx ao Telegram (sempre 200 — AC5, evita re-entrega em loop). Bridge: erro do cérebro → `sendMessage` erro PT-PT + 200 ao webhook. Tool de DB tentada → `tool_error` no generator → run `partial` → envia o texto que houver (não crash). Resposta Anthropic degenerada → mensagem de erro (não crash — AC7). Texto vazio do cérebro → NÃO chamar `sendMessage` com texto vazio (C-guard); enviar fallback PT-PT. Nenhum caminho devolve "sucesso" mascarando falha.

## Acceptance Criteria

> Trace: FR71 (PRD §6.13). AC epic-level AC4 (bot Telegram responde a "olá" < 3s) — esta story, juntamente com a 6.12, é a que materializa o AC4; deferido a verificação em produção (depende de P1-P4).

### AC1 — Roteamento de texto para o cérebro (FR71)

Quando o webhook Edge recebe um update com `type === 'text'`, o handler deixa de retornar o stub `{ok:true, routed:false, type:'text'}` e activa o caminho de processamento do cérebro. O texto `update.message.text` é passado ao pipeline de inferência (conforme o padrão definido pelo `@architect` em `[D-6.13-RUNTIME]`). Os outros tipos (`voice`, `photo`, `unknown`) continuam a retornar stub `routed: false` — a 6.13 apenas trata `text`.

**Verificabilidade:** CI Vitest (mock do pipeline de inferência; update de texto → resposta ao utilizador; update de voz/foto → ainda stub `routed:false`).

### AC2 — Resposta ao utilizador via `sendMessage` (FR71; `lib/telegram/bot-api.ts`)

Após obter o texto de resposta do cérebro (o último evento `text_delta` / conteúdo do evento `done` ou equivalente), o handler envia a resposta ao utilizador via `sendMessage(chatId, textoResposta)` usando o helper existente `lib/telegram/bot-api.ts` (função `sendMessage` — já disponível na 6.11). O `chat_id` usado é o `authorizedChatId` (env `TELEGRAM_CHAT_ID`) já validado pela 6.12.

**Verificabilidade:** CI Vitest (spy de `sendMessage` chamado 1× com `chatId` correcto e texto não-vazio; teste de update de texto "olá" → `sendMessage` com resposta do cérebro mock).

### AC3 — Reutilização do pipeline existente — sem fluxo novo (FR71; EPIC-6.md §5)

A 6.13 **não cria um pipeline de inferência novo**. Reutiliza o executor existente (`lib/agent/executor.ts` / padrão `[D-6.13-RUNTIME]` ratificado pelo `@architect`) ou chama endpoints existentes via `ctx.fetch` same-origin (precedente `[D-6.10-RUNTIME]`). A classificação Haiku + executor Sonnet + Tool Registry são exactamente os mesmos do Epic 1 — o canal Telegram é apenas uma porta de entrada adicional.

**Verificabilidade:** Revisão de código (sem nova lógica de classificação/execução; só ponte + `sendMessage`). CI Vitest (mock do executor produz eventos → texto extraído → `sendMessage` chamado).

### AC4 — Resposta ao Telegram dentro do orçamento Edge <5s (FR71; arch §4.1)

O webhook Edge responde ao servidor do Telegram (ACK do update) dentro do orçamento de <5s (arch §4.1). Conforme o padrão ratificado em `[D-6.13-TIMEOUT]`, o processamento do cérebro ocorre de forma assíncrona (fire-and-forget ou endpoint bridge Node) para não bloquear o ACK. O utilizador recebe a resposta via `sendMessage` após o processamento, que pode ocorrer além dos 5s do webhook.

**Verificabilidade:** CI Vitest (ACK ao Telegram é imediato — não aguarda o cérebro). Produção: verificável após P1-P4 (timing real).

### AC5 — Fallback gracioso em caso de erro do cérebro

Se o pipeline de inferência falhar (erro de rede, timeout, erro do executor), o handler envia ao utilizador via `sendMessage` uma mensagem de erro PT-PT genérica (conforme `[D-6.13-ERROR-RESPONSE]` ratificado pelo `@architect`) em vez de falhar silenciosamente. O webhook retorna 200 ao Telegram em qualquer caso (nunca 500 para o Telegram — o Telegram re-tentaria indefinidamente em caso de 5xx).

**Verificabilidade:** CI Vitest (mock do executor que lança erro → `sendMessage` com mensagem de erro; webhook retorna 200).

### AC6 — Preservação das guardas da 6.12 (C1-C9 intactas)

A 6.13 é uma extensão open-closed da 6.12 — **não toca** nas guardas C1-C9 da 6.12 (secret_token, parse, filtro chatId, rate-limit, detecção de tipo). O `git diff` das linhas de lógica das guardas é VAZIO. Os 32 testes da 6.12 continuam a passar sem modificação. A mudança ocorre apenas no ramo `type === 'text'` do dispatch (passo 5).

**Verificabilidade:** `git diff` das guardas + suite 6.12 verde (32 testes).

### AC7 — Mock MSW fiel ao protocolo real (`mock-protocol-fidelity.md`)

Existe ≥1 teste que falharia se o protocolo do mock divergisse do esperado (ex: campo `text` ausente na resposta do cérebro → fallback gracioso em vez de crash).

**Verificabilidade:** CI Vitest (asserção de shape estrita + teste de degeneração de protocolo).

### AC8 — Suite de testes cresce (sem regressão) e baseline ≥ 2249

### ADR-9 e o problema do cérebro server-side

> CORRIGIDO pelo Architect Gate de Entrada (Aria, 21/06/2026). Ler o veredicto completo na secção "Architect Gate de Entrada" acima — esta secção foi reconciliada com o código real.

O **`runAgent` (`executor.ts:616`) é um módulo NEUTRO**, NÃO `'use client'`. É o `client-executor.ts` (`'use client'`, l.1) que injecta `ctx.db = db` (singleton Dexie) + `InferenceTransport` (proxy para `/api/anthropic/proxy`). No webhook Edge server-side não há browser nem Dexie — mas o bridge Node pode importar `runAgent` directamente: quando NÃO se injecta `executor`/`classifier`, o `runAgent` resolve o provider via `resolveServerExecutor()` (`executor.ts:496`) → `getExecutor()` (`factory.ts:43`), que usa o SDK Anthropic directo a `api.anthropic.com` com `ANTHROPIC_API_KEY` (Node-only, cookieless). **CRÍTICO:** o bridge NÃO deve chamar `/api/anthropic/proxy` — esse é Edge cookie-gated (`proxy/route.ts:90-93`, 401 sem `nexus_session`) e o webhook é cookieless.

**Precedente canónico para invocar o cérebro server-side sem Dexie:** Story 6.10 `[D-6.10-RUNTIME]` — as 3 tools Gmail (listar, criar draft, arquivar) correm server-side via `ctx.fetch` a routes Node (`GET /api/google/gmail/inbox`, `POST /api/google/gmail/draft`, `POST /api/google/gmail/archive`). O executor na 6.10 não tem `ctx.db` (as tools usam rotas HTTP em vez de Dexie directo).

Para a 6.13, o padrão ratificado (Architect Gate) é:
1. O webhook Edge chama (fire-and-forget) `POST /api/telegram/process-text` (route Node, `runtime='nodejs'`)
2. A route Node invoca **`runAgent(text)`** — assinatura REAL `runAgent(userPrompt: string, opts: RunAgentOpts = {})` (`executor.ts:616`); todos os campos de `RunAgentOpts` (l.152-223) são OPCIONAIS. **SEM `executor`/`classifier`** (força o factory SDK Node cookieless) e **SEM `db`** (fica `null`).
