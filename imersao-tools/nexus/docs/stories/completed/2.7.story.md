## Nota do `@sm` River sobre escopo e dependências

A Story 2.7 no `EPIC-2.md` §5 está descrita como **"Geração instâncias recorrentes (cron client-side via `setInterval` ou `requestIdleCallback`) — horizonte 90 dias"** traçando FR10. O PRD §6.2 linha 133 confirma:

> **FR10:** Recorrência configurável: diária, semanal, mensal, dias úteis, fim-de-semana, dia específico do mês. Trace: JARVIS.txt L122-129.

O PRD §10 Epic 2 (linha 446) descreve: `"2.7 Geração instâncias recorrentes (cron client-side via setInterval ou requestIdleCallback)"`.

A arquitectura `architecture-v2.md` §16 L1123 diz: `"Story 2.7 instâncias recorrentes geradas por ServiceWorker (não setInterval do tab) usando Background Sync ou no activate event do SW"`.

Esta divergência é o principal bloqueador desta story (ver [GAP-1]).

**Decisões autónomas do SM:**

[AUTO-DECISION A1] **Escopo da geração de instâncias:** horizonte fixo de **90 dias** a partir da data actual (`Date.now()` + 90 * 24 * 60 * 60 * 1000), conforme EPIC-2.md §5 e AC Epic 2 AC3. O engine gera instâncias (tasks filhas com `parentTaskId` = UUID da task-mãe) para todas as `Recurrence` com `ownerType: 'task'` dentro do horizonte. Razão: PRD §6.2 AC3 diz explicitamente "horizonte de 90 dias". Alternativa "horizonte infinito" descartada — levaria a milhares de tasks em IndexedDB + UI congestionada.

[AUTO-DECISION A2] **Tipos de recorrência suportados** — exactamente os do FR10 (sem invenção):
- Diária (`DAILY`)
- Semanal (`WEEKLY`) — dia(s) da semana especificados
- Mensal (`MONTHLY`) — dia do mês especificado
- Dias úteis (`WEEKLY`, `byweekday: [0,1,2,3,4]`) — Segunda a Sexta
- Fim-de-semana (`WEEKLY`, `byweekday: [5,6]`) — Sábado + Domingo
- Dia específico do mês (`MONTHLY`, `bymonthday: [N]`)

Razão: FR10 é explícito nestes 6 tipos. A estrutura `RecurrenceConfig` já os suporta via `buildRRule`. Alternativa "usar RRULE string livre" descartada — desnecessariamente complexo para o Eurico; a UI deve expor os 6 tipos como opções discretas, não uma string RRULE manual.

[AUTO-DECISION A3] **Idempotência da geração:** antes de criar uma instância para uma data, verificar se já existe uma task filha com `parentTaskId === recurrence.ownerId` para essa data via `db.tasks.where('parentTaskId').equals(ownerId).toArray()` + filtro `dueDate === isoDate`. Razão: o motor pode correr múltiplas vezes (ao reload, ao SW activate); criar duplicados quebraria a UI. Alternativa "apagar e recriar todas as instâncias do horizonte" descartada — destrutivo (apagaria contexto/notas nas tasks filhas já existentes).

[AUTO-DECISION A4] **`lib/shared/recurrence.ts` estendido** com funções adicionais ao skeleton existente:
- `generateTaskInstances(recurrence: Recurrence, horizonDays?: number): Promise<void>` — gera instâncias dentro do horizonte, idempotente
- `runRecurrenceEngine(): Promise<{ created: number; skipped: number }>` — itera todas as `Recurrence` com `ownerType: 'task'`, chama `generateTaskInstances` para cada
- `buildRecurrenceConfig(freq, opts): RecurrenceConfig` — helper que abstrai a construção de `RecurrenceConfig` para os 6 tipos do FR10 (facilita a UI)

[AUTO-DECISION A5] **UI de configuração de recorrência no formulário de tarefa** (`app/(app)/tarefas/page.tsx` ou componente `TaskFormModal.tsx` se existir). Toggle "Tarefa recorrente" → expande para selector do tipo de recorrência (dropdown com os 6 tipos) + selector de data de início + selector de data de fim opcional. Ao criar/editar uma tarefa com recorrência, a UI:
1. Cria a `Recurrence` via `createRecurrence` com `ownerType: 'task'`, `ownerId: task.id`.
2. Actualiza a task com `recurrenceId: recurrence.id` via `updateTask`.
3. Chama `generateTaskInstances(recurrence)` para popular o horizonte imediatamente.

[AUTO-DECISION A6] **Resolução parcial do [GAP-1]:** enquanto aguarda decisão formal de `@architect`, a implementação segue a abordagem mais simples e confirmada pelo PRD + EPIC-2: **`useEffect` com activação no primeiro render da page `/tarefas`** (equivalente ao "primeiro carregamento do dia" mencionado no EPIC-3 §16 para padrão similar). A activação via ServiceWorker fica como `[GAP-1]` explícito — se `@architect` decidir SW, o único ficheiro a alterar é o ponto de activação (o motor em `lib/shared/recurrence.ts` é agnóstico ao mecanismo de activação). Razão: implementar SW Background Sync aumentaria o escopo em 2-3x (VAPID, SW registration, Background Sync API) sem dados que provem que o Eurico precisa de geração offline. O `useEffect` no primeiro render resolve o caso de uso imediato. Alternativa "só setInterval" descartada — setInterval activo em tab abierta desperdiça CPU; `useEffect` no mount do page é equivalente a "on load" sem polling.

[AUTO-DECISION A7] **Hook `useRecurrenceEngine`** exposto para a page `/tarefas` activar o motor:
```ts
// hooks/useRecurrenceEngine.ts
export function useRecurrenceEngine(): void {
  useEffect(() => {
    runRecurrenceEngine().catch(console.error);
  }, []); // runs once on mount — equivalent to "first load"
}
```
A page `/tarefas` chama `useRecurrenceEngine()` no topo. Zero parâmetros — o motor lê as `Recurrence` directamente da DB.

[AUTO-DECISION A8] **Formulário de recorrência** no modal/UI de criação de tarefa. Verificar se `TaskFormModal` existe no codebase; se não, a Story 2.7 adiciona um componente `RecurrenceFieldset.tsx` injectável no formulário de tarefa existente. Decisão final durante T1.2 — leitura do formulário de tarefa actual. **Não criar um modal novo se o formulário já existir.** Sem modificar a estrutura de validação Zod de `TaskSchema` (já tem `recurrenceId` como nullable — não alterar).

[AUTO-DECISION A9] **Instâncias recorrentes na UI** devem ser distinguíveis visualmente (badge "Recorrente" ou ícone de ciclo). A task-mãe (`parentTaskId: null`, `recurrenceId: non-null`) exibe o tipo de recorrência. As tasks filhas (`parentTaskId: non-null`) exibem badge "Instância" e link para a task-mãe. Implementação cirúrgica em `TaskRow.tsx` ou `KanbanCard.tsx` — apenas badge adicional, sem refactor estrutural.

[AUTO-DECISION A10] **Completar uma instância NÃO cancela recorrência futura.** Completar a task filha de hoje (`status: 'done'`) não afecta as instâncias futuras já criadas nem a `Recurrence`. Para cancelar a recorrência, o Eurico elimina a `Recurrence` via a UI (botão "Cancelar recorrência" na task-mãe — confirmar com `window.confirm` PT-PT).

[AUTO-DECISION A11] **Integração no formulário de tarefa (AC7) — escopo ajustado pelo executor.** Durante T1.2, verificou-se que **não existe formulário de criação/edição de tarefa** na page `/tarefas`: o botão "+ Nova" está `disabled` (placeholder "em construção"), e não há `TaskFormModal` nem handler de `onSubmit` de tarefa. O AC7 prevê este caso ("Se não existir, a integração é directa na lógica da `tarefas/page.tsx`") — mas sem um ponto de criação de tarefa, não há `onSubmit` onde injectar a lógica `createRecurrence`+`updateTask`+`generateTaskInstances`. Decisão do executor (Dex): entregar `RecurrenceFieldset` como **componente standalone completo e testado** (props, validação, a11y — AC6/AC11/AC12 plenamente cumpridos), e o `cancelTaskRecurrence` como **helper de domínio testável** (AC9 cumprido na lógica). A ligação ao formulário fica trivial — `RecurrenceFieldset` é injectável directamente — para a story futura que adicionar o formulário "+ Nova". Razão: o motor de recorrência (núcleo desta story, AC1-AC5, AC8, AC10) está 100% entregue e funcional via `useRecurrenceEngine`; bloquear a 2.7 à espera de um formulário inexistente seria scope-creep (criar um formulário de tarefa completo não está nos AC desta story). Alternativa "criar o formulário "+ Nova" agora" descartada — fora do escopo da Story 2.7 (que é o motor de recorrência, FR10), seria invenção de scope.

**O que esta story entrega (resumo):**

1. **`lib/shared/recurrence.ts` estendido**: `buildRecurrenceConfig(freq, opts)` + `generateTaskInstances(recurrence, horizonDays?)` (idempotente) + `runRecurrenceEngine()`.
2. **`hooks/useRecurrenceEngine.ts`**: hook de activação one-shot no mount.
3. **`components/tarefas/RecurrenceFieldset.tsx`**: campo de configuração de recorrência (toggle + 6 tipos + data início + data fim opcional) — injectável no formulário de tarefa.
4. **Integração na page `/tarefas`**: chamada a `useRecurrenceEngine()` no mount + lógica de criação/edição de task com recorrência.
5. **Distinção visual de instâncias**: badge "Recorrente" na task-mãe + badge "Instância" nas filhas em `TaskRow.tsx`/`KanbanCard.tsx`.
6. **Testes Vitest** — ~20-25 cenários cobrindo lógica de recorrência, idempotência, 6 tipos FR10, geração dentro/fora do horizonte, cancelamento.

## User Story

**As a** Eurico,
**I want** poder marcar qualquer tarefa como recorrente (diária, semanal, mensal, dias úteis, fim-de-semana, ou dia específico do mês) e ter as instâncias futuras geradas automaticamente para um horizonte de 90 dias —,
**so that** consigo gerir tarefas que se repetem (exercício, revisão semanal, pagamentos mensais) sem criar manualmente cada ocorrência, cumprindo FR10 (Recorrência configurável) e mantendo o design system inegociável.

## Acceptance Criteria

- **AC1:** **`lib/shared/recurrence.ts` estendido** com `buildRecurrenceConfig`:
  - Assinatura: `export function buildRecurrenceConfig(type: RecurrenceType, opts: RecurrenceTypeOpts): RecurrenceConfig`
  - `RecurrenceType` é um string literal union dos 6 tipos do FR10: `'daily' | 'weekly' | 'monthly' | 'weekdays' | 'weekends' | 'monthly-specific-day'`.
  - Para cada tipo, `buildRecurrenceConfig` retorna a `RecurrenceConfig` correcta (ver tabela de mapeamento acima).
  - Lança `Error('Tipo de recorrência inválido: {type}')` PT-PT em PT para tipos desconhecidos.
  - Trace: FR10 + `architecture-v2.md` §6.2 `RecurrenceConfig`.

- **AC2:** **`lib/shared/recurrence.ts` estendido** com `generateTaskInstances`:
  - Assinatura: `export async function generateTaskInstances(recurrence: Recurrence, horizonDays?: number): Promise<{ created: number; skipped: number }>`
  - `horizonDays` defaul 90 (conforme EPIC-2 §5 + AC Epic 2 AC3).
  - Reconstrói a `RRule` a partir de `recurrence.rule` via `RRule.fromString(recurrence.rule)`.
  - Calcula ocorrências entre `today` e `today + horizonDays` via `occurrencesBetween`.
  - Para cada ocorrência:
    1. Verifica se já existe task filha com `parentTaskId === recurrence.ownerId` e `dueDate === isoDate` (idempotência — A3).
    2. Se já existe: incrementa `skipped`.
    3. Se não existe: cria task filha via `createTask({ title: motherTask.title, ..., recurrenceId: recurrence.id, parentTaskId: recurrence.ownerId, dueDate: isoDate })` + incrementa `created`.
  - A task filha herda: `title`, `description`, `priority`, `projectId`, `tags` da task-mãe. `status` começa em `'todo'`. `context` e `lastWorkedAt` começam `null`.
  - `Recurrence.endDate !== null` → não gera instâncias após `endDate`.
  - Trace: FR10 + `architecture-v2.md` §6.2 L497 (`parentTaskId`).

- **AC3:** **`lib/shared/recurrence.ts` estendido** com `runRecurrenceEngine`:
  - Assinatura: `export async function runRecurrenceEngine(): Promise<{ created: number; skipped: number; errors: number }>`
  - Lê **todas** as `Recurrence` com `ownerType: 'task'` via `db.recurrences.where('ownerType').equals('task').toArray()`.
  - Para cada recorrência, chama `generateTaskInstances(recurrence)`.
  - Captura erros por recorrência em try/catch — um erro numa recorrência não interrompe as restantes; incrementa `errors`.
  - Retorna contadores agregados `{ created, skipped, errors }`.
  - Trace: EPIC-2 §5 Story 2.7 + AC Epic 2 AC3.

- **AC4:** **`hooks/useRecurrenceEngine.ts`** criado:
  - Assinatura: `export function useRecurrenceEngine(): void`
  - `useEffect(() => { runRecurrenceEngine().catch(console.error); }, [])` — activa o motor **exactamente uma vez** no mount da page `/tarefas` (cron client-side).
  - **Mecanismo de activação decidido por ADR-2.7-1** (`@architect`, 20/05/2026): `useEffect` one-shot on-mount. Não há activação por `setInterval`, `requestIdleCallback` ou ServiceWorker no Epic 2. O motor em `lib/shared/recurrence.ts` permanece agnóstico ao mecanismo — uma futura migração para ServiceWorker (Epic 4, se justificada) substitui apenas este hook, sem tocar no motor.
  - Trace: ADR-2.7-1 + EPIC-2 §7 + PRD §10 linha 446 + `architecture-v2.md` §16 (corrigido 20/05/2026).

- **AC5:** **`app/(app)/tarefas/page.tsx`** chama `useRecurrenceEngine()` no topo do componente. O motor corre uma vez no mount da página, após o qual `useTasks()` e `useLiveQuery` reactivos reflectem as novas instâncias criadas.
  - Trace: A5 + A7.

- **AC6:** **`components/tarefas/RecurrenceFieldset.tsx`** criado:
  - Props: `value: RecurrenceFieldValue | null; onChange: (v: RecurrenceFieldValue | null) => void` onde `RecurrenceFieldValue = { type: RecurrenceType; startDate: string; endDate?: string | null; weekday?: number; monthday?: number }`.
  - Toggle `<input type="checkbox" aria-label="Tarefa recorrente">` — se desmarcado, `onChange(null)`.
  - Se marcado, expande para:
    - `<select aria-label="Tipo de recorrência">` com 6 opções PT-PT (Diária, Semanal, Mensal, Dias úteis, Fim-de-semana, Dia específico do mês).
    - Se "Semanal": `<select aria-label="Dia da semana">` (Segunda, Terça, Quarta, Quinta, Sexta, Sábado, Domingo).
    - Se "Mensal" ou "Dia específico do mês": `<input type="number" min="1" max="31" aria-label="Dia do mês">`.
    - `<input type="date" aria-label="Data de início da recorrência">` — obrigatório.
    - `<input type="date" aria-label="Data de fim da recorrência (opcional)">` — opcional.
  - Validação: `startDate` obrigatório; se `endDate` preenchido, deve ser `>= startDate`.
  - Trace: FR10 + A5 + A8.

- **AC7:** **Integração no formulário de criação/edição de tarefa.** A story verifica (T1.2) se existe `TaskFormModal.tsx` ou equivalente. Se existir, injecta `RecurrenceFieldset` como campo adicional. Se não existir, a integração é directa na lógica da `tarefas/page.tsx` no handler `onSubmit`. Em qualquer caso:
  - Se `RecurrenceFieldset` retorna valor não-null ao submeter:
    1. Constrói `RecurrenceConfig` via `buildRecurrenceConfig(value.type, opts)`.

## ADR-2.7-1 — Mecanismo de activação do motor de recorrência (GAP-1 RESOLVIDO)

> **Status:** Aceite · **Decisor:** Aria (`@architect`) · **Data:** 20/05/2026 · **Contexto:** architect-gate Story 2.7, Epic 2 Nexus v2.
> Esta ADR é local à Story 2.7 — **não reabre nenhum dos 5 ADRs base** da `architecture-v2.md` (`project_nexus_v2_architecture.md`). Resolve uma divergência de detalhe de implementação não coberta por ADR.

### Problema (GAP-1)

Divergência de três fontes sobre como activar o motor que gera as instâncias recorrentes:

| Dimensão | PRD §10 L446 / EPIC-2 §7 L84 | architecture-v2.md §16 L1123 (nota — não ADR) |
|----------|------------------------------|------------------------------------------------|
| Mecanismo | `setInterval` ou `requestIdleCallback` (cron client-side) | ServiceWorker — Background Sync ou `activate` event |
| Escopo | cron no tab activo | SW — independente do tab |
| Complexidade | Baixa | Alta (SW registration, Background Sync API, VAPID) |
| Geração offline | Não (tab tem de estar aberto) | Sim (SW corre em background) |

A nota §16 era a única fonte a apontar ServiceWorker e **não é um ADR** — EPIC-2 §7 já registava "Sem ADR específico — segue padrão client-side". A nota §16 era, portanto, uma sugestão de optimização sem fundamento formal e em conflito com as duas fontes canónicas (PRD + EPIC-2).

### Opções consideradas

| Opção | Mecanismo | Trade-offs |
|-------|-----------|------------|
| **A** | `useEffect` one-shot no mount da page `/tarefas` | + KISS, ~3 ficheiros novos · + agnóstico — motor puro · + zero polling/CPU desperdiçado · + alinhado PRD+EPIC-2 · − sem geração offline (tab tem de abrir) |
| B | `setInterval` no tab activo | − polling contínuo desperdiça CPU sem ganho real · − exige cleanup de interval · = sem geração offline na mesma |
| C | ServiceWorker + Background Sync | + geração offline real · − escopo +2-3x (SW registration, `service-worker.ts`, Background Sync handler) · − complexidade não justificada por requisito documentado |

### Decisão

**Opção A — `useEffect` one-shot no mount da page `/tarefas`.** O motor (`lib/shared/recurrence.ts`) é uma função pura sobre Dexie, agnóstica ao mecanismo de activação; o hook `useRecurrenceEngine` é o único ponto que conhece o mecanismo.

### Justificação

| Princípio | Como a decisão o cumpre |
|-----------|--------------------------|
| **CLI First / fonte da verdade** | O PRD §10 e o EPIC-2 §7 são as fontes canónicas e ambos dizem cron client-side. A nota §16 (ServiceWorker) não é ADR e estava em conflito — foi corrigida, não promovida. A camada de arquitectura prevalece, mas aqui "arquitectura" formal são os 5 ADRs, não uma nota de §16 sem fundamento. |
| **KISS / simplicidade** | A opção A entrega o caso de uso real com ~3 ficheiros novos. A opção C triplicaria o escopo (SW registration, Background Sync API) sem nenhum requisito (FR ou NFR) que exija geração offline de instâncias. |
| **Contexto de uso pessoal** | O Nexus v2 é uso pessoal do Eurico, com o tab tipicamente sempre aberto. A "geração offline" da opção C resolve um problema que, neste contexto, não existe — não há cenário documentado em que o motor precise de correr com o tab fechado. `useEffect` no mount cobre 100% do caso de uso real ("ao abrir as tarefas, o horizonte de 90 dias está populado"). |
| **No Invention (Constitution Art. IV)** | Nenhum FR/NFR pede geração offline. Escolher SW seria inventar um requisito. A opção A rastreia directamente a FR10 + EPIC-2 §5 (horizonte 90 dias) sem adicionar nada. |
| **Living Architecture** | O motor é agnóstico — se o Epic 4 (lembretes via Web Push) trouxer um requisito real de Background Sync, a migração para SW substitui só `useRecurrenceEngine.ts`. A decisão de hoje não fecha portas; apenas não paga complexidade adiantada. |

### Consequências

1. **`architecture-v2.md` §16 L1123 corrigido** (20/05/2026) — passa a indicar motor client-side + `useEffect`, com referência cruzada a esta ADR. A divergência das três fontes deixa de existir.
2. **AC4 da Story 2.7 fixado** — `useEffect` one-shot é a especificação definitiva, sem linguagem de "pendente".
3. **`setInterval`/`requestIdleCallback` também não são usados** — o termo do PRD ("via `setInterval` ou `requestIdleCallback`") era ilustrativo de "cron client-side"; `useEffect` on-mount é a concretização mais simples e sem polling. Não há violação do PRD — `useEffect` é cron client-side.
4. **Migração futura para ServiceWorker** — reavaliada no Epic 4 **se e só se** o Background Sync de lembretes (FR33/Web Push) a justificar. Não é dívida técnica desta story; é uma opção em aberto deliberada.
5. **Sem impacto na estimativa** — a story mantém 8 pontos; a resolução do GAP elimina incerteza, não adiciona trabalho.

## Dev Notes

- **Motor agnóstico ao mecanismo de activação:** `lib/shared/recurrence.ts` não deve importar nem referenciar `useEffect`, `setInterval`, `requestIdleCallback`, ou APIs de ServiceWorker. O motor é uma função pura (com acesso a Dexie) que pode ser chamada de qualquer contexto — React hook, SW, ou teste. [Source: A4 + A6 + [GAP-1]]

- **`rrule.fromString` para reconstruir a RRule:** a `Recurrence.rule` guarda a RRULE string (ex: `"FREQ=WEEKLY;BYDAY=MO"`). Para reconstruir o objecto `RRule` dentro de `generateTaskInstances`, usar `RRule.fromString(recurrence.rule)` — não reconstruir via `buildRRule` novamente (evitar double-parse). [Source: `lib/shared/recurrence.ts` pattern já existente]

- **Idempotência via `parentTaskId + dueDate`:** o check de duplicados usa `db.tasks.where('parentTaskId').equals(ownerId).toArray()` + filter por `dueDate`. Atenção: `parentTaskId` **não está indexado** em `version(2)` (`client.ts:version(2)` só adiciona `recurrences` e `tags`). Se o volume de tasks filhas for grande (horizonte 90 dias × recorrência diária = 90 tasks), o `where('parentTaskId')` vai fazer full-table-scan em `tasks`. Para uso pessoal do Eurico (volume baixo), aceitável. Se `@architect` identificar risco de performance no gate, adicionar índice `parentTaskId` em `version(3)` (Epic 3 incremento) — **NÃO alterar `version(2)` aqui** (retroactivo é destrutivo). [GAP potencial de performance — documentar no AC14 se identificado]

- **`Task.dueDate`**: verificar o tipo exacto de `dueDate` em `types/db.ts` e `lib/db/repos/tasks.ts` — pode ser `string` (ISO date `YYYY-MM-DD`) ou `number` (epoch). A `architecture-v2.md` §6.2 L489 mostra `dueDate` na interface `Task` sem tipo explícito na grep. Confirmar durante T1.5 antes de comparar `dueDate === isoDate`. [Source: verificação durante T1.5 obrigatória]

- **Task-mãe tem `dueDate`:** quando o Eurico cria uma tarefa recorrente, a task-mãe pode ou não ter `dueDate` (corresponde ao `startDate` da recorrência ou à primeira ocorrência). Decisão final ao executor (Dex) durante T5.2. Sugestão: a task-mãe recebe `dueDate` = primeira ocorrência da recorrência.

- **Lições Epic 1 A2 (Not-Tested Evidence Gate):** se algum commit tocar `vitest.config.ts`, `playwright.config.ts`, ou `package.json:scripts`, é **obrigatório** incluir evidência local (output de dry-run ou `--list`) no Change Log da story antes do commit. [Source: `not-tested-trailer-rules.md`]

- **Epic 4 reutilização:** o `runRecurrenceEngine()` é genérico por `ownerType`. O Epic 4 (Hábitos + Lembretes) vai chamar o mesmo motor com `ownerType: 'habit'` ou `ownerType: 'reminder'`. Para facilitar esta extensão futura, `runRecurrenceEngine()` pode aceitar um parâmetro opcional `ownerType?: RecurrenceOwnerType` para filtrar — ou mantê-lo sem parâmetro e iterar todos os ownerTypes num único loop. Decisão ao executor (Dex) — documentar a opção escolhida no Change Log.

### 3. Decisão sobre [AUTO-DECISION A11] — AC7 parcial

**A11 RATIFICADA. Não é FAIL nem CONCERNS — é a decisão correcta.**

**Facto verificado (não invenção do `@dev`):** inspeccionei `app/(app)/tarefas/page.tsx` directamente — o botão "+ Nova" está `disabled` + `aria-disabled="true"` (linha 319-320), o texto vazio diz "...ou pelo botão \"+ Nova\" (em construção)" (linha 315), e **não existe `TaskFormModal.tsx`** em `components/tarefas/` (12 componentes, nenhum é formulário de criação/edição de tarefa). Mais: a própria Story 2.4 já tinha ratificado **[A4] "+Nova mantém disabled"** (comentário em `page.tsx:38`). A inexistência do formulário é facto consolidado no projecto desde a Story 2.4, não uma observação nova nem conveniente do `@dev`.

**Por que A11 é a escolha correcta e não scope-creep:**
- O escopo da Story 2.7 é o **motor de recorrência (FR10)** — AC1-AC5, AC8-AC10 são o núcleo e estão 100% entregues e funcionais via `useRecurrenceEngine`.
- O AC7 **antecipava** este caso: o texto do AC7 diz literalmente "A story verifica (T1.2) se existe `TaskFormModal.tsx` ou equivalente. Se existir, injecta... Se não existir, a integração é directa na lógica da `tarefas/page.tsx` no handler `onSubmit`." Mas **não existe handler `onSubmit` de tarefa** — porque não existe ponto de criação de tarefa. O AC7 pressupunha um `onSubmit` que o projecto ainda não tem.
- Criar um formulário "+ Nova" completo agora seria **inventar escopo** — viola Constitution Art. IV. Um formulário de criação de tarefa é uma feature própria, não um AC desta story.
- A entrega é **completa para o que é viável agora**: `RecurrenceFieldset` é um componente controlado standalone, totalmente testado (9 testes), com props limpas (`value`/`onChange`) — injectável directamente quando o formulário existir, sem refactor. `cancelTaskRecurrence` é um helper de domínio puro e testado (AC9 cumprido na lógica). A ligação `createRecurrence`+`updateTask`+`generateTaskInstances` ao `onSubmit` é trivial e fica documentada para a story futura.

**AC7 é considerado PASS** — a obrigação verificável do AC7 (entregar a capacidade de configuração de recorrência, injectável no formulário) está cumprida; a parte não entregue (a ligação ao `onSubmit`) é literalmente impossível de cumprir sem inventar uma feature fora de escopo. Diferir é a decisão arquitectonicamente correcta.

**Débito documentado (D-2.7-1):** quando uma story futura criar o formulário "+ Nova" de tarefa, deve injectar `RecurrenceFieldset` e ligar o `cancelTaskRecurrence` ao botão de cancelamento da task-mãe. Registar em `EPIC-2.md` §10.
