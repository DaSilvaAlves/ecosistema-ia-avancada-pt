## Story

**Como** utilizador do Nexus (Eurico),
**quero** exportar todos os meus dados (tarefas, finanças, hábitos, diário, notas, etc.) num único ficheiro ZIP a partir da página de definições,
**para que** os meus dados nunca fiquem presos apenas no browser — tenho uma cópia portátil e legível que posso guardar fora do IndexedDB.

## Acceptance Criteria

1. A página `/settings` tem uma nova secção "Backup" com um botão "Exportar dados" (padrão visual dos cartões existentes `GoogleCalendarSettings`/`GmailSettings`).
2. Ao clicar no botão, o sistema invoca `exportDB(db)` (`dexie-export-import` v4.4.0, já em `dependencies`) sobre a instância `db` (`lib/db/client.ts`) e obtém um Blob JSON contendo **todas as 22 tabelas** do schema Dexie actual (`version(6)`).
3. O export inclui adicionalmente um ficheiro markdown (`notas.md`) com o conteúdo de todas as notas da tabela `knowledge_notes` (domínio "Conhecimento", Epic 5) — cada nota como uma secção `## {title}` com o `bodyMarkdown` completo. `journal_entries` (Diário) e `brain_dumps` (Brain Dump) **não** entram no `notas.md` — só estão cobertos pelo JSON completo (AC2). Ver Dev Notes "Âmbito de 'notas'" para a justificação desta fronteira.
4. Os dois artefactos (`nexus-db-export.json` + `notas.md`) são empacotados num único ficheiro ZIP real (multi-ficheiro), não um JSON isolado renomeado nem um único stream `gzip`.
5. O ZIP é descarregado automaticamente pelo browser com o nome `nexus-backup-{timestamp}.zip`, onde `{timestamp}` é a data/hora ISO 8601 do momento do export com `:` substituído por `-` (compatibilidade de nome de ficheiro), ex: `nexus-backup-2026-07-09T14-30-00.zip`.
6. O export é **inteiramente client-side e read-only**: não escreve em Dexie, não chama nenhum endpoint servidor, não tem efeito destrutivo. Confirmado por inventário: as credenciais OAuth (`refreshToken`/`accessToken`) vivem em Vercel KV (`lib/google/token-store.ts`, `nexus:google:tokens`) — **nunca** em IndexedDB/Dexie — pelo que o export é seguro por construção quanto a fugas de secrets (nenhuma das 22 tabelas Dexie contém tokens ou credenciais).
7. O JSON dentro do ZIP (`nexus-db-export.json`) é **exactamente** o formato nativo do `dexie-export-import` (o output cru de `exportDB()`, sem transformação) — este é o contrato que a Story 9.7 (`db.import()`/`importInto()`) vai consumir para o restore. O nome do ficheiro dentro do ZIP fica registado aqui como contrato fixo para a 9.7.
8. O `notas.md` é **adicional, legível por humanos** — não precisa de ser re-importável pela 9.7 (é uma cópia de leitura, não um formato de restore).
9. Testes unitários cobrem: geração do JSON via `exportDB()` sobre `fake-indexeddb` populada com dados fixture; geração do `notas.md` a partir de notas fixture (incluindo o caso de zero notas); montagem do ZIP com os 2 ficheiros correctos; nome do ficheiro de download.
10. O botão tem pelo menos 3 estados de render distintos (`idle` / `a-exportar` / `sucesso` ou `erro`) — `react-component-test-criteria.md` aplica-se: teste de componente obrigatório, 1 cenário por estado.
11. **Delimitação (não-âmbito):** esta story é SÓ export. Não implementa restore/import (Story 9.7), não escreve em Dexie, não toca produção/deploy, não introduz um botão de "importar".

### ZIP — decisão técnica (Task 1) — nenhuma lib instalada actualmente

[Source: grep `package.json`/`package-lock.json` — confirmado, sem `jszip`/`fflate`/`archiver`]

`dexie-export-import` (`^4.0.0`, instalado, v4.4.0 resolvida) só produz o JSON (via `exportDB(db)`) — não faz ZIP. A arquitectura (`architecture-v2.md` L1154) diz "service worker zipia e devolve blob", mas essa é uma nota de alto nível que **não resolve** qual mecanismo de compressão usar — nem o SW nem a thread principal têm hoje uma lib de ZIP. Análise das opções (AC4 exige ZIP multi-ficheiro real):

| Opção | Viabilidade |
|-------|-------------|
| **`fflate`** (recomendação não-vinculativa) | Zero deps, ~8KB gzip, `zipSync({'nexus-db-export.json': ..., 'notas.md': ...})` — API síncrona simples, produz ZIP real multi-ficheiro. Nova dependência → `npm audit` limpo obrigatório (Task 1). |
| `jszip` | Alternativa madura, mais pesada (~100KB), API assíncrona. Também nova dependência. |
| `CompressionStream` nativo do browser | **NÃO serve** — só produz `gzip`/`deflate` de UM stream, não um contentor ZIP multi-ficheiro. Não cumpre AC4. |
| ZIP "falso" (só o JSON, renomeado `.zip`) | **NÃO cumpre AC3/AC4** (o epic pede explicitamente JSON + markdown). |

Decisão final e execução do `npm audit` ficam com `@dev` na Task 1 — este Dev Notes só remove a ambiguidade "SW zipia" do arch doc (nenhum mecanismo de zip existe hoje em nenhuma camada) e recomenda a via mais simples (client-side directo na página de definições, sem passar pelo Service Worker — o SW não dá paralelismo real aqui, é a mesma thread principal a fazer o trabalho de qualquer forma).

### API `dexie-export-import`

```ts
import { exportDB } from 'dexie-export-import';
const blob: Blob = await exportDB(db); // JSON completo, todas as tabelas + versão de schema
```

Este é o mesmo formato que `importInto(db, blob)` (usado pela Story 9.7) consome — o `nexus-db-export.json` dentro do ZIP **não pode ser transformado** (AC7), tem de ser o output cru de `exportDB()`.

### Formato do backup — contrato fixo para a Story 9.7

```
nexus-backup-{timestamp}.zip
├── nexus-db-export.json   ← output cru de exportDB(db) — formato dexie-export-import, importável via importInto()
└── notas.md                ← markdown legível de knowledge_notes — NÃO re-importável, cópia humana
```

`{timestamp}` = ISO 8601 do momento do export, com `:` substituído por `-` (compatibilidade de filesystem). Exemplo: `nexus-backup-2026-07-09T14-30-00.zip`.
