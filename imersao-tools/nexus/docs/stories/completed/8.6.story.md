### DESIGN-DECISION D-8.6-SCOPE — a 8.6 é puramente configuração + runbook + smoke test (ZERO código)

**Pergunta:** A story 8.6 requer alterações a código de produção?

**Decisão:** NÃO. O scope é exclusivamente:
- **(a) Configuração:** provisionar `OPENAI_API_KEY` real na Vercel UI (Eurico + @devops) + actualizar `LLM_PROVIDER=openai` e `NEXT_PUBLIC_LLM_PROVIDER=openai` na Vercel UI + desencadear redeploy.
- **(b) Documentação:** criar o runbook em `imersao-tools/nexus/docs/runbooks/cutover-openai-rollback.md` (ficheiro novo, documentação operacional).
- **(c) Operacional:** smoke test manual em `https://imersao.ia.expressia.pt` pelo Eurico; confirmação via `vercel logs` pelo `@devops`.

**Verificação em código real (`main`):**
- `lib/shared/env.ts` — `LLM_PROVIDER`, `NEXT_PUBLIC_LLM_PROVIDER`, `OPENAI_API_KEY`, `assertProviderFlagsAgree()`, `resolveLLMProvider()` já existem e implementam todo o comportamento de fail-loud (8.1 Done).
- `lib/agent/providers/factory.ts` — `getClassifier()` e `getExecutor()` já branching por `resolveLLMProvider()`, `readApiKey(provider)` fail-loud se key ausente (8.1 Done).
- `app/api/openai/proxy/route.ts` — proxy Edge com `OPENAI_URL` constante, auth `Authorization: Bearer`, `getSession()`, rate-limit KV já implementados (8.4 Done).
- `lib/agent/providers/openai.ts` — `OpenAIExecutor` + `OpenAIClassifier` já implementados (8.2/8.3 Done).
- `lib/agent/providers/openai-inference-transport.ts` — transport client já implementado (8.4 Done).
- Parity (8.5 Done) — 2535 PASS, 6 cenários canónicos verdes.

**Conclusão:** Não há nenhum ficheiro de código a criar ou modificar. Alterar o provider em produção é uma questão de variáveis de ambiente (as flags já existem, o código já as lê, o default é `anthropic`). A mudança para `openai` é o flip das duas flags na Vercel UI.

**Alternativa rejeitada:** Criar um script de migração automatizado. Razão: desnecessário — a Vercel UI (ou CLI) já gere env vars de produção; um script seria complexidade sem valor; o padrão do ecossistema é configuração via UI/CLI de produção.

### DESIGN-DECISION D-8.6-CUTOVER-AUTHORITY — Eurico autoriza; `@devops` executa

**Pergunta:** O cutover (flip das flags) é automático ou requer autorização humana?

**Decisão:** Autorização explícita do Eurico — padrão AC13 da Story 4.9 / AC6 da Story 7.3 (verificação manual deferida). O `@devops` executa as operações na Vercel UI/CLI; o Eurico autoriza explicitamente antes de cada step crítico (provisão da key, flip das flags, trigger de redeploy).

**Razão (ADR-10 §1.2.3):** "Produção fica sem cérebro durante a transição. A migração não tem pressão de manter produção viva — o critério é correcção, não uptime. Isto remove a urgência que tipicamente força atalhos." O cutover é a única acção irreversível no curto prazo (rollback existe mas custa um redeploy); portanto exige autorização humana explícita.

**Anti-padrão evitado:** não assumir que o `@devops` pode fazer o flip das flags sem autorização — mesmo que as condições técnicas estejam verdes (parity verde, key validada), o cutover em prod é uma decisão de negócio do Eurico.

## Acceptance Criteria

> Traçados directamente ao **ADR-10 §8 row S6** + **EPIC-8 §6 AC3/AC4** + **EPIC-8 §8 pré-requisito #1**. Nenhum AC inventado. Constitution Artigo IV (No Invention).

**AC1 — Gate de entrada: `OPENAI_API_KEY` real provisionada na Vercel UI (pré-requisito bloqueante)**

- A key OpenAI real (`sk-...`) está provisionada na Vercel UI do projecto Nexus v2 como variável de ambiente **server-only** (production environment)
- A key NÃO está como `NEXT_PUBLIC_OPENAI_API_KEY` nem em qualquer outra variável pública
- Verificável via `vercel env ls --environment production` (lista nomes sem revelar valores) ou Vercel UI > Settings > Environment Variables
- Este AC é **bloqueante** para todos os ACs subsequentes: sem a key real, o smoke test (AC3) é impossível

[Trace: EPIC-8 §8 pré-requisito #1 ("pendente — necessário antes da 8.6"); EPIC-8 §6 AC4 (NFR5 — `OPENAI_API_KEY` server-only); `lib/shared/env.ts` — `OPENAI_API_KEY` em `ServerEnvObject` (não em `PublicEnvSchema`); `lib/agent/providers/factory.ts` `readApiKey('openai')` fail-loud se ausente]

**AC2 — Cutover: flags de provider actualizadas para `openai` em produção**

- `LLM_PROVIDER=openai` definida na Vercel UI para o environment de produção
- `NEXT_PUBLIC_LLM_PROVIDER=openai` definida na Vercel UI para o environment de produção
- As duas flags concordam entre si (ambas `openai`) — `assertProviderFlagsAgree()` em `lib/shared/env.ts` valida no boot do server e lança erro PT-PT se discordarem
- Um redeploy é desencadeado após a mudança das vars (via `vercel --prod` por `@devops` ou via Vercel UI > Deployments > Redeploy)
- Após o redeploy, `vercel logs` não mostra erros de arranque relacionados com as flags ou a key

[Trace: ADR-10 §8 row S6 ("`LLM_PROVIDER=openai` + `NEXT_PUBLIC_LLM_PROVIDER=openai` em prod"); ADR-10 §3.4 (asserção de concordância de flags); ADR-10 §7 R4 (mismatch de flags → falha visível, não silenciosa); `lib/shared/env.ts` — `LLM_PROVIDER: z.enum(LLM_PROVIDERS).default('anthropic')`, `NEXT_PUBLIC_LLM_PROVIDER: z.enum(LLM_PROVIDERS).default('anthropic')`, `assertProviderFlagsAgree()`]

**AC3 — Smoke test em produção: o cérebro responde via OpenAI**

- Após o redeploy, Eurico acede a `https://imersao.ia.expressia.pt` e executa ≥1 prompt com tool calling (ex: "lista as minhas tarefas de hoje" ou equivalente)
- O Nexus v2 responde com conteúdo coerente (cérebro vivo via OpenAI — tool(s) executada(s) + resposta formatada no chat)
- Não há erros 400/500 visíveis na UI relacionados com o provider nem na Vercel function log
- `@devops` confirma via `vercel logs` (ou Vercel Dashboard > Functions) que chamadas ao proxy `/api/openai/proxy` retornam HTTP 200
- **Verificação manual deferida ao Eurico** (padrão AC13 da Story 4.9 / AC6 da Story 7.3 — este AC só é verificável com a key real em produção)
- A evidência do smoke test (screenshot da resposta no chat OU excerpt de `vercel logs` com 200 no proxy) é registada na secção QA Results + Evidence Gate desta story

[Trace: ADR-10 §8 row S6 ("cérebro responde em prod via OpenAI"); EPIC-8 §6 AC3 ("A produção responde via OpenAI após o cutover"); EPIC-8 §6 nota ("verificação manual deferida ao Eurico + @devops, mapeada no draft da 8.6")]

**AC4 — Runbook de rollback documentado e testável**

O ficheiro `imersao-tools/nexus/docs/runbooks/cutover-openai-rollback.md` existe e contém:
- **Procedimento de cutover** (para referência e re-cutover): passos para flip `anthropic` → `openai` nas vars + redeploy
- **Procedimento de rollback** (flip `openai` → `anthropic`): passos exactos + comandos Vercel CLI verificáveis
  - `vercel env rm LLM_PROVIDER production && vercel env add LLM_PROVIDER production` (com valor `anthropic`)
  - `vercel env rm NEXT_PUBLIC_LLM_PROVIDER production && vercel env add NEXT_PUBLIC_LLM_PROVIDER production` (com valor `anthropic`)
  - `vercel --prod` (ou Vercel UI > Redeploy)
- **Critérios de activação do rollback** (quando reverter): smoke test falha, erros 500 recorrentes no proxy, custos anómalos, latência inaceitável
- **Tempo estimado de rollback:** 5-10 min (dois comandos + redeploy Vercel)
- **Confirmação pós-rollback:** verificar que `LLM_PROVIDER=anthropic` está activo + smoke test Anthropic
- **Contacto de escalação:** Eurico (`euricojsalves@gmail.com`)
- O rollback é **logicamente testável** (é o inverso do cutover: flip de flags + redeploy — reversível por construção); o rollback live só é executado se o smoke test (AC3) falhar
- O ficheiro é commitado como parte do PR desta story e revisto por CR `--base main`

[Trace: ADR-10 §8 row S6 ("runbook de rollback documentado e testado; flip para `anthropic`"); EPIC-8 §6 AC3 ("rollback documentado e testado"); D-8.6-RUNBOOK-LOCATION (AUTO-DECISION: `docs/runbooks/`)]
