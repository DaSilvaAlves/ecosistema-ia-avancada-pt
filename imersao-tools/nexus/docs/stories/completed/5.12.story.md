## Decisões deferidas ao @architect (Aria) — gate de ENTRADA obrigatório

> Padrão das Stories 5.7/5.8/5.11: decisões de risco são deferidas ao `@architect` antes da implementação — o `@dev` não implementa nenhuma destas até as decisões estarem registadas com veredicto na story. Nomeadas com `[D-5.12-*]` para rastreabilidade.

**[D-5.12-SCOPE-vs-5.13]** — Fronteira de responsabilidade entre 5.12 e 5.13:

A 5.13 regista as 9 tools no Tool Registry (incluindo `pesquisar_web_e_criar_nota`). A 5.12 implementa a orquestração e o preview do fluxo multi-passo. Mas para o cérebro acionar o fluxo da 5.12, precisa de ter a tool `pesquisar_web_e_criar_nota` registada — o que é trabalho da 5.13.

- Opção A: A 5.12 implementa apenas a **lógica de orquestração** (novo endpoint `/api/conhecimento/web-search-create-note` ou módulo client) + UI de preview; a tool `pesquisar_web_e_criar_nota` é registada na 5.13 e aponta para este endpoint. A 5.12 fica testável como fluxo de UI independente.
- Opção B: A 5.12 regista **antecipadamente** a tool `pesquisar_web_e_criar_nota` (com `requiresPreview: true`) para que o cérebro a possa acionar durante a 5.12; a 5.13 completa as restantes 8 tools. Risco: duplicação de registo se a 5.13 re-registar a mesma tool.
- Opção C: A 5.12 não toca no Tool Registry nem cria endpoint novo; implementa o fluxo inteiramente no lado do cliente como um modo especial da página `/knowledge` (análogo ao Brain Dump: chamada ao endpoint de pesquisa web + criação de nota em cascata com preview). A UI invoca directamente os endpoints existentes (5.11 para pesquisa, repos 5.9 para criação).

`@architect` ratifica: qual a opção? A decisão afecta AC1, AC2, AC3 e a estrutura de ficheiros.

**[D-5.12-PREVIEW]** — Como o preview multi-passo encaixa no mecanismo `requiresPreview` existente:

O mecanismo `requiresPreview` do executor (Story 1.6) foi concebido por-tool (um preview por tool call). O fluxo da 5.12 propõe **múltiplas entidades** (ex: área "Espaço" + caderno "Artemis 2" + nota sobre Artemis 2) de uma só vez, com o utilizador a aprovar/rejeitar o conjunto antes de persistir.

- Opção P1: Preview **consolidado** — o cérebro propõe as N entidades numa só `preview_request` (o utilizador vê "Vou criar: área X, caderno Y, nota Z — confirmas?"). Um único `requiresPreview: true` na tool `pesquisar_web_e_criar_nota`. Fluxo simples, mas não permite aprovação granular por entidade.
- Opção P2: Preview **por-entidade** — o executor faz N preview_requests sequenciais (criar_area → preview → confirmar → criar_caderno → preview → confirmar → criar_nota → preview → confirmar). Reutiliza o mecanismo por-tool. Mais granular, mas mais latência e mais complexidade de estado no cliente.
- Opção P3: Preview via UI especializada (fora do mecanismo `requiresPreview` do executor) — análogo ao Brain Dump (5.8): o fluxo multi-passo não passa pelo executor do cérebro multi-intent; é uma chamada directa ao endpoint de pesquisa web + proposta de área/caderno/nota na UI, com aprovação client-side antes de persistir. Desacopla o fluxo da 5.12 do executor.

`@architect` ratifica: qual a abordagem de preview? A decisão afecta AC3/AC4 e a estrutura de estado.

**[D-5.12-FAILURE]** — Caminho de falha do fetch externo a meio do fluxo multi-passo:

O fluxo propõe: pesquisa web → resultados → proposta de área+caderno+nota → preview → persistência. E se o fetch web falhar depois do utilizador ter iniciado a aprovação? E se falhar a meio da persistência (área criada, caderno não)?

- Eixo (a) Classes de estado: `idle` / `searching` (fetch em curso) / `proposing` (resultados obtidos, aguarda proposta de área/caderno) / `previewing` (proposta gerada, aguarda confirmação do utilizador) / `persisting` (a criar entidades) / `done` / `error`.
- Eixo (b) Transição-já-ocorrida: Área já existe com o nome proposto? O que acontece? Caderno já existe nessa área? Nota com o mesmo `sourceUrl` já existe?
- Eixo (c) Caminhos de falha: Fetch web falha → o fluxo aborta limpo (sem proposta parcial)? Persistência falha a meio (área criada, caderno não) → rollback ou estado parcial visível?

`@architect` analisa os 3 eixos (`internal-state-contract-gate.md`) e regista na story antes de `@dev *develop 5.12`. Sem análise documentada, o gate de saída repete o padrão 4.9 (M1-M4 descobertos pelo CodeRabbit).

**[D-5.12-PERSIST]** — Ordem e idempotência da persistência em cascata:

Ao persistir área → caderno → nota:
- A ordem deve ser Área → Caderno (filho da área) → Nota (filha do caderno) — mas se a área já existir, deve ser reutilizada ou é erro?
- O caderno: se já existir nessa área com o nome proposto, reutiliza ou cria duplicado?
- A nota: `createKnowledgeNote` exige `notebookId` do caderno (pode ser o recém-criado ou um existente).

Contrato real verificado: `createKnowledgeArea` não valida unicidade de nome (pode criar áreas com nomes duplicados). `createKnowledgeNotebook` idem. `createKnowledgeNote` valida apenas que o caderno pai existe — não verifica `sourceUrl` único.

`@architect` decide: a 5.12 deve verificar duplicados por nome antes de criar? O que mostra ao utilizador se a área já existe (usa a existente? cria duplicado? erra?)?

### `[D-5.12-SCOPE-vs-5.13]` — RATIFICADA: **Opção C** (fluxo client-side, sem tocar o Tool Registry)

A 5.12 implementa o fluxo **inteiramente no lado do cliente** como modo especial da página `/knowledge`, análogo ao Brain Dump (5.7/5.8) e à pesquisa web manual (5.11). A UI invoca directamente o endpoint `/api/conhecimento/web-search` (5.11, same-origin) e os repos `createKnowledgeArea`/`createKnowledgeNotebook`/`createKnowledgeNote` (5.9). A tool `pesquisar_web_e_criar_nota` é registada no Tool Registry **só na 5.13** — a 5.12 NÃO toca `lib/agent/tools/index.ts`.

**Evidência (código real):**
- O Brain Dump (`BrainDumpLauncher.tsx:9-19,116-156`) é o precedente directo: estruturação AI + aprovação + persistência são **client-side puros**, sem passar pelo executor do cérebro multi-intent. O parser é um endpoint (`/api/anthropic/proxy`); a orquestração e o preview vivem no cliente.
- A 5.11 (`knowledge/page.tsx:239-289`) já chama `/api/conhecimento/web-search` por `fetch` same-origin e cria nota via `createKnowledgeNote` directo no cliente. A 5.12 estende este mesmo padrão para a cascata área→caderno→nota.
- Registar a tool na 5.12 (Opção B) duplicaria o registo com a 5.13 (risco explícito de re-registo) e arrastaria a complexidade do executor + `ConfirmationProvider` para uma feature que o precedente 5.8 já provou ser melhor servida client-side.

**Trade-off aceite:** o cérebro multi-intent (chat em `/`) **não** aciona o fluxo na 5.12 — o acionamento é pela página `/knowledge` (modo "pesquisar e criar"). O acionamento via linguagem natural no chat ("pesquisa Artemis 2 e cria área Espaço…") chega na 5.13, quando a tool estiver registada e apontar para a mesma lógica de orquestração da 5.12. Isto mantém a 5.12 testável como fluxo de UI independente e desacoplado do executor. **AC2 é ajustado** (ver C2): a classificação multi-intent passa a ser responsabilidade da 5.13; a 5.12 prova a orquestração + preview + persistência.

### `[D-5.12-PREVIEW]` — RATIFICADA: **Opção P3** (UI especializada client-side, preview consolidado)

Preview **consolidado** (1 preview para as N entidades) via componente dedicado `WebSearchCreateProposal.tsx`, **fora** do mecanismo `requiresPreview` do executor. O utilizador vê uma proposta única ("Vou criar: área X [nova/existente], caderno Y [novo/existente], nota Z com fonte URL") e confirma/cancela o conjunto.

**Evidência (código real):**
- `requiresPreview` existe por-tool no executor (`executor.ts:437`, `evaluatePreviewGate`) — confirmado, **não precisa de extensão**. Mas é coerente com Opção C que a 5.12 não use o executor: o gate `requiresPreview` só faz sentido quando a tool é accionada pelo executor (5.13).
- O precedente 5.8 (`BrainDumpModal`/`BrainDumpApprovalView`) usa preview client-side fora do executor — exactamente Opção P3. A 5.12 segue o mesmo molde.
- Preview consolidado (P1-shape) em vez de por-entidade (P2): a cascata área→caderno→nota é uma unidade semântica única (a nota não faz sentido sem o caderno, que não faz sentido sem a área). Aprovação granular por entidade (P2) adicionaria latência e estados intermédios sem valor para o utilizador — o que ele aprova é "criar este conhecimento", não cada nível isolado. P2 fica fora de scope.

**Trade-off aceite:** sem aprovação granular por entidade. Se o utilizador quiser a nota noutro caderno, cancela e reformula (ou usa o fluxo manual da 5.11). Consistente com o "tudo-ou-nada" da transacção de persistência (ver `[D-5.12-PERSIST]`).

### `[D-5.12-PERSIST]` — RATIFICADA: **reutilizar área/caderno existentes por nome; transacção atómica única; idempotência client-side**

Ordem **Área → Caderno → Nota**, numa **única transacção Dexie `'rw'`** sobre `[knowledge_areas, knowledge_notebooks, knowledge_notes]` (all-or-nothing), com **get-or-create idempotente por nome**:
- **Área:** se já existir área com o nome proposto (match exacto após `trim`, comparação case-insensitive PT-PT via `localeCompare`) → **reutiliza** (não cria duplicado). Senão cria nova com `id: crypto.randomUUID()`.
- **Caderno:** dentro da área (nova ou reutilizada), se já existir caderno com o nome proposto → **reutiliza**. Senão cria novo.
- **Nota:** sempre criada nova (`createKnowledgeNote` com `id: crypto.randomUUID()`, `sourceUrl`, `updatedAt: Date.now()`). NÃO se faz dedupe de nota por `sourceUrl` — uma nova pesquisa sobre o mesmo tema é uma nova nota legítima (o utilizador viu o preview e confirmou).

**Evidência (código real):**
- `persistApprovedItems` (`lib/brain-dump/approval-persistencia.ts:244-296`) é o **template exacto**: get-or-create idempotente (`garantirInbox`, `garantirTagDecisao`) DENTRO de uma transacção `'rw'` atómica, com os stores todos declarados na lista (senão `TransactionInactiveError`), e rollback total em falha. A 5.12 replica este padrão para área→caderno→nota.
- Os repos NÃO validam unicidade de nome (`createKnowledgeArea:21-27`, `createKnowledgeNotebook:24-36` — só valida que a área pai existe). A verificação de duplicados é, portanto, **responsabilidade do orquestrador da 5.12** (via `listKnowledgeAreas`/`listNotebooksByArea` lidos DENTRO da transacção, antes do create).
- Schemas exigem `id` UUID v4 (`schemas.ts:409-439`) — gerar via `crypto.randomUUID()` (não IDs determinísticos; os IDs de sistema `SYSTEM_AREA_ID`/`INBOX_NOTEBOOK_ID` da 5.8 são para o `_inbox`, irrelevantes aqui).

**Decisão sobre "transição-já-ocorrida":** reutilizar (não 409, não duplicar) é a escolha correcta porque o utilizador viu o preview com a indicação "[existente]" e confirmou conscientemente. O preview DEVE distinguir visualmente "nova" vs "existente" (C3).

### `[D-5.12-FAILURE]` — Análise de ciclo de vida (`internal-state-contract-gate.md`, 3 eixos contra código real)

O estado distribui-se por 3 camadas: **(L1) endpoint `/api/conhecimento/web-search`** (5.11, Node) → **(L2) orquestrador client `web-search-create.ts`** (proposta + persistência) → **(L3) UI `WebSearchCreateProposal`** (preview + confirmação) → **(L4) repos Dexie** (persistência atómica).

**Eixo (a) — Classes de estado.** Estados da máquina, com o que cada camada faz a cada um:

| Estado | L1 endpoint | L2 orquestrador | L3 UI | L4 Dexie |
|--------|-------------|-----------------|-------|----------|
| `idle` | — | — | convite PT-PT | — |
| `searching` | fetch em curso | aguarda `results` | spinner, sem botões | — |
| `proposing` | devolveu `{results, source}` | formula proposta (lê áreas/cadernos existentes p/ marcar nova/existente) | mostra proposta + botões | — |
| `confirming` | — | executa `persistProposal` (transacção) | progresso, botões off | writes em curso |
| `done` | — | devolve `PersistResult` | sucesso PT-PT + link | committed |
| `error-search` | 503 ou `!resp.ok` ou `results` ausente | propaga erro, **proposta nunca aparece** | `role="alert"`, sem proposta | nada escrito |
| `error-persist` | — | transacção lança → rollback total | `role="alert"` com detalhe | **rollback — zero entidades** |

**Eixo (b) — Transição-já-ocorrida.** Respondido contra código real:
- *Área/caderno já existem com o nome proposto*: tratado por `[D-5.12-PERSIST]` — reutiliza, e a verificação acontece DENTRO da transacção (a leitura `listKnowledgeAreas` e o create são atómicos, sem janela de corrida entre ler e criar).
- *Dupla submissão (utilizador clica "Confirmar" 2×)*: a UI desactiva o botão ao entrar em `confirming` (padrão `WebSearchSaveModal.tsx:94-95` `if (saving) return;` + `disabled={saving}`). **C4** exige teste explícito (eixo b — só 1 persistência).
- *Caderno/área "existente" escolhido para reutilizar é eliminado entre o preview e a confirmação*: como a verificação de existência e o create correm DENTRO da transacção (não no momento do preview), se o caderno foi apagado entretanto o orquestrador relê e cria de novo (get-or-create reavalia) — **não há referência a um id stale do preview**. A proposta carrega NOMES, não IDs; os IDs resolvem-se na transacção. Isto evita o "FK para entidade eliminada" (lição equivalente a M3 da 4.9).

**Eixo (c) — Caminhos de falha.** Respondido contra código real:
- *Fetch web falha (rede, 503, `!resp.ok`, `results` ausente)*: o orquestrador trata como falha ANTES de qualquer proposta — `error-search`, proposta nunca aparece, zero writes. Padrão exacto de `handleWebSearch` (`page.tsx:245-271`): `if (!resp.ok || data === null || !Array.isArray(data.results))` → erro. **NÃO silencia** (lição M4 4.9 + M4 5.11). **C5** exige que o orquestrador inspeccione o body (o endpoint 5.11 pode devolver erro de provider) — não basta `resp.ok`.
- *Persistência falha a meio (área criada, caderno lança)*: **rollback total** pela transacção atómica `'rw'` — zero entidades, nunca estado parcial visível. Isto é estritamente melhor do que o "mensagem explícita do que foi criado parcialmente" sugerido no AC4: com transacção atómica **não há parcial**. **C1** fixa que a persistência É atómica (não sequência de creates soltos) — o anti-padrão a evitar é o `@dev` fazer 3 `await create...` fora de transacção, que deixaria parcial.
- *Cancelamento no preview*: `confirmed === false` → `persistProposal` retorna sem tocar nos repos (zero writes). Sem resíduo.
- *Rede cai entre preview e confirmação*: como a pesquisa já terminou (estamos em `proposing`), a persistência é 100% local (Dexie) — não há rede no caminho de persistência. A única falha possível em `confirming` é Dexie indisponível → `error-persist` + rollback.

**Conclusão do gate de estado:** os 3 eixos estão cobertos pela combinação (transacção atómica + get-or-create por nome dentro da transacção + inspecção do body do fetch). A análise FICA REGISTADA (esta secção) — o gate de saída e o CodeRabbit cobram-na. Lição 4.9 (2 iter evitáveis) endereçada à entrada.
