[AUTO-DECISION A5] **Cascata em `deleteTag`** (não soft-delete, não orphan-leave). Quando Eurico elimina uma tag, o repo:
1. Lista todas as `tasks` que contêm o `tagId` no array `task.tags` via `db.tasks.where('tags').anyOf([tagId]).toArray()` (índice `*tags`).
2. Para cada task, remove o `tagId` do array (`task.tags = task.tags.filter(t => t !== tagId)`) e chama `db.tasks.put(updatedTask)` ou `updateTask(id, { tags: ... })` numa transacção `'rw'` atómica.
3. `db.tags.delete(tagId)` na mesma transacção.

Razão: orphan tags em `Task.tags` seriam ids fantasma — quebraria o `tagsLookup` Map (chave existe mas não retorna `Tag`) e poderia exibir `tagId` cru na UI (regressão visual). [AUTO-DECISION A6] **Confirmação obrigatória antes de eliminar** via `window.confirm` PT-PT inline (precedente das Stories 2.3+2.8 que usam `window.confirm` para deletar tarefa/projecto). Mensagem: `"Eliminar a tag «{nome}»? Será removida de N tarefas vinculadas."` onde N é a contagem prévia (`tasks.where('tags').anyOf([id]).count()`). Razão: cascata é destrutiva — Eurico precisa de saber quantas tasks vão perder a tag antes de confirmar. Alternativa "toast confirm com undo 30s" descartada — pattern não existe ainda no codebase (futuro Epic 8 cleanup), inflação de scope. Alternativa "eliminar sem confirmar" descartada — destrutivo sem aviso.

[AUTO-DECISION A7] **`updateTag(id, patch)`** no repo aceita `Partial<Pick<Tag, 'name' | 'color'>>` (apenas `name` e `color` mutáveis — `id` é imutável). Reutiliza a normalização case-insensitive de `createTag` mas **excluindo o próprio `id`** da verificação de duplicados (renomear tag para o mesmo nome com capitalização diferente é permitido, e a tag estar a comparar contra si mesma é falso positivo). Implementação:
```ts
export async function updateTag(id: string, patch: Partial<Pick<Tag, 'name' | 'color'>>): Promise<void> {
  const existing = await db.tags.get(id);
  if (!existing) throw new Error(`Tag "${id}" não encontrada`);
  if (patch.name !== undefined) {
    const target = normalize(patch.name);
    const all = await db.tags.toArray();
    const duplicate = all.find((t) => t.id !== id && normalize(t.name) === target);
    if (duplicate) throw new Error(`Já existe uma tag com o nome "${patch.name}"`);
  }
  const merged: Tag = { ...existing, ...patch };
  TagSchema.parse(merged);
  await db.tags.put(merged);
}
```

## Acceptance Criteria

- **AC1:** **Repo `lib/db/repos/tags.ts` estendido** com `updateTag(id, patch)`:
  - Assinatura: `export async function updateTag(id: string, patch: Partial<Pick<Tag, 'name' | 'color'>>): Promise<void>`
  - Lança `Error('Tag "{id}" não encontrada')` em PT-PT se `db.tags.get(id)` retornar `undefined`.
  - Se `patch.name !== undefined`, valida duplicado case-insensitive **excluindo o próprio `id`** (`existing.find((t) => t.id !== id && normalize(t.name) === target)`). Lança `Error('Já existe uma tag com o nome "{name}"')` em PT-PT em caso de duplicado.
  - Valida o objecto mergeado via `TagSchema.parse(merged)` antes de persistir.
  - Persiste via `db.tags.put(merged)`.

- **AC2:** **`deleteTag(id)` com cascata atómica**. O repo executa numa única transacção Dexie `'rw'`:
  1. `tasks = await db.tasks.where('tags').anyOf([id]).toArray()` (índice multi-entry `*tags`).
  2. Para cada task: `db.tasks.put({ ...task, tags: task.tags.filter((t) => t !== id), updatedAt: Date.now() })`.
  3. `db.tags.delete(id)`.

  Se a transacção falhar a meio, Dexie faz rollback automático (garantia transaccional). O comportamento da assinatura pública mantém-se compatível com call-sites existentes (`Promise<void>`).

- **AC3:** **`hooks/useTags.ts`** criado com assinatura `export function useTags(): Tag[] | undefined`. Implementação `useLiveQuery(() => listTags(), [])`, paralela a `hooks/useProjects.ts` (Story 2.1) e `hooks/useTasks.ts` (Story 2.1). Retorna `undefined` no 1º render (carregamento Dexie), depois array ordenado alfabeticamente pt-PT.

- **AC4:** **Refactor cirúrgico de 2 pages** consumindo o hook novo:
  - `app/(app)/tarefas/page.tsx:68-69` — substituir `const tags = useLiveQuery(() => listTags(), [])` por `const tags = useTags()`. Remover o import `import { listTags } from '@/lib/db/repos/tags'` (se não for usado noutro lado da page) e o import `useLiveQuery` (se não for usado noutro lado). Adicionar `import { useTags } from '@/hooks/useTags'`. **Zero alteração de comportamento esperado** — refactor puro. `tagsLookup` Map continua construído via `useMemo` na page.
  - `app/(app)/projectos/[id]/page.tsx:~69` — mesmo refactor cirúrgico.

## Dev Notes

- **NÃO recriar a tabela `tags`:** já existe em `version(2)` desde Story 2.1. NÃO incrementar para `version(3)`. NÃO mexer em `lib/db/client.ts`. A Story 2.6 só estende o repo (não o schema Dexie). [Source: `lib/db/client.ts` version(2), `architecture-v2.md §4.2`]

- **Cascata atómica em `deleteTag`:** o padrão Dexie é `db.transaction('rw', db.tasks, db.tags, async () => { ... })`. Se qualquer `put` ou `delete` dentro falhar (ex: constraint), Dexie faz rollback de toda a transacção — garantia ACID local. NÃO fazer 2 awaits separados em try/catch (não-atómico — pode deixar estado inconsistente se segundo await falhar). [Source: `architecture-v2.md` ADR-2 Dexie 4 + Dexie docs Transactions]

- **`updateTag` excluir próprio id na verificação de duplicado:** sem isto, renomear a tag "Trabalho" para "Trabalho" (capitalização idêntica) ou "TRABALHO" (capitalização diferente) lança falso erro de duplicado contra si mesma. A verificação correcta é `existing.find((t) => t.id !== id && normalize(t.name) === target)`. [Source: padrão estabelecido `createTag` Story 2.1 ajustado para `updateTag`]

- **Paleta restrita:** o campo `color: string` em `interface Tag` aceita qualquer string (validação Zod só `min(1)`). A restrição às 7 cores é **enforce-only-em-UI** — não é constraint de DB. Razão: futuro evolução (Epic 5+) pode adicionar cores sem migration; a 2.6 garante consistência do design system via UI mas não bloqueia tags pré-existentes ou tags criadas via tools cérebro futuras com cor fora da paleta. [Source: `.claude/rules/design-system-ia-avancada.md`]

- **Empty array `Task.tags` vs `null`:** após cascata, `task.tags` pode ficar `[]` — é o estado canónico (não usar `null`, não remover o campo). `useTasks()` continua a retornar a task com `tags: []`. `TasksFilters` com `tagId === undefined` ou string que não existe no `*tags` index não retorna tasks vazias — comportamento correcto. [Source: `types/db.ts:493` + lição Story 2.1 Q1]

- **Refactor `useLiveQuery` → `useTags` é puro:** os 2 pages que refactoram já fazem `useLiveQuery(listTags, [])` com deps `[]`. `useTags()` é wrapper exacto. Comportamento idêntico esperado. Se algum teste falhar pós-refactor, é regressão a investigar (não esperado). [Source: `app/(app)/tarefas/page.tsx:68-69`, `app/(app)/projectos/[id]/page.tsx:~69`]

- **`tagsLookup` Map permanece nas pages:** NÃO consolidar para dentro do hook `useTags`. Razão: a `/tags` page só precisa da lista (`Tag[]`), não do lookup; obrigar todos os consumers a pagar custo de construir Map quando só 2 deles precisam viola separação de concerns. Padrão paralelo: `useProjects()` retorna `Project[]`, e cada page consumidora constrói seu próprio derivado (filtro por status, agrupamento). [Source: padrão Story 2.1 hooks + Story 2.9 `tagsLookup` construído inline em `projectos/[id]/page.tsx`]

- **`window.confirm` é a11y nativo aceitável:** todos os browsers modernos têm a11y de `confirm` (anunciado por screen readers). Pattern aceite Story 2.3 (delete task) + Story 2.8 (delete project). Custom dialog modal de confirmação inflacionaria scope sem ganho a11y mensurável. [Source: Stories 2.3 + 2.8 pattern, ratificado por Pax sem CONCERNS]
