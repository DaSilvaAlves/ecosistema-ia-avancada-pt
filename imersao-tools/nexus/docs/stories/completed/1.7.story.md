## User Story

**As a** Eurico (utilizador único do Nexus v2) a interagir com o chat multi-intent,
**I want** poder reverter a última execução do agente carregando num botão undo dentro de 30 segundos após a execução terminar,
**so that** se o agente classifier/executor entender mal o meu prompt PT-PT e criar acções incorrectas (tarefa errada, finança no valor errado, evento na data errada), eu possa desfazer **toda a execução** (todos os tool calls em ordem reversa) sem ter de intervir manualmente em 5 sítios diferentes da app, cumprindo o FR6 do PRD ("Botão undo (toast 30s) reverte última acção do agente") e o AC4 do Epic 1 ("Undo reverte última operação dentro de 30s; após 30s não é possível").

**Fluxo undo end-to-end (esta story implementa o backend):**

```text
runAgent() executa tool reversível com sucesso
  │
  ├─ Após cada tool.execute() bem-sucedida onde tool.reversible === true:
  │    1. Chamar registerUndoEntry(runId, toolCallIdx, { args, result, toolName })
  │    2. registerUndoEntry persiste em KV `nexus:undo:run:<runId>` com TTL 30s
  │
  ├─ runAgent() emite evento `done`
  │
  └─ Durante 30s, runId é "undo-able"
        │
        Cliente clica botão undo (Story 1.9 — fora deste scope):
            POST /api/agent/undo { runId }
              │
              ├─ Edge handler (esta story):
              │    1. Auth check via getSession() — 401 se inválido
              │    2. Lê KV `nexus:undo:run:<runId>` — 410 Gone se TTL expirou
              │    3. Lê AgentRun do payload (toolCalls em ordem)
              │    4. Para cada tool call (em ordem REVERSA):
              │       - toolRegistry.get(toolName).reverse(args, result, ctx)
              │       - Recolhe erros mas continua (best-effort)
              │    5. Apaga entrada KV
              │    6. Retorna 200 { reverted: N, errors: [] }
              │
              └─ Cliente recebe response → marca AgentRun como reverted via markRunReverted(runId) (Story 1.1 — client-side Dexie)
```

**Anti-padrões críticos desta story:**
- NÃO criar o endpoint `/api/agent/prompt` — é Story 1.8
- NÃO criar UI toast undo nem countdown — é Story 1.9
- NÃO alterar `ToolDefinition` (Story 1.3) — `reversible` e `reverse?` já existem
- NÃO alterar `AgentRunSchema` (Story 1.1) — `status: 'reverted'` já existe
- NÃO alterar `ConfirmationProvider` (Story 1.6) — independente do undo
- NÃO chamar `markRunReverted` no servidor — é client-side Dexie (RESOLVED-2 da Story 1.5: executor é stateless, Dexie corre no client)
- NÃO unificar KV namespace com ConfirmationProvider (Story 1.6) — manter separação até ADR explícito

- **AC2:** Novo módulo `imersao-tools/nexus/v2/lib/agent/undo.ts` exporta:
  - **`UndoEntrySchema`** (Zod, em `lib/agent/schemas.ts` para manter convenção canonical Story 1.4):
    ```typescript
    export const UndoEntrySchema = z.object({
      runId: z.string().uuid(),
      timestamp: z.number().int().positive(),
      toolCalls: z.array(ToolCallSchema), // mesmo shape que AgentRun.toolCalls
      expiresAt: z.number().int().positive(),
    });
    export type UndoEntry = z.infer<typeof UndoEntrySchema>;
    ```
  - **`registerUndoEntry(runId: string, toolCalls: ToolCall[], kvClient: VercelKV): Promise<void>`** — persiste em KV chave `nexus:undo:run:<runId>` com TTL 30s (`kvClient.set(key, value, { ex: 30 })`). Valida payload via `UndoEntrySchema.parse()` antes de persistir.
  - **`getUndoEntry(runId: string, kvClient: VercelKV): Promise<UndoEntry | null>`** — retorna `null` se TTL expirou ou entrada nunca existiu. Validação Zod no readback (fail-loud em PT-PT se KV retornar shape corrupto).
  - **`deleteUndoEntry(runId: string, kvClient: VercelKV): Promise<void>`** — apaga após uso (idempotente — `del` em chave inexistente é no-op).
  - **`UNDO_TTL_SECONDS = 30`** — constante exportada (permite override em testes + traçada ao FR6).

- **AC4:** `runAgent()` em `lib/agent/executor.ts` é estendido (NÃO recriado) para registar undo entry após cada tool execute bem-sucedida onde `tool.reversible === true`:
  - **Localização da extensão:** após o branch de sucesso `tool.execute()` (igual à localização onde já se incrementa `toolCallCount` da Story 1.5/1.6), antes do `tool_complete` SSE event ser emitido
  - Acumula `ToolCall` items numa lista local `reversibleToolCalls: ToolCall[]`
  - Após o loop terminar com `done.status === 'success' || done.status === 'partial'`, se `reversibleToolCalls.length > 0`, chama `registerUndoEntry(runId, reversibleToolCalls, ctx.kv)` ANTES de emitir o evento `done`
  - Se `done.status === 'failed'`, NÃO regista undo entry (não há nada a reverter de forma segura)
  - Erros do `registerUndoEntry` são apanhados e emitidos como `tool_error { toolName: 'undo_register', error }` mas NÃO bloqueiam o `done` (best-effort — undo é nice-to-have, não é blocker)

- **AC5:** Novo evento SSE `undo_registered` adicionado ao tipo `ExecutorSSEEvent` em `lib/agent/executor.ts`:
  ```typescript
  | {

      undoableToolCount: number; // length de reversibleToolCalls

  ```
  Emitido **antes** do evento `done`, **apenas se** `reversibleToolCalls.length > 0` E `registerUndoEntry` resolveu sem erro.

- **AC6:** Novo endpoint Edge `POST /api/agent/undo` em `imersao-tools/nexus/v2/app/api/agent/undo/route.ts`:
  - `export const runtime = 'edge'`
  - Body schema (Zod em `lib/agent/schemas.ts`):
    ```typescript
    export const UndoRequestSchema = z.object({
      runId: z.string().uuid(),
    });
    ```
  - Auth: `getSession()` de `lib/auth/session.ts` (Story 0.6 pattern). 401 se sessão inválida.
  - Lookup: `getUndoEntry(runId, kv)`. Se `null`: 410 Gone com body `{ error: 'undo_window_expired' }` (PT-PT message: `'Janela de undo (30s) expirou'`).
  - **Defense-in-depth TTL guard** (RESOLVED-2): Após `getUndoEntry` retornar entry não-null, validar `entry.expiresAt > Date.now()` antes de processar. Se expirou (race window ~1s ou clock skew Edge): `await deleteUndoEntry(runId, kv)` + 410 com mesmo body (`'undo_window_expired'`). Cliente trata igual à expiry natural.
  - Reverse loop: para cada `toolCall` em `reverse()` ordem (último primeiro):
    - `tool = toolRegistry.get(toolCall.toolName)` — se `undefined` (tool removida do registry): adicionar a `errors[]` com `{ toolName, message: 'Tool não registada — não pode ser revertida' }` + `logger.error('Tool not in registry during undo', { runId, toolName })`
    - Se `tool` existe MAS `tool.reverse === undefined` (invariant violation — `reversible: true` mas reverse não definido): adicionar a `errors[]` com `{ toolName, message: 'Tool reverse() não definido — invariant violation' }` + `logger.error('Tool reverse missing — invariant violation', { runId, toolName })` (RESOLVED-6 — invariant violation deve surface em ops sem bloquear undo parcial)
    - `await tool.reverse(toolCall.args, toolCall.result, ctx)` — `ctx` construído inline com o mesmo shape que executor; em try/catch: erro vai para `errors[]`, continua o loop
  - Após loop: `await deleteUndoEntry(runId, kv)` — sempre, mesmo se houve erros parciais
  - Response: `200 { reverted: N, errors: [{ toolName, message }] }` onde `N = total tool calls processados` (não apenas successful — alinha com semântica "best-effort" da Story 1.5)
  - **NÃO chama `markRunReverted`** — é client-side Dexie (cliente faz isso após receber 200, na Story 1.9)

**Decisão de design — best-effort undo registration (AC4):**
Se `registerUndoEntry` falha (ex: KV down, network error), o `runAgent` **não bloqueia** o `done` event nem lança erro. Em vez disso emite `tool_error { toolName: 'undo_register', error }` e continua. Razão:
1. A operação principal (criar tarefa, registar finança) já foi efectuada — falha do undo registration não deve mascarar sucesso da operação
2. Toast de undo é nice-to-have, não é blocker (utilizador pode reverter manualmente)
3. KV down é caso edge raro; logar para observabilidade mas não falhar a UX

**Decisão de design — best-effort reverse loop (AC6):**
No endpoint `/api/agent/undo`, se uma das `tool.reverse()` falha (ex: tarefa já apagada manualmente, finança já editada), o loop continua e acumula em `errors[]`. Razão:
1. Cliente recebe response com lista de erros → pode mostrar UX informativa ("Revertidos 2 de 3 tool calls; falhou: criar_evento (já apagado)")
2. Best-effort respeita semantic da Story 1.5 (`done.status === 'partial'` quando alguns tools falham)
3. Apagar a entrada KV no fim (mesmo com erros) evita estado inconsistente em retry

**Decisão de design — KV namespace separado de ConfirmationProvider (Story 1.6):**
Story 1.6 expôs `ConfirmationProvider` interface com GAP cross-process documentado. Story 1.7 introduz **namespace independente** `nexus:undo:run:<runId>` para evitar acoplamento. Razão:
1. ConfirmationProvider tem semantic diferente (request/response síncrono em window curta) vs undo (storage 30s assíncrono)
2. ADR cross-process (deferido para Story 1.8 ou pelo `@architect` Aria neste início) pode unificar mais tarde se justificado
3. Manter separação inicial preserva opção de unificação futura sem refactor agora

**Decisão de design — endpoint NÃO chama `markRunReverted`:**
RESOLVED-2 da Story 1.5 estabeleceu que executor é **stateless server-side** e Dexie corre **client-side**. O endpoint `/api/agent/undo` corre em Edge runtime, não tem acesso a Dexie do cliente. Cliente (Story 1.9) recebe response 200 e chama `markRunReverted(runId)` localmente. Esta separação respeita ADR-1 (Edge/Node split) e mantém Edge runtime puro.

**OQ-1: Mocking strategy para `@vercel/kv` em testes Vitest.**

Recomendação preliminar do `@sm`: **opção (a)** por simplicidade (mesmo padrão das Stories 1.4-1.6 com Anthropic). `@architect` confirma ou propõe alternativa.

**OQ-2: TTL responsibility — KV expiry vs endpoint guard vs ambos?**
KV expiry com `ex: 30` apaga automaticamente após 30s. Mas a window pode estar entre 29.999s e 30.001s no momento da request. Devemos:
- Confiar 100% no KV expiry (resposta 410 quando `kv.get` retorna `null`) — simples
- Adicionar guard duplo: `if (entry.expiresAt < Date.now()) return 410` — defesa em profundidade
- Ambos

Recomendação preliminar do `@sm`: **defesa em profundidade** (guard duplo). Race condition é improvável mas o cost é negligível e o test fica mais previsível.

**OQ-3: Cross-process ConfirmationProvider (GAP da Story 1.6) — resolver agora ou em 1.8?**
Story 1.6 closure routou esta decisão para "ADR pela `@architect` Aria no início da Story 1.8 ou Story 1.9". Story 1.7 introduz KV real — é candidato natural a unificar coordenação cross-process com undo. Mas o handoff do Gage explicitamente sugeriu **Story 1.7 ou 1.8**.

Recomendação preliminar do `@sm`: **diferir para 1.8** (manter Stories 1.7 limpa de scope cross-process). `@architect` confirma ou puxa para 1.7.

**OQ-4: Multi-tool runs — undo reverte TODAS ou apenas a ÚLTIMA?**
PRD AC4 diz `"Undo reverte última operação"` — singular. Mas Story 1.5 RESOLVED-1 documentou `"Undo precisa de ordem reversa determinística: reverse() de cada tool corre na ordem inversa do execute()"` — plural. E o use case canónico (Epic 1 AC1) é prompt multi-intent que cria tarefa + finança numa só execução — undo deveria reverter ambos para fechar o ciclo.

Interpretação `@sm`: **"última operação" = último `AgentRun` (que pode conter N tool calls)**, e undo reverte **todos os tool calls do run em ordem reversa**. Esta interpretação alinha:
- AC1 Epic 1 (prompt multi-intent é uma operação)
- RESOLVED-1 Story 1.5 (ordem reversa determinística)
- UX (utilizador pediu uma coisa, agente fez 2 tool calls — undo desfaz a coisa toda)

`@architect` confirma esta interpretação ou propõe alternativa.

**OQ-5: Idempotência do endpoint — segundo POST com mesmo runId.**
Se cliente reenvia POST por engano (network blip, double click), 2º POST encontra entrada já apagada → retorna 410 `undo_window_expired`. Isto é correcto comportamento ou queremos retornar 200 `{ reverted: 0, errors: [] }` (idempotente "neutral")?

Recomendação preliminar do `@sm`: **retornar 410** (entrada já não existe = janela expirou semanticamente para o utilizador). Cliente UX trata 410 igual ao TTL natural.

**OQ-6: `tool.reverse` ausente — erro ou warning?**
Se um tool tinha `reversible: true` no momento de execução mas no momento de reverse o `tool.reverse` é `undefined` (ex: tool foi removida do registry entre runs, ou bug de definição), o que fazer?
- (a) Adicionar a `errors[]` com `{ toolName, message: 'reverse() não definido' }` e continuar — alinha com best-effort
- (b) Lançar 500 — violação de invariant, mas pode mascarar undo parcial bem-sucedido

Recomendação preliminar do `@sm`: **opção (a)** — alinha com semantic best-effort.

#### RESOLVED-2: TTL responsibility — defesa em profundidade (KV expiry + endpoint guard) APROVADA

**Decisão:** Implementar **ambos** os checks: KV `ex: 30` (Upstash auto-expiry) **+** endpoint guard `if (entry.expiresAt < Date.now()) → 410` (defense-in-depth).

**Razão (trace canónico):**
- **PRD AC4 (PRD §10 linha 427):** `"após 30s não é possível"` — semântica strict, qualquer leak após 30s é violação.
- **Upstash Redis TTL é precision de 1 segundo, não milisegundo.** Race window potencial: entre `t=29.999s` (registo) e `t=30.000s+lazy_eval` (Upstash deleta lazily on read). Em teoria, leitura num intervalo de ~1s pode retornar entry "que devia estar morta" segundo PRD AC4.
- **Vercel Edge runtime corre em múltiplas regiões** (US, EU, etc.). Clock skew entre regiões é tipicamente <1s mas pode existir. `expiresAt = Date.now() + 30_000` em Edge A pode divergir de `Date.now()` em Edge B na altura da leitura. Defense-in-depth fecha esta lacuna.
- **Cost de implementação é negligível:** 1 linha extra no endpoint. **Cost de teste:** 1 cenário adicional em `tests/unit/api/agent/undo.test.ts`.
- **Teste fica mais previsível:** unit test pode mockar `Date.now()` para simular expiry sem depender do KV TTL real.

**ADR pattern aplicado:** "Confiar mas verificar" (defense-in-depth) é padrão estabelecido em outros pontos do Nexus v2 (auth: cookie HttpOnly + KV session lookup; ConfirmationProvider Story 1.6: schema Zod + runtime check).

**Implicação na implementação:** AC6 actualizado para incluir o guard `entry.expiresAt < Date.now() → 410`. Test estático adicional em AC9 (cenário "410 quando entry existe mas expiresAt expirou").

#### RESOLVED-3: Cross-process ConfirmationProvider GAP — DIFERIR para Story 1.8 APROVADO + ADR-6 NOVO

**Decisão:** Story 1.7 NÃO resolve cross-process ConfirmationProvider. Mantém-se o routing original do handoff Story 1.6 closure: ADR específico de ConfirmationProvider será criado no início da Story 1.8 (`/api/agent/prompt`). Story 1.7 entrega apenas o que é necessário para undo.

**Razão (trace canónico):**
- **Story 1.6 closure routou explicitamente:** "Resolução prevista: ADR a criar pela `@architect` Aria no início da Story 1.8 (`/api/agent/prompt` endpoint) ou Story 1.9 (UI client consumer Dexie)".
- **Semantics fundamentalmente diferentes:**
  - **ConfirmationProvider:** request/response síncrono, window curto (~segundos), padrão pub/sub ou wait-for-resolution. Edge process A suspende SSE stream, espera; Edge process B recebe `POST /api/agent/confirm` e tem de sinalizar A.

- **Story 1.7 não constrange Story 1.8:** Story 1.7 introduz `@vercel/kv` cliente real e `nexus:undo:run:<runId>` namespace. Story 1.8 pode usar o mesmo `kv` singleton mas escolhe livremente:

  - Storage entry `nexus:agent:confirm:<runId>:<toolName>` com short TTL (~60s) + polling do A, OU
  - Outra abordagem que Aria avaliará no início da Story 1.8

#### RESOLVED-4: Multi-tool runs — undo reverte TODOS os toolCalls do último AgentRun APROVADO

**Decisão:** "Última operação" no PRD AC4 = último `AgentRun` (que pode conter N tool calls). Undo reverte **todos os toolCalls do run em ordem reversa**, alinhado com a interpretação `@sm`.

**Razão (trace canónico):**

#### RESOLVED-5: Idempotência endpoint — 2º POST retorna 410 APROVADO

**Decisão:** Segundo POST com mesmo `runId` (após 1º POST consumir) retorna 410 `undo_window_expired`, alinhado com a recomendação `@sm`.

**Razão (trace canónico):**
- **REST semantic correcto:** após 1º POST, a resource "undo window" é APAGADA (via `deleteUndoEntry`). 2º POST encontra resource inexistente — 410 Gone é a resposta canónica HTTP/REST para "resource existed but is permanently gone".
- **Distingue debugging clarity:** 410 sinaliza "entrada já consumida ou TTL expirou" (cliente trata igual). 200 `{ reverted: 0 }` mascararia bugs de UI (double-click) atrás de "sucesso silencioso", tornando debugging mais difícil.
- **Cliente UI responsibility (Story 1.9):** Toast undo deve **desactivar o botão após primeiro click** (single source of truth — botão fica em estado `disabled` ou desaparece). Isto previne 2º POST por design. Se 2º POST acontecer mesmo assim (browser refresh, network retry), 410 é resposta correcta.

**Trade-off explicitado:** A "idempotência neutral" (200 com `reverted: 0`) é uma virtude para APIs públicas onde clientes podem retry agressivo. **Nexus v2 é single-user** (Eurico), Edge endpoint protected by auth, UI controla input — risco de double-click é mitigável at UI layer. 410 é mais informativo.

**Implicação na implementação:** AC6 mantém-se (já especifica 410 quando `getUndoEntry` retorna null E quando defense-in-depth detecta expiry). RESOLVED-5 reforça a interpretação. AC9 já cobre o cenário ("idempotência — segundo POST → 410").

#### RESOLVED-6: `tool.reverse` ausente — opção (a) best-effort + `logger.error` ADENDA APROVADO

**Decisão:** Quando `tool.reverse === undefined` no momento do reverse loop (invariant violation: `reversible: true` mas `reverse` não definido):
1. Adicionar a `errors[]` com PT-PT message identificadora (`'Tool reverse() não definido — invariant violation'`)
2. **Adenda Aria (não estava no draft):** Emitir `logger.error('Tool reverse missing — invariant violation', { runId, toolName })` para observability (Vercel logs), permitindo ops detectar bugs de definição rapidamente
3. Continuar o loop (não bloquear undo dos outros tool calls)

**Razão (trace canónico):**
- **Invariant violation real:** Story 1.7 só regista undo entries para tools com `reversible: true`. Logo, `tool.reverse` DEVERIA estar definido. Se não está, é bug. Mas é bug que pode escapar a `defineTool` actual (Story 1.3 — confirmar se runtime guard valida `reversible: true ⇒ reverse`).
- **Best-effort respeita semantic Story 1.5 `done.status === 'partial'`:** quando alguns tools falham, o run inteiro NÃO é classificado como `failed`. Mesmo princípio aplica-se ao undo: alguns reverses falham, outros sucedem — UX informa "Revertido X de Y, falhou: Z".
- **Logger.error é defesa de observability:** sem isto, o invariant violation seria silenciosamente acumulado em `errors[]` da response — e o cliente provavelmente só mostra toast genérico. Ops nunca saberia. `logger.error` em Vercel Edge logs é o mecanismo standard de alerta (NFR `Observability`, arch §12).
- **Tradeoff aceite:** opção (b) lançar 500 daria visibilidade imediata mas mascararia undos parciais bem-sucedidos. UX inferior.

**Tech debt registada (não bloqueia Story 1.7 — sugestão para futura sprint):**
- **Story 1.3 candidate enhancement:** `defineTool` runtime guard pode validar `reversible === true ⇒ typeof reverse === 'function'`. Se aplicado, RESOLVED-6 invariant violation só pode ocorrer via mutação dinâmica do registry (caso edge raríssimo). Recomendação: criar issue futuro "TD-1.3.X: defineTool valida reverse para reversible tools" — não bloquear Story 1.7.

**Implicação na implementação:** AC6 + AC9 actualizados (já feito acima na edição de 410 expanded + logger.error em invariant violation). Test cases adicionais em AC9 cobrem o cenário.
