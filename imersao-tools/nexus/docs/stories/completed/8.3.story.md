### DESIGN-DECISION D-8.3-JSON-OBJECT — `response_format:{type:'json_object'}` como garantia primária; `stripJsonMarkdownFences` como rede defensiva

**Pergunta:** A OpenAI com `json_object` garante JSON puro sem fences. Então porquê manter o `stripJsonMarkdownFences` (o hotfix conquistado a sangue no caminho Anthropic)?

**Decisão:** O `OpenAIClassifier` envia `response_format: { type: 'json_object' }` no request — esta é a **garantia primária** de que `choices[0].message.content` é JSON puro (elimina a classe de bug que forçou a saga de hotfixes do Haiku, Stories 1.4 + hotfixes 09/05/18/05/31/05). **MAS** mantém `stripJsonMarkdownFences(content)` aplicado antes do `JSON.parse`, **como rede defensiva de custo zero**: se um modelo OpenAI futuro regredir e envolver o JSON em fences (ou `json_object` não estiver disponível num modelo configurado por env), o strip protege. É exactamente a decisão do ADR-10 §4.4 ("mantém `stripJsonMarkdownFences` defensivamente — custo zero, e protege contra regressões de modelo").

**Justificação com trace:**
1. ADR-10 §4.4 prescreve ambos: `response_format:json_object` (garantia) **e** `stripJsonMarkdownFences` (defesa). Não é redundância acidental — é defesa em profundidade explicitamente decidida.
2. `stripJsonMarkdownFences` já é uma função partilhada e Edge-safe em `lib/agent/classifier-json.ts` (extraída no hotfix 31/05 precisamente para ser reutilizável — `classifier-json.ts:1-24`). O `OpenAIClassifier` **importa-a** (REUSE), não a reescreve.
3. Custo zero: sobre JSON já puro, `stripJsonMarkdownFences` devolve a string trimmed intacta (Caso 4, `classifier-json.ts:145-146`) — sem efeito sobre o caminho feliz.

**Alternativa rejeitada:** confiar só no `json_object` e remover o strip. Razão: viola o ADR-10 §4.4; deixaria o classifier OpenAI frágil a uma regressão de modelo (a mesma classe de bug que partiu o caminho Anthropic em produção três vezes). A defesa custa zero.

### DESIGN-DECISION D-8.3-CONTRATO — `ClassificationResult` idêntico ao caminho Anthropic (mesmo contrato canónico)

**Pergunta:** O que o `OpenAIClassifier.classify()` devolve, e como se garante que é trocável com o `AnthropicClassifier` sem tocar a jusante?

**Decisão:** `classify(systemPrompt, userPrompt, opts)` devolve um `ClassificationResult` **byte-compatível** com o do `AnthropicClassifier`: `{ intents, confidence, rawResponse, inputTokens, outputTokens }`, validado pelo **mesmo** `ClassificationResultSchema.parse(candidate)` (`schemas.ts:69-75`). O `rawResponse` preserva o conteúdo **original** da API (antes do strip), tal como no Anthropic (`anthropic.ts:132,153`). A assinatura é a da interface `ClassifierProvider.classify()` (`types.ts:93-99`) — não muda.

**Justificação com trace:**
1. ADR-10 §2: "o **contrato canónico interno** (`LLMStreamEvent` → `ExecutorSSEEvent`) é **agnóstico ao provider**. [...] Tudo a jusante fica intocado." O classifier tem o seu contrato canónico equivalente: `ClassificationResult`. O wrapper PT-PT (Story 1.4, `classifier.ts`) e o `runAgent` consomem `ClassificationResult` sem saber o provider.
2. `ClassifierProvider` (`types.ts:93-99`) é a fronteira de abstracção — o `OpenAIClassifier` implementa-a exactamente como o `AnthropicClassifier`. Injectável em `getClassifier()` sem refactor.
3. `ClassificationResultSchema` (`schemas.ts:69-75`) é o validador único partilhado: `intents: string[]`, `confidence: Record<string,number>`, `rawResponse: string`, `inputTokens/outputTokens: int>=0`. O candidate OpenAI passa pelo mesmo `.parse()` → shape inválido lança `ZodError` (paridade com Anthropic).

**Alternativa rejeitada:** um `OpenAIClassificationResult` próprio. Razão: partiria o contrato agnóstico ao provider e obrigaria narrowing a jusante (wrapper 1.4, parity 8.5). O ADR-10 §2 é explícito que a diferença de provider vive só na fronteira, não no contrato.

### DESIGN-DECISION D-8.3-FACTORY-BRANCH — substituir o `throwOpenAINotImplemented('classifier')` por `new OpenAIClassifier(...)`

**Pergunta:** A 8.1 deixou o branch classifier `openai` da factory a falhar-loud com "ainda não implementado (Story 8.3)". O que a 8.3 muda na factory?

**Decisão:** Em `factory.ts:getClassifier()`, o branch `provider === 'openai'` passa de `readApiKey('openai'); throwOpenAINotImplemented('classifier')` para `return new OpenAIClassifier(readApiKey('openai'))`. O `readApiKey('openai')` (já existente, `factory.ts:40-62`) mantém-se como a validação fail-loud da key. **O branch `getExecutor()` openai NÃO é tocado pela 8.3** — continua a fazer `throwOpenAINotImplemented('executor')` até a 8.2 entregar o `OpenAIExecutor` (coordenação 8.2/8.3 na factory).

**Justificação com trace:**
1. A 8.1 desenhou o fail-loud do branch classifier exactamente como um placeholder a substituir: `throwOpenAINotImplemented('classifier')` referencia "Story 8.3" (`factory.ts:80-89`). A 8.3 é a extensão limpa prevista (8.1 D-8.1-FACTORY: "Quando a S2/S3 entregam [...], o branch passa de `throw` para `new OpenAI...(...)` — extensão limpa, sem refactor").
2. `readApiKey('openai')` já lê `process.env.OPENAI_API_KEY` com fail-loud PT-PT incl. whitespace-only (`factory.ts:45-52`) — a 8.3 reutiliza-o, não o reescreve.
3. `resolveActiveProvider()` (asserção de concordância + enum, `factory.ts:71-74`) já corre antes do branch — a 8.3 herda-o intacto.

**Alternativa rejeitada:** tocar também o branch executor na 8.3. Razão: viola a fronteira S2/S3 (o executor é a 8.2) e criaria colisão com a 8.2 na factory. Cada story substitui o seu próprio branch (ver "Coordenação com a 8.2").

## User Story

**Como** operador do Nexus v2 (Eurico),
**quero** um `OpenAIClassifier` que classifique a intenção multi-intent via OpenAI Chat Completions com JSON nativo (`response_format:json_object`), devolvendo o mesmo `ClassificationResult` que o caminho Anthropic,
**para que** com `LLM_PROVIDER=openai` o cérebro consiga classificar prompts (passo 1 do `runAgent`) através da OpenAI — sem a fragilidade das markdown fences que afligiu o Haiku — e a parity cross-provider (8.5) possa afirmar que os dois classifiers produzem `ClassificationResult` idêntico.

## Acceptance Criteria

> Traçados directamente ao **ADR-10 §8 row S3** (âmbito + AC) + §3.1 (impl atrás da interface) + §4.4 (JSON nativo + strip defensivo) + §4.5 (modelo default). Wording preservado do ADR; nenhum AC inventado. Espelho: `AnthropicClassifier` (`anthropic.ts:98-159`).

**AC1 (`OpenAIClassifier implements ClassifierProvider`, non-streaming)** — Em `lib/agent/providers/openai.ts`, `class OpenAIClassifier implements ClassifierProvider` expõe `classify(systemPrompt, userPrompt, opts?)` que chama `client.chat.completions.create({...})` **non-streaming** (sem `stream:true`). A assinatura é exactamente a da interface `ClassifierProvider.classify()` (`types.ts:93-99`). O construtor recebe `apiKey: string` e cria o cliente `openai` via o helper de opções de cliente partilhado (`buildOpenAIClientOptions`, da 8.2).

Trace: ADR-10 §3.1 ("`OpenAIClassifier implements ClassifierProvider` — SDK `openai`, `chat.completions.create` não-streaming") + `types.ts:93-99` + `anthropic.ts:98-103` (espelho).

**AC2 (`response_format:{type:'json_object'}` no request)** — A chamada `chat.completions.create` inclui **`response_format: { type: 'json_object' }`**, garantindo que `choices[0].message.content` é JSON puro sem markdown fences. O system prompt é enviado como mensagem `{ role:'system', content: systemPrompt }` e o user prompt como `{ role:'user', content: userPrompt }`.

Trace: ADR-10 §4.4 ("o `OpenAIClassifier` usa `response_format: { type:'json_object' }`") + §3.1.

**AC3 (`stripJsonMarkdownFences` defensivo)** — Antes do `JSON.parse`, o conteúdo passa por `stripJsonMarkdownFences(content)` (importado de `lib/agent/classifier-json.ts`, **não reescrito**), como rede defensiva de custo zero contra regressão de modelo. Sobre JSON já puro, o strip devolve a string intacta.

Trace: ADR-10 §4.4 ("mantém `stripJsonMarkdownFences` defensivamente — custo zero, e protege contra regressões de modelo") + `classifier-json.ts:106-147` + D-8.3-JSON-OBJECT.

**AC4 (Devolve `ClassificationResult` idêntico ao Anthropic, validado por Zod)** — `classify()` constrói o candidate `{ intents, confidence, rawResponse, inputTokens, outputTokens }` e devolve `ClassificationResultSchema.parse(candidate)` (`schemas.ts:69-75`). O `rawResponse` preserva o conteúdo **original** de `choices[0].message.content` (antes do strip), tal como no Anthropic. Shape inválido (ex: sem `intents`) → `ZodError` (paridade com Anthropic).

Trace: ADR-10 §4.4 ("`JSON.parse` → `ClassificationResultSchema`") + §2 (contrato agnóstico ao provider) + `anthropic.ts:149-157` (espelho) + D-8.3-CONTRATO.

**AC5 (Usage mapeada)** — O `ClassificationResult` mapeia `usage.prompt_tokens → inputTokens` e `usage.completion_tokens → outputTokens` (não os nomes Anthropic `input_tokens`/`output_tokens`). Os dois campos são inteiros não-negativos (validados pelo schema).

Trace: ADR-10 §4.4 ("Usage: `usage.prompt_tokens` / `usage.completion_tokens`") + §4.1 (mapeamento `prompt_tokens→inputTokens`, `completion_tokens→outputTokens`) + `schemas.ts:73-74`.

**AC6 (Modelo default `gpt-4.1-mini`, temperature 0)** — Quando `opts.model` não é fornecido, usa `DEFAULT_OPENAI_CLASSIFIER_MODEL` (`'gpt-4.1-mini'`, importado de `models.ts:34`, já introduzido na 8.1). `temperature` default 0 (classificação determinística), `max_tokens` default análogo ao Anthropic (`DEFAULT_CLASSIFIER_MAX_TOKENS = 1024`). `opts.model`/`opts.maxTokens`/`opts.temperature` sobrepõem-se quando fornecidos.

Trace: ADR-10 §4.5 ("Classifier [...] `gpt-4.1-mini` [...] temperature 0") + `models.ts:34` + `anthropic.ts:118-120` (defaults análogos).

**AC7 (Validação de inputs, fail-loud PT-PT)** — `classify()` valida que `systemPrompt` e `userPrompt` são não-vazios, lançando `Error` PT-PT claro caso contrário (espelho exacto de `anthropic.ts:110-115`). Falha de conteúdo da API (sem `choices[0].message.content`) → `Error` PT-PT.

Trace: `anthropic.ts:110-131` (espelho) + Constitution Artigo V (Quality First — fail-loud).

**AC8 (JSON malformado → Error PT-PT; mesmo com `json_object`, defensivo)** — Se, apesar do `response_format:json_object`, o conteúdo não for JSON parseável após o strip, `classify()` lança `Error` PT-PT que inclui um excerto do `rawResponse` para debug (espelho de `anthropic.ts:143-147`). Este caminho é defensivo — o `json_object` torna-o improvável, mas é exercido por um teste com conteúdo não-JSON.

Trace: ADR-10 §4.4 (strip defensivo) + `anthropic.ts:141-147` (espelho) + estratégia de testes do prompt (caso "JSON malformado, mesmo com json_object, defensivo").

**AC9 (Factory: branch classifier openai → `OpenAIClassifier`)** — Em `factory.ts:getClassifier()`, o branch `provider === 'openai'` passa de `throwOpenAINotImplemented('classifier')` para `return new OpenAIClassifier(readApiKey('openai'))`. O `readApiKey('openai')` (fail-loud PT-PT, `factory.ts:45-52`) mantém-se. O branch `getExecutor()` openai **NÃO é tocado** (continua a falhar-loud até a 8.2). `resolveActiveProvider()` (asserção + enum) corre antes, intacto.

Trace: ADR-10 §3.2 + 8.1 D-8.1-FACTORY ("o branch passa de `throw` para `new OpenAI...(...)` — extensão limpa") + `factory.ts:91-103` + D-8.3-FACTORY-BRANCH.

**AC10 (Não-regressão — caminho Anthropic intocado, 2400+ verdes por construção)** — Com `LLM_PROVIDER` ausente ou `anthropic`, o comportamento é byte-a-byte o de hoje. `lib/agent/providers/anthropic.ts`, `lib/agent/executor.ts`, `lib/agent/schemas.ts`, `lib/agent/classifier-json.ts`, `lib/agent/tools/registry.ts`, `app/api/anthropic/proxy/route.ts`, `lib/agent/inference-transport.ts` e `lib/agent/client-executor.ts` ficam **intocados** (a 8.3 só os importa onde aplicável). A suite completa (`npm run test:unit`) continua verde. Qualquer falha num teste Anthropic durante a 8.3 = STOP (ADR-10 §6.1).

Trace: ADR-10 §6.1 ("os 2400+ testes Anthropic ficam verdes por construção") + §5 (linhas "INTOCADO").

**AC11 (Testes do classifier OpenAI)** — Existem testes unit (Vitest) com MSW non-streaming para `https://api.openai.com/v1/chat/completions` que cobrem:
- JSON válido → `ClassificationResult` correcto (intents + confidence + rawResponse + usage mapeada);
- **classificação multi-intent** → `intents` com ≥2 domínios + `confidence` per-intent (cenário obrigatório do ADR-10 §6.3 e do prompt);
- JSON malformado (conteúdo não-JSON, mesmo com `json_object` — defensivo) → `Error` PT-PT (AC8);
- shape inválido (sem `intents`) → `ZodError` (AC4);
- usage mapeada de `prompt_tokens`/`completion_tokens` (AC5);
- default model `gpt-4.1-mini` quando `opts.model` ausente (AC6);
- factory: `LLM_PROVIDER=openai` → `getClassifier()` devolve `OpenAIClassifier` (não mais fail-loud); key ausente → fail-loud PT-PT (AC9).
- ≥1 teste **falsificável** que afirma a igualdade do `ClassificationResult` produzido pelo `OpenAIClassifier` com o shape esperado (intents/confidence/usage exactos) — falharia se o mapeamento de usage ou de campos divergisse.

> **Nota de fronteira (8.5):** a 8.3 cobre o classifier OpenAI isoladamente com um mock non-streaming. A **suite de parity cross-provider** (afirma `ClassificationResult` idêntico entre Anthropic e OpenAI para o mesmo cenário) e a **consolidação canónica de `handlers/openai.ts`** são a **8.5** — a 8.3 não as duplica.

Trace: ADR-10 §6.3 (cenário "Classifier multi-intent | JSON sem fences (`json_object`) → `ClassificationResult`") + §8 row S3 ("multi-intent → `ClassificationResult` válido; usage mapeada; JSON sem fences") + `anthropic.test.ts:106-159` (espelho) + estratégia de testes do prompt.

### Ponto de atenção — reuso dos helpers de cliente da 8.2 (NÃO duplicar)

O `AnthropicClassifier` e o `AnthropicExecutor` partilham `isTestEnv()` + `buildClientOptions(apiKey)` (`anthropic.ts:72-85`) para gatear `dangerouslyAllowBrowser` só em test env (MSW intercepta; a key nunca sai do processo). O `OpenAIClassifier` e o `OpenAIExecutor` partilham o equivalente OpenAI (`isTestEnv` + `buildOpenAIClientOptions`), **criado pela 8.2**. A 8.3 **importa/reutiliza** esses helpers do mesmo `openai.ts` — não os recria. Se a 8.2 ainda não aterrou, criar os helpers mínimos e marcar a consolidação como da 8.2.

### Ponto de atenção — `response_format:json_object` + strip defensivo (não confiar só num)

O `json_object` é a garantia primária de JSON puro, mas o `stripJsonMarkdownFences` defensivo (ADR-10 §4.4) tem de ficar **antes** do `JSON.parse`. Importar de `classifier-json.ts` (NÃO reescrever — é a função partilhada single-source-of-truth, Edge-safe). Sobre JSON puro, o strip é no-op (Caso 4) — custo zero confirmado.

### Ponto de atenção — usage com nomes OpenAI (não Anthropic)

A OpenAI devolve `usage.prompt_tokens` / `usage.completion_tokens` (o Anthropic usa `input_tokens`/`output_tokens`). O mapeamento para o `ClassificationResult` (`inputTokens`/`outputTokens`) tem de ler os nomes OpenAI. Confundir os nomes daria `undefined` → `ZodError` no `.parse` (`schemas.ts:73-74` exige int não-negativo). O teste falsificável (AC11) fixa isto.

### [AUTO-DECISION] Localização do MSW non-streaming classifier

ADR-10 §5/§8 coloca o `handlers/openai.ts` canónico (SSE fiel + parity) na **8.5**. Para a 8.3 testar o classifier sem antecipar a 8.5, o handler non-streaming classifier vive **local no test file da 8.3 via `server.use(...)`** (padrão já usado no projecto para overrides por-teste), OU como primeira contribuição a `handlers/openai.ts` se a 8.2 já o tiver criado para o streaming. A consolidação canónica + os testes falsificáveis de fidelidade streaming + a parity são a 8.5. Decisão: o `@dev` escolhe consoante a ordem de aterragem da 8.2 — sem invenção, é resolução de coordenação prevista no ADR-10 §8 (S3/S5).
(reason: o ADR coloca o handler canónico em S5; a 8.3 precisa de um mock mínimo para testar o classifier sem duplicar o trabalho da 8.5)

### [AUTO-DECISION] `max_tokens` e `temperature` default do classifier OpenAI

O ADR-10 §4.5 fixa `temperature 0` (determinística). O `max_tokens` não está fixado no ADR para OpenAI; a 8.3 adopta o mesmo default do classifier Anthropic (`DEFAULT_CLASSIFIER_MAX_TOKENS = 1024`, `anthropic.ts:37`) por paridade comportamental. Sobreponíveis por `opts`. Sem invenção — espelho do default Anthropic existente.
(reason: paridade com o classifier Anthropic; o ADR fixa só temperature 0)
