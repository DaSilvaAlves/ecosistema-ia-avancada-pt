[AUTO-DECISION A1] **UI em página dedicada `/projectos`**, não tab/modal em `/tarefas`. Razão: spec §9 linha 1203 refere-se ao **filtro** em `/tasks` (já existe desde Story 2.3), não à **gestão** de projectos. CRUD com modal+form+filtros precisa de espaço próprio. Consistente com padrão de outras rotas (`/tarefas`, futuro `/finance`, `/habits`). Alternativa "modal full-screen em /tarefas" descartada — congestiona o header de tarefas e torna deep-linking impossível (`/projectos/{id}` desbloqueado na Story 2.9).

[AUTO-DECISION A2] **Layout principal: grid responsivo de cards**, não tabela nem lista. Razão: para single-user pessoal com ~10-30 projectos no total ao longo da vida do app, grid de cards é mais ligível e tira partido de descrições curtas + status badges visuais. Tabela seria over-engineered (sort/sort/sort por colunas é desnecessário). CSS Grid `auto-fill minmax(280px, 1fr)` responde naturalmente a 3/2/1 colunas. Alternativa "lista vertical" descartada — desperdiça espaço horizontal.

[AUTO-DECISION A3] **Filtro por estado: tab strip horizontal** (Activos | Pausados | Concluídos | Todos), default **Activos**. Razão: alinhado com `TasksHeader.tsx` (precedente Story 2.3+2.4+2.5 — tab strip com WAI-ARIA Tabs Authoring Practices: arrow keys + Home/End). 4 tabs porque há 3 estados + total ("Todos" é UX útil para visão geral). Default "Activos" porque é o estado mais consultado em uso diário. Alternativa "Select dropdown" descartada — tabs são mais visíveis e mais rápidos com teclado.

[AUTO-DECISION A4] **Criação/edição via modal centrado** (não slide-up nem inline). Razão: form com 5 campos é demasiado para edit inline (perde-se contexto da grid); slide-up fullscreen é over-engineered para 5 campos. Modal centrado glassmorphism (`rgba(255,255,255,0.025)` + border 0.08 + backdrop-filter blur(12px)) é o padrão design system [IA]AVANÇADA PT para fluxos contidos. Focus trap obrigatório (A11). Alternativa "fullscreen slide-up" descartada — exagero para 5 campos simples.

[AUTO-DECISION A5] **Acções permitidas por card: Edit + Archive + Mark Done**. **Delete fora-de-scope** nesta story. Razão: deletar projecto implica cascata complexa (o que fazer com `Task.projectId === id`? Set null (preservar tarefas mas perder vínculo)? Bloquear deleção se houver tarefas vinculadas? Diálogo de confirmação com contagem?). Sem direcção do PRD, é decisão de produto. Story 2.8 entrega 3 acções suficientes para flow normal (arquivar = pausar = inactivo; mark done = concluído; edit = correcção). Apagar projecto fica para futura story dedicada com regra de cascata definida pelo `@po`. Alternativa "implementar delete com set null em cascata" descartada — viola No Invention (sem PRD/spec).

[AUTO-DECISION A6] **Contadores por card: `X tarefas activas · Y concluídas`** — onde "activas" = `status in ['todo', 'in-progress', 'blocked']` e "concluídas" = `status === 'done'`. Razão: dá pista visual imediata da actividade de cada projecto sem abrir drill-down (Story 2.9). Implementação: `useTasks()` no nível da page + `useMemo` para agrupar por `projectId`. Trade-off: 1 query global a tasks por render da page, mas client-side e Dexie é rápido (NFR3 <2s FCP). Alternativa "queries individuais por projecto via `db.tasks.where('projectId').equals(id).count()`" descartada — N+1 queries Dexie é pior que 1 query + group by client-side.

[AUTO-DECISION A7] **Form com 5 campos + validação client-side via `ProjectSchema.parse()`**:
- `name`: input texto, required, min 1 char (`ProjectSchema` já força isto).
- `description`: textarea, opcional, default vazio (`ProjectSchema` aceita string vazia).
- `status`: select (Activo/Pausado/Concluído), default `'active'` em criação.
- `startDate`: input date (`type="date"`), required, default `today` (`format(new Date(), 'yyyy-MM-dd')`) em criação.
- `deadline`: input date, opcional (nullable).

Validação dispara em submit. Erros PT-PT extraídos do `ZodError` (já vêm PT-PT do schema — "Nome do projecto é obrigatório", "Data de início é obrigatória"). Exibidos abaixo de cada campo + `aria-invalid` + `aria-describedby`. Alternativa "validação em onBlur" descartada — UX inconsistente em form curto, basta submit.

[AUTO-DECISION A8] **Cores por status (badges + accent stripe top do card)**:
- `active` → Cyan `#00F5FF` (action color, projecto vivo)
- `paused` → Gold `#FFB800` (warning amber, atenção)
- `done` → Lime `#39FF14` (success, concluído)

Razão: alinhado com `KanbanCard` (Story 2.4) e `CalendarCard` (Story 2.5) que usam mesmas cores para chip color por estado. Coerência visual cross-feature. Magenta `#FF006E` reservada para erros/atrasos (não aplicável a projectos — projectos não "atrasam" automaticamente, deadline é opcional e não dispara estado). Alternativa "tons azulados para os 3 estados" descartada — perde discriminação visual rápida.

[AUTO-DECISION A9] **Estados vazios PT-PT**:
- Sem projectos (qualquer filtro): "Sem projectos. Cria o primeiro com **+ Novo projecto**."
- Filtro vazio (ex: 0 projectos pausados): "Nenhum projecto neste estado."
- Loading: 6 cards skeleton com pulse animation (precedente `KanbanBoard` skeleton).
- Erro em criação/edição: toast primitivo PT-PT 4s, mesmo padrão Story 2.4/2.5 (`setTimeout` 4s, sem biblioteca).

[AUTO-DECISION A10] **Ordem dos projectos: `createdAt desc`** (padrão actual do repo `listProjects`). Razão: projecto mais recente em cima é UX comum em CRUD. Sem opção de reordenar manual nesta story (esquema `Project` não tem campo `order`/`position` — adicioná-lo violaria No Invention sem PRD update). Alternativa "ordem por deadline" descartada — vários projectos podem ter `deadline: null`, ordenação ficaria inconsistente.

[AUTO-DECISION A11] **Acessibilidade Modal WAI-ARIA Authoring Practices**:
- `<div role="dialog" aria-modal="true" aria-labelledby="modal-title">` no root do modal.
- Focus trap: primeiro elemento focável recebe foco na abertura; `Tab`/`Shift+Tab` ciclam entre elementos focáveis dentro do modal.
- `Escape` fecha modal (e descarta alterações não guardadas? — sem confirmação, alinhado com a11y leve da Story 2.3+2.4 que também não confirmam descartes).
- Click fora (overlay) também fecha modal (mesma semântica que `Escape`).
- Restaurar foco no elemento que abriu o modal (botão "+ Novo projecto" ou kebab menu) ao fechar.
- Form labels apropriados (`<label htmlFor>` + `<input id>`), `aria-required`, `aria-invalid` em erros, `aria-describedby` para mensagens de erro.

[AUTO-DECISION A12] **Navegação entrada para `/projectos`**: nesta story **NÃO** adicionar link explícito em sidebar/nav (não há sidebar implementada — entry via URL directo `/projectos` ou via tools cérebro `criar_projecto`/`consultar_projecto` da Story 2.10). Adicionar link entrará na story de sidebar/nav global (não existe ainda). Botão "Esc · Voltar" no header chama `router.back()` (precedente `TasksHeader.tsx:140`).

### Contadores de tarefas por projecto (A6)

```typescript
// page.tsx — count via useMemo sobre useTasks()
const tasks = useTasks();
const taskCountsByProject = useMemo<Record<string, { active: number; done: number }>>(() => {
  const map: Record<string, { active: number; done: number }> = {};
  if (!tasks) return map;
  for (const t of tasks) {
    if (t.projectId === null) continue;
    const bucket = map[t.projectId] ?? { active: 0, done: 0 };
    if (t.status === 'done') bucket.done += 1;
    else bucket.active += 1;  // todo, in-progress, blocked
    map[t.projectId] = bucket;
  }
  return map;
}, [tasks]);
```

### Padrão para validação Zod no submit (referência)

```typescript
// ProjectFormModal.tsx — onSubmit handler
import { ZodError } from 'zod';
import { ProjectSchema } from '@/lib/db/schemas';
import type { Project } from '@/types/db';

function handleSubmit(e: React.FormEvent) {
  e.preventDefault();
  setErrors({});
  try {
    const candidate: Project = {
      id: mode === 'edit' ? initialValue!.id : crypto.randomUUID(),
      createdAt: mode === 'edit' ? initialValue!.createdAt : Date.now(),
      name: name.trim(),
      description: description.trim(),
      status,
      startDate,
      deadline: deadline === '' ? null : deadline,
    };
    const parsed = ProjectSchema.parse(candidate);  // throws ZodError em validação falhada
    onSubmit(parsed);  // page handler chama createProject/updateProject
  } catch (err) {
    if (err instanceof ZodError) {
      // Map errors[].path[0] -> message
      const fieldErrors: Partial<Record<keyof Project, string>> = {};
      for (const issue of err.errors) {
        const field = issue.path[0] as keyof Project;
        if (!(field in fieldErrors)) fieldErrors[field] = issue.message;
      }
      setErrors(fieldErrors);
    }
  }
}
```

### Padrão para focus trap no modal (referência)

```typescript
// ProjectFormModal.tsx — useEffect focus trap
useEffect(() => {
  if (!modalRef.current) return;
  const focusables = modalRef.current.querySelectorAll<HTMLElement>(
    'input, textarea, select, button, [tabindex="0"]'
  );
  if (focusables.length === 0) return;

  // Focus primeiro input ao abrir
  focusables[0].focus();

  function handleKeyDown(e: KeyboardEvent) {
    if (e.key === 'Escape') {
      onClose();
      return;
    }
    if (e.key !== 'Tab') return;
    const first = focusables[0];
    const last = focusables[focusables.length - 1];
    if (e.shiftKey && document.activeElement === first) {
      e.preventDefault();
      last.focus();
    } else if (!e.shiftKey && document.activeElement === last) {
      e.preventDefault();
      first.focus();
    }
  }

  document.addEventListener('keydown', handleKeyDown);
  return () => document.removeEventListener('keydown', handleKeyDown);
}, [onClose]);
```
