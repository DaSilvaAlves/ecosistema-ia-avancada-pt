## Nota do `@sm` River sobre interpretação

A Story 2.2 no `EPIC-2.md` §5 é descrita como "Migrar dados de tarefas do `localStorage` v1 (`nexus_tasks`) para o schema Dexie v2". O skeleton dessa migration **já existe** desde a Story 0.3 em `lib/db/migrations/v1-to-v2.ts`.

O que a 2.2 entrega é o **refactor** desse skeleton para que passe a delegar nos repos tipados entregues pela Story 2.1, em vez de escrever directamente em `db.tasks.bulkAdd()`. Isto garante:

1. **Validação Zod por tarefa** — cada `V1Task` mapeada é validada por `TaskSchema` antes de persistir. Tarefas inválidas são contadas e reportadas (sem bloquear a migration das válidas).
2. **Mensagens de erro PT-PT consistentes** — via `repos/tasks.ts` (AC6 da 2.1).
3. **Single source of truth** — o repo `tasks.ts` é o único caminho de escrita para a tabela `tasks`; a migration não é excepção.

O restante da migration (flag de idempotência, leitura de `localStorage`, mapeamento `V1Task` → `Task`, rollback strategy) **permanece intacto** — já estava correcto.

## User Story

Como `@dev` (Dex), quero refactorar `lib/db/migrations/v1-to-v2.ts` para que a escrita de tarefas migradas seja feita via `createTask()` de `lib/db/repos/tasks.ts` (em vez de `db.tasks.bulkAdd()` directo), para que a migration respeite a validação Zod e as mensagens PT-PT estabelecidas pela Story 2.1, mantendo a idempotência e o rollback strategy já existentes.

## Contexto

`architecture-v2.md` §4.4 especifica o contrato da migration: idempotente via flag `nexus_v1_migrated_to_v2`, lê `localStorage.getItem('nexus_tasks')`, mapeia `V1Task` → `Task`, e **mantém `localStorage` v1 intacto** para rollback de emergência (Epic 8 Story 8.10 limpa). O pseudocódigo da §4.4 usa `db.tasks.bulkAdd(tasksV2)` — mas esse pseudocódigo foi escrito **antes** da Story 2.1 criar `repos/tasks.ts`. A arquitectura não proíbe o uso de repos na migration — é a direcção correcta para single source of truth.

`EPIC-2.md` §7 reconciliação: "Story 2.2 lê o `localStorage` v1 e escreve no Dexie v2." A forma de escrever é via repos.

`EPIC-2.md` §8 (lição A2 — Not-Tested Evidence Gate): a migration é candidata a commits que tocam código de aplicação sem paths bloqueadores — mas se algum commit tocar `package.json` scripts ou config, activar a secção.

**Código actual do skeleton (Story 0.3):**
- `lib/db/migrations/v1-to-v2.ts` — tem `db.tasks.bulkAdd(tasksV2)` numa transacção. Usa `db` directamente.
- `lib/db/migrations/index.ts` — reexporta `migrateV1ToV2` e `MIGRATION_FLAG_KEY`.
- A interface `V1Task` e o mapeamento para `Task` estão correctos.
- `MigrationResult` já tem os campos `migrated`, `status`, `error`.

**O que muda com o refactor:**
- `db.tasks.bulkAdd(tasksV2)` → loop com `createTask(task)` por tarefa, com tratamento de erro individual.
- A transacção Dexie é removida (ou convertida em try/catch por tarefa) — `createTask` não é transaccional na 2.1, mas isso é aceitável dado que a migration tem flag de idempotência. [AUTO-DECISION: sem transacção wrapping o loop — razão: `createTask` valida via Zod individualmente; falhas parciais são reportadas em `MigrationResult`; a migration pode re-tentar tarefas falhadas numa futura re-execução se o flag não for marcado. Alternativa transaccional foi descartada porque o `bulkAdd` dentro de transacção seria contornar a validação Zod dos repos.]
- `MigrationResult` é estendido com `skipped: number` — conta tarefas inválidas que falharam a validação Zod (sem bloquear as válidas).

## Acceptance Criteria

- **AC1:** `lib/db/migrations/v1-to-v2.ts` refactora o bloco de escrita: o `db.tasks.bulkAdd(tasksV2)` é substituído por um loop que chama `createTask(task)` de `@/lib/db/repos/tasks` para cada tarefa mapeada. A função `migrateV1ToV2` mantém a assinatura `() => Promise<MigrationResult>`.
- **AC2:** A interface `MigrationResult` (em `v1-to-v2.ts`) é estendida com `skipped: number` — conta tarefas que falharam a validação Zod mas **não bloqueia** a migration das restantes. Tarefas inválidas são ignoradas (logged via `console.warn` com mensagem PT-PT e o id da tarefa).
- **AC3:** O campo `migrated` em `MigrationResult` reflecte apenas as tarefas **persistidas com sucesso** via `createTask()`. `skipped` reflecte as tarefas que falharam Zod. `migrated + skipped === v1Tasks.length` quando `status !== 'failed'` global.
- **AC4:** A idempotência é preservada: flag `nexus_v1_migrated_to_v2` é marcado `'true'` em `localStorage` **apenas depois** do loop completo (com ou sem tarefas skipped), nunca antes. Comportamento de `already-done` e `no-data` permanecem inalterados.
- **AC5:** O `localStorage` v1 (`nexus_tasks`) é mantido intacto após a migration — não é apagado nem modificado. Trace: `architecture-v2.md §4.4` ("localStorage v1 mantém-se para rollback emergência"). Anti-padrão explícito: não limpar o `localStorage` nesta story.
- **AC6:** A escrita de dados v1 corromptos/inválidos (task sem `id`, sem `text`, `priority` fora do enum) NÃO bloqueia a migration das tarefas válidas. A tarefa inválida é contada em `skipped`, um `console.warn` com mensagem PT-PT é emitido (ex: `Tarefa ignorada na migration (id: "${t.id}"): ${zodError.message}`), e o loop continua.
- **AC7:** `lib/db/migrations/index.ts` reexporta o tipo `MigrationResult` actualizado (com o campo `skipped`). Nenhuma outra alteração a `index.ts`.
- **AC8:** O mapeamento `V1Task` → `Task` (interface `V1Task`, transformação de campos) permanece **inalterado** face ao skeleton da Story 0.3. Não adicionar campos novos ao mapeamento nem alterar lógica existente.
- **AC9:** Existe `tests/unit/db/migrations/v1-to-v2.test.ts` com cobertura de:
  - Migration com N tarefas v1 válidas → todas persistidas via `createTask`, `migrated === N`, `skipped === 0`, flag marcado.
  - Migration idempotente: segundo `migrateV1ToV2()` devolve `{ status: 'already-done', migrated: 0, skipped: 0 }`.
  - Migration sem dados: `localStorage` sem `nexus_tasks` → `{ status: 'no-data', migrated: 0, skipped: 0 }`, flag marcado.
  - Migration com 1 tarefa inválida (sem `text`) e 2 válidas → `migrated === 2`, `skipped === 1`, flag marcado, `console.warn` chamado 1 vez com mensagem PT-PT.
  - SSR guard: chamar `migrateV1ToV2()` com `window === undefined` simulado → `{ status: 'failed', error: 'No window (SSR)' }`.
  - Verificar que `localStorage` v1 (`nexus_tasks`) não foi apagado após migration bem-sucedida (AC5).
- **AC10:** Quality gates locais passam em `imersao-tools/nexus/v2/`: `npm run lint`, `npm run typecheck`, `npm run test:unit` (todos os existentes + novos), `npm run build`.
- **AC11:** Coverage de `lib/db/migrations/v1-to-v2.ts` é **>= 80% lines** medido via `npm run test:coverage`. Não alterar o threshold global em `vitest.config.ts`.

### Contrato de `createTask` (Story 2.1 AC6)

```typescript
// lib/db/repos/tasks.ts
export async function createTask(input: Task): Promise<Task> {
  TaskSchema.parse(input); // lança ZodError com mensagem PT-PT se inválido
  await db.tasks.add(input);
  return input;
}
```

O `TaskSchema.parse(input)` lança `ZodError` se o input for inválido. A migration deve capturar este erro e continuar com a próxima tarefa (AC6).

### Mapeamento V1Task → Task (já correcto no skeleton)

```typescript
// NÃO alterar este mapeamento (AC8)
const tasksV2: Task[] = v1Tasks.map((t) => ({
  id: t.id,
  title: t.text,          // V1Task.text → Task.title
  description: '',
  priority: t.priority,
  status: t.status ?? (t.done ? 'done' : 'todo'),
  dueDate: t.dueDate ?? null,
  projectId: null,
  tags: [],
  context: t.context ?? null,
  lastWorkedAt: t.lastWorkedAt ?? null,
  recurrenceId: null,
  parentTaskId: null,
  createdAt: t.createdAt,
  updatedAt: Date.now(),
}));
```

**Atenção:** `V1Task.priority` tem os mesmos valores que `Task.priority` (`'high'|'medium'|'low'`) — sem remapeamento necessário. `V1Task.id` pode não ser UUID — `TaskSchema` valida `z.string().uuid()`. Tarefas v1 com `id` não-UUID serão contadas em `skipped` (AC6).

### Padrão do loop de escrita (AC1, AC3, AC6)

```typescript
// Substituir o bloco try/bulkAdd por isto:
let migrated = 0;
let skipped = 0;
for (const task of tasksV2) {
  try {
    await createTask(task);
    migrated++;
  } catch (error) {
    skipped++;
    console.warn(
      `Tarefa ignorada na migration (id: "${task.id}"): ${
        error instanceof Error ? error.message : 'erro desconhecido'
      }`
    );
  }
}
```

### Import de `db` pode ser removido

Se o refactor remover o `db.tasks.bulkAdd` e não usar mais `db` directamente, o import `import { db } from '@/lib/db/client'` pode ser eliminado de `v1-to-v2.ts`. Verificar antes de remover (T3.4).

### Idempotência — ordem do flag (AC4)

```typescript
// CORRECTO: flag SÓ depois do loop
for (const task of tasksV2) { /* ... */ }

return { migrated, skipped, status: 'success' };

// ERRADO: flag antes do loop — nunca fazer
window.localStorage.setItem(MIGRATION_FLAG_KEY, 'true');
for (const task of tasksV2) { /* ... */ }
```
