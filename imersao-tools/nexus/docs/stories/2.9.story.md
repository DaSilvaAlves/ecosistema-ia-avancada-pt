**Decisões autónomas do SM (para ratificação `@po`):**

[AUTO-DECISION A1] **Rota `/projectos/[id]`** (UUID — parâmetro dinâmico Next.js App Router), não slug. Razão: `Project.id` é UUID gerado por `crypto.randomUUID()` — não existe campo `slug` no schema nem no PRD. `[id]` é o padrão natural e único disponível. Alternativa `[slug]` descartada — exigiria campo novo não definido no PRD (violação No Invention Artigo IV).

[AUTO-DECISION A2] **Dual vista: Lista por defeito, Kanban como segunda tab**. FR31 diz "lista + Kanban" — duas vistas, não simultâneas. Lista é o default (mais leve, sem DnD inicializado). Kanban é segunda tab com `KanbanBoard.tsx` reutilizado. Alternativa "ambas vistas em paralelo" descartada — viewport insuficiente, sem precedente de split-view no codebase.

[AUTO-DECISION A3] **Reaproveitar `KanbanBoard.tsx` da Story 2.4** para a sub-vista Kanban, passando tasks já filtradas por `projectId`. `KanbanBoard` recebe `tasks: Task[] | undefined` — o filtro é feito no hook `useTasks({ projectId: id })` na page, não dentro do componente. Zero modificação do `KanbanBoard.tsx`. Alternativa "criar KanbanBoard separado" descartada — duplicação viola YAGNI.

[AUTO-DECISION A4] **Reaproveitar `ProjectFormModal.tsx` da Story 2.8** para a acção de editar o projecto na vista de detalhe. O modal já existe, já tem focus trap WAI-ARIA, validação Zod e mensagens PT-PT. A page passa o `project` como `initialValue` para pré-preenchimento, mesmo padrão da `ProjectCard.tsx` na Story 2.8.

[AUTO-DECISION A5] **Header da página de detalhe** inclui: nome do projecto como `<h1>`, status badge, datas (início + prazo opcional), progress bar `% tasks done`, botão "Editar" (abre `ProjectFormModal`), botão "Esc · Voltar" (`router.back()` para `/projectos`). Sem breadcrumbs complexas — não há sidebar/nav implementada (precedente Story 2.8 A12).

[AUTO-DECISION A6] **Progress bar** calculada client-side: `done_count / total_count * 100`. Se `total_count === 0`, progress = 0 (sem divisão por zero). Cor da barra: Lime `#39FF14` (sucesso). Alternativa "omitir progress" descartada — dá contexto imediato sem drill-down individual nas tasks.

[AUTO-DECISION A7] **Sub-vista Lista** (default) — lista vertical de tasks do projecto agrupadas por status (`todo`, `in-progress`, `blocked`, `done`), reaproveitando o padrão visual de `TaskRow.tsx` da Story 2.3 (ou equivalente simplificado se `TaskRow` tiver dependências de estado da page `/tarefas`). ## User Story

**As a** Eurico,
**I want** uma página dedicada `/projectos/{id}` onde possa ver num único sítio todas as tarefas de um projecto específico — em vista lista ou Kanban — o progresso global e editar os detalhes do projecto,
**so that** consigo gerir o trabalho de um projecto de forma centralizada sem ter de filtrar manualmente em `/tarefas`, cumprindo FR31 (Vista projecto: tarefas vinculadas com vista lista + Kanban).

## Acceptance Criteria

- **AC1:** Rota `/projectos/[id]` activa via Next.js App Router (`app/(app)/projectos/[id]/page.tsx`), `'use client'`. `useParams()` extrai o UUID da URL. Escape global no body chama `router.back()` (precedente `tarefas/page.tsx:101-107` e `projectos/page.tsx`).

- **AC2:** **`ProjectDetailHeader`** apresenta:
  - `<h1>` com nome do projecto, Inter weight 800 1.6rem, cor `#F0F4FF`.
  - **Status badge** JetBrains Mono uppercase PT-PT (`ACTIVO` / `PAUSADO` / `CONCLUÍDO`) com background/border colorido por status (Cyan/Gold/Lime — padrão `ProjectCard.tsx`).
  - **Datas** JetBrains Mono 0.7rem: "📅 Iniciado DD/MM/YYYY" + (se deadline) "⏰ Prazo DD/MM/YYYY" — formato PT-PT via `format(parseISO(date), 'dd/MM/yyyy', { locale: pt })` (precedente Story 2.8 AC4).
  - **Progress bar** horizontal: label PT-PT "N% concluído" + barra Lime `#39FF14` sobre fundo `rgba(57,255,20,0.12)`, percentagem calculada via A6. Se 0 tasks, "0% concluído".
  - **Botão "Editar"** (secondary — não cyan primary) abre `ProjectFormModal` em modo edição com `initialValue={project}`.
  - **Botão "Esc · Voltar"** com `aria-label="Voltar (Esc)"`, chama `router.back()` (precedente `TasksHeader.tsx:138-163`).
  - Header sticky `top: 0`, `background: rgba(4, 4, 10, 0.92)` + `backdrop-filter: blur(12px)`, `z-index: 10`.

- **AC3:** **Tab strip de vistas** (Lista | Kanban), default **Lista**. WAI-ARIA Tabs Authoring Practices:
  - `role="tablist"`, `role="tab"`, `aria-selected`, `tabIndex={active ? 0 : -1}`.
  - Arrow keys ←/→ navegam entre tabs, Home/End vão para primeiro/último.
  - Tab activa exibe o conteúdo correspondente; inactiva fica visível mas não renderiza conteúdo.
  - Precedente: `TasksHeader.tsx:35-39, :53-76` + `ProjectsHeader.tsx` (Story 2.8).

- **AC4:** **Sub-vista Lista** (default). Apresenta tarefas do projecto (`useTasks({ projectId: id })`) agrupadas em secções por status na ordem: "Por fazer", "Em curso", "Bloqueadas", "Concluídas". Cada secção tem `<h2>` PT-PT + contagem `(N)`. Cada task é `<TaskRow ...>` ou `<ProjectTaskRow ...>` (ver A7) com campos: título, prioridade badge, due date (se existir), status. Se `tasks === undefined`, skeleton PT-PT. Se `tasks.length === 0`, empty state A10.

- **AC5:** **Sub-vista Kanban** (segunda tab). `<KanbanBoard tasks={tasks} projects={[project]} tagsLookup={tagsLookup} />` reutilizado da Story 2.4, recebendo as tasks já filtradas por `projectId` (via hook). Drag-and-drop entre colunas funciona e persiste via `setTaskStatus` (mesmo comportamento de `/tarefas`). Se `tasks === undefined`, skeleton do `KanbanBoard` activa automaticamente (já implementado na Story 2.4). Se `tasks.length === 0`, empty state do `KanbanBoard` visível.

- **AC6:** **Estado Loading**: enquanto `project === undefined` (Dexie a carregar o projecto individual), exibir skeleton do header (`<div aria-busy="true" aria-label="A carregar projecto">`) com pulse animation. Precedente skeleton da Story 2.8 (6 cards placeholder).

- **AC7:** **Estado Not Found** (A9): se `project` termina de carregar e o valor é `null` ou `undefined` confirmado (distinto de "ainda a carregar"), exibir glass card centrado com mensagem PT-PT "Projecto não encontrado." + botão "Voltar aos projectos" que chama `router.push('/projectos')`. `aria-live="polite"` na região de not-found.

### Loading vs Not-Found — distinção crítica

```typescript
// page.tsx — padrão recomendado para distinguir loading de not-found
// (problema: useLiveQuery retorna `undefined` tanto enquanto carrega como se não existe)

const [isLoaded, setIsLoaded] = useState(false);
const projectRaw = useLiveQuery(() => getProject(id), [id]);

useEffect(() => {
  if (projectRaw !== undefined || /* dexie settled */ isLoaded) {
    setIsLoaded(true);
  }
}, [projectRaw]);

// Alternativa mais robusta: usar um segundo useLiveQuery que devolve count
// para saber se o id existe:
const projectExists = useLiveQuery(
  () => db.projects.where('id').equals(id).count(),
  [id]
);
// projectExists === undefined → loading; projectExists === 0 → not found; projectExists === 1 → existe
```

### Padrão de `useLiveQuery` com `getProject` (referência)

```typescript
// app/(app)/projectos/[id]/page.tsx
import { useParams, useRouter } from 'next/navigation';
import { useLiveQuery } from 'dexie-react-hooks';
import { getProject } from '@/lib/db/repos/projects';
import { useTasks } from '@/hooks/useTasks';

export default function ProjectDetailPage() {
  const { id } = useParams<{ id: string }>();
  const router = useRouter();

  // Distinção loading vs not-found via count
  const projectExists = useLiveQuery(
    () => db.projects.where('id').equals(id).count(),
    [id]
  );
  const project = useLiveQuery(() => getProject(id), [id]);
  const tasks = useTasks({ projectId: id });

  const isLoading = projectExists === undefined;
  const isNotFound = projectExists === 0;

  // Progress (A6)
  const progress = useMemo(() => {
    if (!tasks || tasks.length === 0) return 0;
    const done = tasks.filter((t) => t.status === 'done').length;
    return Math.round((done / tasks.length) * 100);
  }, [tasks]);

  // Escape global
  useEffect(() => {
    function onKey(e: KeyboardEvent) {
      if (e.key === 'Escape' && !editModalOpen) router.back();
    }
    document.addEventListener('keydown', onKey);
    return () => document.removeEventListener('keydown', onKey);
  }, [router, editModalOpen]);

  if (isLoading) return <ProjectDetailSkeleton />;
  if (isNotFound) return <ProjectNotFound onBack={() => router.push('/projectos')} />;

  return (
    <main>
      <ProjectDetailHeader
        project={project!}
        progress={progress}
        onEdit={() => setEditModalOpen(true)}
        onBack={() => router.back()}
        editButtonRef={openerRef}
      />
      {/* Tab strip Lista | Kanban */}
      {/* Sub-vistas */}
      {editModalOpen && (
        <ProjectFormModal
          mode="edit"
          initialValue={project!}
          onClose={() => { setEditModalOpen(false); openerRef.current?.focus(); }}
          onSubmit={handleEditSubmit}
        />
      )}
    </main>
  );
}
```

### Loading vs Not-Found

Adoptada a abordagem recomendada nas Dev Notes (mais robusta que `isLoaded` flag):

```typescript
const projectExists = useLiveQuery(
  () => db.projects.where('id').equals(id).count(),
  [id],
);
// projectExists === undefined → loading
// projectExists === 0         → not found
// projectExists === 1         → existe
```

Permite distinguir os 3 estados sem state local extra, e o `useLiveQuery` reage à inserção/eliminação do projecto.
